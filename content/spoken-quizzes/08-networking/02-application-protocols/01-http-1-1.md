## 1

A response carries a cache-control header of no-cache, together with a max-age of 3,600 seconds. A CDN receives a request for it 10 minutes later. What does the CDN do?

A, it revalidates with the origin, and serves its copy if the origin answers 304. B, it serves its copy only to requests with no authorization header. C, it serves its copy, since 10 minutes is within the max-age. D, it refuses to store it, so every request goes to the origin.

[think]

The answer is A: it revalidates with the origin, and serves its copy if the origin answers 304.

No-cache allows storage, but requires revalidation before every use, whatever the max-age says. The CDN sends a conditional request and serves its stored body if the origin answers 304, not modified. Refusing to store is no-store, a different directive, and the authorization header affects whether a shared cache may store a response, not revalidation.

## 2

A front-end proxy frames requests by their content-length header, and the back end by transfer-encoding. An attacker sends a POST with both headers, a content length of 6, and a body made of a zero-size last chunk, the empty line that ends it, and the letter G. What does the back end do?

A, it treats G as the start of the next request on that connection. B, it rejects the request because the body is longer than its chunks. C, it waits for more chunks until the front end closes the connection. D, it reads all six bytes as the body, since a content length was sent.

[think]

The answer is A: it treats G as the start of the next request on that connection.

The back end's chunked parser ends the body after five bytes: the last chunk and the empty trailer line. The G stays in its buffer and is prepended to whatever the front end forwards next on that pooled connection, often another user's request. A strict parser, such as Node.js 24's, rejects a request with both headers outright, which is the defence.

## 3

A Node.js service with the default 5-second keep-alive timeout sits behind a load balancer whose idle timeout is 60 seconds. About one request in a few thousand gets a 502 that no application log records, mostly at low traffic. Which change fixes the cause?

A, set the backend's keep-alive timeout above 60 seconds. B, raise the backend's maximum header size to 64 kibibytes. C, lower the backend's keep-alive timeout to 1 second. D, make the load balancer retry failed POST requests.

[think]

The answer is A: set the backend's keep-alive timeout above 60 seconds.

The balancer reuses a connection at the moment the backend's 5-second idle timer closes it, and gets a reset. The side that reuses connections must have the shorter idle timeout, so the backend's must exceed 60 seconds. A shorter backend timeout makes the race more frequent, and retrying POSTs risks duplicate side effects.

## 4

A CDN caches a response with a max-age of 600 seconds, and serves it to a browser with an age header of 540. Ignoring transit delay, how long may the browser reuse its copy without revalidating?

A, not at all, since any age header marks it as stale. B, about 600 seconds, since its own clock starts at zero. C, about 60 seconds, since the age counts against the max-age. D, about 540 seconds, since the age is its remaining lifetime.

[think]

The answer is C: about 60 seconds, since the age counts against the max-age.

Freshness compares the lifetime, 600 seconds, with the current age, which starts from the age header. The browser's copy is 540 seconds old on arrival, so it is fresh for about 60 seconds more. Downstream caches inherit the upstream copy's age, rather than restarting it.

## 5

An API returns a 200 whose last-modified date is 100 days before its date header, with no cache-control or expires header. What may a browser cache do?

A, reuse it for about 10 days without asking. B, reuse it until the last-modified date changes on the server. C, not store it, as it has no explicit lifetime. D, store it, but revalidate on every single use.

[think]

The answer is A: reuse it for about 10 days without asking.

The HTTP caching standard permits heuristic freshness for responses such as a 200 without an explicit lifetime, and suggests 10 percent of the time since the last modification: here, about 10 days. Browsers apply it. The fix is an explicit cache-control header on every response. Revalidating on every use is what no-cache asks for.

## 6

Why did browsers abandon HTTP/1.1 pipelining, while HTTP/2 multiplexing succeeded?

A, responses had to return in order, so a slow one still blocked the rest. B, pipelined headers were compressed, which proxies could not read. C, pipelined requests could not carry cookies or authorization. D, each pipelined request needed a new TCP handshake to start.

[think]

The answer is A: responses had to return in order, so a slow one still blocked the rest.

An HTTP/1.1 response carries no request identifier, so responses must come back in request order, and in the lesson's measurement the fast response still waited 300 milliseconds behind the slow one. Ambiguous failures and broken intermediaries finished it off. HTTP/2 tags every frame with a stream ID, so responses interleave on one connection.
