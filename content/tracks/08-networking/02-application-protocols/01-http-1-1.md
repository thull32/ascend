A Node.js API behind a cloud load balancer returns a 502 to about one request in a few thousand. The application logs show nothing, load tests cannot reproduce it, and it is worst at night. The cause is two defaults: the balancer keeps an idle backend connection for 60 seconds, Node.js closes an idle keep-alive connection after 5, and now and then the balancer sends a request down a connection at the instant Node closes it. A week later a security report arrives: one crafted POST makes your front-end proxy and your backend disagree about where that request ends, so the tail of the attacker's request is glued to the front of the next user's.

Both incidents are about framing: how the two ends of a byte stream agree where a message ends and when the connection may carry the next one. Numbers marked *measured* were taken on 28 September 2026 from a home connection in the US to `example.com` (served by Cloudflare) and on loopback with small Python and Node.js servers.

## The bytes on the wire

A request is a **request line**, zero or more **header fields**, an empty line, and an optional body. Every line ends in CRLF (`\r\n`, bytes `0d 0a`). This is the request `curl --http1.1 https://api.example.com/v1/users/42` writes into its TLS stream:

| Offset | Bytes | Content | Role |
|---|---|---|---|
| 0–26 | 27 | `GET /v1/users/42 HTTP/1.1` CRLF | Method, request target, version, single spaces between |
| 27–49 | 23 | `Host: api.example.com` CRLF | Mandatory in 1.1: one IP serves many host names |
| 50–73 | 24 | `User-Agent: curl/8.5.0` CRLF | |
| 74–86 | 13 | `Accept: */*` CRLF | |
| 87–88 | 2 | CRLF | Empty line: the header section ends here |

That is 89 bytes of ASCII, starting `47 45 54 20 2f 76 31` (`GET /v1`). *Measured:* a loopback server logging raw bytes received exactly this layout from curl 8.5.0, and curl reported `size_request=74` for `https://example.com/`, whose host and path are 15 bytes shorter. The response mirrors it; from the loopback server, a 120-byte head and a 35-byte body:

```text
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 35
ETag: "a3b42b2d7975"
Cache-Control: max-age=60

{"id":42,"name":"Ada","plan":"pro"}
```

The syntax rules that decide whether two implementations agree (RFC 9112):

- **No whitespace between a field name and its colon.** A server must reject `Transfer-Encoding : chunked` with 400, because parsers used to disagree about it.
- Field names are case-insensitive, and line folding (a value continued on the next line) must be rejected or unfolded.
- No `Host`, or two, means 400. *Measured:* Node.js 24 answers a request without `Host` with `400 Bad Request` and `Connection: close`.

Headers are never compressed in HTTP/1.1, so a 600-byte cookie on a request for a 200-byte JSON response is 75% overhead, repeated on every request. [HTTP/2's HPACK](/learn/networking/application-protocols/http-2-and-http-3) removes that repetition.

## How a parser finds the end of a message

TCP delivers a byte stream with no message boundaries ([TCP deep dive](/learn/networking/fundamentals/tcp-deep-dive)), so HTTP carries its own. A parser reads until the first CRLF CRLF, which ends the head. The body length then comes from this ordered list in RFC 9112 §6.3; the first rule that applies wins:

1. A response to HEAD, and any 1xx, 204 or 304 response, has no body, whatever its headers say.
2. A 2xx response to CONNECT turns the connection into a tunnel.
3. `Transfer-Encoding` ending in `chunked`: the body is chunked. Any other transfer coding: 400 for a request, read-until-close for a response.
4. `Content-Length` alone: exactly that many bytes. An invalid value, or several different ones, is a framing error (400, or a proxy discards the response and closes).
5. A request with neither has an empty body.
6. A response with neither ends when the server closes the connection.

Trace a 178-byte buffer holding two copies of the request above, sent back to back:

| Step | Position | Parser action | Result |
|---|---|---|---|
| 1 | 0 | Scan for CRLF CRLF | Found at bytes 85–88; head is 0–88 |
| 2 | 89 | GET, no `Content-Length`, no `Transfer-Encoding`: rule 5 | Body length 0; message 1 is bytes 0–88 |
| 3 | 89 | Scan again | Found at 174–177 |
| 4 | 178 | Rule 5 | Message 2 is bytes 89–177; buffer empty |

With `Content-Length: 35` the parser takes exactly 35 bytes after the head, and byte 36 starts the next message; that off-by-N is the lever request smuggling pulls. Rule 6 costs the connection, and a truncated close-delimited response looks complete, which is why chunked encoding carries an explicit terminator.

## Chunked transfer coding, decoded by hand

A server that does not know the length up front (a streamed template, a compressor, a database cursor) sends `Transfer-Encoding: chunked`: each chunk is a hex size, an optional `;extension`, CRLF, that many bytes, CRLF; a zero-size chunk ends the data, then optional trailer fields and an empty line. *Measured:* over HTTP/1.1, `example.com` served its 559-byte page chunked, although it came from Cloudflare's cache. `curl --raw` against the loopback server shows a 54-byte chunked body undecoded:

```text
1b\r\n{"items":[{"id":1},{"id":2}\r\nb\r\n,{"id":3}]}\r\n0\r\n\r\n
```

| Offset | Bytes | Parser state | Action |
|---|---|---|---|
| 0–3 | `1b` CRLF | Read size line | 0x1b = 27 |
| 4–30 | `{"items":[{"id":1},{"id":2}` | Read 27 data bytes | Append |
| 31–32 | CRLF | Expect CRLF after data | OK |
| 33–35 | `b` CRLF | Read size line | 0xb = 11 |
| 36–46 | `,{"id":3}]}` | Read 11 data bytes | Append |
| 47–48 | CRLF | Expect CRLF | OK |
| 49–51 | `0` CRLF | Read size line | Last chunk |
| 52–53 | CRLF | Trailer section | Empty line: message ends at byte 54 |

curl decoded the 38-byte body `{"items":[{"id":1},{"id":2},{"id":3}]}`. Each chunk costs its hex digits plus 4 bytes of CRLF, so servers emit chunks of kilobytes. Details that bite:

- **The size is hex digits only.** Python's `int("0x5", 16)` and JavaScript's `parseInt("0x5", 16)` both return 5, so decoders built on them are more lenient than the grammar; *measured*, Node.js 24 rejects a `0x5` size with 400. A lenient and a strict parser in one path are a smuggling vector.
- **Trailers** are fields after the data, such as a checksum computed while streaming; gRPC depends on them over HTTP/2 ([gRPC and Protobuf](/learn/networking/application-protocols/grpc-and-protobuf)).
- **Chunking is per hop.** `Transfer-Encoding` is hop-by-hop, so a proxy may receive chunked and send `Content-Length` onward; HTTP/2 and HTTP/3 forbid it because their frames carry lengths. There is no total size, so no progress bar.

## Request smuggling: two parsers, one byte stream

A front end (CDN, load balancer, WAF) forwards many clients' requests to a back end over a few kept-alive connections. If the two disagree about where a request ends, the leftover bytes start the next request on that shared connection, often another user's. The attacker sends:

```text
POST /search HTTP/1.1
Host: shop.example
Content-Length: 6
Transfer-Encoding: chunked

0

G
```

The head is 92 bytes and the body is the 6 bytes `0\r\n\r\nG`. With a front end that frames by `Content-Length` and a back end that frames by `Transfer-Encoding` (CL.TE):

| Step | Front end (Content-Length) | Back end (chunked) |
|---|---|---|
| 1 | Reads the head, sees length 6 | |
| 2 | Reads 6 bytes and forwards all 98 on a pooled connection | Reads the head, sees chunked |
| 3 | | `0` CRLF CRLF: last chunk, no trailers; body ends after 5 bytes |
| 4 | | Answers POST /search; `G` stays in its read buffer |
| 5 | Forwards the victim's `GET /account HTTP/1.1` on that connection | Parses `GGET /account HTTP/1.1`; the victim gets an error |

Whatever bytes are left over become part of someone else's request, and access rules at the front end never saw them as a request, which is why smuggling is fixed at the framing layer, not with filters.

| Variant | Front end frames by | Back end frames by | Cause |
|---|---|---|---|
| CL.TE | Content-Length | Transfer-Encoding | Front end ignores TE |
| TE.CL | Transfer-Encoding | Content-Length | Back end ignores TE |
| TE.TE | Transfer-Encoding | Transfer-Encoding | One side misses `Transfer-Encoding : chunked` or `xchunked` |
| H2.CL, H2.TE | HTTP/2 frames | CL or TE | An HTTP/2-to-1.1 downgrade copies a client's `content-length` |

RFC 9112 settles the ambiguity: `Transfer-Encoding` overrides `Content-Length`, the message ought to be treated as an error, a forwarding intermediary must remove `Content-Length`, and a server must close the connection after responding. *Measured:* Node.js 24 rejects the request above, and the space-before-colon form, with `400` and `Connection: close`; Go 1.27's `net/http` source deletes `Content-Length` and frames by chunked. Neither is exploitable alone; the danger is any hop that frames by `Content-Length` when both are present.

Defences, strongest first: the front end rejects ambiguous requests (both headers, whitespace before a colon, codings other than `chunked`) and re-serialises what it forwards; HTTP/2 end to end; last, no back-end connection reuse. The attack class was published by Watchfire in 2005 and revived by PortSwigger's 2019 ["HTTP Desync Attacks"](https://portswigger.net/research/http-desync-attacks-request-smuggling-reborn) research, which exploited it on production sites, including many behind Akamai's CDN.

## Under the hood: real parsers and their limits

Every server reads the head into a bounded buffer before it can route, so every server has a header limit, and they differ:

| Implementation | Default head limit | Past the limit |
|---|---|---|
| nginx | `client_header_buffer_size 1k`, then up to `large_client_header_buffers 4 8k` | Request line over 8 KiB: 414; one field over 8 KiB: 400 "Request Header Or Cookie Too Large" |
| Node.js 24 (llhttp) | `http.maxHeaderSize` 16,384 bytes (*measured*) | 431 |
| Go 1.27 `net/http` | `DefaultMaxHeaderBytes` 1 MiB (from the source) | 431 |
| Apache httpd | `LimitRequestFieldSize` 8,190 per field, `LimitRequestFields` 100 | 400 |
| Python 3.14 `http.server` | 65,536 bytes per line, 100 fields (from the source) | 431 |

A cookie that grows past 8 KiB works against the Node.js service in development and fails at the nginx in front of it in production.

Timeouts are the other hidden defaults. *Measured* on Node.js 24: `keepAliveTimeout` 5,000 ms, `headersTimeout` 60,000 ms (the defence against slowloris, which trickles one header byte every few seconds on many connections), `requestTimeout` 300,000 ms. Two proxy behaviours surprise people: before nginx 1.29.7 (March 2026), nginx spoke HTTP/1.0 to upstreams by default, one request per connection, unless you set `proxy_http_version 1.1`, `proxy_set_header Connection ""` and a `keepalive` pool (since 1.29.7 those are the defaults, with 32 idle upstream connections per worker, per the [changelog](https://nginx.org/en/CHANGES)), and many fleets still run older versions; and hop-by-hop headers (`Connection`, `Keep-Alive`, `Transfer-Encoding`, `TE`, `Upgrade`) are regenerated at every proxy.

## Methods, status codes and ranges


| Method | Safe | Idempotent | Cacheable | Typical use |
|---|---|---|---|---|
| GET | Yes | Yes | Yes | Read a resource |
| HEAD | Yes | Yes | Yes | GET without the body |
| OPTIONS | Yes | Yes | No | CORS preflight |
| PUT | No | Yes | No | Replace a resource at a known URL |
| DELETE | No | Yes | No | Remove |
| POST | No | No | Rarely | Create, or anything else |
| PATCH | No | Not by default | No | Partial update |

Retry logic keys on idempotency: a library, balancer or mesh may resend `DELETE /orders/9` after a connection error, never blindly `POST /orders`, which may have succeeded before the drop. An idempotency key makes a POST retryable ([API styles](/learn/networking/application-protocols/api-styles) traces one).

- **301/302** let a client switch POST to GET on redirect, dropping the body; **307/308** preserve both. 301 and 308 are permanent and cached, so a wrong one lingers.
- **429** and **503** carry `Retry-After`; a client that ignores it turns overload into a retry storm.
- **502** and **504** usually come from the proxy in front of you: garbage or a reset from upstream, or the proxy's own timeout (nginx `proxy_read_timeout`, 60 s).

**Range requests** fetch part of a resource: `Range: bytes=0-1048575` returns `206 Partial Content` with `Content-Range: bytes 0-1048575/734003200`, and `If-Range: "etag"` prevents mixing bytes from two versions. Resumable downloads depend on this, and adaptive-streaming players fetch media from CDN caches as ranges or segment files, which is how [Netflix's streaming path](/learn/system-design/case-studies/video-streaming-netflix) moves video.

## Keep-alive, measured

HTTP/1.1 keeps connections open by default, so the next request skips the TCP and TLS handshakes. *Measured* with one curl invocation fetching `https://example.com/` twice over HTTP/1.1, timing each with `-w`:

```bash
curl --http1.1 -s -o /dev/null -o /dev/null \
  -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} new=%{num_connects}\n' \
  https://example.com/ https://example.com/
```


| Request | DNS | TCP done | TLS done | First byte | Total | New connections |
|---|---|---|---|---|---|---|
| 1 | 33 ms | 99 ms | 153 ms | 212 ms | 212 ms | 1 |
| 2 (reused) | 0 | 0 | 0 | 67 ms | 67 ms | 0 |

curl's timers are cumulative, so read differences: TCP took 66 ms and TLS 1.3 54 ms, a round trip each ([TLS and PKI](/learn/networking/fundamentals/tls-and-pki)), and request to first byte 59 ms, a round trip to a cache hit. Reuse removed 145 of 212 ms. The same subtraction diagnoses a slow API: if the handler reports 4 ms and request-to-first-byte is 214 ms, the other 210 ms is a proxy queue, a pool wait or a dependency outside the handler's timer ([Debugging the network](/learn/networking/networking-in-practice/debugging-the-network)).

## Idle timeouts and the 502 race

Idle timers on both sides close connections, and their defaults disagree:

| Component | Setting | Default |
|---|---|---|
| nginx, client side | `keepalive_timeout` / `keepalive_requests` | 75 s / 1,000 requests (100 before 1.19.10) |
| nginx, to upstreams | `keepalive` in the `upstream` block | Off before 1.29.7; 32 idle connections per worker since |
| Node.js 24 server | `server.keepAliveTimeout` | 5 s (*measured*); the socket closes 1 s later since Node 24.6 (`keepAliveTimeoutBuffer`) |
| AWS Application Load Balancer | Connection idle timeout | 60 s |

The opening incident, traced:

| Time | Load balancer | Node.js backend |
|---|---|---|
| 0.000 s | Response 1 arrives; connection goes to the idle pool (limit 60 s) | Idle timer starts (5 s; 6 s from Node 24.6, which adds the buffer) |
| 5.000 s | Picks this connection for request 2 | Timer fires; `close()` sends FIN |
| 5.000 s + ~0.2 ms | Request 2 bytes are in flight | Kernel receives data for a closed socket and replies RST |
| 5.001 s | Reads RST, returns 502 | Never saw request 2, so nothing is logged |

The window is about one balancer-to-backend round trip, sub-millisecond inside a zone, so the rate is small and highest when connections idle for about 5 s, at low traffic. The rule: **the side that reuses a connection must have the shorter idle timeout**, so the backend gets 65 s against the balancer's 60. Retries cannot fix it for POST, because the balancer cannot know whether the backend processed the request.

**Closing costs ports.** The side that closes first holds TIME_WAIT for 60 s (a kernel constant; `tcp_fin_timeout` governs FIN_WAIT_2). *Measured:* 300 short loopback connections left 300 TIME_WAIT sockets on the client, none on the server. With the stock ephemeral range 32768–60999 (28,232 ports), a client opening a connection per request to one server address runs out at about 28,232 / 60 ≈ 470 per second, and `connect()` fails with `EADDRNOTAVAIL`. [Connection pooling](/learn/networking/networking-in-practice/connection-pooling-and-keep-alive) sizes pools to avoid it.

## Six connections per origin and head-of-line blocking

A connection carries one request at a time, so a slow response blocks everything queued behind it. *Measured* on loopback with a server whose `/slow` takes 300 ms:

| Setup | `/slow` done | `/fast` done |
|---|---|---|
| Both pipelined on one connection, `/slow` first | 300.7 ms | 300.9 ms |
| Each on its own connection | 300.5 ms | 0.52 ms |

A 0.5 ms response took 300 ms because it queued behind another: **head-of-line (HOL) blocking**. Browsers add lanes instead, capped at **six connections per origin** (scheme, host, port) in Chrome and Firefox: 30 images load in five waves of six, about 300 ms of round trips at the 59–67 ms measured on a warm connection. **Domain sharding** (`img1.`, `img2.`) bought more lanes for extra DNS lookups and handshakes (about 150 ms each, measured above); on HTTP/2 it is an anti-pattern.

HTTP/1.1 specified **pipelining**, sending several requests without waiting. It failed for three reasons:

1. **Responses return in request order**, because an HTTP/1.1 response does not say which request it answers. The measurement above was pipelined: the fast response still waited.
2. **Failure is ambiguous.** If the connection dies after three of five requests, the client cannot tell which were processed, so only idempotent requests may be pipelined.
3. **Intermediaries broke it**, so browsers could not trust a path; Chrome and Firefox shipped it disabled and later deleted the code (Firefox in version 54, in 2017).

HTTP/2 fixes the first by giving every frame a stream id. Server to server, the same rule makes pool size a throughput ceiling: by Little's law, 10 connections to a downstream answering in 20 ms carry at most 10 / 0.020 = 500 requests per second, and request 501 queues inside your client, invisible to the downstream's metrics.

## Caching: freshness, Age and heuristics

A 99% hit ratio instead of 90% is ten times less origin traffic. `Cache-Control` sets freshness:

| Directive | Meaning |
|---|---|
| `max-age=60` | Any cache may serve it until it is 60 s old |
| `s-maxage=600` | Overrides `max-age` in shared caches (CDNs); browsers ignore it |
| `public` / `private` | Shared caches may store it despite `Authorization` / only the browser may |
| `no-cache` | Storable, but revalidate before every use |
| `no-store` | Never written to any cache |
| `must-revalidate` | Once stale, never served without revalidation |
| `stale-while-revalidate=30` | Serve stale up to 30 s while refreshing in the background |
| `stale-if-error=300` | Serve stale up to 5 min if the origin fails |

A cache compares the **freshness lifetime** (`s-maxage`, else `max-age`, else `Expires` minus `Date`, else a heuristic) with the **current age**: the `Age` header it arrived with, corrected for transit delay, plus its time in this cache (RFC 9111 §4.2.3). A CDN stores a `max-age=600` response at t = 0 and serves it to a browser at t = 540 with `Age: 540`:

| Time | CDN copy | Browser copy |
|---|---|---|
| 0 s | Stored, age 0, fresh for 600 s | – |
| 540 s | Age 540, still fresh | Stored with age 540: fresh for 60 s more, not 600 |
| 600 s | Stale: revalidates with the origin | Stale: revalidates with the CDN |

Downstream caches inherit the upstream age; TTLs do not add up.

**Heuristic freshness.** RFC 9111 lets a cache assign a lifetime to a response without one (for status codes such as 200, 301, 404 and 410) and suggests 10% of the time since `Last-Modified`. *Measured:* `example.com` sent `Date: Mon, 28 Sep 2026 14:26:51 GMT`, `last-modified: Sat, 26 Sep 2026 09:10:30 GMT` and no `Cache-Control` or `Expires`: 191,781 s apart, so a browser may reuse the page for 19,178 s, about 5 hours 20 minutes, without asking. An API response with a year-old `Last-Modified` can be reused for about 36 days. Send explicit `Cache-Control` on every response.

## Validation: ETag, If-None-Match and 304

A stale copy is not discarded: the cache asks whether it changed, using the origin's validator. Trace a 200 KB catalogue with `ETag: "v7"` and `max-age=60`:

| Time | Event | Cache decision | On the wire |
|---|---|---|---|
| 0 s | Miss | `GET /catalog`; store body, ETag `"v7"` | 200 and 200 KB |
| 30 s | Request | Fresh (age 30 < 60): serve from cache | Nothing |
| 90 s | Request | Stale: `GET` with `If-None-Match: "v7"` | 304, head only |
| 90 s | 304 arrives | Update stored headers, age resets to 0, serve stored body | – |
| 200 s | Request; the origin is now `"v8"` | Stale: conditional GET | 200, `ETag: "v8"`, 200 KB |

*Measured* on loopback: the 200 response had a 120-byte head and a 35-byte body; the 304 was a 78-byte head and no body, and the conditional request grew by the 31-byte `If-None-Match` line. A 304 saves the body, not the round trip.

- An **ETag** is any opaque string that changes with the representation: a content hash, a version, or for nginx's static files the mtime and size in hex. **Last-Modified / If-Modified-Since** has one-second resolution and misses two changes within a second.
- **ETags must agree across servers**: different mtimes after a deploy, or Apache's old inode-based default, turn every revalidation into a full 200.
- **Optimistic concurrency**: `PUT` with `If-Match: "v7"` returns 412 Precondition Failed if someone wrote `"v8"` first, with no lock.

## Vary, compression and the cache key

A cache key is method plus URL by default; `Vary` adds request headers. `Vary: Accept-Encoding` keeps a Brotli copy and an uncompressed copy apart and is almost always right, provided the cache normalises `Accept-Encoding` to a few values. `Vary: User-Agent` multiplies entries by thousands of user-agent strings and `Vary: Cookie` by the number of sessions, driving the hit ratio toward zero ([CDNs and the edge](/learn/networking/application-protocols/cdns-and-edge) covers key design).

`Content-Encoding: br` or `gzip` compresses the body only. Repetitive JSON and HTML often shrink several times over; already-compressed media gains nothing. Compressing a response that holds a secret (a CSRF token) next to attacker-reflected input leaks the secret through the compressed length (BREACH), so do not compress such responses, or mask the secret per response.

## Production failure modes

| Failure | Symptom | Diagnosis | Fix |
|---|---|---|---|
| Keep-alive race | Rare 502s, none in app logs, worse at low traffic | Balancer idle timeout (60 s) above backend keep-alive (5 s); resets on reused connections | Backend keep-alive above the balancer's |
| Request smuggling | Users get others' responses; errors with methods like `GGET` | Hops disagree on CL vs TE; replay a CL.TE probe in a test environment | Reject ambiguous framing at the edge, HTTP/2 end to end |
| No upstream keep-alive | 502 "Cannot assign requested address" at the proxy | `ss -s` shows tens of thousands of TIME_WAIT; nginx older than 1.29.7 speaks HTTP/1.0 upstream | `proxy_http_version 1.1`, empty `Connection`, `keepalive` pool (the defaults from nginx 1.29.7) |
| Header too large | 400 or 431 for some users, often after login | A grown cookie crosses one hop's limit (nginx 8 KiB, Node.js 16 KiB) | Shrink cookies, align limits |
| Heuristic caching | Data hours or days old; no cache headers anywhere | `Last-Modified` without `Cache-Control` | Explicit `Cache-Control` everywhere |
| Cache fragmentation | CDN hit ratio near zero | `Vary: Cookie` or `User-Agent`, or a per-request query parameter | Drop the `Vary`, normalise the key |

## Trade-offs

| Body framing | Length known up front | Connection reusable | Truncation detectable | Progress and ranges |
|---|---|---|---|---|
| `Content-Length` | Required | Yes | Yes | Yes |
| `chunked` | No | Yes | Yes (terminator) | No total |
| Close-delimited | No | No | No | No |

| Connection strategy | Setup per request | HOL blocking | Server cost | On failure |
|---|---|---|---|---|
| Connection per request | 1–2 round trips, TIME_WAIT | None | Handshakes, ports | Clear |
| Keep-alive, serial | None after the first | Per connection | Socket per concurrent request | Clear, bar idle races |
| Pipelining | None | Yes: in-order responses | Low | Ambiguous |
| Six parallel connections | Six handshakes | Divided by six | Six sockets per client | Clear |
| HTTP/2 multiplexing | One handshake | TCP layer only | One socket | Per-stream reset |

```exercise
  - args: ["1b\r\n{\"items\":[{\"id\":1},{\"id\":2}\r\nb\r\n,{\"id\":3}]}\r\n0\r\n\r\n"]
    expected: {"body": "{\"items\":[{\"id\":1},{\"id\":2},{\"id\":3}]}", "consumed": 54}
    label: the lesson's trace
  - args: ["3;x=1\r\nabc\r\n0\r\nExpires: never\r\n\r\nGET / HTTP/1.1\r\n\r\n"]
    expected: {"body": "abc", "consumed": 33}
    label: extension, trailer, and the next message left unread
  - args: ["5\r\nhel"]
    expected: {"error": "incomplete"}
    label: data cut short
  - args: ["4\r\nhello\r\n0\r\n\r\n"]
    expected: {"error": "malformed"}
    label: data longer than its declared size
  - args: ["0\r\n"]
    expected: {"error": "incomplete"}
    label: last chunk without the empty line
    hidden: true
  - args: ["0\r\n\r\nG"]
    expected: {"body": "", "consumed": 5}
    label: the smuggling body, as a chunked back end sees it
    hidden: true
  - args: ["0x5\r\nhello\r\n0\r\n\r\n"]
    expected: {"error": "malformed"}
    label: a 0x prefix is not a hex digit
    hidden: true
hints:
  - "Search for \"\\r\\n\" from the current position; everything before it, cut at the first \";\", is the size text."
  - "Validate the size text character by character before converting it: int(text, 16) and parseInt(text, 16) both accept \"0x5\"."
  - "After a size of 0, loop over lines until you read an empty one; consumed is the position after that empty line."
```

The two error kinds are different decisions in a real server: `incomplete` means read more from the socket, `malformed` means answer 400 and close the connection, because after a framing error nothing that follows on that connection can be trusted.

## Interviewer follow-ups

**"How does an HTTP/1.1 server know where a request body ends?"** Model answer: it reads to the first CRLF CRLF, then applies the RFC 9112 order: chunked `Transfer-Encoding`, else `Content-Length`, else a request has no body; a response with neither ends at the close. Common wrong answer: "each `recv()` returns one request", which holds on loopback and fails under load when requests coalesce or split.

**"What is request smuggling, and where would you fix it?"** Model answer: two hops disagree about message length, so leftover bytes prefix the next request on a shared back-end connection. Reject ambiguous framing at the edge, re-serialise requests, use HTTP/2 end to end; disabling back-end reuse is the costly last resort. Common wrong answer: "a WAF rule for suspicious bodies", which inspects what the front end parses, not the back end.

**"We see a few 502s per hour behind the load balancer and nothing in the app logs. What do you check?"** Model answer: idle timeouts on both sides of the balancer-to-backend hop (60 s against a 5 s backend keep-alive is the classic), then proxy upstream timeouts, then port exhaustion. Common wrong answer: "add retries", which duplicates POSTs and hides the race.

**"`no-cache`, `no-store`, `max-age=0, must-revalidate`: what is the difference?"** Model answer: `no-store` forbids storage; `no-cache` stores but revalidates before every use; `max-age=0, must-revalidate` is stale on arrival and never served stale, even when the origin is down. Common wrong answer: "`no-cache` means do not cache", which puts `no-cache` on banking pages that need `no-store`.

## What mid-level engineers get wrong

- **Emitting both `Content-Length` and `Transfer-Encoding`**, or proxying bytes without re-framing.
- **Using `no-cache` for secrets.** It permits storage; `no-store` does not.
- **Sending no cache headers at all**, then finding browsers reusing API responses for hours under the 10% heuristic.
- **Ignoring `Age`**, and expecting a browser to cache for the full `max-age` when the CDN copy was already old.
- **Setting the backend keep-alive timeout below the load balancer's**, which produces 502s that no application log records.
- **Retrying POST on connection errors** without an idempotency key, which duplicates orders exactly when the network misbehaves.

## Senior signals

- You state the RFC 9112 body-length rules in order, decode a chunked body by hand, and explain smuggling as two hops disagreeing about them, fixed at the edge.
- You know the real defaults (Node.js 5 s keep-alive and 16 KiB headers, nginx 75 s and 8 KiB, ALB 60 s) and that the reusing side needs the shorter idle timeout.
- You quantify reuse (a round trip each for TCP and TLS 1.3) and TIME_WAIT limits (about 470 new connections per second per destination).
- You compute freshness from `max-age`, `Age` and the 10% heuristic, and use `ETag` for revalidation and optimistic concurrency.
- You trace head-of-line blocking to "one response at a time, in order", and from there to six connections per origin, dead pipelining and pool ceilings.
