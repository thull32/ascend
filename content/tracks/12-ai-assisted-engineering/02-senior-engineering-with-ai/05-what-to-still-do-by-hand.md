If an agent writes most of the code, which of your skills justify a senior salary? Not typing. The ones that let you check the agent's work, decide what it should be doing, and take over when it gets stuck. Those are precisely the skills that decay fastest when the agent does everything, because they are built and maintained by the work you are now delegating.

This lesson is about choosing, deliberately, what to keep doing yourself. Not out of nostalgia, and not everything: the goal is to delegate as much as possible while keeping the abilities that make delegation safe. The centre of the lesson is one bug, a check-then-act race in a quota, that an agent writes fluently, tests green, and ships. You will trace it by hand at the bytecode level, reproduce it on purpose in twelve lines, and fix it in three different stores. Finding it takes one question that no test suite asks for you.

## The verification paradox

You can reliably verify work only at roughly the level at which you could have produced it. A reviewer who could not write a correct keyset pagination query will approve the wrong one, because the wrong one looks fine. A reviewer who has never debugged a race will not see one in a clean-looking diff. Generation became cheap; verification did not, and verification draws on exactly the skills that producing the work used to exercise.

Reviewing is also often harder than writing. The author of a line knows why it is there; the reviewer has to reconstruct that from the outside. When the author is a model, there is no one to ask who actually knows, only a model that will produce a plausible explanation on demand, and the explanation is generated by the same process that generated the bug.

Two pieces of evidence make this concrete rather than a worry. In METR's randomised trial published in July 2025, experienced open-source maintainers worked on real issues in repositories they knew well, with and without AI tools; they were on average about 19% slower with the tools while estimating afterwards that they had been roughly 20% faster. The effect depends heavily on the setting (unfamiliar codebases and greenfield work show different results), but the gap between felt speed and measured speed is the point: your sense of how well the tool is going is not a measurement. And the field experiment on learning described in [Learning without atrophy](/learn/ai-assisted-engineering/senior-engineering-with-ai/learning-without-atrophy) found that unrestricted answer-mode help raised practice scores and lowered exam scores. Feeling faster and feeling competent are both produced by the same fluency that hides the bugs.

The decline is gradual, which is what makes it dangerous. Each skipped exercise is harmless. After a year of skipping them, you are a relay between a ticket and a model, and you cannot tell when the model is wrong. Nobody notices until an incident, or an interview without an assistant.

## The skills that every other skill depends on

## Worked example: a race the tests cannot catch

You ask an agent for a per-user export quota: at most 10 exports per user per day. It produces clean code and tests.

```python
class Quota:
    def __init__(self, limit):
        self.limit = limit
        self.used = {}

    def try_consume(self, user_id):
        used = self.used.get(user_id, 0)      # read
        if used >= self.limit:                # check
            return False
        self.used[user_id] = used + 1         # write
        return True

def test_eleventh_export_is_rejected():
    q = Quota(limit=10)
    assert all(q.try_consume("u1") for _ in range(10))
    assert not q.try_consume("u1")
```

The test passes, every time. It will keep passing, because it runs on one thread and nothing can happen between the read and the write.

In production the service handles requests on a pool of worker threads. User `u1` has used 9 exports and fires two requests at once. Trace the schedule step by step, with `used["u1"]` as the shared state:

| Step | Thread A | Thread B | `used["u1"]` in memory |
|---|---|---|---|
| 1 | reads `used` → 9 | | 9 |
| 2 | `9 >= 10`? no, passes the check | | 9 |
| 3 | (scheduler switches) | reads `used` → 9 | 9 |
| 4 | | `9 >= 10`? no, passes the check | 9 |
| 5 | | writes `9 + 1` | 10 |
| 6 | | returns True; export B runs | 10 |
| 7 | writes `9 + 1` | | 10 |
| 8 | returns True; export A runs | | 10 |

Both exports run. The quota allowed 11, and the stored count says 10, so nothing downstream can even tell. Every row after step 2 is the same bug: A's write in step 7 is computed from a value that stopped being true at step 5. This is the **lost update**, and it is the same anomaly as two database transactions that both read a balance and both write balance minus withdrawal.

## Under the hood: why the GIL does not save you

Engineers who know that CPython has a global interpreter lock sometimes conclude that Python code cannot race. The GIL makes each *bytecode instruction* atomic with respect to other Python threads; it does nothing for a sequence of instructions. Disassemble `try_consume` on CPython 3.14 (`python3 -m dis`) and the read and the write are far apart:

```text
LOAD_ATTR      used
LOAD_ATTR      get
LOAD_FAST      user_id
LOAD_SMALL_INT 0
CALL           2            <- the read: dict.get(user_id, 0)
STORE_FAST     used
LOAD_FAST      used
LOAD_ATTR      limit
COMPARE_OP     >=           <- the check
POP_JUMP_IF_FALSE
...
BINARY_OP      +
LOAD_ATTR      used
LOAD_FAST      user_id
STORE_SUBSCR                <- the write: used[user_id] = ...
```

A dozen instructions separate the `CALL` that reads from the `STORE_SUBSCR` that writes. The interpreter checks whether another thread is waiting for the GIL at regular points and hands it over after a thread has held it for the switch interval, which defaults to 5 milliseconds (`sys.getswitchinterval()` returns `0.005`; it has been the default since Python 3.2). Any blocking call (a socket read, a database query, a `sleep`) releases the GIL immediately. So the window between read and write is small when the code is pure Python, and a thread switch lands inside it only occasionally: the bug appears once in thousands of concurrent pairs, which is worse than always, because it passes load tests and fails on the busiest day.

Now move the count to Redis with `used = await redis.get(key)` followed by `await redis.set(key, used + 1)`, a very common generated pattern. Each `await` yields to the event loop, and the window between read and write becomes a full network round trip, on the order of 0.2 to 1 ms inside one data centre, during which every other coroutine handling a request for the same user runs. What was a rare race in-process becomes a routine one. Free-threaded CPython builds (the no-GIL option available since 3.13) remove the instruction-level atomicity as well, so code that was accidentally safe because of the GIL stops being safe.

## Reproducing it on purpose

An intermittent bug you cannot reproduce is a bug you cannot prove fixed. Two techniques turn the schedule above into a test. The first **scripts the interleaving** with events, so the schedule is exact and deterministic; the second **invites a switch** with `sleep(0)` at the vulnerable point and counts. Both are in this script, which you can run as is:

```python
import threading, time

class Quota:
    def __init__(self, limit):
        self.limit = limit
        self.used = {}

    def try_consume(self, user_id, pause=None):
        used = self.used.get(user_id, 0)      # read
        if pause:
            pause()                           # test hook: let another thread run here
        if used >= self.limit:                # check
            return False
        self.used[user_id] = used + 1         # write
        return True

def scripted_interleaving():
    q = Quota(limit=10)
    q.used["u1"] = 9
    a_has_read, b_has_written = threading.Event(), threading.Event()
    results = {}

    def a():
        def pause():
            a_has_read.set()              # step 3: hand over to B
            b_has_written.wait()          # resume only after B has written
        results["A"] = q.try_consume("u1", pause)

    def b():
        a_has_read.wait()                 # wait until A has read 9
        results["B"] = q.try_consume("u1")
        b_has_written.set()

    ta, tb = threading.Thread(target=a), threading.Thread(target=b)
    ta.start(); tb.start(); ta.join(); tb.join()
    print("scripted:", results, "stored =", q.used["u1"])

def stress(threads=4, rounds=2000):
    q, allowed, lock = Quota(limit=10), 0, threading.Lock()
    barrier = threading.Barrier(threads)
    def worker():
        nonlocal allowed
        barrier.wait()                    # all threads start together
        mine = sum(q.try_consume("u1", pause=lambda: time.sleep(0)) for _ in range(rounds))
        with lock:
            allowed += mine
    ts = [threading.Thread(target=worker) for _ in range(threads)]
    for t in ts: t.start()
    for t in ts: t.join()
    print(f"stress: allowed={allowed} stored={q.used['u1']} limit=10")

scripted_interleaving()
stress()
```

Output on CPython 3.14 (the stress count varies run to run; the scripted result never does):

```text
scripted: {'B': True, 'A': True} stored = 10
stress: allowed=39 stored=10 limit=10
```

The `pause` hook is the important design choice. It is a seam that lets a test choose the schedule, and it costs nothing in production (`None` is falsy). Without a seam, you are left with stress tests that pass on a quiet CI machine, which is the situation the agent's green test left you in. The same idea in an async codebase is an `await` point you can control from the test.

## Fixing it in three places

The fix is always the same in shape: make read, check and write one atomic step, at the store that holds the truth.

In process, hold a lock across all three:

```python
import threading

class Quota:
    def __init__(self, limit):
        self.limit = limit
        self.used = {}
        self._lock = threading.Lock()

    def try_consume(self, user_id):
        with self._lock:
            used = self.used.get(user_id, 0)
            if used >= self.limit:
                return False
            self.used[user_id] = used + 1
            return True
```

Run the stress test against this version and it reports `allowed=10` every time. Note what the lock protects: not the dictionary, which was never corrupted, but the *invariant* `used <= limit` across a multi-step operation. A per-key lock is the refinement when contention between different users matters.

Across processes, push the check into the store so the database performs it atomically, and look at whether a row was updated:

```sql
UPDATE quotas
SET used = used + 1
WHERE user_id = $1 AND day = CURRENT_DATE AND used < 10;
-- 1 row updated: allowed.  0 rows updated: quota exhausted.
```

Row-level locking makes the `WHERE` and the `SET` one step: two concurrent statements on the same row serialise, and the second sees the first's result. This repository's AI budget uses the same shape for exactly this reason; the comment in `crates/core/src/ai/budget.rs` says that a read-then-write version "would let N concurrent requests all read '99 of 100' and all proceed", so the reservation is a single conditional upsert with `RETURNING` telling the caller whether the increment happened.

In Redis, `INCR` is atomic, so increment first and compare the returned value:

```python
new = await redis.incr(key)          # atomic: returns the value after increment
if new == 1:
    await redis.expire(key, 86_400)  # first consumption today sets the TTL
if new > limit:
    return False                     # over by one; the count stays over, which is harmless
return True
```

The count may overshoot the limit by the number of rejected requests, which is fine for a quota and wrong for a stock counter; when the exact number matters, a Lua script that reads, checks and writes on the server in one step is the tool, because Redis runs a script without interleaving other commands. What is never right is the `GET`, compare, `SET` sequence, however many retries you wrap around it, and however many times it passes locally.

How do you find this by hand? One question, asked of every piece of shared mutable state in a diff: *what if another thread or request runs between this read and this write?* It takes seconds. No test suite asks it for you, the agent did not ask it, and the only way to keep asking it is to keep the habit.

## Failure modes of skill decay

Skill decay does not announce itself; it shows up as a pattern in your work. Each row is a symptom you can notice in yourself, what it usually means, and the rep that reverses it.

| Symptom | Diagnosis | Fix |
|---|---|---|
| You approve a 300-line agent diff in four minutes and cannot describe what it changed | Tracing has become skimming; you are reviewing the summary, not the code | Trace one normal and one edge input through every diff before approving; if it takes more than 20 minutes, the diff is too big, and that is a scoping problem to fix upstream |
| A bug report arrives and your first action is to paste the stack trace into the assistant | The hypothesis step has been outsourced; you no longer read a trace top to bottom | First 15 minutes solo: read the trace, name two hypotheses and the observation that separates them, then use the tool |
| The agent "fixes" an intermittent test with `sleep(0.5)` and you accept it | You stopped asking what interleaving produces the failure, so a timing change looks like a fix | Reject any fix you cannot state as an ordering or state change; write the scripted-interleaving test above |
| Your last two schema designs each needed a migration within a quarter | The model proposed the average schema and you did not ask what queries and growth it must serve | Draft the schema and its access patterns yourself first; then ask the model what breaks at 100x rows |
| You freeze in a solo interview on a problem type you have "solved" with help many times | Recognition without production; the fluency illusion from the learning lesson | One timed solo problem a week and a re-solve of last fortnight's problem without looking |
| You cannot estimate your service's peak requests per second within a factor of ten | Estimation has not been exercised since the model started doing the arithmetic | Answer the self-audit below monthly, on paper, before checking any dashboard |

## A self-audit

Try answering these without any assistant. Each maps to a skill in the table above, and each is a question a senior interviewer or reviewer can ask you at any time.

1. What is the time complexity of the last non-trivial function you merged, and what input makes it slowest?
2. Take one endpoint you own. Where would you look first if its p99 doubled after a deploy, and what would each place tell you?
3. Name one piece of shared mutable state in your service and what happens if two requests modify it at once.
4. How many requests per second does your service handle at peak, and roughly how many machines does that take? Show the arithmetic.
5. Which table in your schema would be the most painful to change, and why?
6. What is the worst thing an attacker could do with your most privileged API token, and where is it stored?
7. You committed to the wrong branch and pushed. What exact git commands recover it?
8. Explain, in one paragraph, why your team chose its main datastore over the obvious alternative.

If more than two of these send you reaching for a tool, that is where to put next month's reps. None of them is exotic; all of them are the substrate every AI-assisted workflow runs on.

## A maintenance regimen

Two to three hours a week of deliberate reps is cheap insurance on the skills that make you worth delegating to:

- **Weekly**: one solo timed problem; one AI-written diff traced by hand end to end; the first 15 minutes of one bug debugged without AI.
- **Monthly**: one small task done entirely by hand; one design doc first draft written without assistance; one solo mock interview in this app, compared with your assisted scores.
- **On every change you accept**: state its complexity and one way it could fail before you approve it.

The cost is real: about 5% of a working week. Compare it with the alternative, which is discovering in an incident review or a hiring loop that the skill is gone. [Learning without atrophy](/learn/ai-assisted-engineering/senior-engineering-with-ai/learning-without-atrophy) covers how to make those reps count.

## When doing it by hand is the wrong call

Do not become a purist. Typing boilerplate is not skill maintenance; it is waste. Delegate freely:

- Boilerplate, scaffolding and configuration syntax you can validate.
- Codemods, with the script reviewed rather than the output.
- Test scaffolding, provided you own the expected values.
- API lookups and translations between languages, verified by running them.
- First drafts of routine documentation.

The heuristic that sorts tasks: **if the AI got this wrong, would I be able to tell?** If yes, delegate and verify. If no, either do it yourself or learn enough first that the answer becomes yes. Do by hand what builds or preserves judgement; delegate what only consumes time.

At Netflix scale the same rule sorts whole classes of work. A mass edit across hundreds of services is a codemod plus an automated rollout, which is a program to review; the decision about which consistency model a new service needs is made in a design review by people who can explain it, and that is not delegated to a model however good its draft.

## Interviewer follow-ups

**"Your quota code passed a load test at 500 requests per second. Why did it still fail in production?"** Model answer: a load test only shows the race if a thread switch or an await lands in the window between read and write, and with pure-Python code that window is a few microseconds wide, so the failure rate is tiny until traffic on one key spikes. The fix is to make the check atomic at the store, and the test is a scripted interleaving that forces the schedule, not a bigger load test. Common wrong answer: "the load test was not big enough", which proposes more of the test that cannot prove absence.

**"You said CPython has a GIL. Does that make `self.used[k] = self.used.get(k, 0) + 1` atomic?"** Model answer: no; the GIL serialises individual bytecode instructions, and that statement compiles to a read, an add and a store as separate instructions, with a switch possible between any two. Common wrong answer: "yes, Python threads cannot race on dictionaries", which confuses the dictionary's internal consistency (protected) with the invariant across the operation (not protected).

**"How would you fix this if the count lived in Redis and the exact value mattered?"** Model answer: a Lua script that reads, checks and increments server-side in one step, or `INCR` and compare when overshoot is acceptable; never `GET`, compare, `SET`. Common wrong answer: `WATCH`/`MULTI` with retries described as "transactions", which works but retries under contention and is usually chosen without knowing that.

**"Which parts of your job should not be delegated to an agent, and why those?"** Model answer: the parts whose errors you could not detect, which are also the parts that build judgement: schema and interface design, threat models, the hypothesis step in debugging, the decision about what to build. Everything mechanical and verifiable is delegated. Common wrong answer: a list based on importance ("production code") rather than on verifiability, which bans safe delegation and permits unsafe delegation.

**"How do you know your own skills are not decaying?"** Model answer: unassisted measurements on a schedule: solo problems, solo mock interviews compared with assisted ones, tracing diffs by hand, and the self-audit questions; productivity with the tool is not evidence. Common wrong answer: "I use the tools every day, so I am getting better at them", which measures tool fluency, not the skills that verify the tool.

## What mid-level engineers get wrong

- **Treating green tests as proof of correctness for concurrent code.** Single-threaded tests cannot interleave; the consequence is a race that ships and appears on the busiest day.
- **Believing the GIL makes Python code thread-safe.** Instruction-level atomicity is mistaken for operation-level atomicity; check-then-act sequences race anyway, and become routine races once an `await` sits in the window.
- **Fixing races with sleeps, retries or longer timeouts.** Timing changes make a race rarer, not absent; the bug returns under different hardware or load, now harder to reproduce.
- **Locking the data structure instead of the invariant.** A thread-safe dictionary does not make `used <= limit` hold across a read, a check and a write.
- **Delegating by importance rather than by verifiability.** They hand the model the schema design (hard to verify, hard to reverse) and type the boilerplate themselves (easy to verify, cheap to redo).
- **Measuring themselves by throughput with the tool.** Felt speed and measured speed diverge; the METR result is the cleanest demonstration that the feeling is not a measurement.
- **Skipping the reps because each one is optional.** Skill decay is a sum of harmless omissions; the bill arrives as an incident or an unassisted interview.

## Senior signals

- You can explain the **verification paradox**: you can only reliably check work you could have produced or deeply understand, and you can cite the evidence that felt productivity is not measured productivity.
- You keep **tracing, estimation, first-principles debugging and concurrency reasoning** sharp on purpose, with scheduled reps.
- You ask **"what runs between this read and this write?"** of every shared state in a diff, and you know why single-threaded tests cannot answer it and why the GIL does not either.
- You **reproduce races deterministically** with a scripted interleaving through a test seam, rather than hoping a stress test catches them.
- You fix check-then-act races with **atomic operations at the store** (a lock across the invariant, a conditional `UPDATE`, `INCR` or a server-side script), not retries or sleeps.
- You design **schemas and interfaces yourself** and use AI to critique them.
- You delegate by the rule **"would I be able to tell if it were wrong?"**, and you are not precious about boilerplate.
