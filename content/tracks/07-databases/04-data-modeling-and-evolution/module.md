The first three modules of this track explain what a database does. This one is about the part of database work that fills a senior engineer's week: deciding what the tables look like, changing them once they hold a billion rows, and living with the layers of code and cache that sit between the application and the storage engine. Every lesson measures its claims on PostgreSQL 17, so the numbers you quote in a design review have a source.

The module starts where junior data modelling goes wrong. Normalising the nouns of the domain into tables produces a schema that is correct and slow, because nobody asked which queries would run against it ten thousand times a second. You will write the access-pattern table first (frequency, latency target, cardinality, freshness), derive keys and indexes from it, and pay on the write path only where the table says to: a leaderboard that fell from 34 seconds to 0.4 ms with a summary table, a counter row that caps near 400 updates a second until it is sharded, and materialised views whose two refresh modes take different locks. The same discipline is what a DynamoDB single-table design demands, and the lesson works one end to end, down to read units and partition limits.

Schemas then have to change. `ALTER TABLE` looks harmless in development and can take a site down in production, because the lock it needs queues behind a long-running transaction and every reader queues behind it. You will see the lock each common DDL takes, which ones rewrite the table, the lock queue reproduced with three sessions and bounded by `lock_timeout`, what a failed `CREATE INDEX CONCURRENTLY` leaves behind, and how expand/contract plus a batched, verified backfill turns a column rename into boring deploys.

The last two lessons are about the layers around the database. ORMs make the N+1 query pattern the default and hide it behind a property access; you will measure it at 10, 100 and 1,000 rows, model it at real network round trips, learn when a join loses to two queries, detect it without `pg_stat_statements`, and read the SeaORM code in this very app. Finally, caches: every caching strategy has races with the database, and you will trace four of them step by step and learn which fix closes which. By the end you should be able to defend a schema, a migration plan and a cache design in a design review with the failure modes already written down.
