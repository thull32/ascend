A stream is a batch job that never gets to see the end of its input. That single difference breaks every comfortable assumption: you cannot sort what has not arrived, you cannot know a window is complete, and a machine that crashes mid-computation has to resume without double counting. Stream processing is the collection of mechanisms that restore those guarantees: partitioned logs with replication, watermarks that declare "nothing older is coming", checkpoints that snapshot state consistently across a cluster, and transactional sinks that make retries invisible.

This module works each mechanism on paper before naming a system. It starts inside Kafka, from the segment files and sparse indexes on disk to a produce with `acks=all` traced through the replica fetcher and the high watermark, a broker failure traced through leader epochs and log truncation, and a transaction traced to the last stable offset. It then builds the processing model shared by Flink, Beam, Kafka Streams and Spark Structured Streaming: tumbling, sliding and session windows traced event by event with out-of-order and late data, watermarks propagated as the minimum over partitions, and triggers and accumulation modes mapped across engines. The state lesson follows a checkpoint barrier through source, keyed aggregation and transactional sink, shows what RocksDB uploads in an incremental checkpoint, and works the interval, restore and rescaling arithmetic. The architecture lesson traces why a batch layer and a speed layer disagree and what a lakehouse table changes, and the module ends with change data capture: Postgres logical decoding, Debezium's event envelope, three SQL statements followed to a search index and a cache, the outbox, and the replication slot that can fill a primary's disk.

Every lesson carries production failure modes with symptom, diagnosis and fix (lag spirals, rebalance storms, idle-partition watermark stalls, checkpoint timeouts, state that grows without bound, drifting pipelines, WAL bloat), the numbers behind the settings (how many partitions, how much lateness, how big a checkpoint, how long a transaction timeout), and the follow-up questions a senior interviewer asks. By the end you should be able to take a requirement like "count plays per title per minute, exactly once, with events up to ten minutes late" and turn it into a topology, a set of configs, a failure analysis and an honest statement of which output is final.
