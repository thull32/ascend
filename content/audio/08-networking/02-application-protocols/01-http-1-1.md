## Introduction

A Node.js API behind a cloud load balancer returns a 502 to about one request in a few thousand. The application logs show nothing. Load tests cannot reproduce it, and it is worst at night. A week later a security report arrives: one crafted POST makes your front-end proxy and your backend disagree about where that request ends, so the tail of the attacker's request is glued to the front of the next user's.

Both incidents are about framing: how the two ends of a byte stream agree where a message ends, and when the connection may carry the next one. That is the thread through everything that follows. Three ideas: how a parser finds the end of a message, and how attackers exploit two parsers that disagree; what keeping a connection open buys you, and the race it creates; and how caches decide whether a stored response is still fresh.

## Where a message ends

An HTTP 1.1 request is plain text. A request line, such as GET, a path and the version. Then header lines, then an empty line, then an optional body. Every line ends in a carriage return and a line feed. A simple curl request for one user record is 89 bytes of ASCII. The Host header is mandatory in 1.1, because one IP address serves many host names, and a request with no Host header, or two, gets a 400.

Headers are never compressed in HTTP 1.1. A 600-byte cookie on a request for a 200-byte JSON response is 75 percent overhead, repeated on every single request.

Now the real question. TCP delivers a byte stream with no message boundaries, so HTTP has to carry its own. The parser reads until the first empty line, which ends the head. Then it works out the body length from an ordered list of rules, and the first rule that applies wins. A response to HEAD, and any 204 or 304, has no body, whatever its headers say. If Transfer-Encoding says chunked, the body is chunked. Otherwise, a Content-Length means exactly that many bytes. A request with neither has an empty body. And a response with neither ends when the server closes the connection.

That last rule is expensive. It costs the connection, and a response cut short looks complete. Which is why chunked encoding carries an explicit terminator.

## Chunked encoding

A server that does not know the length up front, such as a streamed template, a compressor or a database cursor, sends the body in chunks. Each chunk is its size written in hexadecimal, a line ending, that many bytes, and another line ending. A chunk of size zero ends the data. After it can come trailer fields, such as a checksum computed while streaming, and then an empty line.

Each chunk costs its hex digits plus 4 bytes of line endings, so servers emit chunks of kilobytes. And chunking is per hop: a proxy may receive chunked and send a Content-Length onward. HTTP 2 and HTTP 3 forbid chunking altogether, because their frames already carry lengths.

One detail bites. The size must be hex digits only. Python's and JavaScript's built-in hex parsers both accept a size written zero-x-5 and return 5, so decoders built on them are more lenient than the grammar. Node.js 24 rejects that size with a 400. A lenient parser and a strict parser in one path are exactly what the next attack needs.

## Request smuggling

A front end, which might be a CDN, a load balancer or a web application firewall, forwards many clients' requests to a back end over a few connections it keeps open. If the two disagree about where a request ends, the leftover bytes become the start of the next request on that shared connection, and that next request is often another user's.

Here is the attack. The attacker sends a POST with both headers: Content-Length 6, and Transfer-Encoding chunked. The body is six bytes: a zero, a line ending, another line ending, and the letter G. Picture two actors: a front end that frames by Content-Length, and a back end that frames by chunked encoding.

Before I tell you: what happens to that G?

[pause]

The front end reads six bytes, so it forwards everything. The back end reads a zero-size chunk and an empty line, so for it the body is over after five bytes. It answers the POST, and the G stays in its read buffer. Then the front end forwards a victim's GET for their account page down that same connection, and the back end parses it as GGET. The victim gets an error. Whatever bytes are left over become part of someone else's request, and the front end's access rules never saw them as a request. That is why smuggling is fixed at the framing layer, not with filters. The reverse disagreement, a malformed Transfer-Encoding header that only one side recognises, and an HTTP 2 to 1.1 downgrade that copies a client's content-length, are all the same bug.

The standard settles the ambiguity. Transfer-Encoding overrides Content-Length, the message ought to be treated as an error, a forwarding proxy must remove the Content-Length, and the server must close the connection after responding. Node.js 24 rejects the request above with a 400. Neither a strict server nor a careful one is exploitable alone. The danger is any hop that frames by Content-Length when both are present.

The defences, strongest first. The front end rejects ambiguous requests, meaning both headers, whitespace before a colon, or any coding other than chunked, and re-serialises what it forwards. Then HTTP 2 end to end. Last, and costly, no reuse of back-end connections.

## Keep-alive and the 502 race

HTTP 1.1 keeps connections open by default, so the next request skips the TCP and TLS handshakes. Measured from a home connection to example dot com: the first request took 212 milliseconds. TCP took 66 of that and TLS 1.3 took 54, a round trip each, and the request itself took 59. The second request, on the reused connection, took 67 milliseconds. Reuse removed 145 of 212.

But both ends run idle timers, and the defaults disagree. A Node.js server closes an idle keep-alive connection after 5 seconds. An AWS Application Load Balancer keeps one for 60. nginx keeps client connections for 75.

Now trace the opening incident. A response comes back, and the load balancer puts the connection in its idle pool. Five seconds later, the balancer picks that connection for a new request at the instant Node's timer fires and closes it. The request bytes arrive at a closed socket, the kernel replies with a reset, and the balancer returns a 502. Node never saw the request, so nothing is logged. The window is about one balancer-to-backend round trip, sub-millisecond inside a zone, which is why it is rare. And it is most likely when connections sit idle for about five seconds, which means low traffic, which means night.

Here is the rule to remember: the side that reuses a connection must have the shorter idle timeout. So the backend gets 65 seconds against the balancer's 60. Retries cannot fix it for POST, because the balancer cannot know whether the backend processed the request.

Closing has a cost too. The side that closes first holds the socket in the time-wait state for 60 seconds. With the stock range of about 28 thousand ephemeral ports, a client that opens a new connection per request to one server address runs out at about 470 connections a second.

## Head-of-line blocking

An HTTP 1.1 connection carries one request at a time, so a slow response blocks everything queued behind it. Measured on loopback: a slow request that takes 300 milliseconds, and a fast one that takes half a millisecond. Pipelined on one connection, slow first, the fast one finished at 300 milliseconds. On separate connections, half a millisecond. That is head-of-line blocking.

Browsers add lanes instead, six connections per origin in Chrome and Firefox. Thirty images load in five waves of six. Domain sharding bought more lanes at the price of extra lookups and handshakes, and on HTTP 2 it is an anti-pattern.

Pipelining, sending several requests without waiting, failed for three reasons. Responses must return in request order, because an HTTP 1.1 response does not say which request it answers, so the fast one still waits. Failure is ambiguous: if the connection dies after three of five requests, the client cannot tell which were processed. And intermediaries broke it, so browsers shipped it disabled and later deleted the code. HTTP 2 fixes the first problem by tagging every frame with a stream ID.

Server to server, the same rule turns pool size into a throughput ceiling. Ten connections to a downstream that answers in 20 milliseconds carry at most 500 requests a second, and request 501 queues inside your client, invisible to the downstream's metrics.

Retries depend on the method. GET, PUT and DELETE are idempotent, so a library or balancer may resend a DELETE after a connection error. It must never blindly resend a POST, which may have succeeded before the drop. An idempotency key makes a POST retryable.

## Freshness and validation

A 99 percent hit ratio instead of 90 is ten times less origin traffic. Cache-Control sets freshness: a max-age of 60 means any cache may serve the response until it is 60 seconds old.

The trap is age. A CDN stores a response with a max-age of 600 seconds, and serves it to a browser 540 seconds later with an Age header of 540. The browser's copy is fresh for 60 more seconds, not 600. Downstream caches inherit the upstream age. TTLs do not add up.

Worse is sending no cache headers at all. The standard lets a cache invent a lifetime, and suggests 10 percent of the time since Last-Modified. Example dot com's page had last been modified a little over two days earlier, with no Cache-Control, so a browser may reuse it for about 5 hours and 20 minutes without asking. An API response with a year-old Last-Modified can be reused for about 36 days. Send explicit Cache-Control on every response.

When a copy goes stale, the cache does not throw it away. It asks whether it changed, by sending the stored ETag in an If-None-Match header. If nothing changed, the origin answers 304 with just a head, and the cache serves its stored body. A 304 saves the body, not the round trip. ETags must agree across servers, or every revalidation becomes a full 200. And If-Match on a PUT gives you optimistic concurrency with no lock: if someone else wrote first, you get 412, precondition failed.

Last, Vary. Vary on Accept-Encoding keeps a compressed copy and an uncompressed one apart, and is almost always right. Vary on User-Agent or Cookie multiplies the entries by thousands and drives the hit ratio toward zero.

## In the interview

A question the lesson expects: we see a few 502s an hour behind the load balancer, and nothing in the app logs. What do you check?

[pause]

Idle timeouts on both sides of the balancer-to-backend hop. A 60-second balancer against a 5-second backend keep-alive is the classic. Then proxy upstream timeouts, then port exhaustion. The wrong answer is "add retries", which duplicates POSTs and hides the race.

And the vocabulary check: no-cache, no-store, and max-age zero with must-revalidate. No-store forbids storage. No-cache stores, but revalidates before every use. Max-age zero with must-revalidate is stale on arrival and never served stale, even when the origin is down. The common wrong answer is that no-cache means do not cache, which puts no-cache on banking pages that need no-store.

## Recap

Four things to remember. The body length comes from an ordered list: chunked, then Content-Length, then nothing for a request or the close for a response. Smuggling is two hops disagreeing about that list, fixed at the edge by rejecting ambiguous framing. The side that reuses a connection needs the shorter idle timeout, so the backend's keep-alive must exceed the balancer's 60 seconds. One response at a time, in order, explains six connections per origin, dead pipelining and pool ceilings. And freshness counts the age a copy already has, so send explicit Cache-Control on every response.
