## Introduction

Thirteen questions from the from-zero module of the fabric networking track. Answer out loud before the answer comes.

None of these overlap with the first set. They follow the last five lessons in order: ARP and the default gateway, the packet walk, transport as the network sees it, what is inside a switch, and how Linux sends and receives packets. Four options each, A to D, then a few seconds to commit.

## Question 1

acme-web1, at 10.1.1.10 slash 24 with gateway 10.1.1.1, opens a connection to acme-db1 at 10.1.2.20. Which MAC address does it resolve with ARP?

A, the gateway's, because 10.1.2.20 is off the host's subnet. B, acme-db1's, because the frame must reach the database. C, the broadcast MAC, because the destination is in another VLAN. D, acme-db1's, obtained from the gateway by proxy ARP.

[think]

The answer is A: the gateway's, because 10.1.2.20 is off the host's subnet.

10.1.2.20 masked with a slash 24 gives 10.1.2.0, not acme-web1's 10.1.1.0, so the default route via 10.1.1.1 matches and the host needs the gateway's MAC. The frame carries the gateway's MAC and acme-db1's IP. The broadcast MAC is used only for the ARP request itself, and proxy ARP would answer with the router's own MAC, not the database's.

## Question 2

A server cannot reach its gateway. Its neighbour table shows the gateway as FAILED, and ping prints "Destination Host Unreachable" from 10.1.1.10, which is the server's own address. What does this tell you?

A, ARP got no reply, so the pings never left the server. B, the gateway received the pings and refused them with ICMP. C, a router beyond the gateway has no route to the destination. D, the gateway answered ARP, but its CPU dropped the pings.

[think]

The answer is A: ARP got no reply, so the pings never left the server.

FAILED means the kernel's ARP requests went unanswered, so it dropped the queued packets and generated the error itself, which is why the message names the server's own address. Nothing reached the gateway. The next checks are layer 2 and the gateway interface: the port's VLAN, the leaf's MAC table, the gateway interface being up.

## Question 3

A keepalived failover moves the virtual IP 10.1.1.50 from acme-lb1 to acme-lb2. Which message makes peers send to acme-lb2 without waiting for their cache entries to time out?

A, a proxy ARP reply from leaf1 for 10.1.1.50, carrying the gateway MAC. B, a gratuitous ARP from acme-lb2, naming 10.1.1.50 as both sender and target IP. C, an ICMP redirect from leaf1, naming acme-lb2 as the better first hop. D, an ARP request from each peer, sent as soon as its entry turns STALE.

[think]

The answer is B: a gratuitous ARP from acme-lb2, naming 10.1.1.50 as both sender and target IP.

The new owner broadcasts the announcement. Hosts that already cache 10.1.1.50 overwrite the MAC, since Linux updates existing entries even when it refuses to create new ones, and the switches learn the MAC's new port. Waiting for STALE and a probe is exactly the slow path the announcement avoids. Proxy ARP would point peers at the leaf, and redirects concern routers, not same-subnet neighbours.

## Question 4

acme-web1, at 10.1.1.10, sends a packet to acme-db1, at 10.1.2.20, through leaf1, spine1 and leaf3, treated as plain routers. On the link from leaf1 to spine1, what are the packet's destination MAC and destination IP?

A, spine1's interface MAC, and acme-db1's IP, 10.1.2.20. B, acme-db1's MAC, and acme-db1's IP. C, the anycast gateway MAC, and acme-db1's IP. D, spine1's interface MAC, and spine1's own IP, 10.254.1.0.

[think]

The answer is A: spine1's interface MAC, and acme-db1's IP.

The destination IP is the end-to-end label and never changes. The destination MAC is the per-link label: leaf1 looked up the next hop, took spine1's MAC from its neighbour table and addressed the frame to it. The next hop's IP is used only to find that MAC and never appears in the packet.

## Question 5

A traceroute shows 95 milliseconds at hop 4, then 12 milliseconds at hops 5 through 8 and at the destination. What is the most likely explanation?

A, hop 4 is a tunnel endpoint adding 83 milliseconds of encapsulation. B, hop 4's CPU answers TTL-expired probes slowly. C, hop 4 is congested and delays all traffic through it. D, the return path from hop 4 is a long-haul circuit.

[think]

The answer is B: hop 4's CPU answers TTL-expired probes slowly.

Packets through hop 4 reach the destination in 12 milliseconds, so the forwarding path through it is not slow. The reply at hop 4 is generated by the router's control plane under a rate limit, and a busy CPU answers late. Congestion at hop 4 would add delay to every later hop as well; only latency that persists to the destination is real.

## Question 6

Leaf1 counts rising CRC errors on its port towards spine2. Where is the fault most likely to be?

A, in spine2's routing table, which mis-forwards frames. B, in the sending host's network card, whose frames carry a bad CRC. C, on any link along the paths that cross spine2. D, on the link between leaf1 and spine2: its optics or cable.

[think]

The answer is D: on the link between leaf1 and spine2, its optics or cable.

Each router builds a new frame and recomputes the frame check sequence on every hop, so a CRC error describes corruption on the one link where the frame was received. A host's bad frame would be dropped at the first hop, and a routing error does not corrupt bits. The one caveat is cut-through switching, where a stomped CRC can be counted on the next link too, which good tooling separates out.

## Question 7

A backup through a VPN gateway connects and completes its TLS handshake, then transfers nothing until it times out. Ping to the server works. What is the most likely cause?

A, the gateway's NAT table expired the connection after the handshake. B, the server's TCP receive window is too small for a backup. C, full-size packets with the don't-fragment bit set are dropped, and their ICMP is filtered. D, the TLS handshake picked a cipher the gateway cannot forward.

[think]

The answer is C: full-size don't-fragment packets are dropped, and their ICMP is filtered.

Small packets, the handshake, TLS and default pings, get through, and full-size ones never arrive. That is the signature of a path-MTU black hole: the tunnel's MTU is below the hosts', fragmenting is forbidden, and the ICMP that would shrink the segments is thrown away. A small window slows a transfer but does not stop it, a cipher does not affect forwarding, and a NAT would not expire seconds after the handshake.

## Question 8

Why does one RoCEv2 GPU-to-GPU transfer tend to collide with others on a single uplink, when thousands of web flows carried in VXLAN spread evenly?

A, a few queue pairs make a few huge flows, with few distinct five-tuples. B, RoCEv2 packets are too large for the ECMP hash to read. C, switches exclude UDP port 4791 from ECMP hashing by default. D, RoCEv2 uses TCP underneath, which pins one path per host.

[think]

The answer is A: a few queue pairs make a few huge flows, with few distinct five-tuples.

Each queue pair is one five-tuple, and GPU traffic travels over a handful of queue pairs carrying very large volumes, so the hash has few flows to spread and two can land on one link. VXLAN writes each inner flow's hash into its outer source port, giving thousands of distinct tuples. Packet size does not affect the hash, RoCEv2 runs over UDP rather than TCP, and port 4791 is hashed like any other.

## Question 9

A BGP session between leaf1 and the route reflector rr1 has been Established for 40 days. What does that prove about transit traffic through leaf1?

A, that the ECMP groups towards both spines are complete. B, that the punt path and the CPU handle small packets. C, that transit packets in every traffic class are forwarded. D, that every route BGP selected is in the hardware FIB.

[think]

The answer is B: that the punt path and the CPU handle small packets.

KEEPALIVEs are punted to the CPU through a protected control-plane policing class, so an Established session proves the punt path, the CPU, the kernel's TCP stack and the daemon work for small packets in one class. Transit traffic depends on what was written into the ASIC. A failed FIB write, an incomplete ECMP group or a bad ACL drops it while the session stays up.

## Question 10

A monitoring system pings the loopback of every switch once a second and reports 2 percent loss on spine2, yet applications see no loss through it. What is the most likely explanation?

A, the hardware FIB is missing spine2's loopback route. B, ECMP is sending the pings over a congested path. C, there is a gray failure on one of spine2's links. D, spine2's control-plane policing is limiting its ICMP class.

[think]

The answer is D: spine2's control-plane policing is limiting its ICMP class.

Pings to a switch are punted to its CPU and pass a policer, so loss there measures the control-plane path. Transit traffic never touches it, which is why applications see nothing. A gray failure or congestion would hurt transit traffic as well. Loss should be measured with probes that cross devices.

## Question 11

2,000 tenant prefixes behind leaf3 resolve to its loopback, which uses a next-hop group containing spine1 and spine2. Spine2 fails. Why does leaf1 converge about as fast as it would for a single prefix?

A, only one next-hop group object is rewritten. B, IS-IS recomputes shortest path first for the loopback only. C, BGP withdraws all 2,000 prefixes in one UPDATE. D, the ASIC reprograms 2,000 entries in parallel.

[think]

The answer is A: only one next-hop group object is rewritten.

In a hierarchical FIB the prefixes point at a shared next-hop group, so removing spine2 is one write to the group and every prefix moves at once. That is prefix-independent convergence. With a flat FIB, each route holds its own next hops, and the update time grows with the prefix count, however the protocols signal it.

## Question 12

A host's single TCP stream to a peer on a 100 gigabit NIC reaches a fraction of line rate, while eight parallel streams fill the link. Per-CPU statistics show one core at 100 percent softirq time. What explains it?

A, NAPI's budget of 300 packets caps every flow's rate. B, the switch hashes the stream onto one congested uplink. C, the receive buffer is smaller than the bandwidth-delay product. D, RSS keeps each flow on one queue, and so on one CPU.

[think]

The answer is D: RSS keeps each flow on one queue, and so on one CPU.

RSS hashes the addresses and ports to choose a queue, and each queue's interrupt and softirq run on one CPU, so a single flow is limited by one core's processing. Eight flows hash to several queues and spread across cores. A window limit would show an idle CPU and an idle link, not a saturated core, and an uplink collision would not depend on host CPU.

## Question 13

A tcpdump on the sending host shows 64,000-byte TCP segments, each marked with an incorrect checksum. What is happening?

A, the kernel is corrupting packets before they reach the NIC. B, TSO and checksum offload finish the packets in the NIC. C, GRO on the sender merged segments before transmission. D, the path MTU is 64 kilobytes, so no segmentation is needed.

[think]

The answer is B: TSO and checksum offload finish the packets in the NIC.

With TSO, TCP hands the NIC one large segment that the NIC cuts into MSS-sized packets, and with checksum offload the NIC fills in the checksums as it transmits. The capture point is above the NIC, so it sees the unfinished super-packet. GRO is a receive-side merge. The wire still carries 1,500-byte packets on a 1,500-byte MTU, and nothing is corrupted.

## Recap

Three ideas kept coming back. Each header has its own job: the IP address is the end-to-end label that never changes, while the MAC address and the frame checksum are rewritten on every link, so ARP resolves only the next hop and a CRC error points at one cable. A switch is two machines: the CPU answers pings, traceroute probes and BGP keepalives behind a policer, while the ASIC forwards everything else, so a healthy session or a slow ping says little about transit traffic. And hashing pins a flow to one path, whether it is an ECMP uplink or an RSS queue on one core, so a few large flows spread badly where thousands of small ones spread evenly.
