After a link fails, every router recomputes its routes, but not at the same moment. For tens to hundreds of milliseconds some routers forward on the new topology and some on the old one, and a packet can be handed back and forth between two of them, or dropped by a router that has lost its route and not yet learned a new one. Given a snapshot of every router's next hop toward one destination, find both failures.

### The networking idea in one minute

A router forwards on the **destination** alone. For a given destination prefix, each router's forwarding table holds a **next hop**: the neighbour it hands the packet to. Each router chooses its next hop on its own, from its own view of the network. Nothing checks that the choices of different routers agree. (A fabric router often has several equal-cost next hops and hashes each flow onto one of them; this problem models a single next hop per router, as if you were following one flow. The follow-up lifts that.)

Usually they do, and the next hops chain together into a path that ends at the router that owns the destination and delivers the packet. While the network is **converging** (recomputing after a change), two things can go wrong:

- A **forwarding loop**. Router A's next hop is B and B's next hop is A, or a longer ring. A packet that enters the ring circulates until its **TTL** (time to live, a hop counter in the IP header that every router decrements) reaches zero and the router holding it discards it. A loop that lives only during convergence is called a **microloop**. It is worse than a drop of the same length, because every looping packet crosses the ring's links many times and can saturate them, hurting traffic that was never headed for the destination.
- A **black hole**. A router has no route to the destination, so it drops the packet. Every router whose path passes through it loses traffic too.

The snapshot for one destination is a directed graph in which every router has **at most one** outgoing edge. Graphs like that are called functional graphs, and every walk in one ends in one of three ways: at the destination, at a router with no next hop, or in a cycle.

The examples use Meridian, a fictional operator with sites in Amsterdam (`ams`), Singapore (`sin`) and San Jose (`sjc`), each a leaf-spine fabric: leaf switches connect servers, spine switches connect leaves, and the spines of two sites are joined by long-haul circuits. Router names look like `leaf2.sin` (leaf 2 in Singapore); `gw1.ams` is an internet gateway and `rr1.ams` a route reflector. External prefixes come from the ranges reserved for documentation (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, RFC 5737).

### The task

Write `routing_loop_detect(destination, next_hops)`.

- `destination` is the name of the router that owns the destination prefix. It delivers the packet itself and never forwards it, so ignore any entry it has in `next_hops` when following packets. A router named in that entry still counts as a router named in the input.
- `next_hops` is a list of `[router, next_hop]` pairs. `next_hop` is a router name, or `None` (`null` in JavaScript) when the router has no route. Each router appears at most once as the first element.
- A router named only as someone's next hop, with no pair of its own, has no forwarding entry: it drops the packet.

Consider a packet for the destination that starts at each router named anywhere in the input (as a router or as a next hop), other than the destination. Return a dictionary (a plain object in JavaScript) with three keys:

- `"looping"`: every router whose packet circulates forever (until TTL expiry). That is the routers on a cycle and every router whose path leads into one.
- `"black_holed"`: every router whose packet is dropped at a router with no route, including that router itself.
- `"cycles"`: each forwarding loop as a list of its routers in forwarding order (each one's next hop is the one after it, and the last one's next hop is the first), starting from the router whose name is smallest. Sort the cycles by their first router.

Routers whose packets reach the destination appear in neither list, and the destination itself never appears in the output. Sort `"looping"` and `"black_holed"` as plain strings, so `"leaf10.ams"` comes before `"leaf2.ams"`.

### Examples

The circuit `spine1.ams`–`spine1.sin` has just failed. `spine1.ams` has already reconverged and sends Singapore traffic down to a leaf, `leaf2.ams`, expecting it to go up through `spine2.ams`. `leaf2.ams` has not heard about the failure yet and still sends it to `spine1.ams`.

A one-router cycle is still a cycle. `spine1.sjc` delivers to `leaf1.sjc`, and `leaf1.sjc`'s own entry is ignored, so following it does not create a loop `leaf1.sjc` → `spine1.sjc` → `leaf1.sjc`.

### Constraints

- `0 ≤ len(next_hops) ≤ 10⁵`
- Router names are non-empty ASCII strings; each router appears at most once as the first element of a pair.
- `destination` may appear anywhere in the input, or nowhere.

### Follow-up

"Real fabrics use ECMP (equal-cost multipath), so a router can have several next hops and hashes each flow onto one of them. What does 'this router loops' mean now, and how does your algorithm change? Then: you collect forwarding tables from 2,000 devices every few seconds for 50,000 prefixes. How do you run this continuously, and how do you avoid paging someone for a loop that existed only because two devices were polled 300 ms apart?"

## Solution

### The naive approach

Simulate the network. For each router, follow next hops with a hop limit, as a real packet's TTL would. With `n` routers, a loop-free path visits each router at most once, so if the walk is still going after `n` steps it is in a loop. Reaching the destination means delivered; reaching a router with no next hop means black-holed.

That is `O(n)` per router and `O(n²)` in all, `10¹⁰` steps at the limits. It also leaves the cycles themselves unknown: you know `leaf1.ams` loops, not which routers form the loop. To find those you need a second pass per router (a router is on a cycle exactly when its walk returns to it), or Floyd's tortoise-and-hare cycle detection per starting router, which is still quadratic overall.

The quadratic part is repeated work. `leaf1.ams` and `leaf3.ams` both go through `spine1.ams` in the second example, and the naive approach walks everything after `spine1.ams` twice.

### The insight

Because each router has at most one next hop, a router's fate is exactly its next hop's fate. Once you know what happens to a packet at `spine1.ams`, every router whose path reaches `spine1.ams` has the same answer, so you never need to walk past a router you have already classified.

The one fate you cannot inherit is the loop, because on a cycle there is no "already classified" router to stop at. You detect it by remembering which routers are on the walk you are doing right now. Arriving back at one of them means you have just closed a cycle, and the cycle is exactly the part of the current walk from that router on. This is the three-state idea from cycle detection in directed graphs (unvisited, on the current path, finished), simplified because each node has at most one edge, so a walk is a straight line and needs no stack.

### The optimal approach

1. Build `nxt`, a dictionary from router to next hop. A router with no entry and a router with `None` are treated the same: `nxt.get(router)` returns `None` for both.
2. Collect every router named anywhere, then remove the destination.
3. Seed `outcome = {destination: "delivered"}`. This is what makes the destination's own entry irrelevant: a walk stops as soon as it reaches a router in `outcome`.
4. For each router, walk forward, appending each new router to `path` and recording its index in `pos`, until the current node is `None`, already in `outcome`, or already in `pos`.
   - `None`: the last router on the path has no route, so the fate is `"black_hole"`.
   - In `pos`: the walk closed a cycle. The cycle is `path[pos[node]:]`; rotate it to start at its smallest name. The fate is `"loop"`.
   - In `outcome`: inherit that router's fate.
5. Give every router on `path` that fate. A router that was already classified produces an empty walk and costs `O(1)`.

```python
def routing_loop_detect(destination: str, next_hops: list[list[str | None]]) -> dict[str, list]:
    nxt = {router: hop for router, hop in next_hops}
    routers = set(nxt) | {hop for hop in nxt.values() if hop is not None}
    routers.discard(destination)

    outcome = {destination: "delivered"}         # the destination never forwards
    cycles = []
    for start in sorted(routers):
        path, pos = [], {}                        # the current walk, and each router's index on it
        node = start
        while node is not None and node not in outcome and node not in pos:
            pos[node] = len(path)
            path.append(node)
            node = nxt.get(node)                  # None: no entry, or an entry with no route
        if node is None:
            result = "black_hole"
        elif node in pos:                         # back on our own walk: a new cycle
            cycle = path[pos[node]:]
            k = cycle.index(min(cycle))
            cycles.append(cycle[k:] + cycle[:k])
            result = "loop"
        else:
            result = outcome[node]                # inherit a fate found earlier
        for r in path:
            outcome[r] = result

    return {
        "cycles": sorted(cycles),
        "looping": sorted(r for r in routers if outcome[r] == "loop"),
        "black_holed": sorted(r for r in routers if outcome[r] == "black_hole"),
    }
```

Trace the first example. The first start is `leaf1.ams`. The walk records `leaf1.ams` (index 0), `spine1.ams` (1) and `leaf2.ams` (2), and the next node, `spine1.ams`, is already at index 1: the cycle is `path[1:] = ["spine1.ams", "leaf2.ams"]`, rotated to `["leaf2.ams", "spine1.ams"]`, and all three routers on the walk get `"loop"`. The next start, `leaf2.ams`, is already in `outcome`, so its walk is empty. `leaf3.ams` walks through `spine2.ams` and `spine2.sin` and stops at `leaf2.sin`, the destination, so all three are delivered. `leaf4.ams` stops after one step, at `spine2.ams`, and inherits `"delivered"`.

Because cycles are disjoint (a router has one next hop, so it can be on only one cycle) and each is rotated to start at its smallest name, sorting the list of cycles sorts them by their first router. Sorting the starting routers is not needed for correctness; it only makes the run deterministic.

**Complexity.** Every router enters `path` exactly once over the whole run, because it is classified as soon as its walk ends and is never walked again. The walks therefore cost `O(n)` in total, where `n` is the number of routers named in the input. Sorting for the output costs `O(n log n)` comparisons, which dominates. Space is `O(n)` for the dictionaries.

### Common mistakes

- **Treating any revisit as a loop.** Reaching a router you saw on an *earlier* walk is not a cycle; it is a shortcut to a known answer. Only a router on the *current* walk closes a loop. That is why `pos` is reset for every start while `outcome` is shared. Using a single `visited` set for both reports `leaf3.ams` → `spine1.ams` as a loop in the second example.
- **Missing routers that appear only as next hops.** `spine3.ams` in the second example has no entry. Building the router set from the keys alone loses it from `"black_holed"`, and a lookup `nxt[node]` that raises instead of returning `None` crashes on it.
- **Walking the destination's entry.** A stale entry on the destination, as in the third example, turns delivered routers into a fake loop if you follow it. Seed the destination as delivered and the problem disappears.
- **Putting tail routers in the cycle.** `leaf1.ams` loops but is not part of the loop. The cycle starts at the router you came back to, not at the start of the walk.
- **Recursion.** A recursive "fate of my next hop" is natural to write, but a chain of `10⁵` routers exceeds Python's default recursion limit of 1,000. The iterative walk has no depth limit.
- **Sorting the cycle instead of rotating it.** The cycle must stay in forwarding order: `["leaf10.ams", "spine3.ams", "spine2.ams", "leaf12.ams", "spine4.ams"]`, not the alphabetical list of those names.

### How to discuss it

Start from the networking: per destination each router has one next hop, so the snapshot is a functional graph and every walk ends at the destination, at a dead end or in a cycle. Give the TTL simulation and its `O(n²)` cost in one sentence. Then say the insight out loud: "a router's fate is its next hop's fate, so I memoise fates, and I keep a separate on-path marker so I can tell 'I've been here this walk' (a loop) from 'I've been here before' (a known answer)." Mention that this is three-colour cycle detection specialised to out-degree one. While coding, name the three stopping conditions and which fate each assigns. Trace a walk that closes a cycle with a tail, because it shows the tail and the cycle being separated by `pos`.

### Networking follow-ups

A network-org interviewer will move from the algorithm to how this is used on a real network.

- **"Add ECMP."** With several next hops per router, the graph is a general directed graph and the question splits in two. "Some flow from this router can loop" means a cycle is reachable from it: compute strongly connected components (Tarjan or Kosaraju), mark every component that contains a cycle, and propagate "can loop" backwards along edges. "Every flow loops" and "some flows are black-holed" need the same kind of reachability for the other fates. Which flows actually loop depends on each router's hash, which the snapshot does not tell you. The common wrong answer is to keep the single-next-hop walk and pick the first ECMP member, which misses loops on the other members.
- **"Where does the data come from, and is the snapshot real?"** Forwarding tables come from every device, typically streamed over gNMI (a gRPC-based telemetry and configuration protocol) or polled. Polls are not simultaneous, so two devices captured 300 ms apart during convergence can look like a loop that never existed, or hide one that did. Timestamp every table and only alert on a loop that persists across several consecutive snapshots. A real microloop lasts tens to hundreds of milliseconds, too short for polling to see reliably; it shows up instead as TTL-expired discard counters and a utilisation spike on the looping links right after a failure.
- **"Why is a microloop worse than a black hole?"** A dropped packet costs one packet. A looping one that enters a two-router loop with a TTL of 64 crosses the link between them about 31 times in each direction before it dies, so a few gigabits a second of looping traffic offers roughly 30 times that load to the link, around a hundred gigabits a second, and drops unrelated traffic that shares it. The [convergence lesson](/learn/fabric-networking/underlay/convergence-and-bfd) works this through on Meridian.
- **"How do networks prevent microloops?"** Ordered FIB updates (update routers farthest from the failure first), segment-routing microloop avoidance (temporarily steer traffic along the post-convergence path with an explicit path), and fast reroute with a precomputed loop-free backup. In a Clos fabric with an eBGP underlay, spines that share one AS reject any path that contains their own AS, so `spine1.ams` drops instead of bouncing the packet off a leaf: a short black hole instead of a loop ([BGP as the underlay](/learn/fabric-networking/underlay/bgp-as-the-underlay)).
- **"Is every black hole a bug?"** No. A discard route for an aggregate the router originates (so packets to unused parts of it are dropped instead of following the default route back out) and remotely triggered black-hole routes used against a DDoS attack are deliberate. A verifier needs an allow-list of intended drops. The opposite case, where every BGP session is up and packets are still dropped because a router in the middle has no route, is [the BGP black hole](/learn/fabric-networking/bgp-fundamentals/the-bgp-black-hole).
- **"Now do it for 50,000 prefixes."** Running this once per prefix repeats work, because most prefixes share forwarding behaviour (every host behind one leaf follows the same path). Group destinations into equivalence classes that every router forwards identically, using longest-prefix match on each table ([longest prefix match](/practice/longest-prefix-match)), and check each class once. That is the core of network verification tools such as Batfish and of the research systems behind them (header space analysis, Veriflow).
- **"What should the platform show?"** For each loop: its members in forwarding order, the prefixes affected, how many routers feed it (the blast radius), and how long it has persisted. For each black hole: the router that drops and whether its drop is on the intended-discard list. Alongside that, the device counters that confirm it in the data plane: TTL-expired discards and no-route drops.
