@0
Three transit networks sit in a triangle: AS 64496, ISP1 at AS 64501, and ISP2 at AS 64502. They peer with each other and pass every route on, and each also has its own link to AS 64511 at the top, which originates 192.0.2.0 slash 24. Meridian, ISP1's customer, just watches what ISP1 tells it. Hold onto one sentence, because it is the whole mechanism: nothing in BGP says a path is dead; a router only finds out when its own AS number comes back to it.

@1
In steady state each network uses its direct link to AS 64511 and keeps two reserves, one through each neighbour. ISP1's table shows all three: 64511 directly, which is best, then 64496 64511, and 64502 64511. Meridian sees an AS path of 64501, 64511.

@2
Now AS 64511 withdraws the prefix on all three sessions at the same moment. The prefix no longer exists anywhere, so the only correct end state is that nobody holds a route. The question is how long the others take to agree.

@3
Each network deletes its direct path and falls back to a reserve. ISP1 takes 64496 64511 through AS 64496. AS 64496 takes ISP1's path, 64501 64511. ISP2 takes 64496 64511. Every one of them is stale: it describes a path through AS 64511 that is gone, but no router can know that yet. Meridian now sees three ASes: 64501, 64496, 64511.

@4
Look at the two arrows between ISP1 and AS 64496. ISP1 forwards to AS 64496, and AS 64496 forwards back to ISP1. A packet Meridian sends to 192.0.2.1 bounces between them until its TTL runs out. The traffic was undeliverable anyway, but the loop burns capacity on a link that healthy traffic shares.

@5
Each network advertises its new best path to its two neighbours, with its own AS added in front: six messages among the three, and one from ISP1 to Meridian. From here on, each further change to a neighbour waits for that session's MRAI timer, the minimum route advertisement interval: 30 seconds for eBGP, as RFC 4271 suggests and some implementations default to, and zero in others.

@6
Thirty seconds later those advertisements are processed. ISP1 receives 64496 64501 64511 from AS 64496, sees its own AS inside, and discards it. Its last option is longer: 64502 64496 64511 through ISP2. AS 64496 finds its own number in both copies it received and has nothing left. So Meridian is now shown a path of four ASes, 64501, 64502, 64496, 64511, for a prefix that has been gone for half a minute. The chart shows the path length at Meridian climbing from two to three to four.

@7
Another 30 seconds. The last stale paths come back either as withdrawals or with the receiver's own AS inside, so ISP1 and ISP2 run out of options too. No network holds a path any more, and ISP1 finally sends Meridian a withdrawal.

@8
The tally: about 60 seconds and 19 BGP messages for a single prefix, the origin's 3 withdrawals and 16 among the three networks, while Meridian was shown paths of two, three and four ASes. That is the asymmetry. An announcement spreads in one pass, because the first path to arrive is real. A withdrawal has to disprove every reserve path first, so bad news travels slowly.

@9
The last frame lists the levers. A shorter timer, even zero, makes each step happen sooner but sends many more updates and costs CPU; a longer one sends fewer updates and converges more slowly. That trade is real: in 2000, Labovitz and colleagues measured internet withdrawals taking about three minutes on average to converge, some up to fifteen. Inside a data center eBGP fabric the fix is structural: give every spine of a site the same AS, 65100 in Meridian's design, and any stale path that climbs back up through another spine fails the loop check at once. PIC and add-path backups make the switch fast when the backup is real, but they do not stop a hunt. Generalise it this way: with n fully meshed networks the hunt takes n rounds, paths grow to n plus one ASes, and the signal to look for is a run of updates for one prefix with steadily longer AS paths, ending in a withdrawal.
