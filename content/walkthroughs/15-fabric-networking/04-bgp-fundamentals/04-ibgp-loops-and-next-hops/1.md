@0
Four autonomous systems sit in a ring: Meridian, AS 64500, at the bottom with its two border gateways, gw1 and gw2; its providers ISP1, AS 64501, and ISP2, AS 64502; and above them a transit provider, AS 64496, that both ISPs buy from. Hold onto one rule, because it is the whole loop check between networks: every time a route leaves an AS, the sender adds its own AS number to the front of the AS path, and every receiver throws the route away if it finds its own number anywhere in that path.

@1
gw1 originates Meridian's public block, 203.0.113.0 slash 24. Its AS path is empty: numbers are added only when a route leaves an AS, so a route still at home carries none. In this run only gw1 announces the block to the internet, which makes the announcement travel a single ring.

@2
First, gw1 passes the route to gw2 over iBGP, inside AS 64500. The AS path is still empty, the next hop is gw1's loopback, 10.255.1.201, and it carries a local preference of 100, an attribute that never leaves the AS. iBGP never adds the local AS number. Remember that; it matters later.

@3
On the eBGP session to ISP1, gw1 adds its own AS: the path becomes 64500. The next hop becomes 198.51.100.3, gw1's address on the link they share, which is where ISP1 will send traffic for Meridian. Local preference is left out.

@4
ISP1 scans the path for its own number, 64501, does not find it, and accepts. To ISP1, Meridian's block is one AS away, via 198.51.100.3.

@5-6
ISP1 passes it to the transit provider, adding 64501 on the left, so the path reads 64501 then 64500, from the nearest AS back to the origin. The next hop becomes ISP1's side of that link, 198.51.100.7. The transit provider finds no 64496 in the path and accepts: Meridian is two ASes away, and the transit provider hands the route on to its other customers, which is how one announcement spreads across the internet.

@7-8
The transit provider sends it on to ISP2 with the path 64496, 64501, 64500, and next hop 198.51.100.8. Each eBGP hop has added exactly one AS and replaced the next hop with its own address. ISP2 accepts too; three ASes away is the only path it has.

@9
Now ISP2 sends its full table to its customer, gw2, and the full table includes Meridian's own block: four ASes long, 64502, 64496, 64501, 64500, with next hop 198.51.100.0.

@10
gw2 finds its own AS, 64500, at the end of the path and discards the route. RFC 4271 calls this an AS loop. Notice that gw2 never sent this route. Its AS did, through gw1, so the check is per AS, not per router. gw2 keeps using the iBGP route it got from gw1.

@11
Traffic flows the opposite way to the announcement. A packet entering ISP2 for 203.0.113.10 follows each AS's next hop back through the transit provider and ISP1 to gw1. And the announcement itself cannot circle this ring forever, because the loop check stops it; a route carries no hop limit of its own.

@12
The path grew by one AS at each of the four eBGP boundaries, and it does two jobs at once: it detects loops with no timers or counters, because the route carries its own history, and it gives a rough distance that best-path selection prefers shorter. It counts networks, not routers, kilometres or milliseconds. The trap is inside an AS: there the path never grows, so it cannot see a loop at all, and iBGP needs a different rule.
