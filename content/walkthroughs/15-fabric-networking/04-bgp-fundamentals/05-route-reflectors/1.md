@0
Four Amsterdam leaves, leaf1 to leaf4, all in the overlay's AS 65000, with two route reflectors, rr1 and rr2, greyed out at the sides. Hold onto one idea, because it is the whole lesson: a route reflector is an iBGP speaker allowed to break iBGP's no-relay rule, and two new attributes catch the loops that breaking it opens. Without reflectors, every leaf needs a session to every other leaf: n times n minus 1, over 2, which is 6 sessions here, 120 for the site's 16 leaves, and 1,128 for 48 leaves across three sites.

@1
Here is why the mesh is needed. Inside one AS the AS path never changes, so it cannot catch loops, and BGP's rule is that a route learned from an iBGP peer is never passed to another iBGP peer. leaf1 hears leaf3's route, but will not relay it to leaf2, so leaf2 must hear it from leaf3 directly.

@2
Route reflection, RFC 4456, relaxes that rule on two routers. Every leaf keeps just two sessions, one to rr1 and one to rr2, plus one session between the reflectors, which are non-client peers of each other. That is 9 sessions for four leaves, more than the mesh's 6. The point is growth: 33 instead of 120 for 16 leaves, and a new leaf needs two sessions, not one to every other leaf.

@3
leaf3, where Acme's 10.1.2.0 slash 24 lives, advertises it to both reflectors. The next hop is 10.255.1.13, leaf3's own loopback, the AS path is empty, and the local preference is 100. In Meridian this travels as an EVPN route, but reflection treats every route type the same way.

@4
rr1 learned the route from a client, and the rule table on screen says a route from a client is reflected to every client and every non-client. Before it does, it adds two attributes. The originator ID, 10.255.1.13, is the router ID of the leaf that injected the route. The cluster list gets rr1's cluster ID prepended: 10.255.1.100.

@5
rr1 reflects the route to leaf1, leaf2 and leaf4, with the next hop still 10.255.1.13, because a reflector changes no forwarding attribute. So traffic for 10.1.2.0 slash 24 goes from each leaf straight to leaf3 through the spines, never through rr1. That is why reflectors sit beside the spines, out of the forwarding path.

@6
rr2 reflected the same route, so leaf1 now holds two identical copies, as its table shows. They tie at every step, even router ID, where a reflected route is compared by its originator ID, the same in both. The last tie-breaker, the lower peer address, picks rr1's copy. Traffic is the same either way, since both name next hop 10.255.1.13, and if rr1 fails the other copy is already there.

@7
rr1 also reflects the route to rr2, its non-client peer. Meridian gives both reflectors of a site one cluster ID, 10.255.1.100, so rr2 finds its own cluster ID in the cluster list and discards the copy as a loop. It loses nothing, because it heard the route from leaf3 directly.

@8
The rules would also send the route back to leaf3, itself a client. Many implementations skip that, and if it does arrive, leaf3 ignores it, because the originator ID is its own router ID. So the two checks split the work: the originator ID stops a route returning to its originator, and the cluster list stops it circling between reflectors.

@9
The shared cluster ID has a cost. Suppose leaf3's session to rr2 drops. rr2 cannot use rr1's copy either, so it holds no copy of 10.1.2.0 slash 24, and every other leaf holds leaf3's routes from rr1 alone. Nothing is lost yet, but redundancy has quietly fallen to one reflector. Giving each reflector its own cluster ID keeps that copy, at the price of more paths in memory; both designs are common.

@10
With leaf3's session to rr2 back up, now rr1 fails. Every leaf already holds the same routes from rr2, and because no traffic ever passed through rr1, forwarding does not change at all: every leaf's traffic is unchanged. One reflector is a control-plane spare, not a forwarding path.

@11
Then rr2 fails too. Each leaf's hold timer expires within 9 seconds, and it deletes every overlay route it learned from the reflectors. Tenant traffic between leaves stops, even though every spine and fabric link is up. That is why the two reflectors go on different spines and power feeds, and why a tool should alarm on losing one, not just both.

The pattern to take away: reflection turns a mesh that grows with the square of the router count into two sessions per router, paid for with two loop checks that compare identifiers, so a duplicated router ID or cluster ID makes them discard good routes while every session stays up. And losing one reflector changes nothing a user sees, so the first loss is the one to alarm on.
