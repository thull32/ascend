@0
On screen, gw1 in Amsterdam, one of Meridian's border gateways, holds three paths to one prefix, 192.0.2.0 slash 24, which belongs to a content network in AS 64511. Path A comes from its own eBGP session to ISP1. Path B comes over iBGP from gw2, also in Amsterdam, which learned it from ISP2. Path C comes over iBGP from the Singapore gateway, which learned it from ISP2 there. The drawing shows one spine per site. Hold onto one idea, because it is the whole algorithm: BGP walks a fixed ladder of comparisons, the first one that separates the paths decides, and nothing below it is consulted. The order of the ladder is the policy.

@1
Step 1 asks whether each path is usable at all. A's next hop, 198.51.100.2, is on a directly connected link. B's, 10.255.1.202, and C's, 10.255.2.201, are gateway loopbacks that IS-IS carries. Every next hop resolves, and no AS path contains Meridian's own number, 64500, so all three are candidates.

@2-4
Steps 2, 3 and 4 are this router's and this operator's own choices, and here they all tie. Weight, a vendor extension that never leaves the router, is 0 on all three, because Meridian sets none. Local preference, the AS-wide choice of exit that import policy sets, is 100 on all three. And none is locally originated: all three were learned from peers.

@5
Step 5, shortest AS path, is the first that separates them. B and C cross two networks, 64502 then 64511. A crosses three: 64501, the transit provider 64496, then 64511. A is out, even though it is the only path gw1 learned directly. AS path length counts organisations, not kilometres or milliseconds.

@6
Step 6, origin, says how the originating AS put the prefix into BGP, and lower wins: IGP, then EGP, then incomplete. B and C both say IGP, so both stay.

@7
Step 7, the lowest MED. B and C both came from AS 64502, so their MEDs are compared, and both are 0. Notice A's MED of 10. It would never have met their 0 even if A had survived, because by default MED is compared only between paths from the same neighbouring AS.

@8
Step 8 prefers a path learned over eBGP to one learned over iBGP. B and C are both iBGP, so it is a tie. This is the step where A would have won, had it not fallen at step 5. Because it sits below AS path length, gw1 ignores its own ISP link.

@9
Step 9 compares the IGP cost to each next hop. B's next hop is 20 away in IS-IS: two fabric links of 10 through spine1. C's is 120, because it crosses the long-haul circuit to Singapore at a metric of 100. C is out and B wins. This is hot-potato routing: among equal exits, leave by the nearest one. It matters, because Amsterdam to Singapore is about 10,500 kilometres of fibre, and C would have added about 52 milliseconds each way inside Meridian.

@10
One path is left after step 9, so steps 10 to 13 grey out as not reached. Multipath, when it is enabled, installs several equally good paths for forwarding but still names one best. Oldest eBGP path, lowest router ID, and shortest cluster list then lowest peer address exist only so that there is always exactly one answer, on every router, every time.

@11
gw1 installs B. Its forwarding table sends 192.0.2.0 slash 24 to next hop 10.255.1.202, resolved through spine1, so traffic crosses the fabric to gw2 and leaves through ISP2. gw1 advertises nothing to its iBGP peers, because its best path came from one of them. And best is per router: gw2 and the Singapore gateway each keep their own ISP2 path at step 8, eBGP over iBGP. Three gateways use two different exits for one prefix, and all three are right.

The pattern to take away: ask which step decided before you ask which path won. Local and deliberate beats global and accidental: first what you chose, then what the path says, then your own network's geometry, then tie-breakers. And this run carries the trap: hot potato ties BGP to the IGP, so raising gw2's link metrics during maintenance would move Amsterdam's exit to Singapore, over 100 milliseconds more round trip, with no BGP session touched.
