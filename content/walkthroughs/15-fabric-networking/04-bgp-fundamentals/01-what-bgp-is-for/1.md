@0
Four autonomous systems in a ring, each a network run under its own policy and its own AS number: Meridian, AS 64500, with two gateways in Amsterdam; its two providers, ISP 1, AS 64501, and ISP 2, AS 64502; and a transit provider, AS 64496, that both ISPs buy from. Every number here comes from the ranges reserved for documentation. Hold onto one rule, because it is the whole loop check: each AS adds its own number to the route's AS path as the route leaves it, and an AS that finds its own number in an incoming path throws the route away.

@1
Gateway 1 originates 203.0.113.0 slash 24, Meridian's public block, with an empty AS path. Numbers are added only when a route leaves an AS, so a route still at home carries none. In this run only gateway 1 announces the block to the internet, so the announcement makes a single trip round the ring.

@2
First, gateway 1 tells gateway 2 over internal BGP, inside AS 64500. The AS path is still empty, the next hop is 10.255.1.201, gateway 1's loopback, and the route carries a local preference of 100, an attribute only internal BGP sends. Internal BGP never adds the local AS number.

@3
Now the external session to ISP 1. Gateway 1 prepends its own AS, so the AS path becomes 64500. The next hop becomes 198.51.100.3, gateway 1's address on the link they share, which is where ISP 1 will send traffic for Meridian. Local preference is left out, because it never leaves its AS.

@4
ISP 1 scans the path for its own number, 64501, does not find it, checks the prefix against the blocks Meridian may announce, and accepts. To ISP 1, Meridian's block is one AS away.

@5-6
ISP 1 passes the route to its provider, prepending 64501 on the left, so the path reads 64501, 64500: from the nearest AS back to the origin. The next hop becomes 198.51.100.7, ISP 1's side of that link. The transit provider finds no 64496 in the path and accepts. It hands the route on to its other customers and peers, which is how one announcement spreads across the internet.

@7-8
The transit provider sends it on to ISP 2, another of its customers: AS path 64496, 64501, 64500, next hop 198.51.100.8. ISP 2 accepts. Since Meridian is not announcing to ISP 2 directly in this run, this is ISP 2's only path, three ASes away.

@9
ISP 2 sends its full table to its customer, gateway 2, and the full table includes Meridian's own block. The path is now four ASes long, 64502, 64496, 64501, 64500, with next hop 198.51.100.0.

@10
Gateway 2 finds its own AS, 64500, at the end of the path and discards the route before best-path selection: an AS loop. The check is per AS, not per router. Gateway 2 never sent this route, but its AS did, and it keeps using the internal route from gateway 1.

@11
Traffic flows the opposite way to the announcement. A packet entering ISP 2 for 203.0.113.10 follows each AS's next hop back through the transit provider and ISP 1 to gateway 1. And the loop check is what stops the announcement circling this ring forever, because a BGP route carries no hop limit of its own.

@12
So the AS path grew by exactly one number at each of the four external boundaries, and not at all inside an AS. It does two jobs at once: loop detection, as gateway 2 just showed, and a rough distance that best-path selection can use. But it counts networks, not routers, kilometres or milliseconds, and it says nothing about cost. That is why every network ranks routes by its own policy first, and why loops inside one AS, where the path cannot grow, need different rules.
