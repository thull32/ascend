@0
On screen is gw2, one of Meridian's Amsterdam border gateways in AS 64500, with three neighbours: ISP2, AS 64502, over eBGP, and two iBGP peers, Amsterdam's gw1 and Singapore's gw1. Hold onto one idea, because it is the whole lesson: a route is never simply received and used. It passes six stages in order, listed in the table: an input table per peer, import policy, the Loc-RIB where one best path per prefix is chosen, the routing table and forwarding chip, export policy per peer, and an output table per peer. gw2's session to ISP2 has just come back after maintenance. Until now it reached 192.0.2.0 slash 24, a content network's prefix, through Singapore's gw1.

@1
ISP2 sends a 70-byte UPDATE. It withdraws nothing. It carries five path attributes: ORIGIN IGP; the AS path 64502 then 64511, so ISP2 heard it from the content network that originated it; next hop 198.51.100.0, ISP2's address on the shared link; MED 0; and community 64502 colon 3010, ISP2's tag for where it learned the route. Then two prefixes that share all of that: 192.0.2.0 slash 24 and 192.0.2.128 slash 25. One UPDATE carries one set of attributes for any number of prefixes.

@2
Both prefixes land in the Adj-RIB-In for ISP2 exactly as received, before any policy. Most routers keep this pre-policy copy only when configured to, with soft reconfiguration; otherwise, when policy changes, they ask the peer to resend everything with ROUTE-REFRESH. BMP monitoring can export the same pre-policy view.

@3
Import policy runs rule by rule. Neither path contains Meridian's own AS, and neither is a bogon or Meridian's own block. Then the length rule: Meridian, like most networks, accepts nothing longer than a slash 24 from the internet, so the slash 25 is rejected. The slash 24 passes and is changed on the way in: local preference 100, the value Meridian uses for a transit provider, and Meridian's own community, 64500 colon 102, meaning learned from ISP2 at gw2.

@4
The post-policy view holds one usable route. Local preference did not arrive with it: that attribute never crosses an AS boundary, so each AS sets its own on import, and from here it travels with the route to every iBGP peer inside AS 64500.

@5
In the Loc-RIB the new path meets the one gw2 was using, from Singapore's gw1. They tie on local preference, 100 each; on AS path length, two each; on ORIGIN, IGP for both; and on MED, 0 for both, a fair comparison because both came from AS 64502. The decision falls to eBGP over iBGP, and the path from ISP2 becomes best.

@6
The best path goes to the routing table and from there into the forwarding chip. The entry for the slash 24 moves: before, next hop 10.255.2.201, Singapore's gw1, across the spines and the long-haul circuit, about 10,500 kilometres away; after, 198.51.100.0, out of the port to ISP2. The Singapore path is not deleted. It stays in the Loc-RIB as a backup, but it is not installed.

@7
Export runs per peer. To its iBGP peers, gw2 sends a 76-byte UPDATE, and the highlighted fields are the ones that differ from what ISP2 sent: the next hop is rewritten to gw2's own loopback, 10.255.1.202, which is next-hop-self; local preference 100 is added; both communities are listed; and only the accepted slash 24 is carried. The AS path is untouched, because a route gains an AS number only when it leaves the AS. Towards ISP2 the rule is Meridian's own blocks only, so this route is denied.

@8
Each peer's Adj-RIB-Out holds what it was sent. Both iBGP peers hold the slash 24 with next hop 10.255.1.202 and AS path 64502, 64511. ISP2's holds only Meridian's block, 203.0.113.0 slash 24, with AS path 64500. Passing ISP2's routes on to ISP1 would offer to carry traffic between two providers.

@9
The change ripples on. Amsterdam's gw1 moves its traffic for the slash 24 from Singapore's gw1 to gw2, because gw2 is 20 away in IS-IS instead of 120. Singapore's gw1 keeps its own path from ISP2, since eBGP beats iBGP there too. And gw2 still holds Singapore's path as a backup, ready if ISP2's session drops again.

@10
The last frame shows the numbers a monitoring tool should show per peer: received from ISP2, 2; accepted after policy, 1; best and installed, 1; advertised to the iBGP peers, 1. Each gap names a stage. Received above accepted points at import policy; accepted above best points at the decision process, or at a next hop that does not resolve. That is the pattern to keep: when a peer sent a route and the router does not use it, the session being up tells you nothing. Walk the stages and find the one where the count drops.
