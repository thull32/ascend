@0
Three routers in a row, a cut-down piece of Meridian's Amsterdam fabric with one spine. R1 is leaf1, R2 is spine1, R3 is leaf3. Acme's web server, acme-web1, hangs off leaf1, and its database, acme-db1, off leaf3. All three routers run IS-IS; only the two leaves run BGP. This run imagines a design Meridian does not use: Acme's subnets in the plain global routing table, with no VXLAN. Hold onto one rule, because it is the whole trap: BGP decides which exit a packet should leave by, but every router on the way must still forward the packet using only what it knows itself.

@1
IS-IS is up on both links, and spine1's table is complete for what IS-IS carries. Four routes: the loopbacks of leaf1, 10.255.1.11, and leaf3, 10.255.1.13, and the two slash 31 link subnets. No Acme subnet is in it, by design. IS-IS carries infrastructure addresses only.

@2
leaf1 opens the BGP session: a TCP SYN from its loopback to leaf3's loopback, port 179. spine1 can forward this packet, because IS-IS gave it a route to 10.255.1.13.

@3
The handshake completes, OPEN and KEEPALIVE messages are exchanged with both sides in AS 65000, and the session reaches Established. The dashed line between the leaves is a TCP connection, not a cable. Every one of its packets physically travels through spine1 as ordinary traffic between two loopbacks.

@4-5
leaf3 advertises Acme's subnet, 10.1.2.0 slash 24, where acme-db1 lives. The next hop is its own loopback, 10.255.1.13, and the AS path is empty, because it originates the route inside AS 65000. spine1 forwards the UPDATE as TCP payload, and the only change it makes is the IP TTL, one lower, 63. It has just carried the only message that mentions 10.1.2.0 slash 24, and it kept no copy, because a router without BGP has nothing that could read it.

@6
leaf1 installs the route. The next hop, 10.255.1.13, is not on a connected link, so leaf1 resolves it recursively: IS-IS says that loopback is reached through 10.254.1.0, which is spine1. The FIB entry becomes 10.1.2.0 slash 24 via spine1. The packet will be handed to the spine.

@7
Now look at the dashboard. The session is Established with one prefix received, both IS-IS adjacencies are up, and the next hop resolves. Every check is green, and none of them has asked whether spine1 can forward a packet for 10.1.2.0 slash 24.

@8
acme-web1 opens a connection to acme-db1 at 10.1.2.20, port 5432. The destination is off its subnet, so the frame goes to its gateway, leaf1, with TTL 64.

@9
leaf1 matches 10.1.2.0 slash 24 in its FIB, decrements the TTL to 63, and sends the packet to spine1, exactly as BGP and IS-IS told it to. The destination is still 10.1.2.20. Nothing in the packet mentions leaf3. The knowledge that this subnet lives behind leaf3 stayed on leaf1, the only router that read the UPDATE.

@10
spine1 looks up 10.1.2.20 against its four routes. Neither loopback covers it, neither link subnet covers it, and there is no default route.

@11
So spine1 discards the packet and counts a no-route drop. It would normally send an ICMP destination unreachable back to 10.1.1.10, but it has no route to Acme's 10.1.1.0 slash 24 either, so even the error has nowhere to go. acme-web1 hears nothing and retries its SYN, on Linux defaults six times over about 127 seconds, before the application sees a timeout. Not an error: a timeout, two minutes later.

@12
That is the trap: the control plane is healthy while the data plane drops every packet. traceroute from acme-web1 shows its gateway, 10.1.1.1, and then only stars, because spine1's Time Exceeded replies cannot route back either. It looks exactly like a dead spine. This is why session Established is not a health check: the signal that finds it is a lookup of the packet's own destination on every router along the resolved path.

@13
Two fixes. Run BGP on spine1 too, so it learns 10.1.2.0 slash 24 itself, through route reflectors in a large fabric, because an iBGP router does not pass on what it learned from another iBGP router. Or encapsulate the packet towards leaf3's loopback, with an MPLS label or a VXLAN header, so the spine needs only the loopback route it already has. Meridian's fabric uses VXLAN for exactly this reason. The general lesson: a BGP route only picks the exit. Whatever lies between you and that exit must either know the destination too, or be asked a question it can already answer.
