@0
The small Amsterdam fabric, two spines and four leaves, built the RFC 7938 way: BGP is the only routing protocol, and there is no IS-IS. Both spines share AS 65100, and each leaf has its own private AS, 65101 to 65104. Every leaf to spine link carries one external BGP session between its two link addresses, eight sessions in all. Hold onto one idea, because the whole design rests on it: a router that finds its own AS number in a route's AS path throws the route away, and because the spines share one number, no path through two spines can survive.

@1
Leaf 1 announces its loopback, 10.255.1.11 slash 32, to spine 1 in a BGP UPDATE over their TCP session on port 179. The AS path holds only leaf 1's own AS, 65101, and the next hop is leaf 1's own address on that link, 10.254.1.1. The packet's T T L is 1, because these peers are directly connected and nothing should ever forward their packets.

@2
The same UPDATE goes to spine 2, with next hop 10.254.2.1. Each spine scans the AS path for 65100, finds only 65101, and accepts. One path, so it is the best: spine 1's table now shows the route straight to leaf 1.

@3
Spine 1 passes its best path on to leaf 2, leaf 3 and leaf 4. It prepends its own AS, so the AS path reads 65100, 65101, and sets the next hop to its own address on each link. The copy to leaf 3 says next hop 10.254.1.4.

@4
Spine 2 does the same, so leaf 3 receives a second copy with the identical AS path, 65100, 65101, and next hop 10.254.2.4.

@5
Leaf 3 now holds two paths, and neither wins on length. Ordinary best-path selection would install only one, but BGP multipath, off by default and switched on in every fabric, installs both: an E C M P route to leaf 1's loopback through both spines, the same forwarding result IS-IS would compute. This is the first reason the spines share one AS. With a different number on each spine, the two AS paths would differ, and most implementations would use only one of them unless told to relax the multipath rule.

@6
External BGP passes on what it learns, so leaf 3 advertises its best path to its other neighbour, spine 2, prepending its own AS: the path is now 65103, 65100, 65101, with next hop 10.254.2.5. From spine 2's point of view, that is a path to leaf 1 that goes down to leaf 3, up to spine 1, and down again: a valley.

@7
Spine 2 finds its own AS, 65100, in that path and discards it. Its table shows the direct path from leaf 1 as best and the valley path as rejected. Because every spine shares AS 65100, no spine ever accepts a path through another spine, so traffic can never take a spine, leaf, spine detour.

@8
Now the link between leaf 1 and spine 2 fails. The session runs over that one link, so it drops as soon as loss of light or B F D reports it. Spine 2 has lost its only usable path, because the looped ones were never accepted, so it sends a withdrawal of 10.255.1.11 slash 32 to leaf 2, leaf 3 and leaf 4.

@9
Leaf 3 removes the path via spine 2 and keeps the one via spine 1, which is now its only path. IS-IS would reach the same forwarding result by flooding and a shortest-path run on every router; BGP reaches it with one withdrawal per leaf and no computation anywhere else. Notice the price: spine 2 itself can no longer reach leaf 1 at all, where an IS-IS spine would detour through a leaf. Packets that reach spine 2 before the withdrawal lands are dropped for those milliseconds.

@10
That is RFC 7938's appeal: one protocol and one set of tools everywhere, policy at every hop, and failures handled by withdrawals between neighbours instead of flooding to every router. The AS plan turns BGP's loop check into a topology rule: with one AS for the spine tier, only valley-free paths, leaf to spine to leaf, exist. The cost is a session on every link, an AS plan to keep correct, and timers that fabrics tune down from BGP's internet defaults. BGP unnumbered, which peers over IPv6 link-local addresses, removes the slash 31 bookkeeping.
