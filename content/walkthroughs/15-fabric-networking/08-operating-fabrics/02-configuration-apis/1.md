@0
On the left, the automation server at 172.16.0.20. On the right, leaf1.ams, reached through a management switch on the out-of-band network. The change looks harmless: tighten leaf1's management access list, MGMT-IN, so that it admits only the automation server itself and the engineers' jump hosts. Today, running revision 41 admits the whole automation subnet, 172.16.0.0 slash 24, and the jump host subnet, 172.16.10.0 slash 24. Hold onto one idea, because it is the whole mechanism: a confirmed commit is a trial with a deadline, and if nobody confirms it, the device undoes it by itself.

@1
The automation opens SSH to TCP port 830 and asks for the NETCONF subsystem. Both sides send a hello listing their capabilities, and leaf1 assigns session 42. Three of them matter here: a candidate datastore to edit, validate, and confirmed commit.

@2
Remote procedure call 101 locks the candidate. Until session 42 unlocks it or ends, no other session can edit it, not another automation job and not an engineer at the command line. leaf1 replies ok.

@3
Call 102 edits the candidate, replacing MGMT-IN's entries. The intended first entry was 172.16.0.20 slash 32. The input had a typo: 172.16.0.2 slash 32. Look at the datastores: the candidate holds the typo, but running is still revision 41, so nothing on the device behaves any differently yet.

@4
Call 103 asks leaf1 to validate the candidate. Every value matches its YANG type, every reference resolves, nothing mandatory is missing, so the answer is ok. That is the trap. Validation proves the configuration is well formed, not that it is safe, and 172.16.0.2 slash 32 is a perfectly good prefix.

@5
Call 104 commits with confirmed, a confirm timeout of 120 seconds, and the persist token chg-4711. The candidate becomes running revision 42, still marked unconfirmed, and leaf1 keeps revision 41 as its rollback point. The timer reads 120 seconds.

@6
Revision 42 is in force, and MGMT-IN no longer admits 172.16.0.20. The automation's next call, a get to verify the change, is dropped by leaf1's own access list, and so is every TCP acknowledgement on session 42. The tool has cut itself off, and the timer is down to 117 seconds.

@7
After 30 seconds without a reply, the automation declares session 42 lost, and leaf1 times the session out too, which releases the candidate lock. The timer shows 87 seconds. Without persist, the protocol would roll back the moment the session ended. With persist, the timer keeps running, so a new session presenting the token could still confirm.

@8
So the automation tries a new session to send the confirming commit, with 60 seconds left. Its SYN to port 830 is dropped by the same access list. The tool holding the token can no longer reach the device, which is exactly the situation confirmed commit was designed for.

@9
At 120 seconds, with no confirming commit, leaf1 restores revision 41 on its own and logs that the confirmed commit timed out and the configuration rolled back. MGMT-IN admits 172.16.0.0 slash 24 again, two minutes after the mistake, with nobody at the console.

@10
The automation's next attempt connects as session 43, reads running, finds revision 41 instead of 42, and marks the change failed and rolled back, with the diff attached for a person. Without confirmed commit, revision 42 would have stayed, every automation job would have failed against leaf1, and an engineer would have had to notice and fix it by hand from a jump host. Had the change cut off the jump hosts as well, only the serial console would have been left, which at a remote site can take hours.

@11
And a cheap check would have caught this one before any commit. Does the candidate MGMT-IN still admit the tool's own address? It fails: only 172.16.0.2 slash 32. Does it still admit the jump hosts? Pass. That is the general lesson. Checks catch the mistakes someone thought of; confirmed commit is the safety net for the rest. It does not limit the damage, since revision 42 was live for the full two minutes, so size the timeout as verification time plus margin, and alert on every timed out rollback, because a change the tool may have recorded as done has failed.
