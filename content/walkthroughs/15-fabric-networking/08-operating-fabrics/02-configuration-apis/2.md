@1-2
The automation opens NETCONF over SSH on port 830, both sides exchange capabilities, and leaf1 assigns session 42. Call 101 locks the candidate, so no other session can edit it, and leaf1 replies ok.

@3

@4
Call 103 validates the candidate, and the answer is ok. Remember what that means: the configuration is well formed, not that it does what was meant.

@5
Call 104 commits with confirmed, a confirm timeout of 120 seconds, and the persist token chg-4711. The candidate becomes running revision 42, unconfirmed, and leaf1 keeps revision 41 as the rollback point.

@6
This time revision 42 still admits 172.16.0.20, so verification works. Call 105, a get, returns the new list, and its first entry, 172.16.0.20 slash 32, is counting hits from this very session. The automation also checks from the jump host subnet that engineers can still log in. The timer reads 117 seconds.

@7
With 109 seconds left, call 106 is a plain commit carrying the persist ID, chg-4711. That is the confirming commit. leaf1 cancels the rollback timer, and revision 42 becomes permanent.

@8
Calls 107 and 108 unlock the candidate and close session 42 cleanly. The change took two commits on purpose, and the second was sent only after the device proved it was still reachable.

@9
Had the verification failed, the automation would simply not have sent the confirming commit, and leaf1 would have returned to revision 41 after 120 seconds. That is why automation uses confirmed commit for every change that could cut off its own access: the safe outcome needs no action at all. The trap is sizing. If the timeout is shorter than commit plus verification, good changes roll back; if verification does not test what the change could break, bad changes get confirmed.
