@0
On screen is a small slice of the Amsterdam fabric, two spines and two leaves. Meridian's collector, 10.250.1.10 behind leaf4, holds a gNMI subscription to every device, opened to each device's gNMI port, 9339. leaf2 streams its interface counters every 10 seconds over the data network, from its loopback 10.255.1.12 through spine1. Off to the side, an out-of-band monitor reaches each device's management port, here 172.16.1.12, through a separate management switch. Hold onto one idea: silence has two explanations, dead or unable to speak, and only a witness that does not share the silent path can tell them apart.

@1
At 10:00:05 a Globex batch job starts offering about 1.1 terabits per second towards the spines, more than leaf2's 800 gigabits per second of uplink. The telemetry carries DSCP zero, the default class, so it waits in the same best-effort queue as the job and is tail-dropped along with it. TCP backs off after each loss, and the stream stalls.

@2
At 10:00:30 the collector has missed three samples in a row from leaf2 and raises an absence-of-data alert. Without that alert nothing would fire at all: there is no bad value to alert on, and the dashboard would keep showing leaf2's values from 10:00:00 as if they were current.

@3
Scope says one device, not the whole site, so the real question opens: is leaf2 dead, or alive and unable to get its data out? The gNMI session's own keepalive cannot help. It travels the same path as the data, so it goes unanswered either way. The table on screen sets out what each signal would say in each case.

@4
First witness: the out-of-band monitor pings 172.16.1.12 over the management network, which the batch job never touches. The reply comes back in 0.6 milliseconds. leaf2 is powered, its operating system is running, and its CPU answers.

@5
Second witness: the neighbours, whose own telemetry still flows. spine1 and spine2 report their links to leaf2 up, their IS-IS adjacencies to it Up, and 399 gigabits per second arriving from it on each 400 gigabit port. The IS-IS hellos still get through because switches send routing protocol packets in a network-control queue, ahead of user traffic.

@6
Verdict at 10:00:35: alive and congested, not dead. The platform shows leaf2 as telemetry blind, neither down nor green, and raises the real problem, saturated uplinks, from the spines' counters. The device's own telemetry stopped exactly when it had the most important thing to say.

@7
At 10:04:05 the job finishes. The old session did not survive four minutes of unanswered keepalives, so the collector closed it and kept re-dialling, and now a new subscription comes up. The samples it never received, 10:00:10 to 10:04:00, are recorded as a gap from a device known to be alive, never as zeros, so no graph shows a fake dip to idle in the busiest four minutes.

@8
The follow-up marks telemetry DSCP 16, class selector 2, the class set aside for operations and management traffic, and gives it a queue with a guaranteed share, so the next saturation cannot silence it. The general rule: let the bulk of the telemetry ride the data network, because a management network is built for SSH and software images, not gigabits of counters. But put the heartbeat and the alert path out of band, so the platform can always say that it is blind here.
