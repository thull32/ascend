@0
One switch, leaf1.ams, with two of its uplinks: swp51 to spine1 and swp52 to spine2, and acme-web1 below it on swp1. On the left sit the source of truth and the automation server at 172.16.0.20, which reaches leaf1 over the out-of-band management network at 172.16.1.11. Hold onto one idea, because the whole loop rests on it: the device should run exactly what the data renders, and the only way to know is to read what it really runs and compare.

@1
The source of truth stores facts, not configuration text. leaf1.ams is a leaf in Amsterdam, with loopback 10.255.1.11, which is also its tunnel endpoint. It has two fabric links at an MTU of 9216 bytes and an IS-IS metric of 10. And it has two Acme segments: VLAN 100 as VNI 10100 on swp1, and a staging segment, VLAN 300 as VNI 10102 on swp5.

@2
A template turns that data into eight lines of configuration: the hostname, the loopback, the two uplinks, then a VLAN line and a port line for each segment. Rendering is a pure function. The same data always gives the same text, so it can be tested, and rerun at any time without touching a device.

@3
On an ordinary night the automation reads leaf1's running configuration through its API, eight lines, and compares it with the render. They match. The diff is empty, and the device runs exactly what the source of truth says.

@4
But yesterday, during an incident, an engineer fighting errors on swp52's optic raised its IS-IS metric to 1000 by hand, so that leaf1 would stop sending traffic over that link. Tonight the running configuration shows metric 1000 where the render says 10. One line differs, and the source of truth did not cause it. That is drift.

@5
Drift has two possible fixes: put the device back to the intent, or change the intent to match the device. The tool cannot know which side is right, so a person decides. The optic on swp52 was replaced this morning, the override is stale, and its owner approves the revert.

@6
Then Acme retires its staging segment, and its record is deleted from the source of truth. The render shrinks from eight lines to six. The VLAN 300 and swp5 lines are simply absent, because a template can only describe what exists, never what used to. On the device, both lines are still there.

@7
The diff from running to intended now has three entries. Change swp52's metric from 1000 back to 10. Remove VNI 10102 from VLAN 300. Remove the access VLAN from swp5. Two of the three are deletions, and deletions are exactly what the rendered text cannot express.

@8
The automation pushes the six rendered lines in merge mode, which is NETCONF's default edit operation, a gNMI update, or an NVUE patch. Merge adds or overwrites every setting the payload names, and leaves everything else alone.

@9
The push reports OK, and swp52's metric is back to 10. But VLAN 300 and swp5 are still configured, because nothing in the payload mentioned them, and the diff still holds two lines. leaf1 keeps advertising an EVPN type-3 route for VNI 10102, with route target 65000 colon 10102. If that VNI is ever reused for another tenant, swp5 joins that tenant's segment.

@10
There are two ways out. Send each deletion explicitly: a NETCONF delete operation, a gNMI delete path, an NVUE unset. Or push in replace mode, where the payload is the complete configuration and the device deletes anything it does not contain. The automation sends the same six lines again, this time as a replace.

@11
leaf1 computed the two deletions itself. VLAN 300 and swp5 are gone, its type-3 route for VNI 10102 is withdrawn, and the diff is empty: rendered and running are the same six lines. The catch is that replace is only safe on the parts of the configuration the source of truth fully models, so tools scope it to those sections, and merge where another team owns the rest.

@12
An hour later the loop runs again. Same data, same render, six lines read back, an empty diff, and nothing pushed. That is idempotency, and it is what lets the loop run continuously: a non-empty diff is always drift or a pending change, never noise.

This is the same loop as infrastructure as code: declare the desired state, diff it against the actual state, act on the difference, check. Additions and changes are easy, because the intent names them. A deletion exists only as a difference against what is running, so a pipeline that renders and pushes in merge mode without diffing never deletes anything. That is why "push succeeded" means nothing on its own: the real check is that the diff is empty afterwards, and a non-empty diff after a push is an alert.
