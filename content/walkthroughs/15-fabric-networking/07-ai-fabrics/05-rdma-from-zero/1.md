@0
Two servers from Meridian's San Jose cluster, srv001 and srv002, each drawn as app, kernel and a 400 gigabit per second NIC on the rail 1 leaf. The job is to move 1 mebibyte from srv001's app into a buffer on srv002, first through a TCP socket, then with one RDMA write. Hold onto one idea: RDMA pays for everything once, at setup, so that on the data path the CPU only describes the transfer, rings a doorbell and later reads a completion, and the NICs do the rest.

@1
The ordinary way first. srv001's app calls send on a TCP socket. That is a system call, so the CPU switches from user mode into the kernel. The tally at the bottom reads one system call.

@2
The kernel copies the whole mebibyte into socket buffers it owns: copy 1, so the app can reuse its buffer the moment send returns and TCP can retransmit. TCP builds its headers and hands the NIC large chunks, which the NIC splits into packets.

@3
The NIC reads those kernel buffers by DMA, puts the packets on the wire through the leaf, and interrupts the CPU so the driver can release them. The kernel keeps the data until srv002 acknowledges it.

@4
On srv002 the NIC writes the packets into kernel memory and interrupts a CPU, and the stack runs in software: NAPI polling, IP, TCP sequence checks, the bytes put in order, ACKs sent back.

@5
srv002's app calls receive, the second system call, and the kernel copies the bytes into the app's buffer: copy 2. Only now can the app use the data.

@6
The TCP tally: two system calls, two CPU copies of every byte, interrupts, and the full stack on both CPUs. One core moves a few tens of gigabits per second of TCP, so a 400 gigabit NIC fed this way needs many cores.

@7
Now RDMA. Once, at setup, each app registers its buffer. The kernel pins the pages, gives the NIC their address translations and returns keys: srv001 gets an lkey for its source buffer, and srv002 an rkey, A 1 B 2 C 3 in hex, registered for remote write. The rkey is a capability: a remote NIC that presents it may write into that buffer.

@8
Each side also creates a reliable connected queue pair and a completion queue, all in the app's memory, where the NIC reads and writes them directly. The apps swap QP numbers, starting sequence numbers, the buffer address and the rkey over an ordinary TCP connection, and step each QP up to ready to send. The table pairs srv001's QP 1 1 2 with srv002's QP 1 A 7, which expects PSN 4 E 2 0.

@9
The data path starts here, and the kernel disappears. srv001's app writes a work request into its send queue: an RDMA write of 1 mebibyte from its buffer, with the lkey, to the remote address, with the rkey, signaled, work request ID 7. Then it rings the doorbell, one write to a NIC register mapped into the app's memory. No system call, no copy.

@10
srv001's NIC reads the buffer by DMA and builds the packets itself: Ethernet, IP with DSCP 26 for the lossless class, UDP to port 4791, then InfiniBand's base transport header with the destination QP and a PSN. 1 mebibyte at 4,096 bytes a packet is 256 packets, PSN 4 E 2 0 to 4 F 1 F.

@11
The first packet, write First, also carries the RDMA extended transport header: the remote address, the rkey and the total length. The frame is 4,174 bytes, so the back end must carry jumbo frames; Meridian's switches run a 9,216 byte MTU.

@12
rail1-leaf1 routes it like any UDP packet: TTL down to 63, both MACs rewritten, into priority 3, the lossless queue DSCP 26 maps to.

@13
srv002's NIC runs three checks, all ticked: QP 1 A 7 exists and is ready, PSN 4 E 2 0 is the one it expects, and the rkey allows remote writes over the whole mebibyte. Then it DMA-writes the 4,096 bytes straight into the app's buffer. srv002's CPU does nothing, and its app is marked unaware.

@14
Packets 2 to 255 are write Middle, with no extended header, because the NIC remembers the address from the first, and the PSN rises by one each time. Packet 256, PSN 4 F 1 F, is write Last, with the acknowledge request bit set.

@15-16
srv002's NIC answers with one cumulative ACK for PSN 4 F 1 F, message sequence number 1, and it crosses the leaf back. Had a packet gone missing, the responder would send a sequence error NAK and the sender would resend everything from that PSN on: go-back-N. Had the ACK been lost, the sender's retry timer would expire and it would resend from the oldest unacknowledged PSN.

@17
srv001's NIC writes a completion entry into the app's completion queue: work request ID 7, status success, opcode RDMA write. The app finds it by polling memory, again without the kernel, and may now reuse its buffer.

@18
The closing table: TCP paid two system calls, two copies, interrupts and the receiving CPU's whole stack; the RDMA write paid none of those, with the transport in NIC hardware, but paid registration and QP setup in advance. That is the pattern: the cost moved, it did not vanish. Setup comes before the first byte, the remote app must be told separately, with a write carrying immediate data or a following SEND, and a transport that recovers by go-back-N wants a network that rarely drops, which is what lossless Ethernet is for.
