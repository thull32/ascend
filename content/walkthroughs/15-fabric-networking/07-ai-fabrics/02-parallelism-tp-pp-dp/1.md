@0
Two servers from Meridian's San Jose cluster, server 1 and server 2, each with eight H100-class GPUs joined by NVLink through an NVSwitch, 450 gigabytes per second each way per GPU. Each GPU also has its own 400 gigabit NIC, 50 gigabytes per second, on its own rail: GPU 0 of every server goes to the rail 1 leaf, GPU 7 to rail 8. Hold onto one idea: the layout fixes how many bytes each GPU sends, but placement decides which of those links carries them, and the NIC is one ninth of NVLink.

@1
The job trains a 13 billion class GPT model, hidden size 5,120, 40 layers, 12.6 billion parameters, on all 16 GPUs, split as tensor parallel 4, pipeline parallel 2, data parallel 2. Megatron's default rank order puts tensor parallelism innermost, then data, then pipeline outermost. So tensor groups are GPUs 0 to 3 and 4 to 7 of each server, each data parallel pair is GPU k with GPU k plus 4 of the same server, and the pipeline puts layers 1 to 20 on server 1 and 21 to 40 on server 2. Only that last dimension crosses the network.

@2
Why split at all? Training needs about 16 bytes per parameter, which is 201 gigabytes for one copy, far more than an 80 gigabyte GPU holds. Split eight ways by tensor and pipeline parallelism, each GPU holds 1.57 billion parameters, about 25 gigabytes plus activations.

@3
The forward pass starts on server 1 with microbatch 1, 4,096 tokens. Each layer's matrices are split across a tensor group of four, and twice per layer, after attention and after the MLP, the four partial results are summed with an all-reduce of 4,096 tokens times 5,120 times 2 bytes, 40 mebibytes. In a ring of four each GPU sends one and a half times that, 60 mebibytes, over NVLink, and both of server 1's tensor groups do it at once.

@4
Add the backward pass and that is four all-reduces per layer. Over 20 layers each GPU sends 4,800 mebibytes per microbatch, 37 and a half gibibytes per step of 8 microbatches. On NVLink that is 11 milliseconds per microbatch, on the critical path because every layer waits for its sums. Through a 50 gigabyte per second NIC it would be 101 milliseconds. That is why tensor parallelism stays inside the server.

@5
After layer 20, stage 0 hands the microbatch's activations, another 40 mebibytes, to stage 1. Each GPU sends only its quarter, 10 mebibytes, to the GPU with the same index on server 2, out of its own NIC and through one switch, its rail leaf.

@6
Each quarter arrives in about 0.21 milliseconds. Server 2's GPUs rebuild the full 40 mebibytes with an all-gather over their own NVLink, and run layers 21 to 40 with tensor all-reduces of their own. Meanwhile server 1 has already started microbatch 2. That overlap is what pipelining means.

@7
In the backward pass the traffic reverses. Server 2 sends back the gradient of those activations, again 10 mebibytes per GPU per microbatch over the same rails, and server 1's GPUs all-gather it over NVLink.

@8
Over 8 microbatches each GPU sends 80 mebibytes and receives 80 across the network per step, tiny next to the tensor traffic. But every handoff sits between two stages' compute, so a slow one stalls the pipeline. Pipeline traffic is small and sensitive to delay.

@9
When the last microbatch's backward pass ends, each GPU holds gradients for its 1.57 billion parameters, 2.9 gibibytes in bf16, and sums them with its twin in the other replica, GPU k with GPU k plus 4 of the same server. An all-reduce between two sends the whole 2.9 gibibytes per GPU, over NVLink, in 7 milliseconds. Since gradients accumulate over all 8 microbatches, it can start, bucket by bucket, only during that last backward pass.

@10
The tally per GPU per step: 37 and a half gibibytes of tensor all-reduce, 2.9 of data parallel all-reduce and 240 mebibytes of pipeline all-gathers on NVLink, 40.7 gibibytes in all, against 160 mebibytes on the network. With this placement 99.6 percent of the bytes never leave a server, and the rails carry only the pipeline handoffs.

@11
Now move the same job. If each server held a whole replica, both stages, each GPU's 2.9 gibibytes of gradients would cross its rail every step, 63 milliseconds at 400 gigabits, only partly hidden behind the last backward pass. Split each tensor group two and two across the servers instead, and half of each ring's hops cross servers: spread over both NICs on each side, about 18.8 gibibytes go through every NIC, putting about 0.4 seconds of blocking all-reduce on the critical path of an 870 millisecond step.

@12
At the scale of the full 1,024 GPU cluster the same rules hold. Tensor parallelism stays inside each server, pipeline and data parallelism span servers, and the data parallel all-reduce, gigabytes per GPU at the same moment every step, is the elephant traffic the back-end fabric is built for. Mixture-of-experts models add all-to-alls, every GPU sending to every other, the hardest pattern a fabric carries. The rule to take away: give the heaviest, most blocking communicator the fastest, least shared links. And the trap: a NIC counter means nothing until you know the job's layout and where its ranks landed.
