@0
On screen are two servers of Meridian's San Jose cluster, srv001 and srv002, each drawn as an app, its kernel and GPU0's 400 gigabit per second NIC, both behind the rail 1 leaf. The job is to move 1 mebibyte between the apps, first through a TCP socket, then with one RDMA write, the operation perftest's bandwidth tool, I B write B W, repeats thousands of times a second. Hold onto one idea: once setup is done, the data path runs entirely in the two NICs, so the benchmark measures the NIC, the PCIe path and the wire, not the kernel.

@1-2
The ordinary way first. srv001's app calls send, a system call into the kernel, and the kernel copies the whole mebibyte into socket buffers it owns: copy 1 on the tally. TCP builds its headers and hands the NIC large chunks to split into packets.

@3-4
The NIC reads those buffers by DMA, sends the packets through the leaf and interrupts the CPU so the driver can release them. On srv002 the NIC writes the packets into kernel memory and interrupts a CPU, and the stack runs in software: NAPI polling, IP, TCP, acks sent back.

@5-6
srv002's app calls receive, the second system call, and the kernel copies the bytes into the app's buffer: copy 2. The tally reads two system calls, two CPU copies of every byte, and interrupts on both sides. One core manages a few tens of gigabits per second of TCP, so feeding a 400 gigabit NIC this way takes many cores.

@7
Now RDMA, and the work moves to setup. Each app registers its buffer once: the kernel pins the pages, hands the NIC their address translations and returns keys. srv002's remote key is registered for remote write, so a NIC that presents it may write into that buffer.

@8
Each side also creates a reliable connected queue pair, its queues in the app's memory where the NIC reads them directly. The two sides swap addresses, queue pair numbers, starting sequence numbers and the remote key over an ordinary TCP connection, the exchange perftest makes before any test starts, and step both queue pairs to ready to send.

@9
The data path starts here. srv001's app writes one work request, an RDMA write of 1 mebibyte into srv002's buffer, and rings the doorbell: a single write to a NIC register mapped into the app's memory. No system call, no copy, no kernel.

@10-11
The NIC builds the packets itself: Ethernet, IP marked DSCP 26 for the lossless class, UDP to port 4791, then the InfiniBand base transport header with the destination queue pair and a sequence number. At 4,096 bytes per packet, 1 mebibyte is 256 packets. The first also carries the RDMA extended header, with the remote address, key and length, making a 4,174 byte frame. That is why the back end runs a jumbo MTU, 9,216 bytes on Meridian's switch ports.

@12
The rail 1 leaf routes it like any UDP packet: TTL down to 63, both MACs rewritten, queued in priority 3, the lossless class. The InfiniBand headers inside mean nothing to the switch.

@13
srv002's NIC checks that the queue pair is ready, the sequence number is the one it expects, and the remote key allows writes to this range. Then it writes the 4,096 bytes straight into the app's buffer. srv002's CPU does nothing at all.

@14
Packets 2 to 255 are write middle, with no extended header and the sequence number rising by one each time. Packet 256 is write last, asking for an acknowledgement.

@15-16
srv002's NIC answers with one cumulative acknowledgement covering all 256 packets; the NICs, not software, guarantee every packet arrived once and in order. Had one gone missing, the sender would have resent everything from the gap, go back N, which is why a single drop costs so much here.

@17
srv001's NIC writes a completion into the app's completion queue: work request 7, success. The app finds it by polling memory, again without the kernel. perftest polls the same way, asking for one completion per hundred work requests, the C Q moderation line in its header.

@18
The comparison: no copies, no system calls, no interrupts on the data path, and a receiving CPU that never ran, so one core can drive the NIC at 400 gigabits. The costs moved to setup and to a network that must not drop. For benchmarking, that is the point. Once the queue pair exists, the host's influence narrows to the PCIe path, the memory the data lands in and the core that polls. So when the result comes in short, suspect the MTU, the PCIe link, NUMA placement and interrupts on the polling core, not the kernel's network stack.
