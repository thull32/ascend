@0
On screen are two of the 128 servers in Meridian's San Jose cluster, server 1 on the left and server 2 on the right. Each holds eight GPUs, joined inside the server by NVLink through NVSwitch chips, and every GPU has its own 400 gigabit per second network card. Down the middle stand the first leaf of each of the eight rails, and above them one spine, ai-spine1, one of eight. Hold onto one rule, because it is the whole design: network card k of every server is cabled to the leaf of rail k. All the GPU1 cards go to rail 1, all the GPU2 cards to rail 2, and so on.

@1
The table sizes the back end for 1,024 GPUs. Each switch has 51.2 terabits per second, 128 ports of 400 gigabits. Every leaf gives 64 ports to network cards and 64 to spines, so it is not oversubscribed. 1,024 cards make 128 per rail, and 128 divided by 64 is two leaves per rail: one for servers 1 to 64, one for servers 65 to 128. Eight rails of two make 16 leaves. Their 1,024 uplinks, divided by 128 ports per spine, need 8 spines, and each leaf runs 8 parallel 400 gigabit links to every one of them. The drawing shows only the first leaf of each rail and one spine.

@2
Why cable it this way? Because it follows the traffic. When NCCL runs a collective across servers, it binds each GPU to its nearest card, the one on the same PCIe switch, and connects GPU k on one server to GPU k on the others. So nearly every byte that leaves a server travels between same-numbered GPUs, inside one rail. The exception is all-to-all traffic, the collective behind mixture-of-experts layers, where a GPU must reach other numbers too. That case comes shortly.

@3-4
First, the common case. GPU3 on server 1 sends to GPU3 on server 2. Its card puts the RDMA write on its own 400 gigabit link to rail3-leaf1, and rail3-leaf1 sends it straight out of the port facing server 2's GPU3. One switch between the two GPUs: no spine, no ECMP choice, and nothing shared with the other seven rails.

@5
Now the awkward case. GPU7 on server 1 has to send to GPU8 on server 2, a different rail. Sent straight from GPU7's own card, the data climbs rail7-leaf1, crosses a spine and comes down rail8-leaf1. That is three switches instead of one, and an ECMP choice among the eight spines, where it can collide with other flows.

@6
NCCL avoids that path with PXN, in NCCL 2.12 and later. GPU7 first copies the data over NVLink to GPU8 in its own server. The detour is cheap: NVLink gives each H100-class GPU about 900 gigabytes per second, 450 each way, against 50 gigabytes per second each way for a 400 gigabit card.

@7
Then server 1's GPU8 card sends the data on rail 8, and rail8-leaf1 delivers it to GPU8 on server 2. One switch again, and the traffic stays rail-aligned. PXN also lets NCCL merge messages from several local GPUs into fewer, larger transfers.

@8
The second table sets the paths side by side. Same rail, same leaf: one switch. Other rail, sent directly: three. Other rail with PXN: one switch, plus the NVLink hop. And the last row is why the spines still matter: server 1 and server 65 are both on rail 1 but on different leaves, so their GPU1s talk through a spine, three switches. A job confined to servers 1 to 64, 512 GPUs, can keep all its rail traffic one switch deep; a job across both halves cannot, which is why every leaf has eight links to every spine.

@9
Last, the cost. Server 2's GPU8 link fails. Every connection NCCL built through that card breaks, and a synchronous collective cannot finish without GPU8, so the job typically stops with an NCCL error and restarts from its last checkpoint. Rails are not redundancy: each card is single-homed, and a rail leaf is shared fate for every server in its group.

That is the pattern to keep. A rail-optimised fabric shapes the network to the collective's traffic, so most bytes cross one switch and never meet a hash. The price is long optical cabling that is easy to get wrong, and failure domains that cut across jobs. So the platform should check every card's LLDP neighbour against the cabling plan, map every card, optic and leaf port to the GPUs and jobs behind it, and watch link flaps per rail, not just per switch.
