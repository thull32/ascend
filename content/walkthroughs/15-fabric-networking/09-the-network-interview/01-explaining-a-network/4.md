@0
The failure part of the one story starts where the packet walk left off: take the encapsulation away and it breaks. On screen are three routers in a row, a cut-down piece of Amsterdam with one spine. R1 is leaf 1, R2 is spine 1, R3 is leaf 3. All three run IS-IS; only the two leaves run BGP. This is a design Meridian does not use, with Acme's subnets in the plain routing table and no VXLAN. The point to land is one moment: every check is green and the packet still dies.

@1
IS-IS is up on both links, and spine 1's table is complete for what IS-IS carries: the two leaves' loopbacks and the two link subnets. No Acme subnet is in it, by design.

@2-3
leaf 1 opens the BGP session, a TCP connection from its loopback, 10.255.1.11, to leaf 3's, 10.255.1.13, on port 179. spine 1 can forward it, because IS-IS gave it a route to that loopback. The handshake completes, OPEN and KEEPALIVE are exchanged, and the session reaches Established. The dashed line is a TCP connection, not a cable: every one of its packets travels through spine 1.

@4-5
leaf 3 advertises Acme's subnet 10.1.2.0 slash 24, where acme-db1 lives, with its own loopback as the next hop. spine 1 forwards the update as ordinary TCP payload and never reads it. It has carried the only message that mentions that subnet, and kept no copy.

@6
leaf 1 installs the route. The next hop is not on a connected link, so it resolves it through IS-IS: 10.255.1.13 is reached through spine 1. So the forwarding entry for 10.1.2.0 slash 24 points at the spine.

@7
Now every check a protocol dashboard runs is green. The BGP session is Established with one prefix received, both IS-IS adjacencies are up, and the next hop resolves. Before the next frame: what has none of those checks looked at?

[pause]

@8-9
Whether spine 1 can forward a packet for that subnet. acme-web1 opens a connection to acme-db1 at 10.1.2.20, port 5432. The packet goes to its gateway, leaf 1, which matches the route, lowers the TTL to 63, and hands it to spine 1, exactly as BGP and IS-IS told it to. The destination is still 10.1.2.20; nothing in the packet mentions leaf 3.

@10-11
spine 1 looks up 10.1.2.20. None of its four routes covers it, and it has no default route, so it discards the packet and counts a no-route drop. Even the error message has nowhere to go, because the spine has no route back to acme-web1's subnet either. acme-web1 hears nothing and retries its connection attempt, on Linux defaults six times over about 127 seconds, before the application sees a timeout.

@12
That is the trap: the control plane is healthy while the data plane drops every packet. A traceroute from acme-web1 shows its gateway and then only stars. This is why session Established is not a health check.

@13
There are two fixes. Run BGP on spine 1 too, in a large fabric through route reflectors, so it learns the subnet itself. Or encapsulate the packet towards leaf 3's loopback, with MPLS or VXLAN, so the spine only needs the route it already has. Meridian uses VXLAN for exactly this reason. The general lesson, and the bridge to your part of the answer: protocol state being up is not the service working, so the platform checks next-hop resolution and probes the data path, not only session state.
