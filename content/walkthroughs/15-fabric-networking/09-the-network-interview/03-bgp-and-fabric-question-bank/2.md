@0
The question is why route reflectors, and the screen builds the answer from the problem. Four Amsterdam leaves, all in the overlay's AS 65000. With plain iBGP every leaf needs a session to every other leaf: n times n minus 1, over 2, which is 6 here and 120 for the site's 16 leaves. Hold onto one idea: a reflector is allowed to break iBGP's no-relay rule, two attributes catch the loops that opens, and it never touches the next hop, so it stays out of the forwarding path.

@1
Why the mesh? Inside one AS the AS path never changes, so it cannot catch loops, and the rule is that a route learned from an iBGP peer is never passed to another iBGP peer. leaf1 hears leaf3's route but will not relay it to leaf2, so leaf2 must hear it from leaf3 directly.

@2
Route reflection relaxes that rule on two routers. Every leaf keeps two sessions, one to rr1 and one to rr2, plus one session between the reflectors: 2 n plus 1. For four leaves that is 9, more than the mesh's 6. For 16 leaves it is 33 instead of 120, and a new leaf needs two sessions, not one to every other leaf.

@3
leaf3, where Acme's 10.1.2.0 slash 24 lives, advertises it to both reflectors with next hop 10.255.1.13, its own loopback. In Meridian it travels as an EVPN route, but reflection treats every route type the same way.

@4
rr1 learned the route from a client, so it reflects it to every client and every non-client peer. First it adds two attributes. The originator ID, 10.255.1.13, is the router ID of the leaf that injected the route. The cluster list gets rr1's cluster ID prepended: 10.255.1.100.

@5
rr1 reflects the route to leaf1, leaf2 and leaf4 with the next hop still 10.255.1.13. Traffic for 10.1.2.0 slash 24 goes from each leaf straight to leaf3 through the spines, never through rr1. That is the slip to avoid: the reflector neither forwards the traffic nor rewrites the next hop.

@6
rr2 reflected the same route, so leaf1 holds two identical copies. They tie at every step, even router ID, where a reflected route is compared by its originator ID, the same in both. The last tie-breaker, the lower peer address, picks rr1's copy. Either way traffic goes to 10.255.1.13, and if rr1 fails, the other copy is already there.

@7
rr1 also reflects the route to rr2, its non-client peer. Both Amsterdam reflectors share one cluster ID, 10.255.1.100, so rr2 finds its own ID in the cluster list and discards the copy as a loop. It loses nothing, because it heard the route from leaf3 directly.

@8
The rules would also send the route back to leaf3 itself. Many implementations skip that, and if it does arrive, leaf3 ignores it because the originator ID is its own router ID. So the originator ID stops a route returning to its originator, and the cluster list stops it circling between reflectors.

@9
The shared cluster ID has a cost. If leaf3's session to rr2 drops, rr2 cannot use rr1's copy either, so every other leaf holds leaf3's routes from rr1 alone. Giving each reflector its own cluster ID keeps that copy, at the price of more paths in memory. Both designs are common.

@10
Now the follow-up: what happens when one fails? With leaf3's session to rr2 back up, rr1 fails. Every leaf already holds the same routes from rr2, with the same next hop, and no packet ever passed through rr1, so forwarding does not change at all.

@11
And both? When rr2 fails too, each leaf's hold timer expires within 9 seconds, and it deletes every overlay route it learned from them. Tenant traffic between leaves stops while every spine and fabric link is healthy. The common wrong answer, that forwarding carries on with the last known state, holds only until that timer fires.

So a reflector pair is a control-plane spare, not a forwarding path, and that sets what to watch: put the two on different spines and power feeds, and alarm on losing one reflector, not just both. The next rung asks why every client exits through the gateway nearest the reflector. The reflector advertises only its own best path, chosen from its own position in the IGP, so clients never see the path their own hot-potato step would pick.
