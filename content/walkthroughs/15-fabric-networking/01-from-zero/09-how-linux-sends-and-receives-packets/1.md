@0
On screen is acme-db1, Acme's Linux database server in Amsterdam, with a 25 gigabit per second network card. A burst of data from acme-web1 for its Postgres connection is arriving from leaf3, its top of rack switch. Hold onto one idea as a frame climbs from the wire to the application: every stage is a queue with a limit, and a stage that overflows drops the packet and records it in its own counter, one that no switch can see.

@1
First, the card. It checks the frame check sequence and that the destination MAC is its own. A corrupt frame is dropped here as a CRC error, the first row of the drop table on the right. Then receive side scaling, RSS, hashes the five-tuple, and this flow's hash picks queue 3 of 8. Every packet of the flow gets the same hash, so it always lands on the same queue and CPU, never reordered.

@2
The card copies the frame by DMA, direct memory access, straight into a buffer the driver handed it in advance, and marks one of ring 3's 1,024 descriptors as filled: 1 filled, 1,023 free, and no CPU involved. If the kernel has fallen behind and no descriptor is free, the card drops the frame, counted under a driver-specific name: rx missed errors on Intel cards, rx out of buffer on NVIDIA ConnectX.

@3
Now the card raises queue 3's MSI-X interrupt, and IRQ affinity has pinned that queue to CPU 3. The handler only masks the queue's interrupts and schedules a poll in the network receive softirq, a deferred kernel task on the same CPU. A burst of thousands of frames costs one interrupt, not thousands.

@4
In the softirq, the driver's NAPI poll takes filled descriptors off the ring, up to 64 per poll and 300 per softirq run, the netdev budget. It wraps each frame in an S K buff, the kernel's packet structure, notes that the card already verified the TCP checksum, and refills each descriptor with a fresh buffer, so the ring reads 0 filled again. If the budget runs out with frames still waiting, the kernel counts a time squeeze in the softnet stat file. A squeeze is not a drop, but it is the warning before one.

@5
Next, GRO, generic receive offload, merges consecutive in-order segments of the same flow before the stack sees them. Four segments of 1,460 bytes, at relative sequence numbers 1, 1,461, 2,921 and 4,381, become one of 5,840 bytes. The IP and TCP code run once instead of four times.

@6
IP checks the header, and the routing decision finds that 10.1.2.20 is one of acme-db1's own addresses, so it goes up the stack instead of being forwarded. Netfilter's prerouting and input hooks run here. A firewall drop shows only in that rule's own counter, and a malformed header in the IP in header errors counter that nstat reports.

@7
TCP finds the connection's socket by its five-tuple, checks that the sequence numbers are the ones it expects, queues the 5,840 bytes in order and schedules an ack to acme-web1. A segment with no matching socket would be answered with a reset instead.

@8
The bytes now wait in the socket's receive queue, Recv Q in ss, which reads 5,840 bytes. The buffer can grow to a default maximum of 6 megabytes, or 32 megabytes since Linux 6.16, and the window TCP advertises to acme-web1 shrinks as it fills. If Postgres stopped reading, the window would reach zero and the sender would pause. Only if memory runs out anyway are segments dropped, counted as TCP receive queue drops.

@9
Postgres, woken through epoll, calls recv, and the kernel copies the 5,840 bytes into its memory. Recv Q is back to zero and the window is full again. Everything from the interrupt to the socket queue ran in software on CPU 3; only this copy runs wherever Postgres is scheduled. So one busy CPU can hold up a whole receive queue.

@10
Which is the failure case. CPU 3 is kept busy for 1 millisecond and cannot run the softirq, while full-size frames keep arriving at 25 gigabit line rate, about 2,030,000 per second. On the chart the 1,024 descriptors are used up in about half a millisecond, and every later arrival is dropped. By the end of the millisecond the card has dropped 1,008 frames, and the only record is the plus 1,008 on its missed counter.

@11
TCP treats those 1,008 drops exactly like drops in the network. acme-web1 retransmits and slows down, so a host drop looks like a network problem; the table says where it really happened. That is the pattern: every stage has its own queue and its own counter. A ring is sized in frames, not time, so the same 1,024 descriptors that cover half a millisecond at 25 gigabits cover only about 0.13 milliseconds at 100 gigabits. The fixes are on the host: a larger ring, more queues spread over more CPUs, or keeping other work off the CPUs that take network interrupts. When TCP retransmits and every switch counter is clean, read the host's counters before blaming the fabric.
