@0
The same picture as before: acme-web1 at 10.1.1.10 on VLAN 100 behind leaf1, acme-app1 beside it, and a fresh connection to acme-db1 at 10.1.2.20 on port 5432, with an empty ARP cache. This time leaf1's gateway interface for VLAN 100 is missing. Hold onto one idea as it plays out: when the gateway never answers, the failure is reported by the server itself, and no packet for the destination ever leaves it.

@1-2
The start is identical. 10.1.2.20 is off acme-web1's subnet, so the default route names the gateway, 10.1.1.1. The cache has no entry, so the kernel creates one in state INCOMPLETE and queues the TCP SYN.

@3-4
The same broadcast request leaves: who has 10.1.1.1, tell 10.1.1.10. leaf1 floods it through VLAN 100, and it would hand a copy to its gateway interface for the subnet, if it had one.

@5
acme-app1 ignores it, since 10.1.1.1 is not its address. And leaf1 has no interface holding 10.1.1.1, so nobody owns the address, and no reply comes back. One probe sent.

@6-7
Linux sends up to three broadcast probes, one second apart. The second goes out at one second, the third and last at two seconds, and neither is answered, while the SYN still waits in the queue.

@8
At three seconds the entry becomes FAILED. The queued SYN is thrown away, and the connect call returns No route to host. A ping would print Destination Host Unreachable, from 10.1.1.10, the server's own address. That is the giveaway: the error comes from acme-web1, not from the network. No packet to acme-db1 was ever sent, so there is nothing to find on the routers.

@9
This is the server that cannot ping its default gateway, and the cache is the first clue: INCOMPLETE, then FAILED, means requests left but no reply came back. That points at layer 2 or the gateway, and the frame lists what to check: whether the link is up, whether the server's port is in the right VLAN, whether the gateway interface exists and is up, and whether a capture on the server shows requests leaving and nothing returning. The general lesson: the gateway is one hop away, so a failure to reach it lives on that hop, and routing protocols cannot explain it. Walk up the layers from the cable, and let the neighbour table tell you which side of the ARP exchange broke.
