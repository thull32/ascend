@0
On screen is one leaf in Meridian's Amsterdam fabric, leaf1, with two Acme servers below it on VLAN 100: acme-web1 at 10.1.1.10, slash 24, and acme-app1 at 10.1.1.13. Acme's database, acme-db1 at 10.1.2.20, is off to the side, somewhere across the fabric. acme-web1 has just booted, so its ARP cache is empty, and an application opens a connection to the database on PostgreSQL's port, 5432. Hold onto one idea, because it is the whole story: the routing table answers with an IP address, but a frame can only be addressed to a MAC address, and ARP is the step that turns one into the other.

@1
First, the host decides whose MAC it needs. 10.1.2.20 ANDed with the mask, 255.255.255.0, gives 10.1.2.0, which is not acme-web1's own network, 10.1.1.0. So the connected route does not match, and the default route does: the packet goes to the gateway, 10.1.1.1. Had the destination been 10.1.1.11, the answer would be yes, and acme-web1 would ARP for 10.1.1.11 itself.

@2
To build the frame, acme-web1 needs the gateway's MAC, and the cache has no entry for 10.1.1.1. The kernel creates one in state INCOMPLETE, with no MAC yet, and holds the TCP SYN, the connection's first packet, in a small queue while it asks.

@3
Here is the question, field by field. The Ethernet header goes to the broadcast MAC, all ones, because the sender does not know whom to ask, with EtherType 0806 in hex, meaning ARP. Inside, 28 bytes: operation 1, a request, sender MAC ending in 53 0A, sender IP 10.1.1.10, target IP 10.1.1.1. The target MAC is all zeros, because that is exactly what is being asked for.

@4
The request enters leaf1. Like any broadcast, the leaf floods it through VLAN 100, and it also hands a copy to its own gateway interface for the subnet, the router that lives inside the VLAN.

@5
acme-app1 receives the broadcast too, sees that 10.1.1.1 is not its address, and discards it. Every ARP request costs every host in the VLAN a little work, one reason large layer 2 domains are avoided.

@6
leaf1 owns 10.1.1.1, so it answers. The request carried acme-web1's IP and MAC, so the leaf first records 10.1.1.10 against the MAC ending in 53 0A in its own neighbour table, and never needs to ARP back. Then it sends a unicast reply, straight to that MAC: operation 2, 10.1.1.1 is at the anycast gateway MAC, ending in 01 01.

@7
acme-web1 caches 10.1.1.1 against that MAC as REACHABLE. Linux keeps an entry REACHABLE for a random 15 to 45 seconds, around a base of 30, then marks it STALE and confirms it again the next time it is used, so a gateway whose MAC changed is noticed.

@8
The queued SYN finally leaves. Look at the two destinations in the header stack: the IP destination is 10.1.2.20, the database, but the Ethernet destination is the gateway's MAC. The IP header names the final destination; the Ethernet header names only the next device on this link.

@9
leaf1 accepts the frame because the destination MAC is its own gateway MAC, and routes it onwards towards acme-db1, the hop by hop walk of the next lesson. Every later packet to any off-subnet destination reuses this one cached entry: one ARP exchange serves them all.

@10
Every Meridian leaf answers for 10.1.1.1 with the same anycast gateway MAC, so a server that moves to another leaf keeps a valid cache. The pattern generalises: resolve the next hop, never the destination, unless the destination is on your own wire, and cache the answer so only the first packet waits. And when it goes wrong, the cache shows it first. An entry stuck at INCOMPLETE and then FAILED means no reply came back, which is why the server's neighbour table is the first thing to check when it cannot reach its gateway.
