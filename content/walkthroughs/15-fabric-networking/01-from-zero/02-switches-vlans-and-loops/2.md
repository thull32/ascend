@0
Two switches, leaf1 and leaf2, joined by one cable on port 49 that has to carry two VLANs. This is a classic layer 2 design, the kind of trunk an MLAG pair's peer link still uses, not how Meridian's leaves are wired. Each switch has an Acme web server in VLAN 100, the 10.1.1.0 slash 24 subnet, and a database server in VLAN 200, 10.1.2.0 slash 24. The one idea to hold: servers never see VLANs; only the link between switches carries a label saying which VLAN each frame belongs to.

@1
The port table shows the two kinds of port. An access port belongs to exactly one VLAN and carries plain untagged frames, so the server on it never knows VLANs exist. Ports 1 and 2 on each switch are access ports, in VLAN 100 and VLAN 200. A trunk port carries several VLANs over one link and marks every frame with its VLAN, using a 4 byte IEEE 802.1Q tag. Port 49 on both sides is the trunk, carrying 100 and 200 tagged.

@2
acme-web1 broadcasts an ARP request: who has 10.1.1.12, which is acme-web3 on the other switch. The Ethernet header holds the all-ones broadcast destination and the EtherType for ARP, 0806 in hex. It leaves the server untagged, like any frame on an access port.

@3
leaf1 puts the frame in VLAN 100 because port 1 is an access port in VLAN 100, and floods it only to the other VLAN 100 ports, which here is just the trunk. acme-db2, on port 2 of the same switch, is in VLAN 200, a separate broadcast domain, so it gets no copy.

@4
On the way out of the trunk, leaf1 inserts the tag right after the source MAC, and the header stack grows a layer. Where the EtherType used to be there is now the tag protocol identifier, 8100 in hex, meaning a VLAN tag follows. Then 3 bits of priority, set to 0, a drop eligible bit, 0, the 12 bit VLAN ID, 100, and finally the original EtherType for ARP. The frame grows by 4 bytes, so a full-size 1,518 byte frame becomes 1,522, and the checksum at the end is recomputed.

@5
The tagged frame crosses the trunk. Frames of both VLANs share this cable, and only the VLAN ID in each tag keeps them apart.

@6
leaf2 reads VLAN ID 100 from the tag, so the frame belongs to VLAN 100 on this switch too, and floods it to its only other VLAN 100 port, port 1. That is an access port, so leaf2 removes the tag on the way out, the EtherType reads ARP again, and the checksum is recomputed.

@7
acme-web3 receives an ordinary untagged ARP request, byte for byte what acme-web1 sent, and will answer it. acme-db3, on the same switch but in VLAN 200, never saw it.

@8
Now the other VLAN. acme-db2 broadcasts an ARP request for acme-db3 at 10.1.2.22. leaf1 floods it only to the trunk, and it crosses the same cable, this time tagged VLAN ID 200, so leaf2 can keep it apart from VLAN 100.

@9
leaf2 floods it to its VLAN 200 access port alone and strips the tag. acme-db3 gets it untagged, and acme-web3 never sees it at all.

@10
One cable, two isolated broadcast domains. Two limits follow from what you just saw. The VLAN ID is 12 bits, so with 0 and 4095 reserved there are only 4,094 usable VLANs, a ceiling large multi-tenant fabrics outgrow, and one reason VXLAN carries a 24 bit identifier instead. And nothing ever errors: a VLAN missing from a trunk, or a server port in the wrong VLAN, drops traffic silently. The usual first symptom is an ARP request that never gets an answer.
