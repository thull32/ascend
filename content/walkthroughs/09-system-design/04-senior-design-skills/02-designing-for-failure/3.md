@0
Three regions, Europe, the US and Asia-Pacific, each with its own leader, and a document title at version 1 everywhere. This is active-active: each region accepts writes locally and replicates them asynchronously to the others. Users get local write latency, and the system survives losing a region. The price is conflicts.

@1-2
A European user edits the title to Draft A. The European leader applies it and acknowledges locally, with no ocean crossing.

@3-4
At the same moment, a US user edits the same title to Draft B. The US leader also applies it on top of version 1, because neither leader knows about the other's write yet. It acknowledges locally too. There are now two different version 2s.

@5-6
The replication streams cross in flight. Each leader receives a write whose parent, version 1, it has already overwritten. That is a write conflict, and there is no first, because there was no shared order.

@7
Both sides detect it. A single leader would have put the writes in sequence. With several leaders, the conflict must be resolved deterministically, so that every region converges.

@8
Resolution by last-writer-wins: keep the higher timestamp everywhere. Europe and the US now both say Draft B, and Draft A vanished with no error. For a setting like a subtitle language that is tolerable. For a counter it is a bug, which is why counters use a CRDT that merges per-region counts, and money uses a home region.

@9
The alternatives: merge the values, keep both as siblings for the application or user to resolve, or give each record a home region so a key never has two writers.

@10
With three leaders, topology matters. Asia-Pacific has not received either write yet; the US leader is only now replicating Draft B to it. All-to-all replication is fastest, but can deliver writes out of causal order, a reply arriving before the message it answers. A star or a ring adds hops but keeps ordering simpler.

@11
The trade-off. Local write latency and surviving a region loss, against conflict handling, no linearizability, and subtle bugs with auto-increment keys and uniqueness constraints. And conflicts are not rare: at one write a minute per key from each region and half a second of lag, about 1.65 percent of writes conflict; at 2 seconds of lag, 6.4 percent.
