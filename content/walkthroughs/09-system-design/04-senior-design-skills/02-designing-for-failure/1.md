@0
Users, an API gateway with one shared pool of 12 threads, and three dependencies behind it: Payments, Search and Recs. A bulkhead partitions resources per dependency, like the watertight compartments in a ship's hull, so a failure in one cannot flood the others. First, the version without one.

@1
Search becomes slow. Calls that took 50 milliseconds now hang for 8 seconds before timing out. Nothing else has changed.

@2
Every Search request now holds a gateway thread for 8 seconds instead of 50 milliseconds. Six are in flight, and half the shared pool is gone.

@3
Search traffic keeps arriving at its normal rate, but calls now leave 160 times slower than they enter. Search alone holds all 12 threads.

@4-5
A checkout request arrives. It needs Payments, which is perfectly healthy. It is rejected anyway, because there is no thread to run it. A slow search box has taken down payments: one dependency's latency became every feature's outage.

@6
The fix: split the 12 threads into three pools of 4, one per dependency. A Search call may only use a Search thread, and when that pool is full, the call is rejected immediately instead of waiting.

@7
Search degrades exactly as before, and fills its 4 threads. But it cannot borrow from anyone else.

@8
The next Search call finds its pool full and fails in microseconds, with a clear search unavailable. The page renders without the search box instead of hanging.

@9
Checkout arrives, takes a Payments thread from a pool with 3 to spare, and succeeds. The compartment held.

@10
Then Search recovers, and its pool drains back to empty. The fix has its own failure mode: pool sizing. Too small, and a normal traffic spike to one dependency rejects legitimate calls, a self-inflicted outage. Too large, and the isolation is only nominal. Size each pool from measured concurrency, the request rate times the latency, with headroom, and alert on rejections.

@11
The trade-off. Bulkheads cap the blast radius of any one dependency at the size of its compartment, at the cost of lower peak utilisation, since idle threads in one pool cannot help another, and one more number per dependency to tune. The same idea scales up to connection pools, worker processes, and whole availability zones.
