@0
Users, a router, two identical production environments, blue and green, and one shared database. This is blue-green deployment: blue serves all traffic while green sits idle; you deploy to the idle one, test it, then flip the router, and rollback is flipping back. Watch the database, because that is what decides whether the flip back actually works.

@1
Steady state. Every request goes to blue, running version 1. Green sits idle.

@2
Version 2 is deployed to green while blue keeps serving. A failed deploy here hurts nobody, because green is not in the path.

@3
The schema change ships first, as an expand step: add a nullable column or a new table, never rename or drop. Both version 1 and version 2 can run against it. Both will be live at once, if only for seconds, and the rollback path depends on it.

@4
Green is verified in production with smoke tests and synthetic requests on an internal hostname. Same hardware and configuration as blue.

@5-6
The router flips, and all traffic moves to green at once. In-flight requests on blue are drained, not killed. Users are on version 2 with no downtime, and blue is left running exactly as it was.

@7
Then a bug that only real traffic reveals: the error rate climbs. Because the switch was all or nothing, every user is affected until someone reacts.

@8
Rollback is the same flip in reverse. Seconds, no redeploy, no rebuild. And it works only because the expand-only migration left the schema readable by version 1.

@9
Here is what would have broken it. A migration that renamed or dropped a column for version 2 would crash version 1 on rollback. And data version 2 wrote to the new column is invisible to version 1, so writes made during the green window may need reconciling. Sessions and background jobs on the old colour need the same care.

@10
Version 2.1, with the fix, goes to green and is flipped in. Blue becomes the idle environment for the next release; the colours alternate.

@11
Only once no version that needs the old shape can ever be live again does the contract step run, dropping what is no longer used. Expand and contract are separate deploys, often days apart.

@12
The trade-off. Zero-downtime deploys and the fastest possible rollback, at the cost of double capacity, every schema change forced into expand and contract, and a switch of all traffic at once, so a bad release hits everyone. The rule underneath works for any deploy strategy: every version that can be live at the same time must work with every shape of data it can meet.
