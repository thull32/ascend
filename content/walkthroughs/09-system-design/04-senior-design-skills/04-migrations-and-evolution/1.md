@0
Users, a facade, the legacy monolith, and a new service. This is the strangler fig: put a facade in front of the old system, then move one capability at a time behind it into new services. The monolith keeps serving everything not yet moved, and is strangled gradually, route by route.

@1
Request 1, for users. Today every route goes to the monolith. The facade is a do-nothing proxy, and that is the safe first step: deploy it alone and prove it adds no latency and no errors.

@2
Step 1. The users capability has been rebuilt in the new service, and the facade's table is flipped for that one route. Flipping is a configuration change, so it can be reversed in seconds if the new service misbehaves.

@3-4
Request 2, for users, goes to the new service, and the client cannot tell anything changed. Request 3, for orders, is still owned by the monolith, so the facade forwards it there untouched.

@5
Step 2, and a safer one: orders is shadowed. The facade sends request 4 to both systems, returns the monolith's answer, and compares the new service's response offline. Every mismatch is a bug found with no user impact.

@6
After a clean shadow period, orders is flipped for real. The monolith still owns billing and search, and still runs. Nothing forced a big-bang cutover.

@7-10
Requests 5 and 6, for billing and search, go to the monolith. Requests 7 and 8, for users and orders, go to the new service. Two systems are serving one product, and the client sees one API.

@11
Here is where it gets hard: the data. The new service and the monolith both need the orders table. Either the new service reads the monolith's database, which is the coupling you meant to remove, or you replicate data between them, with change data capture or dual reads, until the last consumer moves. Moving the data is usually the slow part.

@12
Eventually every route points at new services, the monolith serves nothing, and it is switched off. The facade can stay on as the API gateway. Each step was small, reversible, and shipped value on its own.

@13
The trade-off. Many low-risk increments replace one risky rewrite, and old and new coexist for months. The price is running both, with double infrastructure and two codebases to keep consistent, and a facade that must be kept honest. The shared database is where most migrations stall.
