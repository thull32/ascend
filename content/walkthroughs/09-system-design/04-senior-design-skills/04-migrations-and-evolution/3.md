@0
Users, a load balancer, nine instances of the stable version, one canary slot, and a metrics service that compares them. This is a canary release, and a migration moves reads to a new store the same way: send a small slice of real traffic to the new path, compare its metrics with the old path on the same window, and widen the slice only when the gate passes.

@1
Version 2 is deployed to one instance alongside the nine stable ones. It gets no traffic yet, and its health checks pass.

@2
Stage 1: 10 percent of traffic goes to the canary, 1 of the next 10 requests, and 9 go to stable. If version 2 is broken, at most one user in ten sees it, and only briefly.

@3
The analysis compares both versions on the same window: error rate, 99th percentile latency, saturation. The canary has no errors, like stable, and its 99th percentile of 120 milliseconds is within 1.2 times stable's 118, so the gate passes and the share widens.

@4
Stage 2: 50 percent. Now the canary sees enough traffic to hit a code path the 10 percent slice never exercised: 2 of its 5 requests fail, and its 99th percentile jumps to 410 milliseconds.

@5
The gate fails. The canary has 2 errors in 5 requests, while stable's 5 requests on the same window have none. Because both run side by side, the comparison isolates the release from ambient noise.

@6
Automatic rollback: the load balancer's weight for version 2 goes to zero. The bad release reached only the canary's share of traffic for one window, instead of everyone for as long as a human took to notice.

@7-8
Version 2.1, with the fix, starts again at 10 percent. Every promotion repeats the same gate; nothing is trusted because it passed last time. At 50 percent it is clean: no errors, and 121 milliseconds against 118. And because the gate compares like with like, a traffic spike that slows both versions does not fail the canary.

@9
Promotion. The remaining instances roll to version 2.1, and it becomes the stable version.

@10
The traps. With only a handful of canary requests per window there may be too few samples to see a 1 percent error rate, so the gate must require a minimum count, not just a rate. A canary that gets only the easy traffic, cache hits or one region, passes and then fails at full load. And stateful sessions need sticky routing, or the same user bounces between versions. For a data migration, that means moving reads by cohort, sticky per user.

@11
The trade-off. A bad release, or a bad new store, costs one analysis window for a small cohort, and real traffic reveals problems tests miss. The price is a slower rollout, two versions live for hours, per-version metrics, and analysis that must be statistically honest.
