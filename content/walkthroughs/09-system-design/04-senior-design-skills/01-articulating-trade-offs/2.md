@0
The same app, cache and database, the other end of the dial. The database says views 9 equals 100. With write-behind, the cache acknowledges a write immediately and persists it to the database later, asynchronously and usually in batches.

@1-2
The app writes views 9 equals 101. It lands in the cache, marked dirty, and is acknowledged in about 1 millisecond, before the database has seen anything. That is where write-behind gets its speed.

@3
A second write to the same key, 102, overwrites the dirty entry. Two application writes will become one database write. That is coalescing.

@4
More writes pile up: views 9 equals 103, and views 4 equals 7. The buffer keeps only the latest value per key, so two dirty entries stand for four writes.

@5-6
A flush fires, every 500 milliseconds or when the buffer fills, and the cache writes both rows to the database in one round trip. The entries are clean again. Four application writes cost one database write.

@7
A new write, views 9 equals 104, is dirty again, and acknowledged instantly.

@8
Then the cache node dies before the next flush. The 104 was acknowledged to the client, but never reached the database. It is lost.

@9
After recovery, the database serves 103, although the client was told 104 succeeded. Write-behind turns a durability guarantee into a durability probability.

@10
In the template: I choose write-behind because write latency and database load dominate. It costs up to one flush interval of acknowledged writes, a few hundred milliseconds, if a cache node dies, and the database lags the cache. That is acceptable for data like view counts. If the data were money or anything a user was promised, I would move the dial back to write-through.
