@0
A Kafka topic with three partitions, each an ordered, append-only log, and a consumer group called g1 with two consumers. The producer hashes each message's key to pick a partition. Here is the rule to hold: order is guaranteed inside a partition and nowhere else, so all the events for one key stay in order because they all land in the same partition.

@1
The first message has the key user 1. Its hash, modulo 3, is 1, so it is appended to partition 1 at offset 0. The broker never reorders or rewrites the log.

@2
The key user 7 also hashes to partition 1, so it is appended behind the first record, at offset 1.

@3
The key order 9 hashes to partition 2 and lands there at offset 0.

@4
User 1 again: same key, same partition, appended at offset 2, behind the earlier user 1 event. Whoever reads partition 1 sees this key's events in the order they were written.

@5-6
Cart 5 goes to partition 0 at offset 0, and user 7 again to partition 1 at offset 3. Partition 1 holds four records, the others one each.

@7
Now the group coordinator assigns partitions. Each partition belongs to exactly one consumer in the group: consumer 1 gets partitions 0 and 2, and consumer 2 gets partition 1. Partitions, not messages, are the unit of parallelism.

@8
Consumer 1 polls partition 0 and receives its record. The consumer tracks its own position, an offset, per partition, and the broker deletes nothing when it is read. Another consumer group could read the same log from the start, independently.

@9
After processing, consumer 1 commits offset 1, its next offset to read. The order of commit and work decides the guarantee. Commit after processing gives at-least-once, because a crash between the two replays the records. Commit before gives at-most-once. Exactly-once needs transactions or an idempotent sink.

@10-11
Consumer 2 polls partition 1 and processes offsets 0 to 3 in order. Once offsets 0 to 2 are done it commits offset 3, and starts on offset 3.

@12
Consumer 2 dies after processing offset 3, before committing it. The committed offset for partition 1 stays at 3.

@13
After its session timeout, the coordinator rebalances and consumer 1 now owns all three partitions, picking up partition 1 from the last committed offset, 3. Offset 3, which consumer 2 processed but never committed, is delivered again. While the rebalance runs, the whole group pauses.

@14
Two limits come from this design. A group can use at most 3 consumers here, one per partition; a fourth would sit idle, so the partition count you choose at creation caps your parallelism. And a hot key sends all its traffic to one partition, which one consumer must handle alone.

@15
The trade: partitioning by key buys per-key ordering and horizontal scale on a simple, durable broker. It costs global order, ties parallelism to the partition count, and pauses consumption during rebalances. Choose a key that spreads the load but keeps together the events that must stay in order, such as the order identifier.
