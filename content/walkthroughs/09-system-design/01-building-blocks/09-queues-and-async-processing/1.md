@0
On the left, a producer. In the middle, a queue, and below it a dead-letter queue. On the right, two workers. The queue separates the producer from the workers in time and in rate: the producer drops work off and moves on, and each worker pulls when it has capacity. Keep one rule in mind, because everything here follows from it: a message is deleted only when a worker says it has finished.

@1
The producer publishes a burst of 12 messages. The broker stores each one and acknowledges straight away, so the queue depth jumps to 12 and the producer never waits for any of the processing.

@2
Worker 1 receives message 1. Notice what the broker does not do: it does not delete it. It hides it for a visibility timeout of 30 seconds, so nobody else picks it up while worker 1 is busy.

@3
Worker 2 takes message 2. The two workers run in parallel, and each message goes to exactly one of them. These are competing consumers.

@4
Worker 1 finishes and acknowledges, and only now is message 1 deleted. The depth drops to 11. Acknowledging after the work is what makes the queue survive a worker crash, and the next frame shows why.

@5
Worker 2 crashes halfway through message 2. It never acknowledged, so message 2 is still in the queue, only invisible.

@6
The visibility timeout runs out, message 2 becomes visible again, and worker 1 picks it up as a retry. That is at-least-once delivery: nothing is lost, but a message can be delivered twice.

@7
Worker 1 acknowledges message 2, and the depth falls to 10. But suppose worker 2 had already charged the card before it died. The charge has now happened twice, and the queue cannot know how far the crashed worker got. That is why every consumer must be idempotent, deduplicating on a message identifier.

@8
Worker 2 restarts and the two workers drain the backlog, messages 3 to 11, until one message is left. Adding workers adds throughput, but messages taken by different workers can finish in any order. The queue orders delivery, not completion.

@9-10
The last one, message 12, is a poison message: its payload makes the handler throw every time. Worker 1 rejects it, and the broker makes it visible again and counts one more receive.

@11
After the maximum receive count, 3 here, the broker moves message 12 to the dead-letter queue instead of retrying it forever, which would tie up a worker and hide the bug. The main queue is empty, and someone inspects the dead letter and replays it by hand.

@12
So a queue buys decoupling in time and workers you can add at will. It costs at-least-once delivery, which means idempotent consumers, no ordering from end to end, and a backlog that can grow silently. Alert on the age of the oldest message, because depth alone hides a consumer that has stalled.
