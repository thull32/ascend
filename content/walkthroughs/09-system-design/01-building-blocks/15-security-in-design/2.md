@0
A client and a server, about to agree on keys. TLS 1.3 needs one round trip before encrypted application data can flow; TLS 1.2 needed two. Watch how much the first two messages carry.

@1
The client sends its ClientHello. It lists the cipher suites it supports, and it already includes its half of the key exchange, its key share, along with the server name, so the server can pick the right certificate.

@2
The server answers with its ServerHello: it picks the suite and returns its own key share. Both sides can now derive a handshake secret, so everything after this point in the same flight is already encrypted: the certificate chain, a signature proving the server holds the matching private key, and Finished.

@3
The client verifies the chain, from root authority to intermediate to the server's own certificate, and checks the name and the validity dates. Then it sends its own Finished and, in the same flight, its HTTP request. The key exchange gives forward secrecy: a private key stolen later cannot decrypt this session.

@4
The encrypted response comes back. Total cost, one round trip before data. Resumption can even send data with zero round trips, with replay caveats.

@5
On a fresh connection over TCP, the first response byte arrives after three round trips: TCP's handshake, this TLS handshake, then the request itself. A reused connection pays only the last, and QUIC folds the two handshakes into one. This trace authenticates only the server. With mutual TLS the client also presents a certificate and the server verifies it, and that is how the lesson gives every internal service a proven identity: short-lived certificates from an internal authority, rotated automatically, so the user service knows the caller is the reporting service and can refuse it.
