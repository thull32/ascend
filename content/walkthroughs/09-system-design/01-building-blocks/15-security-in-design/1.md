@0
On screen is a typical read path: a browser, a CDN edge, a load balancer, a stateless API service, Redis as a cache, and Postgres. Look at it the way the lesson asks you to in a design review, by drawing the trust boundaries: the edges where the level of trust changes. Every crossing is where a caller must be authenticated, its request authorised, and its data turned from untrusted into validated.

@1
The browser fetches a static file, app dot js, from the nearest CDN edge, straight from its cache. The origin is never touched.

@2
The dynamic request, a GET for the lessons list, reaches the load balancer, and TLS terminates here. This is the first boundary, from the untrusted internet to the edge. In the lesson's design this is where the gateway validates the user's token and applies rate limits, and where it strips any identity headers the client tried to send, such as its own tenant ID.

@3
The balancer picks a healthy API instance by least connections. This hop is the second boundary, from the edge into the internal services. The lesson's rule is that the internal network is not trusted: the call carries a service identity, proven with mutual TLS, and the user's context travels with it, so the API can check both may this service call me, and may this user see this record.

@4
The API checks the cache first, asking Redis for the key lessons v3.

@5
Miss. The key is not there yet.

@6
So the API falls through to Postgres, about 5 milliseconds. This is the third boundary, from the service into the data tier. Least privilege lives here: the workload's database role reads its own schema and nothing else, and in a multi-tenant design every lookup is by tenant and ID, with row-level security as a second wall.

@7
The database answers with 42 rows.

@8
The API stores the result in Redis with a 60 second time to live.

@9
And responds, in roughly 1 millisecond at the balancer, 1 for the cache miss and 5 at the database, plus serialisation.

@10
The review questions on screen are about availability: what happens when Redis is down, and when the database is slow. Ask the security questions of every arrow too. What is the caller's identity, and how is it proven? What may that identity do, on this resource? What does an attacker who gets past this boundary gain? The opening story of the lesson is what happens when nobody asks: one compromised container, a trusted internal network, and the whole user table readable through an API meant only for the mobile app.
