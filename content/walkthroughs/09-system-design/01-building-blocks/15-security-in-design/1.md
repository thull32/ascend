@0
A browser, a gateway, the invoices service, and Postgres, with a reporting service sitting below on the internal network. Draw the trust boundaries the way the lesson asks you to in a design review: the edges where the level of trust changes. This request crosses three, and the table lists them. At each one the caller is authenticated and its request authorised. The internal network is not trusted.

@1
Boundary one, internet to edge. The browser asks for invoice 981 with its token. The gateway terminates TLS, applies rate limits, and validates the user's short-lived access token, its signature and its expiry. The user belongs to tenant t7.

@2
The browser also sends its own X-Tenant-Id header, naming a different tenant, t9. The gateway strips inbound identity headers. The tenant comes only from the validated token, never from something the client typed.

@3
Boundary two, edge to internal. The gateway calls invoices over mutual TLS and passes the user's token along. Invoices checks the caller's certificate, so it knows this is the gateway and not just anything that reached the network, and checks that the user context permits reading this invoice.

@4
Boundary three, internal to data. The lookup is by tenant and ID, and row-level security filters to tenant t7 as a second wall. The tenant is set inside the transaction, so a pooled connection cannot carry the previous tenant's setting into this query.

@5-6
The row belongs to t7, so it comes back, and the invoice goes back through the gateway to the user who owns it.

@7
Now an insecure direct object reference: the same user asks for invoice 982, which belongs to tenant t9. The lookup filters by tenant t7, finds no row, and the answer is 404. Guessing IDs gains nothing.

@8
And the lesson's opening story: a compromised reporting container calls invoices directly. Its certificate proves it is the reporting service, the policy does not allow that identity to read invoices, and it carries no user token at all. The answer is 403. One breached container does not get the whole table.

@9
At every boundary, ask three questions: who is calling, how is that proven, and may they do this to this resource? An attacker who gets past one boundary gains only what that boundary's identity was allowed, which is the whole point of drawing them.
