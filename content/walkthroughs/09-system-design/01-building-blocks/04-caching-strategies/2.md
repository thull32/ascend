@0
An app server, a cache, and a database, both holding price 7 at 10. In write-through, every write goes to the cache, and the cache writes it to the database synchronously before acknowledging. So a read after a write through the cache finds the new value, at least while writes to a key happen one at a time.

@1-2
The app sets the price to 12, and the write enters through the cache, the front door of the write path. The cache marks 12 as pending, forwards the update to the database, and waits. That synchronous hop is what makes it through.

@3-4
The database commits, and only then is the app acknowledged. Any read from now on sees 12. The cost is on screen: write latency is the cache write plus the database write, about 6 milliseconds instead of about 1.

@5
A read hits the cache and gets 12. There is no invalidation step to forget, as long as every write goes through the cache, one at a time for each key.

@6-7
Now the lesson's hole: two writers, with nothing ordering their writes to this key. Writer A sets 13 in the cache, and writer B sets 14 right after it, so the cache holds 14.

@8-9
B's database write lands first, and A's lands last. The cache says 14, the database says 13, with no error anywhere, and they stay that way until the next write or an eviction. The fix is to serialise writes for each key, with a version check or a per-key lock, so both stores apply them in one order.

@10-12
The second failure mode. With both stores back at 14, the database goes down, and a write of 15 arrives. The cache cannot complete the synchronous write, so the write fails, and the cache keeps 14. Writes are exactly as available as the database, never more.

@13
The trade-off: simple reads that are fresh after a write, against slower writes, writes that need ordering for each key, and a cache filled with keys nobody reads. And writes that bypass the cache, such as a batch job, are invisible to it until the time to live runs out. Compare write-behind, which trades durability for write speed.
