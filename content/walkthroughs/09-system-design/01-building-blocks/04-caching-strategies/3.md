@0
An app server, a cache, and a database that holds a view counter, views 9, at 100. The table underneath is the write-behind buffer: dirty entries waiting to be flushed. The rule: the cache acknowledges a write at once and persists it to the database later, asynchronously and in batches.

@1-2
The app sets views 9 to 101. It lands in the cache, the entry is marked dirty, and the app is acknowledged in about a millisecond, before the database has seen anything. That is where write-behind gets its speed.

@3-4
A second write to the same key, 102, simply overwrites the dirty entry, then 103 arrives along with a second key, views 4 at 7. The buffer keeps only the latest value per key, so several application writes will become one database write. This is coalescing, the same trick the database's own buffer pool uses.

@5-6
The flush fires, every 500 milliseconds or when the buffer fills, and the cache writes both rows in one batch. The entries are clean again, and four application writes cost one database write.

@7
A new write, 104, is dirty again and acknowledged instantly.

@8
Then the cache node dies before the next flush. The client was told 104 succeeded, but it never reached the database. It is gone.

@9
After recovery the database serves 103. Write-behind turns a durability guarantee into a durability probability, and in this design the cache has quietly become the system of record for everything unflushed.

@10
The trade-off: the lowest write latency and the fewest database writes, against a window of possible loss and a database that lags the cache. For view counts the loss is noise. For orders, balances, or anything a user was told succeeded, it is a silent data-loss bug. If you need that throughput for data that matters, put a durable log in front of the database instead.
