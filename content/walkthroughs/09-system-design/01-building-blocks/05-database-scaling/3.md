@0
Same three shards, a different rule. Hash the key, take the result modulo the shard count, and that number is the shard. Nearby keys land on unrelated shards, so the shape of the key no longer decides where the load goes.

@1-3
Alice hashes to a large number whose remainder modulo 3 is 2, so she goes to S3. Bob and Hank also come out at 2, so S3 again. No table is involved: any router computes the same answer on its own.

@4
Judy's hash leaves a remainder of 0, so she goes to S1.

@5
After four keys the shards hold one, zero and three. What matters is the sequential case: orders 3,001, 3,002 and onwards hash to unrelated shards just like these names, so there is no hot tail.

@6
Failure mode one. A range query, names from A to C, cannot be routed, because the hash scattered those names. The router sends the scan to every shard and merges the results. That is scatter-gather: its cost grows with the shard count, and its latency is the slowest shard's.

@7
Failure mode two. Add a fourth shard and the modulus changes from 3 to 4. Every one of the four keys now computes a different shard and has to be migrated while the system serves traffic. Consistent hashing exists to shrink that to about a quarter of the keys.

@8
Failure mode three. Hashing spreads keys, not load. One celebrity key still lands on one shard. The fix is to split that hot key with a suffix, so its writes spread over several shards, and read from all the copies.

@9
The trade-off: uniform load and routing with no shared state, paid for with scatter-gather range queries and painful resharding. Range sharding is the mirror image, and many systems, Cassandra and DynamoDB among them, combine the two: hash the partition key, then sort by range within a partition.
