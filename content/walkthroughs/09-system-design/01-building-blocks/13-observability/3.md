@0
An event source, a window operator, and a sink. At scale, nobody stores every request event in the metrics system: ten thousand instances can emit a million samples a second. Instead the pipeline aggregates, and the tool is a window, which turns an endless stream into finite groups. These are tumbling windows of 10 seconds: fixed size, never overlapping, so every event belongs to exactly one window, and each window emits one result when it closes. Twelve events will arrive, at 1, 3, 6, 9, 12, 14, 17, 22, 25, 27, 31 and 33 seconds.

@1-4
The first four, at 1, 3, 6 and 9 seconds, all fall in the window from 0 to 10, and its count climbs to 4. The window stays open after each one, because a later event might still belong to it.

@5
The event at 12 seconds belongs to the next window. That is the signal that the first one is complete: the operator emits a count of 4 to the sink and throws that window's state away. Notice when the result appears. A window's answer is available only once the next window has started.

@6-7
Events at 14 and 17 seconds join the window from 10 to 20. With 12, its count is 3.

@8
The event at 22 seconds closes it: a count of 3 goes to the sink.

@9-11
Events at 25 and 27 seconds join the window from 20 to 30, and the event at 31 closes it with a count of 3. The sink now holds three results.

@12
The event at 33 seconds joins the window from 30 to 40, which stays open, waiting.

@13
Two other shapes are worth knowing. Sliding windows overlap. Here they are 10 seconds long, starting every 5, so every event is counted in 2 windows and a result comes out every 5 seconds. Smoother output, for twice the state.

@14
Session windows have no fixed size. Events with at most 4 seconds between them merge into one session, and a session closes only after a longer silence. The 5 second gap between 17 and 22 seconds splits these twelve events into 2 sessions. The size is driven by the data, so a key that never goes quiet holds state without bound.

@15
Tumbling is cheapest, one bucket per key; sliding trades memory for smoothness; sessions fit user behaviour but need merging. All three assume you know when a window is complete, and in a real pipeline events arrive late. An event that lands after its window was emitted is either dropped or forces a correction, and that choice is why two dashboards built on the same data can disagree by a little.
