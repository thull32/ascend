@0
A browser, a gateway, an orders service, an inventory service, and a collector below them. A trace exists to answer one question: for one request, where did the time go? Metrics cannot answer it, because they have already thrown away which request was which. A trace is a tree of spans joined by one trace ID, and the ID travels between services in the W3C traceparent header: a version, the trace ID, the caller's span ID, and a sampled flag. The table will list the spans as they appear.

@1
The request arrives with no traceparent, so the gateway starts a trace: a new 16-byte trace ID, here ending in 4736, and a root span, s1, marked as sampled.

@2
The gateway calls orders and sends the header with its own span, s1, as the parent. Orders creates a child span, s2, under s1.

@3
Orders calls inventory with the same trace ID and its own span, s2, as the parent. Inventory creates s3 and runs its query.

@4
The response unwinds, and each service ends its span and records how long it took: 900 milliseconds at the gateway, 860 in orders, 720 in inventory, 700 of them in the query.

@5
Each service exports its spans to the collector in the background. The collector groups them by trace ID and stitches the tree from the parent links. Now the answer is a picture: this request took 900 milliseconds, and 700 of them were one inventory query. No metric could have said that.

@6
The failure mode: an orders build that drops the header on this call. Inventory sees no parent, so it starts a new trace with a different ID, and the tree splits in two. The slow query now sits in a trace that nobody connects to the slow request.

@7
So propagate the header on every hop, including retries and messages that pass through queues, and let the sampled flag travel with it, so every service keeps or drops the same traces. A hop that drops the header does not fail loudly; it just breaks the tree.
