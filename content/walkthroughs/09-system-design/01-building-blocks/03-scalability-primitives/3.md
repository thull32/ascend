@0
One read path: a browser, a CDN edge, a load balancer, a stateless API service, Redis and Postgres. The diagram shows one request, so do the multiplication yourself as you watch: every replica you add to the service makes this same trip, against the same cache and the same database.

@1
A static file is served by the nearest CDN edge from its cache. The origin never sees it.

@2-3
A dynamic request reaches the load balancer, where TLS terminates, and the balancer picks a healthy API instance by least connections. The instances are stateless, so any one of them will do. This is the part that scales out cleanly: add a replica, and the balancer spreads requests across one more.

@4-5
The service checks Redis first, and misses. Every replica's misses go to the same Redis.

@6-7
So it falls through to Postgres, about 5 milliseconds, and the database answers. Every replica's queries and connections arrive here too.

@8
The service populates the cache with a time to live of 60 seconds, so the next minute of reads for this key stay off Postgres.

@9
And it responds: balancer, cache miss, database, serialisation.

@10
Now multiply. Thirty replicas, each with HikariCP's default pool of 10 connections, want 300 database connections, and Postgres runs a process per connection with a default limit of 100. Little's law says what the work needs: 2,000 requests a second times one 5 millisecond query is 10 concurrent queries, so 300 connections are doing the work of 10. The load balancer distributes requests; nothing distributes the database. So the order of moves is: make each request do less to the database, pool connections, add read replicas, scale the primary vertically, and only then partition. And ask of this path what happens when Redis is down, and when the database is slow: a circuit breaker, timeouts and load shedding.
