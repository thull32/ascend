@0
Clients on the left, a load balancer in the middle, and three servers on the right, each showing how many requests it has in flight. The rule is one sentence: every new request goes to the server with the fewest requests in flight. Keep it in mind, because that count is a health signal in disguise.

@1-6
The first three requests arrive while every count is zero, or tied at the lowest. Request 1 goes to server 1, request 2 to server 2, request 3 to server 3. With everything equal, least connections looks exactly like round robin.

@7-8
Request 4 arrives with all three servers holding one request each. It is a tie, so it goes to server 1, which now holds two.

@9
Now the difference shows. Server 2 finishes its request and drops to zero, while servers 1 and 3 are still working on theirs. Server 2 is simply the faster one at this moment.

@10-11
Request 5 arrives with counts of 2, 0 and 1. It goes to server 2, the one with nothing in flight.

@12-13
Request 6 arrives with counts of 2, 1 and 1. Server 2 wins the tie again and takes it. Server 1, still holding the two requests it was given, receives nothing new. A server that is slow accumulates in-flight work and stops being chosen; round robin would keep feeding it its full share.

@14
That is why the balancer adapts to slow requests and uneven backends without anyone configuring it. The price is per-backend state on the balancer, which is fine for layer 7 proxies such as Envoy and HAProxy. The lesson's better default goes one step further: pick two replicas at random and send to the less loaded one. In its simulated load test, that kept the 99th percentile nearly flat up to 95 percent utilisation, where random routing more than doubled it. One warning: a server with zero in flight because it has just booted gets a burst before its caches are warm, which is why balancers offer a slow start.
