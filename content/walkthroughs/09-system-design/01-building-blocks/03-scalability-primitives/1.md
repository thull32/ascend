@0
Clients, a load balancer, and three replicas, each showing how many requests it has in flight. Server 3 has gone bad: it takes 300 milliseconds per request, three times the 100 of the others. Nobody has told the balancer. Requests arrive every 50 milliseconds, and the rule is one sentence: each goes to the replica with the fewest in flight, ties to the one picked longest ago. Keep it in mind, because that count is a health signal in disguise.

@1-3
At first everything ties. Request 1 goes to server 1, request 2 to server 2. At 100 milliseconds server 1 finishes, so servers 1 and 3 tie at zero, and server 3, which has had nothing yet, gets request 3. So far this looks exactly like round robin.

@4
At 150 milliseconds server 2 finishes too. Request 4 arrives with server 3 still holding its request, so the tie is between servers 1 and 2, and server 1 takes it.

@5-6
Request 5 goes to server 2, the only one with nothing in flight. At 250 milliseconds server 1 has finished request 4 and takes request 6. Server 3 is still on request 3, so its count stays at one and it keeps losing to whichever fast replica has just emptied.

@7-8
The same pattern for requests 7 and 8: server 2, then server 1. Server 3 finishes only at 400 milliseconds.

@9
Over these 8 requests server 3 took 1, while servers 1 and 2 took 4 and 3. Its long-running request kept its count up, so new work flowed to the fast replicas without anyone measuring latency. Round robin would have sent it 2 of the 8, and they would queue behind its 300-millisecond requests while the fast replicas sat partly idle. The price is per-backend state on the balancer, which is fine for layer 7 proxies such as Envoy and HAProxy. The lesson's better default goes one step further: pick two replicas at random and send to the less loaded one. One warning: a replica with nothing in flight because it has just booted gets a burst before its caches are warm, which is why balancers offer a slow start.
