@0
Users, an API gateway with one shared pool of 12 threads, and three dependencies behind it: Payments, Recommendations and Search. The idea is the bulkhead, named after the watertight compartments in a ship's hull: partition threads per dependency, so a leak in one compartment cannot flood the others. First, the version without it.

@1
The recommendations service becomes slow, as in the lesson's example: calls that took 5 milliseconds now hang for 500 milliseconds before they time out. Nothing else has changed.

@2-3
Every Recommendations call now holds a gateway thread for 500 milliseconds instead of 5. Six are in flight and half the pool is gone. Recommendations traffic keeps arriving at its normal rate, but calls now leave 100 times slower than they enter, and soon Recommendations alone holds all 12 threads. That is Little's law: in flight equals rate times latency, so when the latency grows, the threads it holds grow with it.

@4-5
A checkout request arrives. It needs Payments, which is perfectly healthy. It is rejected anyway, because there is no thread to run it. A slow recommendations service has taken down payments: one dependency's latency became every feature's outage.

@6
The fix: split the 12 threads into three pools of four, one per dependency. A Recommendations call may only use a Recommendations thread, and when that pool is full, the call is rejected at once instead of waiting.

@7-8
Recommendations degrades exactly as before and fills its four threads, but it cannot borrow anyone else's. The next Recommendations call finds its pool full and fails in microseconds with a clear recommendations unavailable, so the page renders without recommendations instead of hanging.

@9
Checkout arrives, takes a Payments thread from a pool with three to spare, and succeeds. The compartment held.

@10
Then Recommendations recovers, and its pool drains back to empty. The fix has its own failure mode: sizing. Too small, and a normal spike to one dependency rejects legitimate calls, an outage you caused yourself. Too large, and the isolation is in name only. Size each pool from measured concurrency, rate times latency, with headroom, and alert on rejections.

@11
The trade-off: bulkheads cap the blast radius of any one dependency at the size of its compartment, at the cost of lower peak utilisation, since idle threads in one pool cannot help another, and one more number per dependency to tune. Pair it with a timeout, which bounds how long each call can hold a thread. The same idea applies to connection pools, worker processes and whole availability zones.
