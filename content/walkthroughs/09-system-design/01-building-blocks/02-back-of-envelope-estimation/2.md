@0
The photo service's read path: a viewer, a CDN edge, and the origin, which here is the object store. The first request for a photo is served from the origin and cached at the edge; every later request near that edge is answered without the origin hearing about it. Hold onto that, because it is the whole capacity argument: the origin only sees the misses.

@1
Viewer A asks for a 200-kilobyte photo. DNS or anycast has already sent them to the nearest edge.

@2
The edge does not have it yet, so it fetches the photo from the object store. This is one of the 5 percent of reads that reach the origin.

@3-4
The origin responds, and its cache control header lets the edge keep the photo for a year: photos never change once uploaded, so there is nothing to expire. Viewer A gets the bytes after about 120 milliseconds.

@5-6
Now viewer B, near the same edge, asks for the same photo. It is served from the edge in about 10 milliseconds, and the origin never sees the request.

@7
Now scale it to the lesson's numbers. At peak, 17,000 image reads a second at 200 kilobytes each is about 3.5 gigabytes a second, all served at the edge. With a 95 percent hit ratio, the origin sees only the 5 percent that miss: about 870 requests and 174 megabytes a second. The origin's size is set by the miss rate, not by the user count. That is also the trap: drop the hit ratio to 70 percent and the misses go from 5 percent to 30, so the origin fleet grows about six times.
