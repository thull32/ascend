@0
Users, an API gateway with 12 threads, and three dependencies behind it: payments, search and recommendations. A bulkhead partitions resources per dependency, like the watertight compartments in a ship's hull, so one breach cannot flood the rest. First, the version without one: a single shared pool.

@1
Search becomes slow. Calls that took 50 milliseconds now hang for 8 seconds before timing out. Nothing else has changed.

@2
Every request to search now holds a gateway thread for 8 seconds instead of 50 milliseconds. Six are in flight, and the shared pool is half gone.

@3
Search traffic keeps arriving at its normal rate, but calls leave 160 times slower than they enter, and search alone now holds all 12 threads. This is Little's law at work: the concurrency a dependency demands is its rate times its latency.

@4
A checkout request arrives. It needs payments, which is perfectly healthy.

@5
It is rejected anyway, with a 503, because there is no thread to run it. A slow search box has taken down payments. One dependency's latency became every feature's outage.

@6
The fix: split the 12 threads into 3 pools of 4, one per dependency. A search call may only use a search thread, and when that pool is full the call is rejected at once instead of waiting.

@7
Search degrades exactly as before and fills its 4 threads. But it cannot borrow from anyone else.

@8
The next search call finds its pool full and fails in microseconds with a clear search unavailable. The page renders without the search box instead of hanging.

@9
Checkout arrives, takes a payments thread from a pool with 3 to spare, and succeeds. The compartment held.

@10
The fix has its own failure mode: sizing. Too small, and a normal spike to one dependency rejects legitimate calls, an outage you caused yourself. Too large, and the isolation is only nominal. Size from measured concurrency with headroom: the lesson's rule is rate times 99th percentile latency times a margin, so 50 calls a second at 120 milliseconds, times 3, is about 20 threads. And alert on rejections.

@11
The price is lower peak utilisation, because idle threads in one pool cannot help another, and one more number to tune per dependency. Bulkheads and breakers cover each other's gaps: a breaker never trips on a dependency that is slow but under its failure threshold, and a bulkhead catches exactly that.
