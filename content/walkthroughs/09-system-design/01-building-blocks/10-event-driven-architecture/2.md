@0
An orchestrator on one side, and three services, each with its own database: order, inventory and payment. There is no transaction that spans them, so a saga runs the business transaction as a sequence of local transactions, each committed at once. If a later step fails, the earlier ones are not rolled back. They are undone, by compensating transactions. The table is the saga's own log, which the orchestrator persists.

@1
Step 1: the order service creates the order, as pending, and commits. That change is visible to everyone immediately. A saga has no isolation.

@2
Step 2: the inventory service reserves the stock, reservation r9, and commits. The orchestrator is now on step 2 of 3.

@3
Step 3 fails: capturing the payment is declined. The order and the reservation are already committed in other services, and no database rollback can reach them.

@4
So the orchestrator switches to compensation. It runs the undo action for every completed step, in reverse order. Each compensation is itself a local transaction, retried until it succeeds.

@5
The newest step first: release the stock. The reserved units go back to the available count.

@6
Then step 1's compensation: the order is marked failed, and an OrderFailed event goes out. The row stays, as the record of what happened.

@7
The saga ends as aborted. Every transition was written to the saga log before the next call. If the orchestrator crashed halfway, its replacement would read that log and resume from the last recorded step, instead of leaving a half-done order. That only works if each command carries a key derived from the saga and the step, so a repeated capture returns the first attempt's result instead of charging again.

@8
The caveats. Other requests can see the intermediate states: an order that was pending, then failed. A compensation might arrive twice, so it must be idempotent. And some actions have no undo, like an email already sent, so put the irreversible step last.

@9
Sagas keep services independent and available with no locks across services, but you give up atomicity and isolation, and you design every compensation by hand. The alternative, choreography, removes the coordinator, at the cost of a flow nobody can read in one place. When a multi-step flow must be undone on failure, give it an owner.
