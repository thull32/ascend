@0
An order service, its Postgres database, a relay, and Kafka. The service must update its database and publish an event, and both must happen or neither. Two separate writes cannot promise that, and the first three frames show why.

@1-2
The naive dual write. First the order commits. Then the service publishes. If it crashes in between, or the broker is unreachable, the order exists and the event never goes out, so billing and shipping never hear about it. Publish first instead, and you get the mirror bug: an event for an order that never committed.

@3
The fix takes the broker out of the transaction. The event is written into an outbox table in the same database transaction as the business row. One local commit covers both, and a separate relay moves the rows to the broker.

@4-7
Four requests arrive, and each one commits its order row and its outbox row together. If a transaction fails, neither row exists, and there is nothing to publish. The database now holds 4 orders and 4 pending outbox rows, and Kafka has received nothing yet.

@8
The relay polls the outbox for pending rows. Change data capture can replace the polling, by tailing the write-ahead log instead.

@9
The relay publishes the pending rows in id order, and Kafka now holds 4 events. Key them by the aggregate's id, and the order per aggregate is kept.

@10
Then the relay marks the rows sent. Sent rows can be purged later.

@11
Now the failure this design accepts. Suppose the relay had crashed after publishing row 4 but before marking it sent. On restart it would find row 4 still pending and publish it again. The outbox gives at-least-once delivery, never exactly-once, so the outbox row's id becomes the event id that consumers deduplicate on.

@12
The trade: reliable publication using only the database's own transaction, at the cost of an extra table, a relay to run, up to one polling interval of latency, and consumers that must tolerate duplicates. Never publish from application code after a commit.
