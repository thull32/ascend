@0
An order service, its Postgres database, a relay, Kafka, and a consumer downstream. The service must update its database and publish an event, and both must happen or neither. Two separate writes cannot promise that, and the next frames show why.

@1-2
The naive dual write. First the order commits. Then the service publishes. If it crashes in between, or the broker is unreachable, the order exists and the event never goes out, so billing and shipping never hear about it. Publish first instead, and you get the mirror bug: an event for an order that never committed.

@3
The fix takes the broker out of the transaction. The event is written into an outbox table in the same database transaction as the business row, with an event id minted right there. One local commit covers both, and a separate relay moves the rows to the broker.

@4-7
Four requests arrive, and each one commits its order row and its outbox row together, events e1 to e4. If a transaction fails, neither row exists, and there is nothing to publish. The database now holds 4 orders and 4 pending outbox rows, and Kafka has received nothing yet.

@8
The relay reads the pending rows in id order. It can poll, or change data capture can tail the write-ahead log instead.

@9
For each row it publishes the event and then marks the row sent. E1, e2 and e3 go out and are marked: Kafka holds 3 events, and the outbox shows 3 sent and 1 pending.

@10
It publishes e4, and the broker has it.

@11
Now the failure this design accepts. The relay crashes after publishing e4 and before marking it sent. The row still says pending, although the event is already in Kafka.

@12
On restart the relay finds e4 pending, publishes it again, and marks it. Kafka now holds e4 twice. The outbox gives at-least-once publication, never exactly-once.

@13
The consumer receives e4 a second time, finds that event id already processed, and skips it. The id minted in the outbox transaction is what every consumer deduplicates on, and that is what turns at-least-once publication into an effect that happens once.

@14
The trade: reliable publication using only the database's own transaction, at the cost of an extra table, a relay to run, up to one polling interval of latency, and consumers that must tolerate duplicates. Never publish from application code after a commit.
