@0
A client, a command handler, an event store and a read model, all for one bank account, account 42. Here is the idea the whole picture rests on: the balance is never stored. The source of truth is the ordered list of facts that produced it. A command is checked against state rebuilt from past events, and if it is valid, a new event is appended. State is a fold over the log.

@1-2
The first command is open account. The handler replays the account's events, of which there are none, so the balance is 0, and the rule passes. It appends account opened as event 1, with an expected-version check. That check is optimistic concurrency: if another writer appended first, this append fails and the command is retried against fresh state.

@3-6
Deposit 50 arrives. The handler replays the one event, finds a balance of 0, and appends deposited 50 as event 2. Then withdraw 20: it replays two events, finds 50, and appends withdrawn 20 as event 3. The balance is now 30, and notice that each load replays the whole stream from the start.

@7-8
Now withdraw 100. The handler replays three events and gets 30. Thirty is less than 100, so the command is rejected and nothing is appended. That is the difference between the two words: a command can fail, but an event, once written, is a fact and cannot.

@9-12
Deposit 10 is valid, and becomes event 4, for a balance of 40. Close account is valid too, and becomes event 5. The balance stays at 40, and the stream holds five facts.

@13
A projector subscribes to the stream and keeps a read model shaped for queries: here a plain balance, 40, as of event 5. It could equally be a search document or a report. It is eventually consistent with the store, and it can be rebuilt from scratch at any time.

@14
That is replay. Delete the read model and fold the five events again, and you get 40. Fold only events 1 and 2, and you see the balance as it was back then. Audit, debugging and new projections come for free, because no fact was ever overwritten.

@15
The first failure mode: an account with a million events takes a million applies to load. Snapshots fix it. Periodically store the state with its version, and replay only the events after it. A snapshot is a cache, so changing the fold means rebuilding it.

@16
The second failure mode: events are forever. A changed rule cannot rewrite history, only add a compensating event. A new event schema needs upcasters for the old versions. And a request to delete someone's data needs crypto-shredding: encrypt per user, and throw the key away.

@17
So event sourcing buys a complete audit trail, time travel and cheap new read models. It costs lagged reads, snapshot and schema-versioning machinery, and a model most teams find harder than a row you can update. Use it where the history is the product, such as ledgers, licences and workflows.
