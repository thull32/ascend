@0
An app, Postgres, a change data capture connector, and a Kafka topic. Instead of the app writing to both the database and the topic, which is a dual write, the connector tails the database's write-ahead log and turns every committed change into an event. The database's own commit order becomes the event stream.

@1
Setup. The connector creates a replication slot, so Postgres keeps the log from that point on, and takes a consistent snapshot of the existing rows, streaming them as synthetic inserts. From then on it needs only the log.

@2-3
The app commits an insert on users. The database writes it to the log at position 1 before acknowledging; the app knows nothing about the topic. The connector decodes that entry into a change event carrying the row before and after, publishes it to the topic keyed by primary key, and confirms position 1 to the slot. The gap between the commit and the publish is the staleness a downstream consumer can see.

@4-7
The same happens for an update on users, at position 2, and for an insert on orders, at position 3. Each change goes into the log, out through the connector, and onto the topic, in commit order, and each is confirmed.

@8-9
Then a delete on users, at position 4. The connector publishes it like any other change. Catching deletes is something polling a table misses. But this time the connector has not yet confirmed position 4: the slot still says 3.

@10
The first failure mode. The connector crashes right there. On restart it resumes after the last confirmed position, 3, publishes position 4 again, and confirms it. The topic now holds that delete twice. Delivery is at-least-once, so consumers must apply events idempotently: upsert by key, or deduplicate by log position.

@11
The second failure mode. The slot pins the log. With the connector down for 3 days, Postgres keeps every segment since the confirmed position, and the primary's disk climbs to 95 percent. Monitor slot lag, and set a retention cap.

@12
Why not dual writes? If the app wrote to Postgres and to the topic itself, a crash between the two would lose an update, and two concurrent writers could publish their updates in opposite orders. Tailing one log makes the database the single arbiter of order.

@13
The trade: change data capture gives exactly the database's order with no application changes, and it catches deletes. But it couples consumers to the table schema, so a column rename can break them, it delivers at-least-once, and it adds slots, lag and connector restarts to operate. Paired with an outbox table, it is the lesson's preferred relay: commit order, and tens of milliseconds of latency.
