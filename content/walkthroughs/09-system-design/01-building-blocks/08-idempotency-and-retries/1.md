@0
A client, a payments API, an idempotency store and a ledger. The rule that makes this safe: the client attaches a unique key, and the server guarantees that the same key produces the same effect once, however many times it arrives.

@1
The client generates a key, k1, and sends it with the payment request. Remember from the lesson that where the key is minted matters: it must belong to this payment and be reused on every retry of it, or it dedupes nothing.

@2
The API checks the store and finds no entry, so it claims k1 atomically with a set-if-not-exists. That claim is the lock: a concurrent duplicate cannot also start. A select followed by an insert would be the check-then-act race that charged the lesson's customer twice.

@3-4
The real work happens once: the ledger records a 20 dollar charge. Then the response is saved under k1 before it is returned, so a retry can be answered without redoing the work.

@5
The reply is sent, and lost: a timeout, a dropped connection, a crashed pod. From where the client stands, it cannot tell whether the charge happened.

@6
So it retries, with the same key. Without the key, this would be a second 20 dollar charge.

@7-8
The store has k1 with a saved response. The API replays it without touching the ledger. Charges: still one. At-least-once delivery plus an idempotent server gives an exactly-once effect, which is the only kind of exactly once there is.

@9
A different case: a copy arrives while the first attempt is still in progress. The set-if-not-exists fails, so the API returns 409 Conflict, or waits for the first to finish, rather than charging twice.

@10
Keys k2 and k3 each charge once, so the ledger shows three charges. Different keys are different intents; the key identifies the payment, not the endpoint.

@11
The details that bite. Scope keys per account, so two tenants who both send key 1 never get each other's response. Store a hash of the request body, and reject a reused key with a different payload rather than replay the wrong answer. And expire keys, but not before the client's retry window ends.

@12
The trade-off: one extra store round trip per request and a keyspace to expire, in exchange for safe retries at every layer. Stripe, Adyen and most payment APIs require it. The case this picture skips is a crash after the charge but before the response is saved; the lesson's fix is a lease on the in-progress key and passing the same key to the processor, so a re-driven charge returns the original.
