@0
A client, a payments API, the Postgres database that holds the idempotency keys and the payments, and a card processor. The rule that makes this safe: the client mints one key for this payment, order-7781, and sends that same key on every retry of it. The server guarantees that one key produces at most one charge, however many times the request arrives.

@1
Delivery 1: the client posts a 30 dollar payment with the key in the Idempotency-Key header.

@2
The API claims the key by inserting a row for it, with a hash of the body and the status in progress. The key is the table's primary key, scoped to the account, so only one insert can succeed. That atomic claim is the lock; a select followed by an insert would be the check-then-act race that charged the lesson's customer twice.

@3-4
Delivery 2 arrives while the first is still in progress: a double click, or a client that timed out early. Its claim fails because the key exists and is in progress, so the API answers 409, retry shortly, and charges nothing.

@5
The real work happens once: the processor charges 30 dollars. The same key goes to the processor too, so if this call is ever repeated, the processor recognises it and returns the original charge.

@6
One transaction then records the payment, marks the key done, and saves the response, 201 with the new charge's ID. The payment and the saved response commit together, so neither can exist without the other.

@7
The response is sent, and lost: a timeout, a dropped connection, a crashed load balancer. From where the client stands, it cannot tell whether the charge happened.

@8
Delivery 3: the client retries with the same key. Without the key, this would be a second 30 dollar charge.

@9-10
The key exists, it is done, and the body hash matches: the same request again. The API replays the saved response byte for byte and never calls the processor. Charges: still one. At-least-once delivery plus an idempotent server gives an exactly-once effect, which is the only kind of exactly once there is.

@11
A client bug: the same key with a different body, 300 dollars instead of 30. The stored hash does not match, so the API answers 422 and charges nothing, rather than replay the wrong answer.

@12
The details that bite. Scope keys per account, so two tenants who both send key 1 never get each other's response. Keep keys longer than any client retries: Stripe keeps them at least 24 hours, because a retry after its key expires is treated as new and charges again. And decide what a failed attempt leaves behind.

@13
The trade-off: one extra write per request and a table of keys to expire, in exchange for safe retries at every layer. The key belongs to the payment, not the attempt: a fresh key per retry would deduplicate nothing. And the crash after the charge but before the commit is covered by a lease on the in-progress key plus the same key at the processor, so a re-driven charge returns the original.
