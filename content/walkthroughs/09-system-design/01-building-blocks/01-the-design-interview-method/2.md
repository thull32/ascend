@0
Three boxes: an app server, Redis, and Postgres. The rule to hold onto is that the application owns the cache logic. It reads the cache first, falls back to the database on a miss, and writes the result back itself. The cache never talks to the database. The key on screen is user 42; on the redirect path, picture a short key instead.

@1-2
The app asks Redis for the key, and misses: nothing has been loaded for it yet, either because the cache is cold or because the entry expired.

@3-4
So the app falls through to the database, the source of truth, and gets the row back.

@5
The app puts the row into the cache with a time to live. Only keys that are actually read get cached, so the memory goes to the links people actually click.

@6
The second read is a hit, served in about half a millisecond without touching the database. On the redirect path, this is the common case.

@7-8
Now a write: the app updates the database first, then deletes the cache entry rather than writing the new value into it. A delete is idempotent and cannot race with another writer's set, and the next read reloads the fresh row.

@9
That next read misses, reloads version 2 and repopulates. Every write costs one extra miss on the following read.

@10
Here is the race worth naming. Reader A misses and reads version 1 from the database. Writer B updates to version 2 and deletes the key. Then A's late set writes version 1 back, and the cache serves the stale value until its time to live runs out.

@11
That is the trade-off. Cache-aside is simple and resilient, because a cache outage only means more database reads, but cache and database can briefly disagree, and the time to live is what bounds how long. In the lesson's design that is 24 hours with 10 percent jitter, so a warm-up never expires all at once. Before you settle on it, ask what a burst of misses on one key does to the database.
