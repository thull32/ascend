@0
This is the redirect path you draw for the URL shortener, as five boxes: a browser, an L7 load balancer, a stateless redirect service, Redis as the cache, and Postgres behind it. A GET for a short key goes through the balancer to the service, which asks Redis first and Postgres only on a miss. Keep the budget in view: a p99 under 20 milliseconds, server-side.

@1
A click arrives for the short key x7Kq. The balancer terminates TLS and picks any healthy redirect instance. They hold no state, so any one will do, which is what lets you add more later without a second thought.

@2
The balancer to the service is one same-zone hop, about half a millisecond.

@3-4
The service asks Redis for the key. The cost is the round trip, about half a millisecond; Redis itself answers in microseconds. It is a hit, and the long URL comes straight back.

@5
The service answers 302 with a Location header, about 1 millisecond after the request reached the balancer. With a 90 percent hit ratio, nine clicks in ten end right here and never touch the database.

@6-7
Now a click on a link nobody has followed recently, a9Zp. Same path, a different key, and this time Redis has nothing: a miss.

@8-9
So the service falls through to Postgres with a primary-key lookup, about a millisecond including the round trip, and the row comes back. Two milliseconds so far.

@10
Before replying, the service fills the cache with a time to live, so the next click on a9Zp is a hit.

@11
Then 302 again, two to three milliseconds in, well inside the 20 millisecond target. The misses set the p99, so the miss path is the one to make fast: an index on the short key, and a connection pool sized so a miss never waits for a connection. Walk it out loud in the interview, hop by hop.

@12
Why 302 and not 301? A browser caches a 301 and stops asking, which saves load but loses click events, destination changes and takedowns of malicious links. And the diagram is not the answer; what breaks is. When the Redis primary dies, 20,000 reads a second land on Postgres, and connections run out before the processor does. That is the deep dive the interviewer is steering you towards.
