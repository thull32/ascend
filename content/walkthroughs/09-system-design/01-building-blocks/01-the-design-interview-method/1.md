@0
This is the read path you draw at minute 19, as six boxes: a browser, a CDN edge, a load balancer, a stateless API service, Redis as the cache, and Postgres as the database. Static files go to the edge; everything dynamic goes through the balancer to the service, and the cache sits in front of the database. The request on screen is a generic API read rather than a redirect, but a redirect walks exactly the same hops.

@1
First, a static file, the app's JavaScript. The nearest CDN edge serves it from its own cache, and the origin is never touched.

@2-3
Now a dynamic request. It reaches the load balancer, where TLS terminates, and the balancer picks a healthy API instance by least connections. The instances are stateless, so any one of them will do, which is what lets you add more of them later without a second thought.

@4-5
The service asks the cache first. That is cache-aside: the application checks Redis before anything else. This time the key is not there yet, so the cache answers with nothing.

@6-7
So the service falls through to the database, which answers with the rows. This is the miss path, the slow branch of every latency budget you write.

@8
Before replying, the service writes the result back into Redis with a time to live of 60 seconds, so the reads in the next minute never touch Postgres.

@9
And the response goes back to the browser. Its latency is the sum of the hops you just watched: balancer, cache, database, serialisation. Walk it out loud in the interview, hop by hop, and check the total against the 20 millisecond target.

@10
The diagram is not the answer; what breaks is. The two questions to expect: what happens when Redis is down, and what happens when the database is slow. Degrade to the database behind a circuit breaker, and protect it with timeouts and load shedding. In the lesson's version of this probe, 20,000 reads a second land on Postgres when the cache dies, and connections run out before the processor does. That is the deep dive the interviewer is steering you towards.
