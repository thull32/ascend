@0
Four boxes: a client, a payments API, an idempotency store, and a ledger that records charges. A POST is not idempotent by specification, so the contract has to make it so. Hold onto one promise, because it is the whole mechanism: the same key produces the same effect exactly once, however many times it arrives.

@1
The client generates a key, k1, for this attempt and sends it with the request: charge 20 dollars, key k1.

@2
The API checks the store first. There is no entry, so it claims k1 atomically, with a set-if-not-exists, and marks it in progress. That atomic claim is what stops a concurrent duplicate from also starting the work.

@3
Now the real work happens, once. The ledger records a 20 dollar charge.

@4
Before replying, the API saves the response under k1: 201 Created, with the new charge's ID. The order matters. A retry can only be answered from the store if the answer is already there.

@5
The reply is sent, and lost. A timeout, a dropped connection, a crashed pod. From the client's side, it cannot tell whether the charge happened.

@6
So it retries, with the same key. Without a key, this would be a second 20 dollar charge.

@7
The store already has k1, with a saved response.

@8
The API replays that saved response, 201 Created, without touching the ledger. Charges: still 1. At-least-once delivery plus an idempotent server gives an exactly-once effect.

@9
The other race is a copy that arrives while the first is still in progress. The set-if-not-exists fails, so the API answers 409 Conflict, or waits for the first to finish, rather than charging twice. In the lesson's trace, that is the 409, retry shortly.

@10
Different keys are different intents. Keys k2 and k3 each charge once, and the ledger now holds 3 charges. The key identifies the attempt, not the endpoint.

@11
Three details bite. Scope keys per account, so clients cannot collide. Store a hash of the request body, and reject a reused key with a different body: the lesson's 422. And expire keys, but not before the client's retry window ends; Stripe prunes keys once they are at least 24 hours old.

@12
The price is one extra store round trip per request and a keyspace to expire. The return is safe retries at every layer. And put it in the contract on day one: adding it later leaves every existing client unsafe to retry.
