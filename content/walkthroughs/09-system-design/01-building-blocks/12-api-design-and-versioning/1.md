@0
Three boxes: a client, an orders API, and the Postgres database that holds both the orders and a table of idempotency keys. A POST is not idempotent by specification, so the contract has to make it so. Hold onto one promise, because it is the whole mechanism: the client mints one key for this operation, k1, sends the same key on every retry, and one key creates at most one order.

@1
Attempt 1: the client posts cart A, with k1 in the Idempotency-Key header.

@2
The API claims the key by inserting a row for k1, with a hash of the body, h1, and the status in progress. The key is the table's primary key, scoped to the caller, so only one insert can succeed, and only that attempt goes on to do the work.

@3-4
Attempt 2 arrives while the first is still running: the lesson's concurrent duplicate. Its claim fails because k1 already exists and is in progress, so the API answers 409, retry shortly, and creates nothing.

@5
The first attempt creates order 1, and in the same transaction marks k1 done and saves the response, 201 with order 1. The order and its saved response commit together, so a retry can only ever find both or neither.

@6
The response is sent, and lost: the client's read timed out. From the client's side, it cannot tell whether the order was created.

@7
Attempt 3, the client's retry, with the same key. Without a key, this would be a second order.

@8-9
The record for k1 is done, and the body hash matches: the same request again. The API replays the saved response, 201 with order 1, byte for byte, without doing the work. Orders: still 1. At-least-once delivery plus an idempotent server gives an exactly-once effect.

@10
Attempt 4 is a client bug: the same key k1 with a different body, cart B. The stored hash differs, so the API answers 422, key reused with a different body, and creates nothing.

@11
Three details bite. Scope keys to the caller, so one client can never replay another's response. Keep keys for a documented window longer than any client retries: Stripe prunes keys once they are at least 24 hours old, and a key reused after pruning starts a new request. And decide what a failed attempt leaves behind.

@12
The price is one extra write per request and a table of keys to expire. The return is safe retries at every layer, as long as the key belongs to the operation, not the attempt. And put it in the contract on day one: adding it later leaves every existing client unsafe to retry.
