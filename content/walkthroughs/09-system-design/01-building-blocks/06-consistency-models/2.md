@0
This is where the vanishing comment comes from. One leader accepts every write and streams its log to two followers, which apply it in order and serve reads. Watch for the moment the client's own write disappears, because that history is exactly what eventual consistency allows and read-your-writes forbids.

@1-2
The client writes x equals 2. The leader logs it at position 8, applies it, and acknowledges straight away, because the followers are asynchronous: neither has the change yet.

@3
The leader streams position 8 to the followers. Healthy and in one zone, that takes milliseconds; under a bulk load or across regions, it can take seconds.

@4-5
The client's next read goes to Follower 1, still at position 7, and gets x equals 1. The client wrote 2 and read 1. In the lesson's terms that is history H5: program order puts the client's write before its read, so every model except eventual forbids it.

@6
A few milliseconds later both followers apply position 8 and agree with the leader. That is all eventual consistency promises: replicas converge once writes stop. The lesson's simulation says how often the gap bites: immediately after a write, a single-replica read is stale about half the time.

@7
The fix is a session guarantee, not a stronger database. Send recent writers to the leader, or carry the write's log position as a token and let a follower serve the read only once it has applied that far. Other users can still see the old value, which is usually fine: they cannot know the write happened.

@8
Now the leader switches to synchronous mode with Follower 1: it waits for Follower 1 to confirm each write before acknowledging. Usually only one follower is synchronous, so one slow follower cannot stall every write.

@9-11
The client writes x equals 3. The leader logs position 9, ships it, and waits until Follower 1 has it durably on disk.

@12
Only then does the client hear OK, so the write exists on two nodes. The cost is one more round trip on every commit.

@13-14
The leader dies. Follower 1, at position 9, is the most up-to-date, so it is promoted, and Follower 2 follows it. Because position 9 was synchronous, nothing acknowledged is lost. With asynchronous replication, failover can make data that was already read un-happen. And the old leader must be fenced before it comes back believing it still leads.

@15
The trade-off: asynchronous is fast and tolerant of slow followers but can lose acknowledged writes; synchronous keeps a second copy at the price of latency and of availability when that follower is slow. Either way the replicas are eventually consistent for reads, so decide which reads need a token.
