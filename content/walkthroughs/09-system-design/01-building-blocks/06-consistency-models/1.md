@0
Three replicas, R1, R2 and R3, all holding x equals v1 at timestamp 9, and no leader. A write must be acknowledged by W of them, here 2, and a read must hear from R of them, also 2. Two plus two is four, which is more than three, and that inequality is the whole idea: every read overlaps every set of replicas that acknowledged a write, so a read reaches at least one replica holding the latest acknowledged write.

@1-2
The client sends a write to a coordinator, and any node can play that role. The coordinator sends x equals v2, timestamp 12, to all three replicas in parallel.

@3
R1 and R2 acknowledge. R3 is slow, a garbage collection pause or a disk stall. Two acknowledgements are all W asks for, so the coordinator does not wait for it.

@4
The client hears OK while R3 still holds v1. The write path tolerated one slow replica without anyone noticing.

@5
Now a read arrives. The coordinator contacts only two replicas, not all three: it asks R2 for the data and R3 for a digest, a hash of the value.

@6
R2 returns v2 at timestamp 12. R3's digest does not match, so the coordinator fetches its full data: v1 at timestamp 9. This is the overlap at work: two replicas out of three must include at least one of the two that acknowledged the write, so the newest version is among the replies, and the newest timestamp wins.

@7-8
Before answering, the coordinator writes v2 back to R3 and waits for it. That is blocking read repair, and it costs the read an extra round trip. Only then does the client get v2.

@9
Now the case the caption warned about: a write that has reached one replica but not two. R1 has applied v3 at timestamp 15; the copy to R2 is still on the wire, and the write has not been acknowledged.

@10
Reader B consults R1 and R3. It sees v3 on R1, the newest value, so B returns v3.

@11
Reader C starts after B has returned and consults R2 and R3. If B's read had written nothing back, neither of them has v3, and C gets v2: a value appeared and then disappeared. No single order of events explains that, so quorum reads alone are not linearizable.

@12
The fix is the write-back from before, done by B's read before it returns: B writes v3 to R3, so v3 sits on two replicas, a write quorum, and C's read must include one of them. C reads v3, at the cost of that second round trip.

@13
The failure mode in tuning. Set W plus R at or below N, say one and one, and there is no overlap at all: a read may consult only replicas that missed the write, and the client sees an old value after a newer one was acknowledged. Tune per workload instead: write to all and read from one for read-heavy data, write to one only for data you can afford to lose.

@14
What write-back still does not fix: two concurrent writes ordered by last-writer-wins timestamps, a failed write left on one replica that later gets repaired into view, and sloppy quorums, where nodes outside the key's home accept writes during a partition. Operations that must be linearizable need consensus.

@15
The trade-off: no leader, no election, availability through partial failures, and consistency you can tune per request. In exchange, every operation touches several replicas, and the guarantees are weaker than they look. This is the design of Dynamo, Cassandra and Riak.
