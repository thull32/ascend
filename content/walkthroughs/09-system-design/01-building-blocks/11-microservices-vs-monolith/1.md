@0
A browser, a content delivery network edge, a load balancer, an API service, Redis, and Postgres: a typical read path. Count the boundaries a request crosses on its way through, because every one of them is a network hop, and a hop is where a microsecond becomes a millisecond.

@1
A static asset comes from the nearest edge, out of its cache. The origin is never touched.

@2-3
A dynamic request goes to the load balancer, where TLS ends. The balancer picks a healthy API instance by least connections. The instances keep no state, so any one will do.

@4-5
The API checks the cache first. It is a miss: the key is not there yet.

@6-7
So it falls through to the database, about 5 milliseconds, and the database answers.

@8
The API puts the result in the cache with a time to live of 60 seconds, so the next minute of reads never touches Postgres.

@9
And it responds. The total is about 1 millisecond at the balancer, 1 for the cache miss, 5 at the database, plus serialisation. Every one of those boxes was a separate process, and every arrow paid a round trip.

@10
Now multiply. Each hop also has to be up, so availabilities in series multiply: five services at 99.9 percent, called in sequence, give 99.5 percent end to end, about 3.6 hours of downtime a month instead of 43 minutes. And each hop adds its own tail: with five calls in sequence, a quarter of requests take longer than any single service's 99th percentile. So ask in review what happens when a hop fails. If Redis is down, degrade to the database behind a circuit breaker. If the database is slow, use timeouts and load shedding.
