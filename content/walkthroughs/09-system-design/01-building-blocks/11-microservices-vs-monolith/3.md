@0
Four services, orders, payments, inventory and ledger, each with a sidecar proxy beside it, and a control plane above. The sidecar intercepts all of its service's traffic, in and out. Retries, timeouts, mutual TLS, routing and telemetry move out of the application code and into the mesh.

@1
The control plane pushes routing rules, retry and timeout policy, and short-lived certificates to every sidecar. The application containers never see any of this.

@2
Orders makes a plain HTTP call to payments on port 8080, exactly as it would without a mesh. Rules in the pod redirect that connection into the orders sidecar. The application has no idea a mesh exists.

@3
The orders sidecar resolves payments, picks a healthy endpoint, and opens a mutually authenticated TLS connection to the payments sidecar. Both sides check identity from the certificate, not from an IP address.

@4
The payments sidecar checks the authorization policy, that orders may call payments, ends the TLS, and forwards plain HTTP over localhost to the application.

@5
The response comes back through both sidecars, and each records the latency, the status and a trace span. That is the price on every call: two extra proxy traversals, together on the order of a millisecond.

@6
Payments starts failing. The orders sidecar applies the retry policy it was given: one retry within budget, with a timeout, and no change to the orders code. Retrying is safe only because the call is a GET; a proxy cannot know whether a failed POST already charged a card.

@7
After 5 consecutive server errors, the sidecar ejects that payments endpoint from its pool and fails fast. That is outlier detection, a circuit breaker per endpoint. Once payments recovers, the endpoint is let back in after a cool-down.

@8
Every sidecar reports the same metrics and trace spans, so the mesh gives you a service graph, the golden signals on every edge, and distributed traces, in the same shape for every language.

@9
Traffic shaping. The control plane moves to config version 2 and tells the orders sidecar to send 10 percent of payment calls to a version 2 subset. Canary releases, header-based routing and fault injection become configuration, not code.

@10
The failure modes. The control plane is a new critical dependency: sidecars keep running on their last config, but new pods cannot join and certificates stop rotating. Each proxy adds latency and memory to every pod. And debugging now spans the app, the sidecar and the mesh config.

@11
So a mesh buys uniform mutual TLS, retries, routing and observability in every language with no application changes, in exchange for an extra hop and a control plane that is itself a distributed system. It pays at dozens of services in several languages. At five services in one language, a shared client library does the same job.
