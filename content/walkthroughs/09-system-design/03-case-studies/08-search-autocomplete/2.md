@0
Three mappers and two reducers, running the classic word count. The daily batch for autocomplete is the same job: read each search as a record, and the query as the word. A MapReduce job is two functions. Map turns each record into key and value pairs; reduce folds all the values for one key. The framework does everything else.

@1
Three input splits: the cat sat, the dog sat, the cat ran. The master assigns one map task per split, preferring the machine that already holds the split on its own disk. Move the compute to the data.

@2
Each mapper emits a pair, word and 1, for every word. Map looks at one record at a time and keeps no state, which is what makes it so easy to run in parallel.

@3
A combiner can run the reduce function locally on each mapper's output, so a word one mapper saw twice crosses the network once, as a count of 2. In this tiny input no mapper sees a word twice, so nothing shrinks here. On a day of search logs, where one mapper sees the same popular query many times, that is where it pays. It is valid because summing is associative and commutative.

@4
Shuffle, step one: every pair is routed to a reducer by hashing its key. The and ran go to reducer 1; cat, sat and dog go to reducer 2. All the values for one word land on one reducer, whichever mapper produced them.

@5-6
Step two: each reducer pulls its partition from every mapper's local disk, then merges and sorts by key. Reducer 1 now has ran with one 1, and the with three. This all-to-all transfer is the expensive part of the job.

@7
Each reducer calls reduce once per key and writes its output. The appears 3 times, cat and sat twice, dog and ran once. For autocomplete, that output is the count of searches per normalised query, and counting distinct users per query is the same shape, with query and user as the key, or a HyperLogLog per query.

@8
Now the failures it absorbs. Suppose mapper 3 had died mid-task. The master notices the missed heartbeat and reruns the same split on mapper 1. That is safe because map is deterministic, and its output appears atomically only when the task completes.

@9
Two more. A straggler, one slow machine, would hold up the whole job, so the master runs backup copies of the last tasks. And key skew: one hot key sends most values to a single reducer.

@10
The trade-off: writing every stage to disk gives simple, restartable fault tolerance, at the price of speed for multi-stage jobs. Spark keeps intermediate data in memory instead. Here the batch runs once a day, and freshness within the day comes from a separate streaming path with 5 minute windows.
