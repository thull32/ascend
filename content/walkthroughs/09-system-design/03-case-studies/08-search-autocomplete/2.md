@0
Three mappers and two reducers, running the classic word count. The daily batch for autocomplete is the same job: read each search as a record, and the query as the word. A MapReduce job is two functions. Map turns each record into key and value pairs; reduce folds all the values for one key. The framework does everything else.

@1
Three input splits: the cat sat, the dog sat, and the the the the ran. The master assigns one map task per split, preferring the machine that already holds the split on its own disk. Move the compute to the data.

@2
Each mapper emits a pair, word and 1, for every word. The third mapper emits the 1 four times. Map looks at one record at a time and keeps no state, which is what makes it so easy to run in parallel.

@3
A combiner runs the reduce function locally on each mapper's output. The third mapper's four pairs for the leave as a single pair, the 4, so eleven pairs become eight before anything crosses the network. On a day of search logs, where one mapper sees the same popular query many times, that is where it pays. It is valid because summing is associative and commutative.

@4
Shuffle, step one: every pair is routed to a reducer by hashing its key, here the sum of its character codes, mod 2. The and ran go to reducer 1; cat, sat and dog go to reducer 0. All the values for one word land on one reducer, whichever mapper produced them.

@5
Step two: reducer 0 pulls its partition from every mapper's local disk, then merges and sorts by key. This all-to-all transfer is the expensive part of the job.

@6-7
Now the failures it absorbs. Mapper 2 dies after reducer 0 has fetched from it but before reducer 1 has, and its map output, on its local disk, is lost. The master notices the missed heartbeats and reruns the same split on mapper 1. That is safe because map is deterministic: the rerun produces identical bytes.

@8
Reducer 1 fetches mapper 2's segment from its new location, along with the others. Nothing is lost and nothing is counted twice.

@9
Each reducer calls reduce once per key and writes its output. The appears 6 times, sat twice, and cat, dog and ran once each. For autocomplete, that output is the count of searches per normalised query, and counting distinct users per query is the same shape, with query and user as the key, or a HyperLogLog per query.

@10
Two more failure modes. A straggler, one slow machine, would hold up the whole job, so the master runs backup copies of the last tasks. And key skew: one hot key sends most values to a single reducer.

@11
The trade-off: writing every stage to disk gives simple, restartable fault tolerance, at the price of speed for multi-stage jobs. Spark keeps intermediate data in memory instead. Here the batch runs once a day, and freshness within the day comes from a separate streaming path with 5 minute windows.
