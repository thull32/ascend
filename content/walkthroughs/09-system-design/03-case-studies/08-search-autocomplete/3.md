@0
Three hosts: a user in Tokyo, an edge cache in Tokyo, and the origin in Virginia. The picture caches a video segment, the generic example; for autocomplete, read the object as the suggestion list for one short prefix, and the origin as the suggest servers. The rule: the first request misses and goes to origin, and later requests nearby are served by the edge.

@1-2
User A's request reaches the nearest edge, which does not have it: a miss. So the edge fetches from origin, about 150 milliseconds of round trip across the Pacific.

@3-4
The origin responds with a Cache-Control header. Here it says keep it for a day; for suggestions the lesson uses 300 seconds on short prefixes, because a suggestion list must change when a query starts trending. User A gets the answer after about 160 milliseconds, and the edge now holds a copy.

@5-6
User B, nearby, asks for the same thing and is served from the edge in about 5 milliseconds. The origin never sees it.

@7
The general lessons on screen are the ones that matter: the hit ratio is what you optimise, the cache key decides what counts as the same request, and invalidation is a purge or a new URL. For autocomplete, the key is the normalised prefix, language and region. There are only 18,278 prefixes of up to three letters per language, so a small key set carries most of the traffic, and the edge answers about 60 percent of requests. The time to live has a cost too: a 5 minute edge time to live, on top of 6 minutes of origin freshness, makes a trending query take up to 11 minutes to appear, one minute over target. And the kill list cannot wait for a time to live at all: removing a harmful suggestion purges every prefix of it from the edge.
