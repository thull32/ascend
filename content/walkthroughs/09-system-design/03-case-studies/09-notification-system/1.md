@0
Four boxes: the order service as the producer, the notification API, Redis holding the dedupe keys, and Kafka, where accepted notifications are enqueued. The producer's dedupe key is order 8812 shipped. It is derived from the event, so every retry and every replay of that event carries the same key. The promise: one key produces the effect at most once, however many times the request arrives.

@1
The first delivery: POST a notification, carrying the dedupe key.

@2
The API claims the key atomically with a set-if-not-exists. In this design that is one Redis command, with a 24 hour expiry that is the dedupe window. Only one caller can create the key, so only one delivery goes on to do the work.

@3
The work happens once: notification n 77 is enqueued to Kafka.

@4
The response, 202 with the notification ID, is saved under the key before it is returned, so a later request with the same key gets the original ID back. Note the gap: Redis and Kafka are separate systems, so a crash between the enqueue and this write would leave the key in progress until its expiry.

@5
The reply is lost. In the lesson's trace it is worse than a lost reply: the order service's consumer is killed before committing its Kafka offset.

@6
So the same event is processed again, and the API is called again with the same key. In the lesson, a new consumer re-reads the event 30 seconds later. Without the key, the customer would get a second shipped notification.

@7
The key exists, it is done, and the body hash matches: the same request again.

@8
The API replays the saved response, the original notification ID, and enqueues nothing. Enqueued: still one.

@9
One more case: a producer bug sends the same key with a different template. The stored hash does not match, so the API answers 422 and does nothing. The key names a different request.

@10
The details that bite. Scope keys per caller: here the key includes the user, so one producer can never collect another's response. Keep keys for longer than any retry, because a request after the key expires is treated as new. The window is a cost and a promise: a deliberate replay of a topic from three days ago finds every key expired, so the API also rejects events older than the window, and every message carries an expiry.

@11
And this is only the first of three layers. Redis replicates asynchronously, so a failover can lose the last second of keys. Behind this layer, each delivery job has a deterministic ID so a sender drops a job it already completed, and each push carries a collapse ID, so a resend replaces the first copy on the phone instead of adding a second.
