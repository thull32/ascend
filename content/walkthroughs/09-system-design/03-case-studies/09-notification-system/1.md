@0
Four boxes: a client, an API, an idempotency store, and a ledger that records the work. The picture uses the classic example, a payments API charging 20 dollars. For notifications, read the client as a producer service such as the order service, the key as its dedupe key, order 8812 shipped, and the ledger entry as one notification enqueued. The promise: the same key produces the same effect exactly once, however many times it arrives.

@1-2
The producer sends the request with key k1. The API checks the store, finds nothing, and claims k1 atomically with a set-if-not-exists. In the notification design that is one Redis command, with a 24 hour expiry that is the dedupe window.

@3-4
The real work happens once, and the response is saved under k1. For notifications, the saved value is the notification's ID, so a later request with the same key gets the original ID back.

@5-6
The reply is lost, and the client retries with the same key. In the lesson's trace it is worse than a lost reply: the order service's consumer is killed before committing its Kafka offset, and 30 seconds later a new consumer re-reads the same event and calls the API again.

@7-8
The store has k1 with a saved response, so the API replays it without touching the ledger. Charges: still 1. For the notification, the set-if-not-exists fails, the lookup returns the original ID, and nothing new is enqueued.

@9
A copy that arrives while the first is still in progress fails the set-if-not-exists too, and gets a 409 Conflict, or waits, rather than doing the work twice.

@10
Different keys are different intents: k2 and k3 each do their work once. Order shipped and order delivered are two notifications, with two keys.

@11
Three details bite. Scope keys per account: here the key is the user plus the dedupe key, so the same event from two services is caught too. Reject a reused key with a different body. And expire keys, but not before the retry window ends. The window is a cost and a promise: a deliberate replay of a topic from three days ago finds every key expired, so the API also rejects events older than the window, and every message carries an expiry.

@12
And this is only the first of three layers. Redis replicates asynchronously, so a failover can lose the last second of keys. Behind this layer, each delivery job has a deterministic ID so a sender drops a job it already completed, and each push carries a collapse ID, so a resend replaces the first copy on the phone instead of adding a second.
