@0
The request topic: three partitions, each an ordered, append-only log, and two planners in one consumer group. The key is the user ID. The producer hashes it to choose a partition, and every event for one user lands in the same partition, in order. Hold onto that, because it is how the planner gets race-free state.

@1-3
User 42's first event goes to partition 2. User 7's goes to partition 1. User 42 again: partition 2, behind the first.

@4-6
User 9 lands in partition 0, user 7 again in partition 1, and user 42 a third time in partition 2. Partition 2 now holds three events, all for user 42, in the order they were written. So order shipped can never overtake order confirmed inside the platform.

@7
The coordinator assigns each partition to exactly one planner. Planner 1 gets partitions 0 and 2, planner 2 gets partition 1. That is the point of the design: every request for user 42 is handled by planner 1 alone. Caps, digests and quiet hours are read-modify-write on per-user state, and with one owner there is no race. Without it, two planners could both read 2 marketing pushes sent today, both send, and a cap of 3 becomes 4.

@8-9
Planner 1 polls partition 0, receives user 9's event, and after processing commits offset 1. Committing after processing gives at-least-once: a crash in between replays the event. The planner checkpoints its per-user state together with its offsets, so a restart replays only what came after the last checkpoint.

@10
Planner 2 dies. After its session timeout, planner 1 takes over partition 1, resuming from the last committed offset. In the lesson's sizing, a moved partition's state, under a gigabyte, is restored in about 9 seconds, during which those users' messages wait.

@11
The limits. A group can use at most one planner per partition. And a hot key sends all its traffic to one partition: a user who receives a flood of events, say 100,000 likes, becomes a hot partition, and digesting must absorb it. After the first like, one push saying Ana and 36 others liked your photo, instead of 36 more pushes.

@12
The trade-off: per-user ordering and owned state, at the price of no global order, parallelism capped by the partition count, and pauses during rebalances. The alternative, Redis counters checked on every message, costs a network call per cap check and still has the race.
