@0
An event source, a window operator, and a sink that receives results. The lesson counts clicks in one-minute windows; the picture shrinks them to 10 seconds so a dozen events fill four windows. Tumbling windows have a fixed size and never overlap, so every event belongs to exactly one window, chosen by its event time, and each window emits one result when it closes.

@1-4
Events at 1, 3, 6 and 9 seconds all fall in the window from 0 up to 10, and its count climbs to 4. It stays open, because a later event might still belong to it.

@5
An event at 12 seconds belongs to the next window. So the first window is complete: the operator emits a count of 4 to the sink and discards that window's state. A window's result exists only once the next window has started.

@6-8
Events at 14 and 17 seconds bring the second window to 3, and an event at 22 seconds closes it: 3 is emitted.

@9-11
25 and 27 join the window from 20 to 30, and the event at 31 closes it with a count of 3.

@12
The event at 33 is the second in the window from 30 to 40, which is still open.

@13
For comparison, sliding windows: 10 seconds long, starting every 5. Windows overlap, so each event is counted in 2 of them, and a result comes out every 5 seconds: smoother output, twice the state.

@14
And session windows have no fixed size. Events closer together than 4 seconds merge into one session, which closes only after a gap. The same 12 events form 2 sessions, from 1 to 17 seconds and from 22 to 33. Size follows the data, so a key that is never quiet holds state forever.

@15
Tumbling is the cheapest, one bucket per key, which is why the click counts use it. But all three assume you know when a window is complete, and that raises the catch: which clock? The lesson assigns each click by event time, the moment of the tap, not when it arrives, and fires partial counts every 10 seconds while the window is open, so the dashboard is fresh long before the final count.
