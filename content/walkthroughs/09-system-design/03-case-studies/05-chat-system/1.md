@0
A client and a server, and one TCP connection between them. A WebSocket starts life as ordinary HTTP, then upgrades, on the same connection, to a persistent protocol that carries frames in both directions. Every phone and laptop in the chat system holds one of these, for hours.

@1
The client sends a normal HTTP GET with an Upgrade header and a random key. To any proxy on the way, it looks like a regular request.

@2
The server answers 101 Switching Protocols, with a value computed from the key to prove it understood the upgrade. From here on, HTTP is over on this connection.

@3
Now frames flow both ways, independently. The client sends one, here a subscribe. Frames from the client are masked, to defeat proxy cache poisoning.

@4
And the server pushes whenever it likes, with no request needed. That is why chat needs this: a message for you can be delivered the moment it is stored. Ping and pong frames keep NATs and load balancers from dropping the idle connection. In the chat design, those heartbeats matter because carrier NATs often expire idle mappings after minutes, and a dead mapping looks like a live socket to both ends until the next write fails.

@5
The choice: WebSockets for low-latency traffic in both directions; server-sent events when only the server pushes, which for chat would need a second channel for sends. The price is state. Each of the 500 gateways holds about 200,000 of these connections, and that state is what makes deploys, crashes and routing the hard parts of chat.
