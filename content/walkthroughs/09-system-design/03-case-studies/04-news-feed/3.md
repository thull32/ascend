@0
The post created topic, split here into two partitions, and two fan-out workers in one consumer group. Inside one group, Kafka behaves like a work queue: each partition is owned by exactly one worker, so each event is fanned out by one worker. Nothing is deleted on read. A worker's progress is the offset it commits, and the number to watch is lag: the log-end offset minus the committed offset.

@1
The post service appends four events to each partition, offsets 0 to 3, and moves on. That separation is what lets an author get a reply in milliseconds while fan-out happens behind it. Lag is 4 on both partitions.

@2-3
Worker 1 polls partition 0 and fans out offsets 0 and 1, then commits offset 2, the next event it wants. Committing after the work is at-least-once: a crash before the commit replays the batch. Partition 0's lag drops to 2.

@4
Worker 2 polls partition 1 and fans out offsets 0 and 1: for each post it pushes the post ID into each follower's timeline.

@5
Then worker 2 crashes before committing. The committed offset for partition 1 is still 0, although both events have already been fanned out.

@6
After the session timeout the coordinator gives partition 1 to worker 1, which resumes from the committed offset, 0. Both events are fanned out a second time. A push into a timeline is not idempotent, so a timeline can now hold a post ID twice. The lesson deduplicates the 300 candidate IDs at read time, which is cheaper than a sorted set that would roughly triple memory.

@7
Now a spike. The post service appends 8 more events to each partition while worker 1, alone, gets through only 4 in total. Lag climbs to 8 and 10, and the oldest unprocessed event is 4 to 5 seconds old. Nothing fails. Feeds simply go stale.

@8
And it keeps growing: another 8 events per partition, while worker 1 manages 4 more on each. Lag is 12 and 14, the oldest event about 10 seconds old, already past the 5 second fan-out target. A count of waiting events says little on its own, so alert on lag in time: the age of the oldest unprocessed event, measured from post creation.

@9
Worker 2 restarts and the group rebalances back to one partition each. With two workers draining, each gets through 6 events while only 2 more arrive, and the lag comes down to 8 and 10. A third worker would sit idle: with 2 partitions, 2 workers is the most this group can use, so the partition count caps how fast fan-out can catch up.

@10
The trade-off: a log gives a work queue whose backlog is durable and replayable, at the price of per-partition parallelism and at-least-once redelivery after every crash or rebalance. Size partitions for the catch-up rate you need, make the handler's effects safe to repeat, and when producers outrun consumers, expect stale feeds rather than failures.
