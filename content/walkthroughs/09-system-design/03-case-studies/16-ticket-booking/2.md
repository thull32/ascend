@0
A client, an API, an idempotency store whose keys live for 24 hours, and a ledger of charges. In the booking system this is the checkout: a fan who clicks Pay three times, or whose phone retries on a flaky connection, must end up with exactly one order. Hold onto one rule: the same key produces the same effect exactly once.

@1-2
The client generates one key, k1, for this checkout attempt, and sends it with a request to charge 20 dollars. The store has no entry, so the API claims k1 atomically with a set-if-not-exists and marks it in progress.

@3-4
The real work happens once: one charge. Before replying, the API saves the result, 201 Created with the charge's reference, under k1.

@5-6
The reply is lost on the way back. The fan sees a spinner, and the client retries with the same key. Without the key, this would be a second charge.

@7-8
The store already has k1 with a saved response, so the API replays it without touching the ledger, or the payment provider. Charges: still 1.

@9
The second click can also arrive while the first is still in progress. Its set-if-not-exists fails, and the API answers 409 Conflict, or waits, rather than charging twice.

@10
Different keys are different intents: k2 and k3 each charge once. The key identifies the attempt, not the endpoint, so a new checkout gets a new key and every retry reuses the old one.

@11-12
Two details bite: scope keys per account, and store a hash of the request body so a reused key with a different body is rejected. In the lesson's checkout the key is the order ID, it travels to the payment provider as its idempotency key too, and a timeout there is resolved by querying the provider by that key before deciding anything.
