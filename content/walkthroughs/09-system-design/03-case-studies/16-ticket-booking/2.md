@0
A fan's browser, the checkout API, its Postgres database, and the card provider. A fan who clicks Pay three times, or whose phone retries on a flaky connection, must end up with exactly one order. Hold onto one rule: the browser mints one key for this checkout, k1, and sends that same key on every retry, and one key produces the effect at most once.

@1-2
The first click arrives with k1 in its Idempotency-Key header. The API claims the key by inserting a row for k1 with a hash of the request body. The key is the table's primary key, scoped to the caller, so only one insert can succeed, and only that request goes on to do the work.

@3-4
The second click arrives while the first is still in progress. Its claim fails, because k1 already exists, so the API answers 409, retry shortly, and does nothing a second time.

@5
The work happens once: the API asks the card provider to authorise the order total, and the same key travels with it, so a repeated call is recognised by the provider too.

@6
Then one transaction records order o 42, marks k1 done and saves the response. The order and the key commit together, so there is no moment when one exists without the other.

@7
The response is lost on the way back. The fan sees a spinner and cannot tell whether anything happened.

@8-10
The browser retries with the same key. The API finds k1 done with a matching body hash, so this is the same request again, and it replays the saved response, 201 with order o 42, without going near the card provider. Authorisations: still one.

@11
A client bug looks different: the same key with a different body, here different seats. The stored hash does not match, so the API answers 422 and does nothing, because the key names another request.

@12-13
Two details bite. Keys are scoped per caller, and they must live longer than any client keeps retrying, because a retry after the key expires is treated as new. And the key belongs to the checkout, not to the attempt: a fresh key per retry would deduplicate nothing.
