@0
Three replicas, R1, R2 and R3, all holding x equals version 1. The rule: a write waits for W acknowledgements, a read for R replies, out of N copies. Here N is 3 and both W and R are 2. Two plus two is more than three, so every read set overlaps every set of replicas that acknowledged a write. Hold onto that overlap; it is the whole guarantee, and watch for the one moment it does not cover.

@1-2
A client sends a write, x equals version 2, to a coordinator. Any node can coordinate. It sends the write to all three replicas in parallel, with a timestamp.

@3-4
R1 and R2 acknowledge. R3 is slow: a garbage collection pause, a disk stall. Two acknowledgements meet W, so the coordinator replies success without waiting, even though R3 still holds version 1. A quorum tolerates one slow or dead replica on the write path, and that is why quorums cut tail latency.

@5
A read arrives. The coordinator contacts only R replicas, two of them, not all three. It asks R2 for the data, and R3 only for a digest, a hash of its value.

@6
R2 returns version 2 with timestamp 12. R3's digest does not match, so the coordinator fetches its full data: version 1, timestamp 9. Because R plus W is more than N, at least one of the two it heard from was in the write quorum, so the newest version is among the replies, and the newest timestamp wins.

@7
Before answering, the coordinator writes version 2 back to R3 and waits for it. This is blocking read repair. The read pays extra round trips, so that no later quorum read can go backwards.

@8
Only now does the client get version 2. Every replica holds it.

@9
Now a write that is still in flight. R1 has applied version 3, the copy to R2 is still on the wire, and the write has not been acknowledged. The overlap is a promise about acknowledged writes only.

@10
Reader B's quorum is R1 and R3. It sees version 3 on R1, the newest timestamp, so B returns version 3.

@11
Reader C starts after B has returned, and reads R2 and R3. If B's read had written nothing back, neither of them has version 3 yet, and C gets version 2. A value appeared, then disappeared. No single order of events explains that, so quorum reads alone are not linearizable.

@12
Blocking read repair closes this case. B writes version 3 to R3 before it returns, so version 3 sits on two replicas, a write quorum, and C's read must include one of them. C reads version 3.

@13
Break the rule and the guarantee goes. With W of 1 and R of 1, there is no overlap at all, and a read can miss a write that was acknowledged. Writing to all and reading from one suits read-heavy data; writing to one suits data you can afford to lose.

@14
What even blocking read repair does not fix: two concurrent writes ordered by last-writer-wins timestamps, a failed write that reached one replica and is later repaired into view, and sloppy quorums, where hinted handoff lets writes land outside the home replicas. Operations that must be linearizable need consensus; Cassandra's lightweight transactions use Paxos.

@15
The trade-off: no leader, no election, writes that keep working through partial failures, and consistency you can tune per request. The cost is that every operation touches several replicas, and the guarantees are weaker than they look. For this store, which must always be writable, that is the right bet; for balances or inventory, the lesson picks consensus instead.
