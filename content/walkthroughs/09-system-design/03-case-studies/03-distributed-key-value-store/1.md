@0
This is what happens inside one replica, a log-structured merge tree. Four parts: a commit log, an in-memory sorted table called the memtable, a level of flushed files called L0, and a merged level called L1. One idea makes it fast: every disk write is sequential. Nothing on disk is ever updated in place.

@1-2
The first puts: a equals 1, b equals 2. Each is appended to the commit log for crash safety and inserted into the memtable, with no disk seek. Then c equals 3, and a is overwritten with 4. In memory, a simply becomes 4; the log still holds both records.

@3-4
A put of d fills the memtable, at 4 entries in this picture. So it flushes: the memtable is written as one sorted, immutable file, SST-1, with a sparse index and a bloom filter, in a single sequential write. The log segment can now be dropped, and a fresh memtable takes new writes.

@5
Now b is set to 9 and c is deleted. SST-1 is immutable, so neither touches it. The delete is itself a write: a tombstone for c goes into the memtable.

@6
Read c. The memtable is checked first and holds the tombstone, so the answer is not found, even though SST-1 still contains c equals 3. The newest level wins.

@7
Read a. It is not in the memtable, so SST-1's bloom filter is asked. It says maybe, the index points to the block, and one disk read returns 4. A bloom filter lets a read skip files that cannot hold the key; at 10 bits per key, it is wrong only about 0.8 percent of the time.

@8
Two more puts fill the memtable and it flushes as SST-2. Now two L0 files overlap: both hold b and c, so a read for b must check SST-2 before SST-1. Read cost grows with every flush.

@9-10
Compaction fixes that. A background merge-sort turns the two files into one non-overlapping L1 file. Newer values win, so b is 9. In this single engine, the tombstone drops both itself and the old c. In the replicated store, compaction keeps tombstones until a grace period has passed, 10 days by default in Cassandra, for a reason the lesson calls the tombstone trap. And a read for b now checks one file.

@11
The costs. Compaction competes with foreground disk work, and if it falls behind, writes stall as L0 piles up. Tombstones must survive long enough, or deleted keys come back. Old versions take space until they are merged away.

@12
The trade-off: excellent write throughput and sequential disk writes, at the price of slower point reads and background compaction to tune. The B-tree makes the opposite bet. This store chose the LSM tree because writes are 20 percent of its million operations a second, and appends beat in-place updates.
