@0
A client and a server, and one connection between them. A WebSocket starts life as an ordinary HTTP request, then upgrades to a persistent, two-way framing protocol on the same TCP connection.

@1
The client sends a normal GET, carrying headers that ask to upgrade to websocket, plus a random key.

@2
The server answers 101 Switching Protocols, with a value computed by hashing that key, which proves it understood the upgrade. From here on, HTTP is over on this connection.

@3
Now frames flow in both directions independently. The client sends one; client frames are masked, which stops a confused proxy from caching them.

@4
And the server pushes whenever it likes, with no request needed. Small ping and pong frames keep load balancers and network address translators from dropping a connection that looks idle.

@5
WebSockets fit two-way, low-latency traffic like games and collaborative editing; server-sent events are simpler when only the server pushes. For the editor, this one socket per open document is what makes the numbers work: each batch of keystrokes costs one frame on a connection that is already open, not a new request with its own handshakes. Alice's X reaches the server in about 35 milliseconds, and that is the distance from London to Virginia, nothing else.
