@0
Four boxes: a client, an API, an idempotency store, and a ledger that records the work. The picture uses the classic example, a payments API charging 20 dollars. For the upload pipeline, read the request as the complete call, the key as the upload's ID, and the ledger entry as a started transcode workflow. One promise holds it together: the same key produces the same effect exactly once, however many times it arrives.

@1
The client sends the request with key k1. In the pipeline, complete is idempotent on the upload ID, so the key comes for free.

@2
The API checks the store. No entry, so it claims k1 atomically, with a set-if-not-exists, and marks it in progress. That claim stops a concurrent duplicate from also starting work.

@3-4
The real work happens once: the ledger records one charge, and in the pipeline, one workflow starts. Before replying, the API saves the response under k1, so a retry can be answered from the store.

@5
The reply is sent, and lost. In the lesson's trace, this is the response to complete vanishing on flaky Wi-Fi, after the last of 256 parts landed.

@6
So the client retries, with the same key. Without the key, this would be a second charge, or here, the same file transcoded twice: roughly 1.2 vCPU-hours of encoding for a 10 minute video, thrown away.

@7-8
The store has k1 with a saved response, so the API replays it without touching the ledger. Charges: still 1. For the uploader, the retry returns the same video ID and starts no second workflow.

@9
The other race is a copy that arrives while the first is still in progress. The set-if-not-exists fails, so the API answers 409 Conflict, or waits for the first to finish, rather than doing the work twice.

@10
Different keys are different intents. Keys k2 and k3 each do their work once. The key identifies the attempt, not the endpoint.

@11
Three details bite: scope keys per account, store a hash of the request body and reject a reused key with a different body, and expire keys only after the client's retry window ends.

@12
The price is one extra store round trip and a keyspace to expire. The pipeline needs the same guarantee from a second direction too: a sweeper also starts workflows for uploads that have every part but were never completed, so starting the workflow is idempotent on the video ID as well.
