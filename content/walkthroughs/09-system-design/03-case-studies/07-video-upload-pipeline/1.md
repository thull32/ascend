@0
Four boxes: the creator's app, the upload API, the Postgres database that holds uploads and their idempotency keys, and the workflow engine that transcodes. The key here is the upload's own ID, up 81f, and it comes for free: complete is idempotent on the upload ID, so every retry of complete carries it. One promise holds the picture together: one key produces the effect at most once, however many times the request arrives.

@1
The first delivery: POST complete for upload up 81f, carrying the key.

@2
The API claims the key by inserting a row for up 81f, in progress, with a hash of the body. The key is the table's primary key, scoped to the caller, so only one insert can succeed, and only that delivery goes on to do the work.

@3
The work happens once: the API starts the transcode workflow for video v 9Qx. The same key goes downstream too, so if this call were ever repeated, the workflow engine would recognise it.

@4
One transaction records that upload up 81f became video v 9Qx, marks the key done, and saves the response, 202 with the video ID. The record and the key commit together, so there is no moment where one exists without the other.

@5
The reply is sent, and lost. In the lesson's trace, this is the response to complete vanishing on flaky Wi-Fi, after the last of 256 parts landed. The app cannot tell whether its call worked.

@6
So the app retries, with the same key. Without it, the same file would be transcoded twice: roughly 1.2 vCPU-hours of encoding for a 10 minute video, thrown away.

@7
The key exists, it is done, and the body hash matches: this is the same request again.

@8
The API replays the saved response byte for byte, and starts nothing. Workflows: still one. For the uploader, the retry returns the same video ID.

@9
One more case: a client bug sends the same key with a different parts list. The stored hash does not match, so the server answers 422 and does nothing. The key names a different request.

@10
The details that bite. Scope keys per caller, so one client cannot replay another's response. Keep keys longer than any client retries, because a retry after the key expires is treated as new and does the work again. And decide what a failed attempt leaves behind.

@11
The price is one extra write per request and a table of keys to expire. The pipeline needs the same guarantee from a second direction too: a sweeper also starts workflows for uploads that have every part but were never completed, so starting the workflow is idempotent on the video ID as well. The key belongs to the operation, not to the attempt.
