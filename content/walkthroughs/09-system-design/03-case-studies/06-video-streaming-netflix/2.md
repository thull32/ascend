@0
One Open Connect site, with four appliances placed on a hash ring. Files are hashed onto the same ring, and each file lives on the first appliance clockwise from it. Any component can compute a file's appliance with no lookup table.

@1-3
Title 81's 1080p AV1 encode hashes to 63 degrees, and the first appliance clockwise is N4. Title 81's 4K HEVC encode lands at 349 degrees, wraps past the top of the circle, and also reaches N4. Title 17's 720p encode, at 152 degrees, is N4 as well.

@4-6
Title 44's 1080p AV1 encode, at 162 degrees, walks to N3. So do title 17's English audio at 264 and title 44's 480p encode at 187. Note that the unit here is a file, one encode of one title, not a title: different renditions of the same title can land on different appliances.

@7
Now add an appliance, N5, at 340 degrees. Only the files on the arc it takes over move: the three between N2, at 161 degrees, and 340, now on N5. The N4 files never move. With hash mod N, nearly every file would. That matters because filling is done in an off-peak window a few hours long, and every moved file is bytes to download in it.

@8
Look at the ring and you can see the catch: four positions placed at random are badly spread, and N1 and N2 own nothing. Real systems give each machine many positions so the load evens out. And for a hit title, one copy is not enough: popular files get several copies across the site, so no single appliance takes all of that title's traffic.
