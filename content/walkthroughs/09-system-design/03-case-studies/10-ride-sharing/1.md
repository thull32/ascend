@0
Clients on the left, a load balancer in the middle, and three servers, each showing how many connections it holds. In this design the servers are the connection gateways, and every online driver holds one open connection to one of them. The rule on screen is the whole idea: each new arrival goes to the server with the fewest in flight right now.

@1-2
Request 1 arrives while every count is zero. Server 1 has the fewest, so it gets it, and its count goes to 1.

@3-6
Request 2 arrives with counts of 1, 0 and 0, so it goes to server 2. Request 3 finds 1, 1 and 0, and goes to server 3. So far this looks exactly like round robin.

@7-8
Request 4 finds all three servers at 1. It is a tie, and server 1 takes it, rising to 2.

@9
Now the difference. Server 2 finishes its request and drops back to 0. Round robin would not notice; it would simply hand the next arrival to whoever is next in turn.

@10-11
Request 5 arrives with counts of 2, 0 and 1. Least-connections sends it to server 2, the emptiest.

@12-13
Request 6 finds 2, 1 and 1, ties between servers 2 and 3, and goes to server 2. The counts end at 2, 2 and 1: the load follows what each server actually holds, not the order of arrival.

@14
This adapts to slow requests and uneven backends, at the price of the balancer tracking a count for every backend, which layer 7 proxies such as Envoy and HAProxy do anyway. For the gateways it matters even more. A driver connection lasts for hours, so counting new requests says nothing about load. After a gateway restarts, round robin keeps handing it only its usual share of new connections while the others keep their old ones, and it stays nearly empty for hours. Balancing by open connections fills it first.
