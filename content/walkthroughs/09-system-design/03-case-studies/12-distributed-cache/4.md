@0
Forty readers, the app servers, a cache holding one hot key, the feed, with 2 seconds left to live, and a database that sees about one query a second for it. This is a stampede, also called a dog-pile.

@1
The time to live runs out, and the key vanishes while 40 requests a second are still asking for it.

@2-4
Forty requests arrive in the same instant. All of them check the cache, and all of them miss, because nobody has put the value back yet.

@5
So all 40 run the expensive query. A database sized for about one query a second on this key gets 40 at once: latency goes from 5 milliseconds to seconds as queries queue, the connection pool drains, and unrelated queries stall.

@6
Eventually all 40 return the same rows and all 40 write the same value back. Cascading failures often start exactly here. In the lesson's numbers it is worse: a key read 50,000 times a second, with a 20 millisecond rebuild query, sends about 1,000 readers to the database before the first one sets the value.

@7-8
The first fix is coalescing. The first request to miss takes a short lock on the key, a set-if-not-exists that expires after 500 milliseconds. The other 39 see the lock and wait briefly, or serve a stale copy if one exists.

@9-10
Only the lock holder queries the database. It writes the fresh value, releases the lock, and the waiters read it from the cache: 1 query instead of 40.

@11
Two more defences. Keep serving the stale value while one background job refreshes it, or refresh early with a probability that rises as expiry nears. And jitter the time to live, so many keys never expire together.

@12
Each has a price: the lock adds a round trip and a short wait on every miss, and stale serving means briefly out-of-date data. Both are far cheaper than a database falling over under 40 times its load. The lesson's version of the lock is the lease from Facebook's Memcache paper: the server hands one client a token, issues at most one per key every 10 seconds, and tells everyone else to wait or take a slightly stale value.
