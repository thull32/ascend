@0
Zoom into a single cache node that holds only 3 keys. The app will ask for eight keys in order: A, B, C, A, D, B, E, A. The table lists what the node holds, most recently used first. The rule: every access moves a key to the front, and when the node is full, the key at the back, the one untouched for longest, is evicted.

@1-3
A, B and C all miss. There is room, so each is loaded from the database and inserted at the front. The node is now full: C, then B, then A at the back.

@4
Step 4 asks for A again: a hit. A jumps from the back to the front. Recency is updated on reads as well as writes, so B, last used at step 2, is now at the back.

@5
D misses. The node is full, so B is evicted and D goes to the front: D, A, C.

@6
B is asked for again, one step after it left. Another miss, and C is evicted to make room: B, D, A.

@7-8
E misses and pushes out A, and then step 8 asks for A, which has just gone. A miss again, and D is evicted. The node ends holding A, E and B.

@9
The tally is 1 hit in 8 requests: this sequence touches more distinct keys than the node can hold. The worse failure is a one-off scan, a report or a crawler reading many keys once each, which pushes every genuinely hot key out, so the next real requests all miss. Variants such as a small probationary segment admit a key to the main cache only on its second touch.

@10
LRU is the default anyway: a hash map plus a doubly linked list gives constant-time lookup, promotion and eviction, and it adapts instantly when the working set shifts. Its blind spot is that it tracks recency only, so a key read a thousand times looks the same as one read once a moment ago. Real servers approximate it. Redis samples a handful of keys and evicts the oldest of the sample, and Memcached segments its LRU into hot, warm and cold regions so a scan cannot flush the working set.
