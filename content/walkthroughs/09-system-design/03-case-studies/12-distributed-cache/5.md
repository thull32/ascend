@0
An app server, Redis as the cache, and Postgres holding user 42 at version 1. In cache-aside the application owns the logic: it reads the cache first, falls back to the database on a miss, and writes the result back itself. The cache never talks to the database.

@1-2
The read path. The app asks the cache for user 42 and gets nothing, because the key is cold or has expired.

@3-4
It falls through to the database, the source of truth, which takes about 5 milliseconds and returns version 1.

@5
The app puts version 1 into the cache with a 300 second time to live. Only keys that are actually read get cached, so memory goes to hot data.

@6
The second read is a hit, in about half a millisecond, without touching the database.

@7
The write path. The app updates the database first, to version 2.

@8
Then it deletes the cache entry instead of writing version 2 into it. A delete is idempotent, and two deletes cannot land out of order the way two updates can. The next read reloads the fresh row.

@9
And it does: the next read misses, loads version 2 and puts it in the cache. Every write costs one extra miss.

@10
Now the classic race. Reader A misses and reads version 1 from the database, then stalls, say for a 50 millisecond garbage-collection pause. Writer B updates to version 2 and deletes the key. Then A wakes and sets version 1. The cache now serves stale data until its time to live runs out.

@11
Cache-aside is simple and resilient: a cache outage only means more database reads. But the window between a slow reader's database read and its set is where a stale value slips in. The lesson closes it with a lease. The miss hands A a token, B's delete invalidates it, and A's late set carries a dead token and is rejected. The time to live stays as the backstop that bounds every inconsistency.
