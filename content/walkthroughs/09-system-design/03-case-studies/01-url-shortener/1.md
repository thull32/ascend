@0
Four boxes: a client, an API, an idempotency store, and a ledger that records the work. The picture uses a payments API charging 20 dollars, because that is the classic case, but the shortener's create is the same shape: read the ledger as the link table, and the charge as minting a short link. Hold onto one promise: the same key produces the same effect exactly once, however many times it arrives.

@1
The client generates a key, k1, for this attempt and sends it with the request. In the shortener, mobile clients retry on timeout, so this Idempotency-Key header is mandatory.

@2
The API checks the store. There is no entry, so it claims k1 atomically, with a set-if-not-exists, and marks it in progress. That claim is what stops a concurrent duplicate from also starting the work.

@3
Now the real work happens, once. The ledger records one charge; in the shortener, one link row is written.

@4
Before replying, the API saves the response under k1. A retry can only be answered from the store if the answer is already there. The shortener keeps this record per owner and key for 24 hours.

@5
The reply is sent, and lost. A timeout, a dropped connection, a crashed pod. The client cannot tell whether its request worked.

@6
So it retries, with the same key. Without the key, this is how one tap on shorten becomes two links.

@7-8
The store already has k1, with a saved response, so the API replays it without touching the ledger. Charges: still 1. At-least-once delivery plus an idempotent server gives an exactly-once effect, and the user gets back the same short link.

@9
The other race is a copy that arrives while the first is still in progress. The set-if-not-exists fails, so the API answers 409 Conflict, or waits for the first to finish, rather than doing the work twice. That is the shortener's 409 for a key still in progress.

@10
Different keys are different intents. Keys k2 and k3 each do their work once, and the ledger now holds 3. The key identifies the attempt, not the endpoint.

@11
Three details bite. Scope keys per account, which is why the shortener's table is keyed by owner and key, so keys from different clients never clash. Store a hash of the request body, and reject a reused key with a different body. And expire keys, but not before the client's retry window ends.

@12
The price is one extra store round trip per create and a keyspace to expire. At 600 creates a second that is cheap, and it removes a whole failure mode: duplicate links seconds apart for the same owner and URL.
