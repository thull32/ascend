@0
This shows the design the lesson rejects, so you can see why. A Kafka topic with three partitions, each an ordered, append-only log, and two consumers in one group. The producer hashes each message's key to choose a partition, so every event for one key lands in the same partition, in order.

@1-6
Six click events arrive, keyed by short link. aZ3kP9x hashes to partition 0. q8Lm2Tt goes to partition 1. aZ3kP9x again, to partition 0, behind its first event. x1Yb7Qe to partition 1. aZ3kP9x a third time, partition 0 again. And Pz04nWc to partition 1. Notice the shape: partition 0 holds only one link, and partition 2 is still empty.

@7
The group coordinator assigns each partition to exactly one consumer. Consumer 1 gets partitions 0 and 2, consumer 2 gets partition 1. Partitions, not messages, are the unit of parallelism, and partition 2 received no keys at all: hashing spreads keys, not load.

@8-9
Consumer 1 polls partition 0 and receives its records in offset order, then commits offset 3 after processing. Committing after processing gives at-least-once: a crash between the two replays records. The shortener's aggregator handles that by making each closed window an idempotent upsert, so a replay overwrites counts instead of doubling them.

@10-11
Consumer 2 polls partition 1 and works through offsets 0 to 2. Having finished 0 and 1, it commits offset 2, and starts on offset 2.

@12
Consumer 2 dies after processing offset 2 but before committing it. The committed offset for partition 1 is still 2.

@13
After its session timeout the coordinator rebalances, and consumer 1 takes over partition 1, resuming from the last committed offset, 2. So offset 2 is delivered again: exactly the replay the idempotent upsert absorbs. The group pauses during the rebalance.

@14
Now the limits. A group can use at most 3 consumers here, one per partition. And a hot key sends all its traffic to one partition, which one consumer must handle alone. That is the problem: when a push notification sends aZ3kP9x 30,000 clicks a second, every one of them would queue behind partition 0.

@15
Keying buys per-key order, and counting does not need it, because counts are commutative. So the shortener partitions by producer instance and pre-aggregates: each redirect instance flushes a map of counts every second, and a link taking 30,000 clicks a second becomes 50 messages a second, one per instance. Choose keys that keep together only what must stay ordered.
