@0
A client, a payments API, an idempotency store whose keys live for 24 hours, and a ledger that records charges. Hold onto one promise: the same key produces the same effect exactly once, however many times it arrives.

@1
The client generates a key, k1, for this attempt, and sends it with a request to charge 20 dollars.

@2
The API checks the store and finds nothing, so it claims k1 atomically with a set-if-not-exists, marking it in progress. A concurrent duplicate now cannot also start processing.

@3
The real work happens once: the ledger records one 20 dollar charge.

@4
Before replying, the API saves the response, 201 Created with the charge's reference, under k1. That ordering is what lets a retry be answered without redoing the work.

@5
The reply is sent and lost: a timeout, a dropped connection, a crashed pod. The client cannot tell whether the charge happened. This is the unknown outcome the whole lesson is about.

@6
So the client retries, with the same key. Without a key, this would be a second 20 dollar charge.

@7-8
This time the store has k1 with a saved response, and the API replays it without touching the ledger. Charges: still 1. At-least-once delivery plus an idempotent server gives an exactly-once effect.

@9
A different race: a second copy arrives while the first is still in progress. Its set-if-not-exists fails, so the API answers 409 Conflict, or waits for the first to finish, rather than charging twice.

@10
Different keys are different intents. Keys k2 and k3 each charge once, and the ledger now holds 3 charges. The key identifies the attempt, not the endpoint.

@11
The details that bite: scope keys per account so clients cannot collide, and store a hash of the request body, so a reused key with a different payload is rejected; the lesson answers that with 422, because it is a client bug. Expire keys, but not before the client's retry window ends.

@12
The cost is one extra store round trip per request and a keyspace to expire, in exchange for safe retries at every layer. In this design the same idea repeats at every boundary: the client's key into the payment service, our attempt key into the provider, the provider's event ID on webhooks, and an event ID for downstream consumers.
