@0
A client, the payment service, its Postgres database with a table of idempotency keys, and the PSP that actually moves money. Hold onto one rule: the client mints one key for this payment, k1, and sends that same key on every retry. One key produces the effect at most once, however many times the request arrives.

@1
The first delivery: POST a 20 dollar payment, with k1 in the Idempotency-Key header.

@2
The service claims the key by inserting a row for k1, in progress, with a hash of the body. The key is the table's primary key, scoped to the caller, so only one insert can ever succeed, and only that delivery goes on to do the work.

@3
A second delivery arrives while the first is still in progress: a double tap, or a client that timed out early and retried.

@4
Its claim fails, because k1 already exists and is still in progress. The service answers 409, retry shortly, or makes it wait for the first to finish. Either way it does not charge a second time.

@5
The work happens once: the PSP charges 20 dollars. The same key goes downstream too, so if this call is ever repeated, the PSP recognises it.

@6
One transaction records payment pay 7Q, marks k1 done, and saves the response, 201 with the payment reference. The record and the key commit together, so there is no moment where one exists without the other.

@7
The reply is sent and lost: a timeout, a dropped connection, a crashed load balancer. The client cannot tell whether the charge happened. This is the unknown outcome the whole lesson is about.

@8
So the client retries, with the same key. Without it, this would be a second 20 dollar charge.

@9
The key exists, it is done, and the body hash matches: this is the same request again.

@10
The service replays the saved response byte for byte, and charges nothing. Charges: still one. At-least-once delivery plus an idempotent server gives an exactly-once effect.

@11
One more case: a client bug sends k1 again, but for 30 dollars instead of 20. The stored hash does not match, so the service answers 422 and does nothing. The key names a different request.

@12
The details that bite. Scope keys per caller, so one client cannot replay another's response. Keep keys longer than any client retries, because a retry after the key expires is treated as new and charges again. And decide what a failed attempt leaves behind.

@13
The cost is one extra write per request and a table of keys to expire, in exchange for retries that are safe at every layer. In this design the same idea repeats at every boundary: the client's key into the payment service, our attempt key into the PSP, the PSP's event ID on webhooks, and an event ID for downstream consumers.
