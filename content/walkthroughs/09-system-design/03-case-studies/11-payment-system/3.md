@0
The payment service, its Postgres database holding both the payment rows and an outbox table, a relay, Kafka, and the entitlements service downstream. The problem: the payment service must update its database and publish a payment-succeeded event, and both must happen or neither. Two separate writes cannot promise that.

@1-2
Here is the naive dual write. The payment commits, and then the service publishes. If it crashes in between, or the broker is unreachable, the payment exists and the event never goes out, so the customer pays and never gets the product. Publishing first has the mirror problem: an event for a payment that never committed.

@3
The fix is to write the event into the outbox table in the same database transaction as the payment row, with an event id minted right there. One local commit covers both, and a separate relay moves rows to the broker.

@4-6
Three requests arrive, and each commits its payment row and its outbox row together: e1, e2 and e3. In the real service, the status change and the ledger entry commit in that same transaction. If a transaction fails, none of it exists, and there is nothing to publish. The database now holds three payments and three pending outbox rows, and Kafka has nothing yet.

@7
The relay reads the pending rows in id order, by polling, or by tailing the write-ahead log with change data capture, which avoids polling.

@8
For each row it publishes the event and then marks the row sent. E1 and e2 go out and are marked.

@9
It publishes e3, and the broker has it.

@10
Then the relay crashes, after publishing e3 but before marking it sent. The row still says pending, although the event is already in Kafka.

@11
On restart the relay finds e3 pending, publishes it again, and marks it. Kafka now holds e3 twice. The outbox gives at-least-once publication, never exactly once.

@12
The entitlements service receives e3 a second time, finds that event id already processed, and skips it. It may see an event twice, but it can never miss one, and deduplicating on the id makes the grant happen once.

@13
So the price is an extra table, a relay to run, about one polling interval of publish latency, and consumers that must tolerate duplicates. In exchange, a payment that succeeded always produces its event.
