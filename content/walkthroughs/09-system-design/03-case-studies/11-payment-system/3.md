@0
A service, its Postgres database holding both the business rows and an outbox table, a relay, and Kafka. The problem: the service must update its database and publish an event, and both must happen or neither. Two separate writes cannot promise that.

@1-2
Here is the naive dual write. The order commits, and then the service publishes. If it crashes in between, or the broker is unreachable, the order exists and the event never goes out, so billing and shipping never learn about it. Publishing first has the mirror problem: an event for an order that never committed.

@3
The fix is to write the event into the outbox table in the same database transaction as the business row. One local commit covers both, and a separate relay moves rows to the broker.

@4-6
Three requests arrive, and each commits its order row and its outbox row together. If a transaction fails, neither row exists, and there is nothing to publish. The database now holds 3 orders and 3 pending outbox rows, and Kafka has nothing yet.

@7
The relay polls the outbox for pending rows. It could instead tail the write-ahead log with change data capture, Debezium for example, which avoids polling entirely.

@8
It publishes each pending row in ID order, and Kafka now holds 3 events. Keying by the aggregate's ID keeps per-aggregate ordering.

@9
Then it marks the rows sent, and sent rows can be purged later.

@10
The failure mode, shown on row 3, now pending again: if the relay crashes after publishing a row but before marking it sent, on restart it publishes that row a second time. The outbox gives at-least-once delivery, never exactly-once.

@11
So the price is an extra table, a relay to run, about one polling interval of publish latency, and consumers that must tolerate duplicates. In the payment system, the status change, the ledger entry and the outbox row commit together, and the entitlement service dedupes on the event ID. It may see an event twice, but it can never miss one.
