@0
Six boxes across the screen: the browser, the operating system's stub resolver, a recursive resolver, a root server, the dot com servers, and example.com's own authoritative server. We need the address of example.com, and every cache misses, so each step walks one level down the delegation tree.

@1-2
The browser asks the stub, and its cache misses. The stub forwards to the configured recursive resolver, an ISP's or a public one, and that misses too.

@3-4
The recursive resolver asks a root server. The root does not know the answer; it refers it to the dot com servers.

@5-6
It asks the dot com server, which refers it again, to example.com's authoritative name servers.

@7-8
It asks the authoritative server, which finally answers with the address and a time to live of 300 seconds.

@9-10
The recursive resolver caches the record for those 300 seconds and passes it back, and the browser can connect. Every later lookup in the next 5 minutes is one cache hit instead of four round trips.

@11
Short time to live values enable fast failover but raise resolver load and make the cold path slower; CDNs typically use 20 to 300 seconds. For a crawler, the cold path is the normal path. It makes 2,000 fetches a second across 15,000 hosts, and in the lesson's traced fetch a missed lookup cost 40 milliseconds. So each crawler shard runs its own caching resolver and prefetches addresses for hosts about to reach the head of the queue, which turns that time into zero.
