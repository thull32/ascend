@0
The crawler's visited set, as a Bloom filter: 16 bits, all zero, and 3 hash functions. It answers have I seen this URL with definitely not or probably yes. Never definitely yes, and it never forgets a URL it was given.

@1-2
Add a.com slash: its hashes are 10, 3 and 0, so those bits are set. Then a.com slash about hashes to 3, 0 and 5; two of those are already set, so only bit 5 is new.

@3-4
b.org slash x sets 0, 15 and 2, and c.net slash sets 10, 15 and 8. Four URLs, and 7 of the 16 bits are set.

@5-7
Look up a.com slash: bits 10, 3 and 0 are all 1, so it is probably seen. A filter never says no to a URL it holds. The check against the stored URL table confirms it.

@8-9
Look up a URL that was never added, labelled evt-100: bits 14, 5 and 12. Bit 14 is 0, so it is definitely new, and it goes straight to the frontier with no lookup at all. For a crawler that is the common, cheap case.

@10-11
Now evt-102, also never added: bits 8, 15 and 2, and every one of them was set by other URLs. A false positive. Checked against the table, it is not there. Here is the subtle point for a crawler: if you trust the filter blindly, a false positive means a genuinely new URL is never crawled.

@12
You cannot delete, because a bit may be shared, and the false-positive rate climbs as the filter fills, so it must be sized for the final count.

@13
At crawler scale that is ten billion URLs. For a 1 percent false-positive rate, about 10 bits per URL and 7 hash functions: 12 gigabytes. So 1 percent of new URLs get a wrong maybe. For low-priority links that is acceptable; for sitemap and high-priority URLs, confirm every maybe against the URL table, in sorted batches, so thousands of checks cost one sequential pass instead of thousands of disk seeks.
