lesson: exactly-once-semantics
viz: The outbox makes the event as durable as the business write
frames: 15
source: d52cc1f6e297dd30
---
@0
A checkout service, its Postgres database, a relay, Kafka, and a consumer downstream. The service must save a payment row and publish an event about it, and both must happen or neither. Exactly once starts here, at the very first hop: if the event can be lost before it ever reaches the broker, nothing downstream can save you.

@1-2
The naive dual write. The payment commits, then the service tries to publish, and the publish never arrives. If the service crashes at that moment, or the broker is unreachable, the payment exists and the event does not, so nobody downstream ever learns. Publish first instead, and you get the mirror problem: an event for a payment that never committed.

@3
The fix is to write the event into an outbox table, in the same database transaction as the payment row, and to mint the event's id right there. One local commit covers both, and a separate relay moves rows to the broker afterwards.

@4-7
Four requests arrive, and each commits its payment row and its outbox row together, events e1 to e4. If a transaction fails, neither row exists and there is nothing to publish. The event is now exactly as durable as the business write.

@8
The relay reads the pending rows in id order, by polling or by tailing the write-ahead log with change data capture.

@9
For each row it publishes the event, then marks the row sent. E1 to e3 go out and are marked.

@10
It publishes e4, and the broker has it.

@11
Here is the catch. The relay crashes after publishing e4, but before marking it sent. The row still says pending, although the event is already in Kafka.

@12
On restart the relay sees e4 pending and publishes it a second time, then marks it. Kafka now holds e4 twice. The outbox gives at-least-once publication, never exactly once.

@13
So the consumer must be idempotent, and the thing it deduplicates on is the event id minted in that same local transaction. It receives e4 again, finds the id already processed, and skips it. Not a Kafka offset, which changes when the relay republishes: the second copy of e4 sits at a new offset with the same id.

@14
The cost of all this: an extra table, a relay to run, publish latency of one polling interval or the change data capture lag, and consumers that tolerate duplicates.
