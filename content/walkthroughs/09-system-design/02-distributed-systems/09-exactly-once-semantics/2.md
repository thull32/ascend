lesson: exactly-once-semantics
viz: The outbox makes the event as durable as the business write
frames: 13

@0
An order service, its Postgres database, a relay, and Kafka. The service must save its business row and publish an event about it, and both must happen or neither. Exactly once starts here, at the very first hop: if the event can be lost before it ever reaches the broker, nothing downstream can save you.

@1-2
The naive dual write. The order commits, then the service tries to publish, and the publish never arrives. If the service crashes at that moment, or the broker is unreachable, the order exists and the event does not, so nobody downstream ever learns. Publish first instead, and you get the mirror problem: an event for an order that never committed.

@3
The fix is to write the event into an outbox table, in the same database transaction as the order. One local commit covers both, and a separate relay moves rows to the broker afterwards.

@4-7
Four requests arrive, and each commits its order row and its outbox row together. If a transaction fails, neither row exists and there is nothing to publish. The event is now exactly as durable as the business write.

@8-10
The relay reads the pending rows, by polling or by tailing the write-ahead log with change data capture. It publishes them in id order, so Kafka now holds four events, and then marks the rows sent.

@11
Here is the catch. Suppose the relay crashes after publishing row 4, but before marking it sent. Row 4 is pending again, and on restart the relay publishes it a second time. The outbox gives at-least-once delivery, never exactly once.

@12
So consumers must be idempotent, and the thing they deduplicate on is the event's id, minted in that same local transaction. Not a Kafka offset, which changes when the relay republishes. The cost of all this: an extra table, a relay to run, publish latency of one polling interval, and consumers that tolerate duplicates.
