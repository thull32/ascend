@0
A producer, a spare replacement for it, and two brokers holding partition payments-0, with broker 1 as leader. This is Kafka's idempotent producer, and one idea carries it: every batch says who sent it and where it sits in that sender's sequence. A batch carries a producer ID, an epoch, and the sequence number of its first record, and the partition leader remembers, per producer, the last sequence and the last five batches it appended.

@1
On start the producer asks for an ID and gets producer ID 4001, epoch 0. Sequence numbers count records per partition, starting at 0.

@2
Batch B0 carries sequences 0 to 2. The producer ID is new and the batch starts at 0, so the leader appends it at offsets 100 to 102 and caches its range.

@3
B1, sequences 3 and 4, follows on: 3 is the last sequence plus one, so it is appended at 103 and 104. But the acknowledgement is lost on the way back.

@4
B2, sequences 5 to 7, was in flight alongside B1. It is appended at 105 to 107 and acknowledged. Up to five batches may be in flight at once.

@5
After the request timeout, the producer resends B1. Its range, 3 to 4, matches a cached batch, so the leader answers with the original offset, 103, and writes nothing. The retry that would have duplicated a payment is absorbed.

@6
Now broker 1 fails. B3, sequences 8 and 9, gets not leader or follower, but B4, sequence 10, reaches the new leader on broker 2, which rebuilt the producer state from the replicated log: the last sequence is 7. Ten is not 8, so B4 is rejected as out of order. A failed batch makes every later one fail its check, so nothing can overtake it.

@7
The client resends B3 and then B4, in sequence order. Eight follows 7, then 10 follows 9, and both are appended, at 108 to 110. Ordering survived the retries, and B1 was written once.

@8
The epoch exists for one scenario: the old producer is not dead, only paused. A replacement starts with the same transactional ID. It gets the same producer ID with the epoch bumped to 1, and the broker learns that epoch 0 is over.

@9
The old producer wakes up and sends with epoch 0. The leader checks the epoch first: 0 is lower than 1, so the batch is rejected as fenced. The zombie cannot write, even though nobody told it that it had been replaced.

@10
Now the scope, precisely. This removes the duplicates that one producer session's own retries create, on one partition. A producer restarted without a transactional ID gets a new producer ID, so its resend is a new record; so is the application calling send twice; and nothing downstream is covered.

@11
The cost is small: a few bytes per batch, a small cache per producer on each leader, and at most five requests in flight, so that a retried batch is still cached when it arrives. In return, retries can neither duplicate nor reorder. Exactly-once beyond one partition needs transactions, and beyond Kafka it needs idempotent sinks.
