@0
Kafka, a ledger consumer, and the ledger database. The table is the ledger, and its primary key is the event id. The one idea: the producer minted the event's id once, when the event was created in the outbox transaction, so every redelivery of that event carries the same id. That id is all the consumer needs to apply the event once.

@1
The first delivery of event b arrives.

@2
The consumer inserts the ledger row, a credit of 1,200 cents to account 2, with the event id as its primary key. One row inserted, and committed.

@3
Event b will arrive again. A relay that crashed before recording its progress republishes it, or a consumer that restarted before committing its offset reads it twice. With at-least-once delivery, duplicates are normal, not exceptional.

@4-5
The second delivery: the same event, with the same id. The insert hits the primary key and changes nothing, zero rows. The ledger still holds one row for event b.

@6-7
A third delivery goes exactly the same way: zero rows, still one row in the ledger.

@8
Three deliveries, one ledger row. The database's own unique constraint did the deduplication, inside the same transaction as the write. No separate dedupe store, no time window, no clock.

@9
The condition is that the id is minted once at the source and stays with the event through every retry and replay. An id generated by the consumer, or a new one per publish attempt, deduplicates nothing.
