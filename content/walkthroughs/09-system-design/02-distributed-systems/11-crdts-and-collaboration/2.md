@0
Three processes, P1, P2 and P3, each holding a vector of counters, one per process, all at zero. This is the machinery an MV-Register uses to tell a later write from a concurrent one. The rules: every event adds one to your own slot; a message carries your whole vector; a receiver takes the larger value slot by slot, then adds one to its own.

@1-3
P1 has a local event, 1, 0, 0, then sends a message carrying 2, 0, 0. P2 receives it, takes the maximum with its zeros, and bumps its own slot to reach 2, 1, 0. P2 now knows everything P1 knew.

@4
Meanwhile P3 has a local event of its own: 0, 0, 1. It has heard from nobody.

@5-6
P2 sends 2, 2, 0 back to P1, and P1 merges it into 3, 2, 0.

@7-9
P3 has another event, then sends 0, 0, 3 to P1. P1 merges and bumps its slot, reaching 4, 2, 3.

@10
Now compare. One event is before another when every slot is less than or equal, and they differ. P1's first event, 1, 0, 0, against its send, 2, 0, 0: the first precedes the second. If these were two writes to a register, the later one simply replaces the earlier.

@11
P1's first event, 1, 0, 0, against P3's first event, 0, 0, 1. Each is bigger in some slot, so neither happened before the other. They are concurrent. Here the two registers part ways. An MV-Register keeps both values as siblings, for the application or the user to resolve, as in Dynamo's shopping cart and Riak. An LWW-Register picks one by timestamp and silently drops the other, and with clock skew it can even drop a write that was causally later.

@12
The trade-off. Version vectors give exact causality and conflict detection, but they grow with the number of writers. Keying them by client makes them explode, which is why Riak moved to dotted version vectors. And detecting a conflict is only half the job: something still has to merge the siblings.
