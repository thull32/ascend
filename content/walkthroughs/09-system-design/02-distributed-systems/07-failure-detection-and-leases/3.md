@0
Two clients, A and B, a lock service, and the storage the lock protects. A distributed lock lets one client at a time touch the resource. Because a client can die while holding it, the lock is a lease with a time limit, and that expiry is where the trouble starts.

@1-2
A asks for the lock and gets it, with token 33 and a 10 second lease. A must renew or finish before then.

@3-4
B asks too, and is refused. B waits and retries. So far mutual exclusion works.

@5
Now A stops for 15 seconds. A stop-the-world garbage collection, a page fault to swap, a virtual machine being migrated, or just a slow network. A is not dead, only late, and it cannot tell.

@6
The lease expires. The lock service cannot tell a paused client from a dead one, and releasing the lock is the only way not to block forever.

@7-8
B acquires the lock with the next token, 34, and writes to storage. That is legitimate: B holds the lock.

@9
A wakes up. From its own point of view nothing happened: it acquired the lock, ran some code, and is about to write. It has no idea 15 seconds went by.

@10
Storage accepts A's write on top of B's. Two clients wrote under one lock, mutual exclusion is broken, and the file is corrupted. No choice of lease length fixes this, because a pause can always be longer.

@11
The fix is fencing tokens. The lock service hands out a strictly increasing token with each grant, every write carries its token, and storage remembers the highest one it has accepted.

@12
Replay the moment with fencing. A's late write arrives carrying its stale token, 33.

@13
Storage has already seen 34, so it rejects 33. The old holder is fenced off, and B's work is safe. Fencing puts the check on the resource, the only party that can actually enforce it. The resource must accept an equal token, since one holder writes many times, and reject anything lower.

@14
So ask what the lock is for. If it is for efficiency, to avoid duplicate work, a simple lock with a time limit is fine, and the occasional double run is harmless. If it is for correctness, you need a consensus-backed lock service and fencing tokens checked at every resource, and both add latency and complexity.
