@0
An app, a Bloom filter, and a store on disk. The filter is 16 bits, all zero, with 3 hash functions. It answers one question, have I seen this key, with one of two answers: definitely not, or probably yes. Never definitely yes. That one-sided answer is what makes it useful as a compact digest of a set of keys.

@1
Add k1. Its three hashes point at bits 7, 14 and 9, and those bits are set to 1.

@2-4
Add k2, setting bits 10, 11 and 0. Then k3, setting 13, 8 and 3. Then k7, setting 1, 4 and 15. Bits only ever get set; the array never shrinks, and the filter never forgets a key it was given.

@5-6
Query k1. Check bits 7, 14 and 9: all three are 1, so the answer is probably present. The filter can never miss a key it holds. There are no false negatives.

@7
Only now does the app pay for a disk read, and it finds the key.

@8-9
Query evt-100, which was never added. Its bits are 14, 5 and 12, and bit 5 is 0, so evt-100 is definitely absent, and the disk read is skipped. In anti-entropy, that same definite no is the useful answer: a replica sends a filter of its keys, the peer tests each of its own keys, and every definite no is a key the first replica certainly lacks, so it gets sent.

@10-11
Query evt-104, also never added. Its bits are 10, 9 and 0, and every one of them happens to have been set by other keys. That is a false positive. Here the app reads the disk and finds nothing, which is harmless. In anti-entropy, a false positive means a key the other replica lacks looks present, so it is not sent, and survives until the next round or a Merkle tree comparison.

@12
You cannot delete from a Bloom filter, because clearing a bit might erase another key's evidence and create a false negative. Counting filters, with a small counter per bit, or periodic rebuilds handle churn. And the false positive rate climbs as the filter fills, so size it for the final key count.

@13
The trade-off. A few bits per key buy a definite no for the great majority of misses, at the cost of a tunable false positive rate and no deletes. A million keys at a 1 percent false positive rate take about 1.2 megabytes, under 10 bits per key, in a single message.
