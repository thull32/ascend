@0
Two regions, Europe and the US, each with its own leader and its own client. Both leaders hold a document title at version 1. Each accepts writes locally, in about 2 milliseconds, and replicates them to the other asynchronously across a round trip of about 150 milliseconds. Users get local write latency. The price is conflicts, and this picture shows one being born.

@1
The European user edits the title to Draft A. The European leader applies it on top of version 1, making its version 2.

@2
It acknowledges in 2 milliseconds. No ocean crossing, and the write would survive even if the link to the other region were down.

@3
At the same moment, the US user edits the same title to Draft B. The US leader also applies it on top of version 1. Neither leader knows about the other's write yet.

@4
That is acknowledged locally too. There are now two different version 2s.

@5
The replication streams cross in flight.

@6
Each leader receives a write whose parent, version 1, it has already overwritten. That is a write conflict. There is no first write here, because the two leaders never shared an order.

@7
Both sides detect the conflict. A single-leader system never faces this, because the one leader puts every write in sequence. A multi-leader system has to resolve it deterministically, so that every leader converges on the same answer.

@8
The first resolution is last-writer-wins: keep the write with the higher timestamp everywhere. Both leaders now say Draft B. It converges, but Draft A was silently thrown away, a lost update, and clock skew decided who lost.

@9
The alternatives. Merge the values, as a CRDT or a text merge does. Keep both as siblings and let the application or the user choose, as Riak and Dynamo's shopping cart do. Or give each record a home leader, so that a given key never has two writers at all.

@10
With more than two leaders, the topology matters. All-to-all is fastest, but can deliver writes out of causal order, a reply arriving before its question. A star or a ring adds hops but keeps ordering simpler.

@11
So the trade is local write latency and surviving an outage between regions, against conflict handling, no linearizability, and subtle bugs in auto-increment keys and uniqueness constraints. Use multi-leader across regions or for offline clients, and avoid it inside one datacenter.
