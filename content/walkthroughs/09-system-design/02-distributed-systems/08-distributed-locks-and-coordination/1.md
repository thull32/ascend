@0
Two clients, A and B, a lock service, and a storage file the lock protects. The lock is a key with a time limit, a lease, so that a client that crashes while holding it cannot block everyone forever. Keep one question in mind as you watch: is this lock here for efficiency, or for correctness? The answer decides whether what follows matters.

@1-2
A asks for the lock and is granted it, with token 33 and a 10 second lease. A must renew or finish within those 10 seconds.

@3-4
B asks and is refused, so B waits and retries. Mutual exclusion is working.

@5
Then A stops for 15 seconds: a garbage collection pause, a page fault to swap, a virtual machine migration, or a slow network. A is not dead, only late, and nothing inside A can tell it so.

@6
The lease expires. The lock service cannot tell a paused client from a dead one, and releasing is the only way not to block forever.

@7-8
B acquires the lock with token 34 and writes to storage, quite legitimately.

@9
A resumes, believing it still holds the lock. From its point of view, it acquired the lock, ran some code, and is about to write.

@10
Storage accepts A's write on top of B's, and the file is corrupted. Two holders, one lock. No lease length prevents this, because a pause can always outlast it. And a stronger lock service does not help either, since the lock service did nothing wrong.

@11
The fix moves the check to the resource. Each grant carries a strictly increasing token, every write carries the token, and storage remembers the highest token it has accepted.

@12-13
Replay with fencing. A's late write carries 33. Storage has already seen 34, so it rejects the write, and B's work is safe.

@14
So ask first what the lock is for. For efficiency, skipping duplicate work, a single Redis key with a time limit is enough, and the rare double run is harmless. For correctness, you need a consensus-backed lease plus a fencing token checked by the resource, or better, a design that needs no lock at all, such as making the work idempotent.
