@0
An order service, its Postgres database, a relay, and Kafka. The service must do two things: save the order, and publish an event saying so. Both must happen, or neither. Two separate writes to two separate systems cannot promise that, and this picture shows why, then shows the fix.

@1
The naive dual write. First, the order commits in the database.

@2
Then the service publishes, and this publish never arrives. If the service crashes here, or the broker is unreachable, the order exists but the event never goes out, so billing and shipping never hear of it. Publishing first has the mirror problem: an event for an order that never committed.

@3
The fix: write the event into an outbox table, inside the same database transaction as the order. One local commit covers both, and a separate relay moves the rows to the broker afterwards.

@4-7
Four requests arrive. Each one commits its order row and its outbox row together, in a single transaction. If that transaction fails, neither row exists, and there is nothing to publish. The outbox table fills with four pending events.

@8
The relay polls the outbox for pending rows. It could instead tail the write-ahead log with change data capture, Debezium for example, and avoid polling entirely.

@9
It publishes each pending row in id order, and Kafka now holds four events. Order per aggregate is preserved if events are keyed by the aggregate's id.

@10
Then it marks the rows sent. Sent rows can be purged later.

@11
Now the failure mode. Suppose the relay crashes after publishing row 4, but before marking it sent. Row 4 is pending again, so on restart the relay publishes it a second time. The outbox gives at-least-once delivery, never exactly once, which is why each event carries a unique id for consumers to deduplicate on.

@12
The trade-off. Reliable publication using nothing but the database's own transaction, at the cost of an extra table, a relay to run, publish latency of one polling interval, and consumers that must tolerate duplicates.
