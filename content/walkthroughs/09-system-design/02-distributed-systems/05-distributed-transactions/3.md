@0
An order service, its Postgres database, a relay, Kafka, and a consumer downstream. The service must do two things: save the order, and publish an event saying so. Both must happen, or neither. Two separate writes to two separate systems cannot promise that, and this picture shows why, then shows the fix.

@1
The naive dual write. First, the order commits in the database.

@2
Then the service publishes, and this publish never arrives. If the service crashes here, or the broker is unreachable, the order exists but the event never goes out, so nothing downstream ever hears of it. Publishing first has the mirror problem: an event for an order that never committed.

@3
The fix: write the event into an outbox table, inside the same database transaction as the order, with an event id minted right there. One local commit covers both, and a separate relay moves the rows to the broker afterwards.

@4-7
Four requests arrive. Each one commits its order row and its outbox row together, in a single transaction: e1, e2, e3, e4. If a transaction fails, neither row exists, and there is nothing to publish. The outbox now holds four pending events, and the database readout says so: four orders, four pending.

@8
The relay reads the pending rows in id order. It could poll, as here, or tail the write-ahead log with change data capture and avoid polling entirely.

@9
For each row it publishes the event and then marks the row sent. E1 to e3 go out and are marked: Kafka holds three events, the outbox shows three sent and one pending.

@10
It publishes e4, and the broker has it.

@11
Now the failure mode. The relay crashes after publishing e4, but before marking it sent. The row still says pending, although the event is already in the broker.

@12
On restart, the relay finds e4 pending, publishes it again, and this time marks it. The broker now holds five events, with e4 twice. The outbox gives at-least-once publication, never exactly once.

@13
The consumer receives e4 a second time, finds that event id already processed, and skips it. That is why the event carries a unique id minted in the outbox transaction: deduplicating on it turns at-least-once publication into an effect that happens once.

@14
The trade-off. Reliable publication using nothing but the database's own transaction, at the cost of an extra table, a relay to run, publish latency of one polling interval or of the change data capture lag, and consumers that must tolerate duplicates.
