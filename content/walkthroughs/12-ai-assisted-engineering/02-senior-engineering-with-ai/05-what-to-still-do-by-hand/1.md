@0
Two threads and one shared counter, starting at 0. This is the bare mechanism under the quota bug in try consume, without the quota check: each thread increments the counter. The trap is that an increment is not one step. It is three: load the value into a private register, add 1, store it back. And the scheduler may switch threads between any two of them.

@1-3
First, one thread alone. T1 loads 0 into its register, adds 1, so its register holds 1 while the shared counter is still 0, then stores it. The counter is 1. Run without interruption, the increment is correct.

@4-5
Now both threads increment at the same time, and the scheduler interleaves their loads before either one stores. T1 loads 1. T2 loads 1. Both registers hold 1.

@6
Each adds 1 to its own copy. Both registers now hold 2, and the shared counter is still 1.

@7-8
T1 stores 2. Then T2 stores 2 as well. The counter stays at 2. T1's increment has been overwritten: a lost update.

@9
Three increments ran, so the answer should be 3, and it is 2. In try consume the same interleaving happens around the check: both threads read 9 exports used, both pass the check against the limit of 10, both write 10, and both exports run. The quota allowed 11 and the stored count says 10, so nothing downstream can even tell. Because the result depends on timing, single-threaded tests never interleave and cannot see it. The fix is to make the read, the check and the write one indivisible step: a lock, or an atomic operation. Tracing code precisely, instruction by instruction, is the core of verification, which is why it stays on the list of skills to keep doing by hand.
