@0
Two worker threads, A and B, and one shared count: how many exports user u1 has used today. The limit is 10, and u1 has used 9. Try consume does three things in order: read the count, check it against the limit, and write the count plus one. Two requests from u1 arrive at once, so both threads run try consume together. The trap is that the check and the write are separate steps, and the scheduler may switch threads between them.

@1
Thread A reads the count: 9.

@2
A checks whether 9 is at least 10. It is not, so A passes the check and is about to write.

@3
Before A writes, the scheduler switches threads. B reads the count, and it is still 9.

@4
B checks 9 against 10 and passes too. Same check, same value, same answer.

@5
B writes 9 plus 1, and the count is 10. The quota is now used up, but A has already passed its check.

@6
B returns true, and export B runs.

@7
A resumes and writes its own 9 plus 1: the count is 10 again. A computed that from a value that stopped being true the moment B wrote, so B's increment is lost.

@8
A returns true, and export A runs as well.

@9
Eleven exports against a limit of 10, and the stored count says 10, so nothing downstream can even tell. A single-threaded test never interleaves, so it passes every time. The fix is to make the read, the check and the write one indivisible step: a lock held across all three, or a single conditional update that the store performs atomically. Tracing code like this, step by step and thread by thread, is the core of verification, which is why it stays on the list of things to keep doing by hand.
