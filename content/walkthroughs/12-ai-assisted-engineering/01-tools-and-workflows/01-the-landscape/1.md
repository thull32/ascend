@0
Five boxes in a loop: the user's task, the model deciding, a tool running, the observation it returns, and a final answer. The task: how many open pull requests are older than 7 days? The agent has two tools, one that lists pull requests and one that returns today's date. Hold onto the division of labour, because it is the whole lesson: the model only decides; the harness executes.

@1
Iteration 1. The model reads the transcript, which so far is just the task, about 340 tokens, and decides it needs the list first. It does not run anything. It emits a structured tool call: list the pull requests whose state is open.

@2
The harness, not the model, executes that call. Tool results are the agent's only contact with reality, so this is where you validate arguments and sandbox side effects.

@3
The result comes back, 12 pull requests with their creation dates, and is appended to the transcript. From now on it is part of the context for every decision, so a verbose tool output is paid for again on every later iteration.

@4-6
Iteration 2. The prompt is now about 750 tokens. Older than 7 days needs today's date, so the model calls the date tool. The harness runs it, and the answer, September the 26th, 2026, is appended too.

@7
Iteration 3, about 1,210 tokens. With the dates and today both in context, the model works out the answer itself and stops: 4 open pull requests are older than 7 days, numbers 412, 418, 421 and 430. No tool call means the loop ends.

@8
Three model calls and two tool calls. Notice the prompt size at each call: 340, then 750, then 1,210, because the whole transcript is resent every time, so the total cost grows roughly with the square of the loop's length. That is why harnesses carry guards: an iteration cap, here 6, a token budget, timeouts on tools, and a human confirmation before anything irreversible. Swap these two tools for grep, edit file and run tests, and this is a coding agent.
