@0
When an operator's state outgrows memory, Flink and Kafka Streams keep it in RocksDB, an embedded log-structured merge tree on local disk. This picture shows that tree on its own: a client making puts, a write-ahead log, an in-memory memtable that holds four entries, a level of flushed files called L0, and a merged level, L1. Writes are collected in memory, flushed as immutable sorted files, and merged later. Keep your eye on the word immutable; it is what makes checkpoints cheap.

@1-2
Put a equals 1 and b equals 2. Each goes to the log, for crash safety, and into the sorted memtable, with no disk seek. Then c equals 3, and a equals 4. The overwrite just replaces a in memory: a 4, b 2, c 3.

@3-4
Put d equals 5, and the memtable is full. It is flushed in one sequential write as SST-1, a sorted, immutable file with a sparse index and a Bloom filter, and a fresh memtable takes over.

@5-6
Put b equals 9 and delete c. The delete is a tombstone in the memtable; SST-1 is never touched. Read c, and the memtable answers first: not found, even though SST-1 still holds c equals 3. The newest version wins.

@7
Read a. It is not in memory, so SST-1's Bloom filter is asked, says maybe, and one disk read returns a equals 4. This is the per-access cost the lesson warns about: unlike state on the heap, every read may serialise, and may touch disk.

@8
Two more puts fill the memtable again, and it flushes as SST-2: b 9, the tombstone for c, e 6 and f 7. Two files now overlap, so a read for b has to check SST-2 before SST-1.

@9-10
Compaction merges the two into one L1 file. Newer values win, so b is 9, and the tombstone removes c and then itself. A read for b now looks in exactly one file.

@11
The failure modes: compaction competes with foreground work and can fall behind, and then writes stall; tombstones must survive until the bottom level or deleted keys come back.

@12
Now the payoff for a stream processor. Files are never modified after they are written, so a checkpoint only has to upload the files created since the last checkpoint. SST-1 and SST-2 were written once; after compaction, only the new L1 file is new. That is incremental checkpointing, and it is why RocksDB is the default backend for large state.
