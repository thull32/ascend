@0
A client, a command handler, an event store, and a read model, all for one bank account, account 42. The source of truth here is not the balance. It is the ordered list of facts that produced the balance. Hold onto one sentence: state is a fold over the log. Start from nothing, apply each event in order, and you have the current state.

@1-2
The command open account arrives. The handler rebuilds the account by replaying its events, of which there are none, checks the rule, and appends event 1, account opened. The append carries an expected version: it only succeeds if the log is still at version 0, so a concurrent writer would make it fail and retry against fresh state. Balance: 0.

@3-4
Deposit 50. The handler replays one event, gets a balance of 0, and appends event 2, deposited 50. Balance: 50.

@5-6
Withdraw 20. Replay two events, balance 50, the withdrawal is allowed, and event 3 is appended. Balance: 30.

@7-8
Withdraw 100. Replay three events, balance 30, and 30 is less than 100, so the command is rejected and nothing is appended. Commands can fail. Events, once written, are facts, and cannot.

@9-12
Deposit 10 is valid, so event 4 makes the balance 40. Then close account, also valid, and event 5, account closed, leaves the balance at 40. The log now holds five events, and nobody has ever stored the number 40.

@13
A projector subscribes to the log and maintains a read model, here a plain balance column, at 40 as of event 5. It lags the store slightly, and it can be thrown away and rebuilt at any time.

@14
That is replay. Delete the read model, fold all five events again, and you get 40. Fold only events 1 and 2 and you get 50, the balance as it was at that moment. Audit, debugging and new views come for free, because no fact was ever overwritten. This is exactly the relationship between a Kafka changelog and a state store.

@15
The first cost: an account with a million events needs a million steps to load. Snapshots fix it: every 100 events, store the state with its version, and replay only what came after.

@16
The second cost: events are forever. A changed rule cannot rewrite history, only add a compensating event. Old event versions need upgrading as they are read. And a request to delete someone's data needs crypto-shredding: encrypt per user, then throw the key away.

@17
So you get a complete audit trail, time travel and cheap new read models, in exchange for reads that lag writes, snapshot and versioning machinery, and a model that is harder to reason about than a row you can update. Kappa's reprocessing is this same move at scale: rebuild a table by folding its log again, with a new function.
