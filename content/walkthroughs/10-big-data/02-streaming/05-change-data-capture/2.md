@0
An order service, Postgres holding an orders table and an outbox table, a relay, and Kafka. The service must do two things: save an order, and publish an event saying so. Both must happen, or neither. Two separate writes cannot promise that.

@1-2
Here is the naive version. The order commits, and then the service publishes. If it crashes in between, or the broker is unreachable, the order exists and the event never goes out, so billing and shipping never hear about it. Publishing first has the mirror problem: an event for an order that never committed.

@3
The fix: write the event as a row in an outbox table, in the same database transaction as the order. One local commit covers both, and a separate relay moves outbox rows to the broker later.

@4-7
Four requests arrive. Each one commits its order row and its outbox row together, and the outbox fills with order created 1, 2, 3 and 4, all pending. If any of those transactions had failed, neither row would exist, and there would be nothing to publish.

@8
The relay finds the pending rows. Here it polls the table; with change data capture, such as Debezium reading the log, there is no polling at all.

@9-10
The relay publishes the four events in id order, so Kafka now holds four events. Key them by order id and each order's events stay in order. Then it marks the rows sent, and they can be purged later.

@11
Now the failure mode. Suppose the relay had crashed after publishing row 4 but before marking it sent. Row 4 is still pending, so on restart the relay publishes it again. The outbox gives at least once delivery, never exactly once.

@12
That is the deal: reliable publication using nothing but the database's own transaction, for the price of an extra table, a relay to run, a little publish latency, and consumers that deduplicate by event id.
