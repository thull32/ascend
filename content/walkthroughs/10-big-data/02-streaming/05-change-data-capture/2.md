@0
An order service, Postgres holding an orders table and an outbox table, a CDC relay such as Debezium, Kafka, and a consumer downstream. The service must do two things: save an order, and publish an event saying so. Both must happen, or neither. Two separate writes cannot promise that.

@1-2
Here is the naive version. The order commits, and then the service publishes. If it crashes in between, or the broker is unreachable, the order exists and the event never goes out, so downstream never hears about it. Publishing first has the mirror problem: an event for an order that never committed.

@3
The fix: write the event as a row in an outbox table, in the same database transaction as the order, with an event id minted right there. One local commit covers both, and the relay moves outbox rows to the broker later.

@4-7
Four requests arrive. Each one commits its order row and its outbox row together, and the outbox fills with events e1 to e4, all pending. If any of those transactions had failed, neither row would exist, and there would be nothing to publish.

@8
The relay picks up the pending rows in id order. A polling relay would query the table; CDC reads the change from the write-ahead log instead, so there is no polling at all.

@9
For each row the relay publishes the event, then records it as sent: e1 to e3 go out and are marked.

@10
It publishes e4, and the consumer processes it.

@11
Now the failure mode. The relay crashes after publishing e4, before recording its progress. The row still says pending, although the event is already in Kafka.

@12
On restart the relay finds e4 pending and publishes it again. The outbox gives at least once publication, never exactly once: Kafka now holds e4 twice.

@13
The consumer receives e4 a second time, finds that event id already processed, and skips it. Deduplicating on the id minted in the outbox transaction is what turns at least once publication into an effect that happens once.

@14
That is the deal: reliable publication using nothing but the database's own transaction, for the price of an extra table, a relay to run, a little publish latency, and consumers that deduplicate by event id.
