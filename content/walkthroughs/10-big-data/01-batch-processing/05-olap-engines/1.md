@0
This is a log-structured merge tree, the pattern a ClickHouse part follows. On screen: a client, a write-ahead log, an in-memory memtable that holds four entries, a level of freshly flushed files called L0, and a merged level, L1. The idea in one sentence: writes are collected in memory, flushed as immutable sorted files, and merged later in the background. Every disk write is sequential; the price is that a read may have to look in several places.

@1-2
The client puts a equals 1 and b equals 2. Each put is appended to the log, for crash safety, and inserted into the sorted memtable. No disk seeks. Then c equals 3, and a equals 4. Overwriting a just replaces the value in memory, so the memtable holds a 4, b 2, c 3, while the log still has all four records.

@3
Put d equals 5, and the memtable is full: four of four.

@4
Flush. The memtable is written out in one sequential write as SST-1, an immutable sorted file holding a 4, b 2, c 3, d 5, with a sparse index and a Bloom filter. The log segment can now be dropped, and a fresh memtable takes new writes.

@5
New writes never touch SST-1. Put b equals 9, and delete c. A delete is just another write: a tombstone for c in the memtable. The real removal waits for a merge.

@6
Read c. The memtable is checked first, finds the tombstone, and answers not found, even though SST-1 still holds c equals 3. The newest version wins.

@7
Read a. It is not in the memtable, so the read goes to SST-1. Its Bloom filter says maybe, its index points at the right block, and one read returns a equals 4.

@8
Two more puts, e and f, fill the memtable and it flushes as SST-2: b 9, the c tombstone, e 6, f 7. Now two files overlap in key range; both hold b and c. A read for b has to check SST-2 before SST-1, and that read cost grows with every flush.

@9
Compaction: a background merge sort of the two files into one non-overlapping L1 file. Newer values win, so b is 9. The tombstone removes c equals 3, and since nothing older remains, the tombstone goes too. L1 holds a 4, b 9, d 5, e 6, f 7.

@10
Read b now: the memtable is empty, L0 is empty, and there is one file to look in. The merge paid a write cost once to make every later read cheaper.

@11
The failure modes. Merging competes with foreground work and can fall behind; then the small files pile up and writes have to stall. Tombstones must survive until they reach the bottom level, or deleted keys come back. And repeated writes to one key waste space until the next merge.

@12
Now read it as ClickHouse. Every insert creates an immutable sorted part, like the flush you just saw, and background merges combine parts the way compaction combined SST-1 and SST-2. That is why one-row inserts from hundreds of servers fail with too many parts: they create parts faster than merges can absorb them. Batch thousands of rows per insert, about once a second.
