@0
A router and three shards. The key space is cut into contiguous ranges: S1 owns A to I, S2 owns J to Q, S3 owns R to Z. The router keeps that range table, so finding a key is a binary search over the boundaries, with no hashing. Object stores partition their key space this way internally, and so do many databases.

@1-3
Keys arrive. Alice starts with A, so she goes to S1. Bob starts with B, S1 again. Hank starts with H, still inside A to I, so S1 again. Inside a shard the keys are stored in sorted order.

@4
Judy starts with J, which is the first letter of S2's range, so she goes to S2.

@5
Here is what range partitioning buys you. A query for every name between A and I touches exactly one shard and reads a contiguous run of sorted keys. That locality is the whole point.

@6
Now the same scheme with a different key: auto-increment order ids. S1 holds orders 1 to 1,000, S2 holds 1,001 to 2,000, and S3 holds everything from 2,001 up. Every new order id is the largest yet, so it always lands in the last range.

@7
So every insert, 3,001, 3,002, 3,003, goes to S3, which takes all of the writes while S1 and S2 take none. This is the hot tail. Adding more shards does not help, because a new shard receives nothing until the tail moves into its range. A timestamp at the start of a key does exactly the same thing.

@8
Two fixes. Split the hot range automatically as it grows and move half of it to another shard, which is what Bigtable, HBase and CockroachDB do. Or salt the key with a hash prefix, which spreads the writes but breaks cheap range scans.

@9
That is the trade. Range partitioning gives cheap range scans and sorted locality, but it needs a range table to maintain and rebalance, and it is exposed to hot spots on sequential or skewed keys. Hash partitioning is the mirror image. On an object store, S3 splits hot prefixes for you over time; until it has, a client that pushes past the per-prefix rate gets a slow-down error and has to back off.
