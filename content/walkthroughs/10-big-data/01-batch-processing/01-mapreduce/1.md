@0
A word count, run the MapReduce way. On screen is a master at the top, three mappers in the middle, two reducers at the bottom, and three lines of input: the cat sat, the dog sat, and the cat ran. Hold onto the contract, because it is the whole model. You write two functions, map and reduce. The framework splits the input, schedules the work, moves every pair with the same key to the same reducer, and re-runs anything that fails.

@1
The master hands out three map tasks, one split each. It prefers a worker that already holds that split on its own disk, because shipping a small program to the data is cheaper than shipping the data to the program.

@2
Each mapper calls map on its line and emits the word with a count of 1 for every word it sees. Mapper M1 emits the 1, cat 1, sat 1. Three pairs per mapper, nine in all. Map looks at one record at a time and remembers nothing, which is why the three mappers never need to talk to each other.

@3
Next, the combiner: the reduce function run locally on each mapper's output before anything crosses the network. If one line had said the twice, it would leave as a single pair, the 2. Here no line repeats a word, so the table is unchanged. The combiner is only allowed because adding is associative and commutative; it changes how many bytes carry the answer, never the answer.

@4
The shuffle begins with partitioning. Every pair goes to a reducer chosen by hashing its word, mod 2. The and ran go to R1. Cat, sat and dog go to R2. Whichever mapper produced a pair, all the values for one word end up in the same place.

@5
Now R1 pulls its partition from all three mappers' local disks, then merges and sorts by key. It ends up holding ran with one value, and the with three ones. This all-to-all transfer is the expensive part of every job.

@6
R2 fetches its partition the same way: cat with two ones, dog with one, sat with two. Three mappers times two reducers makes six fetches. Because map output sits on local disk between the stages, a reducer that dies can simply fetch again.

@7
Each reducer calls reduce once per key and writes one output file. The result: cat 2, dog 1, ran 1, sat 2, and the 3. Notice that R1 wrote the and ran, and R2 wrote the rest, so nothing is globally sorted across the two files.

@8
Now the failure the design exists for. Say M3 had died before finishing its map task. The master notices the missed heartbeat and re-runs the same split on M1. That is safe because map is deterministic, and its output is written to a temporary file and renamed only on completion, so a half-finished run leaves nothing behind.

@9
Two more ways a job goes slow. A straggler, one slow machine, holds up the end of the job, so the master runs backup copies of the last tasks and takes whichever finishes first. And key skew: one hot word sends most of the values to a single reducer, which finishes long after the rest.

@10
That is the trade. Writing every stage to disk gives simple, restartable fault tolerance on cheap hardware, but it makes iterative and multi-stage jobs slow. Spark keeps intermediate data in memory and recomputes a lost partition from its lineage instead. Faster, and it needs more care. Either way, the shuffle is where the time goes, so it is the first thing to look at in any slow job.
