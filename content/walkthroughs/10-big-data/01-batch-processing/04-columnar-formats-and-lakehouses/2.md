@0
This is multi-version concurrency control in a single database, shown on one row, and it is the idea a table format scales up to whole files. Instead of locking a row for readers, the database keeps several versions of it, and shows each transaction the versions that were committed when its snapshot was taken. The row is a balance of 100, created by transaction 5. The next transaction id will be 12.

@1-2
Transaction 1 begins and takes its snapshot: it will see everything committed before id 12, and nothing later, however long it runs. It reads the balance. The version was created by transaction 5, which is committed, so it is visible: 100. No lock is taken.

@3
Transaction 2, id 12, sets the balance to 80. Nothing is overwritten. A new version with value 80 is appended, created by 12, and the old version is marked as deleted by 12. Transaction 2 holds a row lock, but only against other writers.

@4-5
Transaction 1 reads again while transaction 2 is still open. It still sees 100. The new version was created by 12, which is not before 12, and is not even committed yet. A repeatable read, without waiting on anyone's lock.

@6
Transaction 2 commits. The version with 80 becomes visible to snapshots taken from now on.

@7-8
Transaction 3 starts after that commit and sees 80. Transaction 1 keeps seeing 100. Two open transactions see two different values of the same row, and both are correct for their snapshots. Transaction 1's snapshot is what keeps the old version alive.

@9-10
Now transaction 1 tries to write the row it read, setting it to 90. But the current version was changed by transaction 12, which committed after transaction 1's snapshot. First committer wins: transaction 1 is aborted with a could not serialize error, and retrying it is the application's job.

@11
A subtler failure, write skew, is described here but not drawn. Two transactions each read a row the other one writes, such as two doctors each going off call after seeing two on call, and both commit. Snapshot isolation does not stop it; only serializable isolation does.

@12
Transaction 1 is gone, and no live snapshot can see the old version any more, so it is garbage and vacuum reclaims it. Only the 80 remains. The failure mode is a long-running transaction, which pins every old version behind it, so tables bloat.

@13
Readers never wait, at the price of version storage and garbage collection. Now scale it up, as the lesson does. An Iceberg or Delta table does the same with whole files: a query pins one snapshot and reads exactly its files, a writer commits a new snapshot beside it, and old snapshots are removed by snapshot expiry, the table-scale vacuum. That is also why a deleted row stays readable through time travel until the snapshots that reference it expire.
