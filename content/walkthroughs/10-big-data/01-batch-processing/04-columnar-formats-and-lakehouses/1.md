@0
A reader, a Bloom filter, and the object store behind it. The filter is 16 bits, all zero, and 3 hash functions. It answers one question, have I seen this key, with one of two answers: definitely not, or probably yes. Never definitely yes. In a Parquet file what sits behind the filter is a column chunk, and the filter is what lets a reader skip it for a point lookup that min and max statistics cannot prune.

@1
Add the key evt-1. The three hashes give positions 14, 13 and 12, and those bits are set to 1. Bits only ever go from 0 to 1; the array never forgets.

@2-3
Now ask whether evt-1 is present. The filter checks the same three positions, 14, 13 and 12. All three are 1, so the answer is probably present. A key that was added always finds all its bits set, so there are no false negatives.

@4
Only now does the reader pay for a fetch from the object store, and it finds the key. Lookups so far: 1.

@5-6
Ask about evt-101. Its hashes land on 1, 2 and 15. Bit 1 is still 0, and if evt-101 had ever been added, bit 1 would be 1. So it is definitely absent, and the read is skipped entirely. This is the win: most lookups for missing values cost no read at all.

@7-8
Now evt-441, which was never added. Its hashes happen to land on 14, 13 and 12, exactly the bits evt-1 set. Every bit is 1, so the filter says probably yes, the reader fetches, and finds nothing. That is a false positive. Lookups are now 2. It never makes an answer wrong; it only costs one unnecessary read, and that cost is what you tune.

@9
Two caveats. You cannot delete from a Bloom filter, because clearing a bit might erase another key's evidence and create a false negative; counting filters or periodic rebuilds handle churn. And the false-positive rate climbs as the filter fills, so size it for the final number of keys. The rule of thumb on screen: about 10 bits per key with 7 hash functions gives roughly 1 percent.

@10
So a few bits per value buy a certain no for the vast majority of misses, at the price of a tunable false-positive rate and no deletes. In Parquet that means a lookup on a random, unclustered id can skip most column chunks instead of reading them all.
