@0
Seven tasks in a nightly pipeline. RO and RP load raw orders and raw payments. SO and SP are the staging models built from them. FR is the revenue fact table, which needs both staging models. DC is the customer dimension, which needs staged orders. And DB, the dashboard extract, needs both FR and DC. Each task is labelled with how many upstream tasks it is still waiting for. The orchestrator's rule is one sentence: a task becomes runnable when every task it depends on has succeeded, that is, when its count reaches zero. That is Kahn's algorithm for topological order. RO and RP wait for nothing, so both start in the ready queue.

@1-2
Take RO, position 1. Removing it drops staged orders, SO, from 1 to 0, so SO joins the queue.

@3-4
Take RP, position 2. Staged payments, SP, drops to 0 and joins the queue. In a real run RO and RP were ready together, so they could have run in parallel.

@5-6
Take SO, position 3. It feeds two tasks. FR drops from 2 to 1, still waiting on payments. DC drops to 0 and is ready.

@7-8
Take SP, position 4. Now FR's last dependency is done, so it drops to 0 and joins DC in the queue.

@9
Take DC, position 5. The dashboard extract, DB, drops from 2 to 1: it still needs FR.

@10-11
Take FR, position 6. DB drops to 0, the last task to become ready.

@12
Take DB, position 7. Every task has run, and none ran before its inputs existed.

@13
The order: RO, RP, SO, SP, DC, FR, DB. Computing it costs time proportional to the tasks plus the edges. Notice what the queue told you along the way: whenever two tasks sat in it together, such as SP and DC, or DC and FR, they had no dependency between them and could run at the same time. That is how an orchestrator fills its workers: tasks that are ready together run in parallel.
