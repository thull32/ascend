@0
This is the memory a serving engine has to manage, the KV cache, and how a paged allocator lays it out. Prefill runs the three prompt tokens, The cat sat, through the model and stores each token's key and value in every layer, then emits on. The allocator does not reserve one long region. It hands out fixed-size blocks, 2 tokens each here so that one fills quickly; vLLM's default is 16. Three tokens need 2 blocks, placed wherever GPU memory is free: the block table maps logical block 0 to physical block 7, and logical block 1 to physical block 2. Block 2 has one free slot.

@1
Decode step 1. The new token, on, computes its key and value, and they go into the free slot of the last block. No allocation. Attention follows the block table across all four cached pairs, wherever the blocks physically sit, and emits the.

@2
Decode step 2. The token the computes its pair, but every allocated block is full. Only now does the allocator take a new block, physical block 41, and append it to the block table. Attention follows the table across five pairs and emits mat. Memory grows a block at a time, exactly as fast as the sequence does.

@3
Five tokens in three blocks, and the only waste is the unfilled tail of the last block, one slot. A contiguous allocator would have reserved the maximum context for this sequence up front; in the lesson's example that wastes 75 percent of the reserved memory, where pages waste half of one percent. Pages also allow sharing: requests with the same prefix point their block tables at the same physical blocks, which is the in-GPU half of prefix caching.
