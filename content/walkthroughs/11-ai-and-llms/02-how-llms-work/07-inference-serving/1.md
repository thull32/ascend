@0
This is the memory a serving engine has to manage: the KV cache. Prefill runs the three prompt tokens, The cat sat, through the model in one pass and stores each token's key and value vectors in every layer. Three pairs, computed once and kept, because attention at every later step needs them.

@1
Decode step 1. Only the new token, on, runs through the layers. It appends one new key and value pair and attends over all four. The cache has grown by one token, and recomputing instead would already have cost 7 pairs against 4.

@2
Decode step 2: the new token, the, appends one more pair. Five cached, 12 without a cache.

@3
Decode step 3: mat appends another. Six cached, 18 without. The point for serving is the shape of this growth: one entry per token, per layer, for every active sequence, growing one step at a time to a length nobody knows in advance.

@4
In real numbers that is about half a megabyte per token for a 7-billion-class model in 16-bit without grouped-query attention, so a 4,000-token sequence holds about 2 gigabytes. That memory, not arithmetic, limits how many sequences one GPU can batch. These frames show the cache itself, not how it is laid out in memory. The layout is the lesson's next point: a naive allocator reserves room for the maximum length of every sequence and wastes most of it, while paged attention, introduced with vLLM, hands out fixed blocks of 16 tokens only as each sequence fills its last one, like virtual memory.
