Prefill: the prompt, here The cat sat, runs through the model in one pass, and every layer computes and stores a key and a value for every prompt token. Three pairs here. For the coach, the prompt is the persona, the curriculum map, the lesson, the editor contents and the conversation so far: thousands of tokens, all prefilled before the first word of the answer. This is the work prompt caching saves.

@1
Decode step 1. Only the new token, on, is computed. It adds one key and value pair and attends over all four. Within one generation, earlier tokens are never recomputed: 4 pairs, against 7 without the cache.

@2
Step 2 adds the: 5 pairs, against 12.

@3
Step 3 adds mat: 6 pairs, against 18. That is the cache inside one generation. Prompt caching keeps a prefix's keys and values across requests, so when the next request starts with a byte-identical prefix, the provider loads them instead of prefilling again. That cuts both the price of those tokens and the time to first token.

@4
The catch is the words byte-identical, in render order: tools, then system, then messages. The coach's first version put the editor contents before its only cache breakpoint, so a learner who edited code between questions missed the cache every time and paid the 1.25 times write premium on every turn, more than with caching off. The fix split the prompt: a stable block, persona and curriculum map, with its own breakpoint, then the volatile context after it. The general rule: stable content first, volatile content last, and check the cache-read counters in every response to prove it works.
