Prefill: request 1's prompt, here The cat sat, runs through the model in one pass, and every layer computes and stores a key and a value for every prompt token. Three pairs here. For the coach, the prompt is the persona, the curriculum map, the lesson, the editor contents and the conversation so far: thousands of tokens, all prefilled before the first word of the answer. The last position predicts the first output token, on.

@1
Decode step 1. Only on runs through the layers. It adds one key and value pair, four cached, and attends over all of them to emit the. Within one generation, earlier tokens are never recomputed.

@2
Step 2 does the same for the, five cached, and emits mat. That is the cache inside one generation.

@3
Request 1 ends with the reply, on the mat. Its working cache would normally be freed. Prompt caching keeps the prompt's three pairs as a cache entry for that exact prefix, about five minutes by default, refreshed on every hit.

@4
Request 2 resends everything: the prompt, the reply, and the learner's next message, nine tokens. Its first three are byte-identical to the cached prefix, so the provider loads those pairs instead of prefilling them.

@5
Prefill runs only over the six new tokens: six computed instead of nine. That cuts both the price of the cached tokens and the time to first token.

@6
The catch is the words byte-identical, in render order: tools, then system, then messages. The coach's first version put the editor contents before its only cache breakpoint, so a learner who edited code between questions missed the cache every time and paid the 1.25 times write premium on every turn, more than with caching off. The fix split the prompt: a stable block, persona and curriculum map, with its own breakpoint, then the volatile context after it. The general rule: stable content first, volatile content last, and check the cache-read counters in every response to prove it works.
