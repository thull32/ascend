@0
The tool-use loop in nine frames. The model reads the task and the transcript, and it only ever emits one of two things: text, or a structured call with typed arguments. Two tools are defined: list PRs, which takes a state, and today. The task: how many open pull requests are older than 7 days?

@1
Iteration 1. The model decides it needs the list first, and emits a structured call: list PRs, with state open. The prompt so far is about 340 tokens.

@2
The model does not run anything. The harness, your code, executes the call. This is the boundary to defend: validate the arguments here, and sandbox any side effects.

@3
The result is appended to the transcript: 12 pull requests with their creation dates. Every token of it is sent again on every later request, so the size of a tool result is a cost decision.

@4
Iteration 2. Older than 7 days needs today's date, so the model calls today. The prompt has grown to about 750 tokens, because the whole transcript is resent.

@5
The harness executes today.

@6
And appends the result: 26 September 2026.

@7
Iteration 3. With the dates and today's date in context, the model works out the answer itself and ends its turn: 4 open pull requests are older than 7 days, numbers 412, 418, 421 and 430. No tool call, so the loop ends. Note that the date comparison and the count were the model's own arithmetic. The lesson's advice applies: if date arithmetic must be right, give it a tool rather than trusting the model.

@8
Three model calls and two tool calls. By the last call the prompt has grown to about 1,210 tokens, and because each call resends the whole transcript, the three calls together processed about 2,300 input tokens. The loop needs guards: an iteration cap, here 6, a token budget, timeouts on tools, and human confirmation for anything irreversible. That resending is why cost grows roughly with the square of the number of iterations.
