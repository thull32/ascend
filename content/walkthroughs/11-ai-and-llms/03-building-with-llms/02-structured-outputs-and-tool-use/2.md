@0
The lesson's return question as a loop. The model reads the task and the transcript, and it only ever emits one of two things: text, or a structured call with typed arguments. Two tools are defined: get order, which takes an order id, and get return policy, which takes a country. The task: I'm in Germany, can I still return order 48213?

@1
Iteration 1. The harness sends the system prompt, the tool definitions and the question, 1,012 input tokens, and the model decides. It needs the order and the German return policy, and asks for both in one turn: two structured calls, get order for 48213 and get return policy for Germany.

@2
The model does not run anything. The harness, your code, decides what runs: two read tools, so both run. This is the boundary to defend: validate the arguments here, and sandbox any side effects.

@3
Both results are appended to the transcript: the order was delivered on 2 September and is electronics; the policy allows 30 days, but 14 for electronics. Every token of it is sent again on every later request, so the size of a tool result is a cost decision.

@4
Iteration 2. The harness resends the transcript, now 1,203 tokens. The delivery date, the 14-day rule and today's date from the system prompt are all in context, so the model answers without a tool call and the loop ends: unfortunately not; electronics bought in Germany can be returned within 14 days, and this order was delivered 18 days ago.

@5
Two model calls and two tool calls, about 2,215 input tokens across both calls, although the last one sent only 1,203: the transcript is resent every time, which is why cost grows roughly with the square of the number of iterations. One thing to notice: the 18 days was the model's own date arithmetic. If it must be right, give it a tool. And every later request in this conversation carries the whole transcript again.
