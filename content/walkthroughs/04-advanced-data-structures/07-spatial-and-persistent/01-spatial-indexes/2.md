@0
A geohash names a cell on the map with a short string, and each extra character names a smaller cell inside the last one. So geohashes fit a trie, and a prefix is a region. Watch seven cells go in, then a query for everything inside one region.

@1-4
Four cells around the Eiffel Tower: u09tunq, u09tunr, u09tunm and u09tunw. The first creates seven nodes. Each of the other three shares the first six characters, u09tun, and adds only one node. Neighbouring cells share a long prefix.

@5
u09tuq5 shares five characters, u09tu, and branches off one level higher. It is nearby, but in a different six-character cell.

@6-7
Now two cells on either side of the Greenwich meridian, just 208 metres apart: gcpuzgq and u10hb53. The first shares nothing with anything so far. The second shares only the u. These two neighbours share no prefix at all with each other, because the very first bit, longitude below or above zero, differs.

@8-14
The query: everything in cell u09tun. Walk the prefix one character at a time: u, 0, 9, t, u, n. Every key in the subtree below this node starts with u09tun, so every point in it lies inside that cell.

@15-20
Enumerate the subtree, children in sorted order, and the answer comes out in order: u09tunm, u09tunq, u09tunr and u09tunw. The cost is the prefix length plus the size of the subtree. In a database this is a single range scan on a sorted index.

@21
Enumerating a subtree costs its size, which is why production autocomplete caches the top few completions at each node. But the lesson for geohashes is the converse trap you saw with the meridian pair: a shared prefix means close, but close does not mean a shared prefix. So a radius search never scans one cell. It scans the cell containing the query plus its 8 neighbours.
