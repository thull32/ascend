@0
A Fenwick tree runs on one small trick: low bit of i, the value of the lowest set bit of i. It decides which block of elements each cell of the tree is responsible for. On screen are two four-bit rows. The top is 12, which is 1100. The bottom reads 0100, labelled 4. At four bits that is also exactly what minus 12 looks like in two's complement: negation flips every bit above the lowest set bit and keeps that bit itself. So 12 and minus 12 agree in one place only, the lowest set bit.

@1-5
AND keeps a bit only when both rows have it. Working from the right: bit 0, both zero, so zero. Bit 1, both zero, zero. Bit 2, both one, so one. Bit 3, 12 has a one but the bottom row does not, so zero.

@6
The result is 0100, which is 4. That is the low bit of 12. In a Fenwick tree it means cell 12 stores the sum of the four elements ending at position 12, positions 9 through 12.

@7-12
The visualisation goes on to the other two operators on the same rows. OR turns a bit on when either row has it, and the answer is 1100, 12 again: nothing changes, because the low bit was already set in 12.

@13-18
XOR turns a bit on when the rows differ. Bit 2 is one in both rows, so it switches off, and the result is 1000, which is 8. That is 12 with its lowest bit dropped, 12 minus 4.

@19
Both moves you just saw are the whole data structure. A prefix query subtracts the low bit to step left: a query that reaches cell 12 adds its block of four, then jumps to cell 8, which covers 1 through 8, and stops. An update adds the low bit to step up into the next block that contains it. Each step clears or carries one bit, so both loops run at most about log n times, and the hardware does each bitwise operation in a single instruction.
