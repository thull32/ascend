@0
Why does padding work? Because memory never moves one element at a time. Here an array of 64 elements is split into cache lines of 8, and the cache has room for 4 lines. The rule to hold: touching one element pulls in its whole line, all 7 neighbours with it. The line, not the variable, is the unit the hardware moves, and the unit that cores fight over.

@1
Read element 0. Its line is not cached, a miss, so all of line 0, elements 0 to 7, is fetched from main memory into slot 0. That costs about a hundred times a cache hit.

@2-8
But now elements 1 through 7 are free. Each read is a hit, served in a few cycles, because the first miss already brought them in.

@9-16
Element 8 starts a new line: one more miss fetches elements 8 to 15 into slot 1, and the next seven reads are all hits.

@17-18
Now jump ahead in strides of 8, one element per line. Element 16 is a miss that fetches line 2, and element 24 is a miss that fetches line 3. Each strided access lands on a new line, so each pays for a full line it barely uses.

@19-26
The cache is full, so from element 32 on, every strided read is a miss that also evicts the least recently used line: lines 0, 1, 2 and 3 are thrown out in turn to make room for lines 4 to 7.

@27
Twenty-two accesses: 14 hits and 8 misses. Sequential reads use every element of each line they fetch; strided reads pay a whole line per element. Locality, not element count, sets the cost. Now apply that to a ring buffer. Head and tail are two words, and if they share a line, the hardware cannot tell them apart: every write to one drags the whole line, and the other index with it, between cores. Put each index on its own line, and each core's writes invalidate only its own.
