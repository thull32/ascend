@0
The other engine. An LSM tree absorbs writes in memory and writes to disk only in large sequential runs, which are merged later. On screen: the write-ahead log, a memtable that holds four entries, a level of overlapping files, L0, and a merged level, L1. Keep the same two counts as for the B-tree: pages per read, and bytes per write.

@1-2
Put a equals 1, b equals 2, c equals 3, then a equals 4. Each is a log append and an insert into the sorted memtable. No page is read or rewritten; overwriting a just replaces it in memory.

@3-4
d equals 5 fills the memtable, and it is flushed as one sorted, immutable file, SST-1, in a single sequential write. In a real engine that flush is tens of megabytes, shared by a million rows. That is why the write path is so cheap.

@5-6
Put b equals 9 and delete c. SST-1 is never touched; the delete is just a tombstone in the memtable. A read for c finds the tombstone first and answers not found, even though SST-1 still holds c equals 3. That stale copy on disk is space amplification.

@7
A read for a misses the memtable, and goes to SST-1, where the Bloom filter says maybe and one block read returns a equals 4.

@8
Two more puts, e and f, and the memtable flushes as SST-2. The two L0 files overlap, both holding b and c, so a read for b must check both, newest first. Every flush adds a place to look. That is the LSM tree's read amplification.

@9-10
Compaction merges the two files into one non-overlapping L1 file: a 4, b 9, d 5, e 6, f 7. The newer b wins, and the tombstone cancels c and then disappears. Now a read for b touches one file. But compaction had to read and rewrite every byte it merged. In a real tree with five levels, that is about 36 times the original write, all of it large and sequential, and compaction reads as much as it writes, competing with your queries for disk bandwidth.

@11
When compaction falls behind, L0 piles up and writes stall. Tombstones must reach the bottom level, or deleted keys come back. And a burst of writes to one key wastes space until it is merged away.

@12
So with leveled compaction the LSM tree wins on space, about 1.1 times the live data, and keeps every write sequential, and pays in read cost: more places to look, rescued for point reads by Bloom filters, but not for range scans. The honest default: if your working set fits in memory and writes are not the bottleneck, use a B-tree. Reach for an LSM engine when write throughput per disk, storage cost or drive endurance is the constraint you are actually hitting.
