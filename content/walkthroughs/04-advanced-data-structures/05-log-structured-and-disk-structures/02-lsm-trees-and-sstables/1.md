@0
A log-structured merge tree, the engine inside RocksDB, Cassandra and most modern key-value stores. On screen: a write-ahead log, a memtable in memory that holds four entries, a level of sorted files called L0, and a merged level below it, L1. The bargain to hold onto: every disk write is sequential, and the price is that a read may have to look in several places.

@1-2
Put a equals 1 and b equals 2. Each put is appended to the log, for crash safety, and inserted into the memtable, a sorted structure in memory. No disk seeks. Then c equals 3, and a equals 4. Overwriting a just replaces the value in memory; the log still holds both records.

@3-4
Put d equals 5, and the memtable is full. It is flushed as one sorted, immutable file, SST-1, holding a 4, b 2, c 3, d 5, with a sparse index and a Bloom filter, in a single sequential write. The log segment can be dropped, and a fresh memtable takes new writes.

@5
Now put b equals 9, and delete c. Neither touches SST-1, because SST-1 never changes. The new b goes into the memtable, and the delete writes a tombstone for c. The real removal happens later.

@6
Read c. The memtable is checked first, and it holds the tombstone, so the answer is not found, even though SST-1 still contains c equals 3. The newest level always wins.

@7
Read a. It is not in the memtable, so the read goes to SST-1. Its Bloom filter says maybe, its index points at the right block, and one disk read returns a equals 4.

@8
Two more puts, e and f, fill the memtable, and it flushes as SST-2: b 9, the tombstone for c, e 6, f 7. Now the two L0 files overlap, since both hold b and c, so a read for b must check SST-2 before SST-1. Every flush adds another place to look. That is read amplification.

@9-10
Compaction fixes it in the background: a merge sort of the two files into one non-overlapping L1 file. Newer values win, so b is 9. The tombstone for c cancels c equals 3 and then disappears itself, because nothing older remains. What is left is a 4, b 9, d 5, e 6, f 7. Read b now: the memtable and L0 are empty, and one file answers. Compaction pays a write cost now to make every later read cheaper.

@11
Three things go wrong. Compaction competes with foreground disk traffic and can fall behind, and then L0 piles up and writes stall. Tombstones must survive until they reach the bottom level, or deleted keys come back to life. And a burst of writes to one key wastes space until compaction catches up.

@12
The trade: sequential writes, excellent write throughput and compression, with no in-place updates and no fragmentation. You pay with slower point reads and range scans, and a background compaction process that has to be tuned. The B-tree makes the opposite bet.
