@0
An LSM read cannot know which sorted file holds a key, so without help it would open every file. The help is a Bloom filter in front of each SSTable. Here is one: sixteen bits, three hash functions, sitting between the app and the file on disk. It answers definitely not, or probably yes, never definitely yes. A zero bit is proof of absence.

@1
The file holds the key evt-1. Its three hashes are 14, 13 and 12, so those bits are set.

@2-4
A read for evt-1 checks bits 14, 13 and 12. All are one: probably present. Only now does the read pay for a disk access, and it finds the key. A filter never says no to a key the file holds.

@5-6
A read for evt-100 hashes to 14, 5 and 12. Bit 5 is zero, so the file cannot hold it, and the disk read is skipped entirely. This is the case that matters for an LSM tree: a key that lives in one file is absent from all the others, and for each of those, the filter costs no disk read at all.

@7-8
A read for evt-441, which this file does not hold, hashes to 14, 13 and 12, the same bits evt-1 set. The filter says maybe, the read goes to disk, and finds nothing. A false positive: one wasted block read, harmless to correctness.

@9
Two caveats. Bits cannot be cleared, because clearing one might erase another key's evidence. That fits SSTables, which are never modified: each file gets its filter once, when it is written. And the false-positive rate climbs as a filter fills, so size it for the keys the file will actually hold.

@10
Here is the number to remember. With a 1 percent false-positive filter per file, a read that checks 30 files for a missing key costs about 0.3 wasted block reads on average, not 30. A few bits per key in memory buys definitely not here for nearly every file a read does not need.
