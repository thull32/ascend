@0
A client, a database engine with its buffer pool in memory, and two things on disk: an append-only log and the data files. The whole technique is one rule, so hold onto it: before you modify a data page, append a record describing the change to the log, and make that record durable. Durability comes from the log. The data files are allowed to lag behind.

@1-2
A transaction changes account 1 from 100 to 50. The engine does not touch the page yet. It appends a log record first, number 1 in the log sequence, still sitting in a memory buffer.

@3
Now fsync, and log record 1 is durable. That is one sequential write at the end of a file, which even a spinning disk does at hundreds of megabytes a second. The same change as random page writes would be about a hundred times slower.

@4
Only now is the page modified, page 7, in the buffer pool in memory. On disk, the data file still says 100. That is fine, because the log can rebuild the page.

@5
The client hears committed. The acknowledgement waits for the log record to be on disk, not the page, so commit latency is about one fsync, a tenth of a millisecond to a millisecond on a solid-state drive.

@6-7
A second transaction moves account 2 from 0 to 50. Logged as record 2, and synced. Pages 7 and 9 are now dirty in memory. Under load, many transactions committing together share one fsync, which is group commit: throughput rises while each commit still waits only one fsync.

@8
Then the power fails. The buffer pool is gone. The data files still say account 1 is 100 and account 2 is 0, yet both commits were acknowledged. But the log holds records 1 and 2.

@9-10
On restart, the engine reads the log forward from the last checkpoint, which here is the very beginning, and redoes records 1 and 2, rebuilding pages 7 and 9. Each page stores the sequence number of its last change, so replay skips anything already applied and is safe to repeat. Records from transactions that never committed are undone afterwards.

@11
A checkpoint flushes the dirty pages to the data files, and the checkpoint moves up to record 2. The log before it can be recycled, and recovery never has to read further back than the last checkpoint.

@12
The trade: every change is written twice, but the first write is sequential and batched, and the second is deferred and coalesced. Commit latency is fsync. Turn fsync off, or run on a disk that lies about it, and you lose acknowledged commits. Postgres, InnoDB, SQLite in WAL mode and RocksDB all work this way.
