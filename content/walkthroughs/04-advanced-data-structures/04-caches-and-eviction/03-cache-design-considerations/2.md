@0
Cache-aside, the most common caching pattern. The application owns all the logic: it reads the cache first, falls back to the database on a miss, and writes the result back itself. The cache never talks to the database. Keep one question in mind as you watch: what happens when a read and a write overlap?

@1-4
The read path. The app asks the cache, and misses: nothing has been loaded for this key yet, either because the cache is cold or because the entry expired. So the app falls through to the database, the source of truth, at about 5 milliseconds, and gets the row back.

@5-6
The app puts the row into the cache with a time to live. Only keys that are actually read get cached, so memory goes to hot data. The second read is a hit, served in about half a millisecond without touching the database.

@7-8
The write path. The app updates the database first, to version 2. Then it deletes the cache entry, rather than writing version 2 into it. A delete is idempotent, and two concurrent writers updating the cache could land in the opposite order from the database. A delete cannot.

@9
The next read misses, loads version 2 and fills the cache again. That is the cost of invalidating: every write buys one extra miss on the next read.

@10
And here is the classic race. Reader A misses and reads version 1 from the database, then stalls. Writer B updates the row to version 2 and deletes the key. Then A wakes up and writes its stale version 1 into the cache, where it stays until the time to live expires. Facebook's memcache paper fixed this with leases: a delete invalidates the reader's token, and a set with a stale token is rejected. The cheaper defence is a short time to live on every entry, which bounds the damage.

@11
The trade: cache-aside is simple and resilient, since a cache outage just means more database reads, but the cache and the database can briefly disagree. Choose the time to live from what the product can tolerate, not from a default.
