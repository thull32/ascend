@0
HyperLogLog counts distinct items by reading hashes from the most significant end. A good hash turns each distinct key into a random string of bits, and in a random string, half start with a 1, a quarter start with zero then 1, and at least r leading zeros turns up once in 2 to the power r. Each row here is an 8-bit hash. Count the zeros before the first 1, and keep the longest run you have seen, R.

@1
178 is 1 0 1 1 0 0 1 0. It starts with a 1: no leading zeros, the most common case, so the first 1 is at position 1 and R stays at 0.

@2-3
75 is 0 1 0 0 1 0 1 1: one leading zero, a one-in-two event, so R becomes 1. Then 41 is 0 0 1 0 1 0 0 1: two leading zeros, a one-in-four event, and R becomes 2.

@4
220 starts with a 1. Nothing new.

@5
75 again. A duplicate hashes to exactly the same bits, so it has the same single leading zero and cannot raise the maximum. This is the property a distinct count needs: repeats add nothing.

@6
23 is 0 0 0 1 0 1 1 1: three leading zeros, a one-in-eight event. R becomes 3.

@7-8
99 has one leading zero and 150 starts with a 1. Neither beats 3.

@9
The longest run is 3, so the estimate is about 2 to the 3, which is 8 distinct values; there were 7. That is the whole idea, and also its weakness: a single maximum is noisy, and one lucky hash with a long run of zeros inflates it enormously. So HyperLogLog routes each hash to one of many registers by its first few bits, keeps a maximum per register, and combines them with a harmonic mean.
