@0
An app on the left, a database on disk on the right, and between them a Bloom filter: sixteen bits, all zero, and three hash functions. The filter answers one question, have I seen this key? It can say definitely not, or probably yes, but never definitely yes. Hold onto the asymmetry, because it is the whole structure: a zero bit is proof of absence, and a one bit is not proof of anything.

@1
Add the key evt-1. The three hashes land on bits 14, 13 and 12, so those three bits are set to one. Bits only ever go from zero to one; the array never forgets.

@2-4
Now ask about evt-1. Check bits 14, 13 and 12. All three are one, so the answer is probably present. A key that was added can never be missed, because adding it set every bit the query checks. Only now does the app pay for a disk read, and it finds the key.

@5-6
Ask about evt-101. Its bits are 1, 2 and 15, and all three are zero. One would be enough: if evt-101 had ever been added, bit 1 would be one, so it is definitely absent, and the disk read is skipped entirely. This is the win: most lookups for missing keys cost no disk access at all.

@7-8
Now evt-441, which was never added. Its hashes happen to land on 14, 13 and 12, the very bits evt-1 set. All one, so the filter says probably yes, the app reads the disk, and finds nothing. That is a false positive. It is harmless for correctness, and it is the cost you tune away by giving the filter more bits per key.

@9
Two failure modes. You cannot delete: clearing a bit might erase another key's evidence and create a false negative, so churn needs a counting Bloom filter, with a small counter per bit, or a periodic rebuild. And the false-positive rate climbs as the filter fills, so size it for the final key count, not today's.

@10
The trade: a few bits per key in memory buys definitely not here for the vast majority of misses, at the price of a tunable false-positive rate and no deletes. That is why log-structured stores check a Bloom filter before every SSTable read, and why browsers, content delivery networks and databases use them the same way.
