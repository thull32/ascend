@0
A suffix array is an index: build it once, then answer each query with a binary search. To see why that is worth building, watch the alternative, which needs no index at all. Rabin-Karp searches the text bananabandana for the pattern ana. It hashes the pattern once, to 67, and then gives every three-letter window of the text a hash too. The trick that makes it fast: each window's hash is rolled from the previous one in constant time.

@1-2
Window 0, ban, hashes to 32. Not 67, so it is skipped without comparing a single character. Roll: drop the b, shift, add the next a. The new window hashes to 67.

@3-7
A hash match is only a candidate, because different strings can share a hash. So verify: a, n, a, all three agree. A genuine match at position 1.

@8-15
Roll on. Window 2, nan, hashes to 50 and is skipped. Window 3 rolls back to 67, is verified character by character, and is a second match, at position 3.

@16-27
Now a long run of skips: nab, aba, ban, and, nda, dan, with hashes 38, 99, 32, 70, 29 and 35. None is 67, so not one of those windows has its characters examined. Each costs a constant-time roll and a comparison of two numbers.

@28-33
The last window, ana, hashes to 67 again, is verified, and is the third match, at position 10.

@34
Three matches, at 1, 3 and 10, in expected time linear in the text plus the pattern. That is excellent for one query. But it is linear per query: every new pattern scans the whole text again. A suffix array costs n log n to build, and then each query is a binary search: about 30 probes per bound, even for a billion characters of text. Once the same text is queried thousands of times, the index pays for itself. That is the trade behind genome aligners such as BWA and Bowtie.
