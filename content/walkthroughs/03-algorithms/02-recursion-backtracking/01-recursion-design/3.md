@0
This is the call stack itself, for the lesson's fact of 4, whose base case is fact of 0. Main calls fact of 4, and its result slot still reads a question mark. Every call needs its own frame, holding its argument, the address to return to, and any locals.

@1
Fact of 4 cannot finish yet: it needs fact of 3 first. So a new frame is pushed. Inside it, n is 4, and the return address points back to main. That n stays parked in its frame while the call waits.

@2-4
The same thing three more times. Fact of 3 pushes a frame with n equal to 3, returning to fact of 4. Fact of 2 pushes one with n equal to 2. Fact of 1 pushes one with n equal to 1, and it still is not the base case, so it needs fact of 0. Each frame remembers its own n and who to hand its answer to.

@5
Fact of 0 is the base case: no further call, it will return 1. The stack is at its deepest: six frames, main plus five fact calls. That is the point of this picture. Recursion depth is memory that is live right now, and in most runtimes it comes from a fixed-size region.

@6-7
Fact of 0 returns 1. Its frame is popped, and the value lands in fact of 1, which resumes right after its call and multiplies by its own n: 1 times 1. Then fact of 1 returns 1 to fact of 2, which now shows 2 times 1 waiting to be computed.

@8-9
Fact of 2 returns 2, and fact of 3 computes 3 times 2. Fact of 3 returns 6, and fact of 4 computes 4 times 6. Each pop hands one value down to the frame below and wakes it up exactly where it left off.

@10
Fact of 4 returns 24, its frame is popped, and main's result slot now reads 24.

@11
Five fact frames were pushed and popped in last-in, first-out order, and the stack pointer is the only bookkeeping the machine needed. The catch is in the peak, six frames here, which grows with n. Ask for a large enough n and the stack runs out long before the answer arrives. A function whose depth grows with the input size is a latent crash; one whose depth grows like log n is safe for anything you can store.
