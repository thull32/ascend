@0
Six numbers: 3, 2, 1, 5, 6 and 4. This is ordinary quicksort with the Lomuto partition and the last element as pivot. Watch it with one question in mind: if we only wanted the element at sorted index 1, the second smallest, which of these steps would we actually need?

@1
The first partition covers the whole array, with pivot 4.

@2-4
3, 2 and 1 are each smaller than 4. They are already at the front, so each one joins the small region by swapping with itself.

@5-6
5 and 6 are not smaller, so they are left where they are.

@7
The pivot swaps into position 3. The array reads 3, 2, 1, 4, 6, 5. Neither side is sorted, but 4 is exactly where it belongs, and we now know the three smaller elements sit in positions 0 to 2. We want index 1, which is less than 3. Quickselect would throw the right side away right here.

@8-11
Quicksort carries on with the left side, positions 0 to 2, pivot 1. Neither 3 nor 2 is smaller, so the pivot lands at position 0. Index 1 is greater than 0, so quickselect would keep only positions 1 and 2.

@12-14
Positions 1 to 2, pivot 3. 2 is smaller, and 3 settles at position 2. Index 1 is now a range of one element, so quickselect would stop and return the 2 at position 1: three partitions over 6, then 3, then 2 elements.

@15-17
Everything from here is work quickselect never does. Quicksort goes back to the right side, positions 4 and 5, with pivot 5. 6 is larger, so 5 swaps into position 4.

@18
Sorted. Quicksort pays for both sides at every level, and over log n levels that is n log n. Quickselect pays for one side, and with a random pivot each surviving side shrinks geometrically, so the total is linear on average: about two passes over the data for an element near either end, and about three and a half for the median. That is the whole idea: the pivot lands at its final index, and only one side can contain the answer.
