@0
Seven numbers: 4, 2, 2, 8, 3, 3 and 1. Every one is a small whole number, no larger than 8. That one fact changes the game: instead of comparing elements, we can use each value as an index into an array of counts, one slot for every possible key from 0 to 8. All nine counts start at zero.

@1-4
Walk the input once. The first value is 4, so the count in slot 4 goes up to one. Then 2, and slot 2 goes to one; the next 2 bumps it to two. Then 8, and slot 8 becomes one.

@5-7
3 twice, so slot 3 reaches two, and finally 1 sets slot 1 to one. The histogram now reads: one 1, two 2s, two 3s, one 4, one 8. Not a single comparison so far.

@8-10
Now walk the counts in key order and write each key out as many times as it was counted. Slot 1 holds one, so 1 goes to position 0. Slot 2 holds two, so 2 goes to positions 1 and 2.

@11-12
Slot 3 holds two: 3 goes to positions 3 and 4.

@13-14
Slots 5, 6 and 7 are empty and contribute nothing. One 4 goes to position 5, and one 8 to position 6.

@15
Sorted: 1, 2, 2, 3, 3, 4, 8, with no comparisons at all. The cost is the length of the input plus the number of possible keys, here nine buckets, which is why counting sort escapes the n log n lower bound: that bound only applies to algorithms that learn about the input by comparing. The trap is the key range. Counting sort wants it to be about the size of the input; for 32-bit integers the counts array alone would be 16 gigabytes, which is the problem radix sort solves. And to sort records rather than bare numbers, stably, you turn the counts into starting positions and place each record in input order.
