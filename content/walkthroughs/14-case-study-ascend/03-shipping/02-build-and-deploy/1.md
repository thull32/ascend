@0
Ascend deploys by starting a new container, migrating, and switching traffic once it is ready. The lesson's point is the schema, and blue-green makes it easiest to see. Two identical environments: blue serves everything, green sits idle, and both share one database. Deploy to the idle one, test it, flip the router; to roll back, flip back. Hold onto this: both versions run against one schema, briefly during a switch and indefinitely after a rollback.

@1-2
Steady state: every request goes to blue, on version 1. Version 2 is deployed to green, and a failure there hurts nobody, because green is not in the path.

@3
The schema change ships first, as an expand step: add a nullable column, add a table, never rename or drop. Version 1 and version 2 must both be able to run against it.

@4
Green is verified in production with smoke tests and synthetic requests, on the same hardware and configuration as blue.

@5-6
The router flips, and all traffic moves to green at once. Requests in flight on blue drain rather than being killed. Users are on version 2 with no downtime, and blue is left running as it was.

@7
Then version 2's bug appears under real traffic, and the error rate climbs to 4 percent. Everyone is affected, because the switch was all or nothing.

@8
Rollback is the same flip in reverse: seconds, no rebuild. And it works only because the expand-only migration left the schema readable by version 1.

@9
What would have broken it: a migration that renamed or dropped a column version 1 reads. Rolled back, the old code would boot and then fail on every query that names it. And whatever version 2 wrote into its new column is invisible to version 1, so data from the green window may need reconciling. In Ascend this is exactly the rollback case: the previous binary boots against the newer schema, logs a warning, and starts without migrating, which is safe only under this rule.

@10-11
The fix ships as version 2.1 and is flipped in, and the colours alternate. Only when no version that needs the old shape can ever run again does the contract step drop the old column, in a separate deploy, often days later.

@12
Blue-green gives zero downtime and the fastest rollback, for double the capacity and all-at-once exposure. The rule it forces carries over to any deploy style: append-only migration files are necessary but not sufficient. Every migration must leave the schema usable by the previous release.
