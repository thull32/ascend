@0
The reference solution that took down a machine had a resize loop whose condition could never become false. This is the correct version, for contrast. A hash table starts with 2 buckets, chaining entries inside each bucket, and a load-factor bound of 0.75: whenever the number of entries divided by the number of buckets exceeds 0.75, the table doubles and every key is rehashed. Watch the one thing the broken loop got wrong: each resize changes the quantity the next check measures.

@1-2
Set a. Its hash is 97, and 97 mod 2 is 1, so it goes into bucket 1. One entry, two buckets: a load factor of 0.5.

@3-4
Set b. Hash 98, mod 2 is 0, so bucket 0. Now 2 entries in 2 buckets, a load factor of 1.

@5
That exceeds the bound: 2 is more than 0.75 times 2. So the table allocates 4 buckets. The hash values do not change; only the modulus does.

@6-7
Rehash b: 98 mod 4 is 2, so it moves from bucket 0 to bucket 2. Rehash a: 97 mod 4 is 1, so it stays in bucket 1.

@8
Both entries were recomputed and copied, one of them into a new bucket, and the load factor is back to 0.5. This is the step the runaway loop never had: the bucket count in the condition grew along with the array, so the check now passes.

@9-12
Set c: 99 mod 4 is 3, bucket 3, a load factor of 0.75, which is not over the bound. Set d: 100 mod 4 is 0, bucket 0. Four entries in 4 buckets, a load factor of 1.

@13
Over the bound again: 4 is more than 0.75 times 4. Allocate 8 buckets.

@14-17
Rehash all four with mod 8. d moves from bucket 0 to bucket 4. a stays in 1, b in 2, and c in 3.

@18
All four entries were recomputed and copied, though only d changed bucket. The load factor is 0.5 again, and the loop that grew the table has ended because its condition changed. Spread over the inserts that filled the table, each resize costs a constant amount per insert.

@19-20
Set e: 101 mod 8 is 5, bucket 5. Five keys, 8 buckets, a load factor of about 0.63, and no resize.

@21
Doubling keeps the load factor bounded, so lookups stay constant time on average, at the price of an occasional pause to rehash everything. The runaway version doubled the array every pass but tested a capacity it never updated, so each pass allocated twice as much as the last and reached gigabytes in under a second. And the lasting fix was not to the one solution: the validator was changed to put hard limits on itself before running anything.
