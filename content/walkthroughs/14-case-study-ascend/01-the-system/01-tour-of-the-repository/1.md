@0
This is the textbook web stack, not Ascend. Six boxes: a browser, a CDN edge, a load balancer, an API service, a Redis cache and a Postgres database. Step through it once, then map each box onto what Ascend actually runs, because the differences are the design decisions.

@1
Static assets come from the nearest CDN edge, out of its cache. The origin is never touched.

@2-3
A dynamic request for lessons reaches the load balancer, where encryption terminates, and goes to whichever stateless API instance has the fewest connections.

@4-5
The API checks the cache first, and misses: the key is not there yet.

@6-7
So it falls through to Postgres, about 5 milliseconds, which answers with 42 rows.

@8
The API stores the result in Redis with a 60 second time to live, so the next minute of reads skips the database.

@9
It responds, 200 OK with an entity tag. Roughly 1 millisecond at the balancer, 1 for the cache miss, 5 at the database, plus serialisation.

@10
The textbook scales by adding API instances behind the balancer, with the cache and the database as shared state. Now map it onto Ascend. The CDN is the browser's own cache plus content-hashed assets marked immutable for a year, while the page itself is never cached; for a single-region product that gets most of a CDN's benefit. The load balancer is Railway's edge, in front of one replica, or two with the phase 2 flag. And there is no Redis at all, because the hot data, the curriculum, is compiled into the binary. One binary, one database.
