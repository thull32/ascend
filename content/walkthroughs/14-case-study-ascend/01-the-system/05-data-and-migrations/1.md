@0
The browser, the Ascend API and Postgres, with an empty table of idempotency keys underneath. Today Ascend's comment endpoint is not idempotent: a double click or a retry inserts two comments, which is why the web client never retries a mutation. This is what it would take to make that retry safe. Hold onto one rule: the browser mints one key per intent, k1, and sends that same key on every retry, and one key produces the effect at most once.

@1
The first request arrives: POST to the comments endpoint, with k1 in its Idempotency-Key header.

@2
The API claims the key by inserting a row for k1 with a hash of the body. The key is the table's primary key, scoped to the caller, so only one insert can succeed, and only that request goes on to do the work.

@3-4
A second copy arrives while the first is still in progress: the double click. Its insert fails because k1 already exists, so the API answers 409, retry shortly, and does not insert a second comment.

@5
The first request finishes. Comment 812 and the key's saved response commit in one transaction, so there is never a comment without its key, or a key without its comment.

@6
The response is lost on the way back. The browser cannot tell whether the comment was posted.

@7-9
So it retries, with the same key. Without the key, the server would see a brand-new comment and insert it again. Instead it finds k1 done, with a matching body hash, and replays the saved response: 201, comment 812. Comments: still one.

@10
A client bug looks different: the same key with an edited text. The stored hash does not match, so the server answers 422 and does nothing, because the key names another request.

@11
The details: scope keys per user, keep them longer than any client keeps retrying, and decide what a failed attempt leaves behind.

@12
The cost is one extra write per request and a table of keys to expire. Ascend's progress PUT never needs this, because it is idempotent by construction; the comment POST would need it before any retry logic is added to the client.
