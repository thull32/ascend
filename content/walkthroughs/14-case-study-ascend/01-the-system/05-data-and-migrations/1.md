@0
Ascend's progress PUT is idempotent by construction: send it five times and you get the same row. Its POST endpoints for comments and submissions are not, so a retry inserts twice. This picture shows the general fix on a classic example, a payments API that must never charge twice: a client, the API, an idempotency store and a ledger. The rule: the same key produces the same effect exactly once, however many times it arrives.

@1
The client generates a key, k1, for this attempt, and sends it with a request to charge 20 dollars.

@2
The API finds no entry for k1, so it claims it atomically with a set-if-not-exists and marks it in progress. A concurrent duplicate cannot also start.

@3-4
The real work happens once: the ledger records one charge. Then the response is saved under k1 before it is sent, so a retry can be answered without redoing the work.

@5
The reply is lost: a timeout, a dropped connection, a crashed pod. The client cannot tell whether the charge happened.

@6-8
So it retries with the same key. The API finds k1 with its saved response and replays it without touching the ledger. Charges: still 1. At-least-once delivery plus an idempotent server gives an exactly-once effect.

@9
If a second copy arrives while the first is still in progress, the set-if-not-exists fails, and the API answers 409 Conflict, or waits, instead of charging twice.

@10
Different keys are different intents: k2 and k3 each charge once, for 3 charges in all. The key identifies the attempt, not the endpoint.

@11
The details that bite: scope keys per account, store a hash of the body so a reused key with a different payload is refused, and expire keys, here after 24 hours, but never before the client's retry window ends.

@12
The price is one extra round trip per request and a keyspace to expire. For Ascend it can be simpler still: a client-generated id per comment or submission, and a unique constraint on the user and that id, so a retry hits the constraint and gets the existing row back. Until then the web client does the safe thing and retries only queries, never a mutation.
