@0
System scenarios are written in a small language: declare some nodes, then send messages between them, and each message becomes one frame with its note. This one is the textbook read path: a browser, a CDN edge, a load balancer, an API service, a Redis cache and a Postgres database. The same renderer, log and variables panel draw every system scenario.

@1
One message: the browser fetches the app's JavaScript from the CDN edge, which serves it from cache.

@2-3
Two messages: the request for lessons reaches the load balancer, then a stateless API instance.

@4-5
The API asks the cache. Then a state change marks the cache as a miss, in red, and the cache's reply, nil, is the next message.

@6-7
The API falls through to the database, about 5 milliseconds, and the database answers with 42 rows.

@8
A state change and a message together: the cache now holds the lessons with a 60 second time to live, and the arrow shows the write that put them there.

@9
The response goes back to the browser, 200 OK with an entity tag.

@10
The last frame sets variables instead of sending a message: the next request is a cache hit in about a millisecond. That is what the language buys. Nobody draws arrows by hand, authors think in messages instead of coordinates, and because every scenario has the same state shape, one test can check every scenario at once, for example that every message goes between nodes that exist. That check matters, because the renderer silently skips an arrow whose endpoint is unknown.
