@0
JavaScript in a page runs on one thread, the same thread that paints the screen and handles clicks. On screen: that thread, two host threads for timers and the network, and three queues: the call stack, microtasks and macrotasks. The little program logs A, sets a zero-millisecond timer, starts a fetch, queues a promise callback, and logs B. The rule to watch: callbacks run only when the call stack is empty.

@1-3
Logging A runs at once. Setting the timer hands it to the host and returns; its callback is not queued yet, because even zero milliseconds means "after the current script". The fetch starts a request on the network thread and returns a pending promise, without blocking.

@4
The promise is already resolved, so its callback, m, goes into the microtask queue. Meanwhile the timer expires on the host, and its callback goes into the macrotask queue.

@5
Logging B runs. Nothing queued can run while the script is still on the stack.

@6-7
The script finishes, the stack empties, and the loop drains microtasks first: m runs and logs C.

@8
Then one macrotask: the timer callback runs and logs D.

@9-10
The response arrives, the fetch promise resolves, and its handler goes into the microtask queue and runs, logging E. The output is A, B, C, D, E.

@11
Now picture a learner's infinite loop running where the script ran. The stack never empties, so the timer callback that is supposed to stop it never gets to run, and the tab freezes. That is why Ascend runs learner code in a dedicated worker, a second thread with no access to the page, while the main thread stays responsive, keeps the clock, and terminates the worker when its time is up.
