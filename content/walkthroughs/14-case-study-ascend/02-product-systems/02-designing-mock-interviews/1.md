@0
The interview transcript lost entries because of a bug with a very old shape: load, modify, store, with no version check. This picture strips it to the bone. Two threads share one counter, and each wants to add 1. Adding 1 is really three steps, load the value into a private register, add 1 there, store it back, and the scheduler can switch threads between any two of them.

@1-3
First, one thread alone. T1 loads the counter, 0, adds 1 in its register, and stores 1. Run without interruption, the increment is correct.

@4-5
Now both threads increment at the same time, and their loads interleave before either one stores. Both read the counter as 1, so both registers hold 1.

@6
Each adds 1 to its own copy. Both registers now hold 2.

@7
T1 stores 2. So far, so good.

@8
Then T2 stores 2 as well, on top of it. The counter stays at 2, and T1's increment is gone: a lost update.

@9
Expected 3, got 2. Because the result depends on timing, code like this can pass every test and fail in production. Now map it back to the interview. The counter was the transcript, a JSON array in one row. Each streaming task had loaded its own snapshot of the row, appended its reply in memory, and written the whole array back. Whichever task wrote last won, and the other's entry vanished. The fix has the same shape as an atomic increment: append inside the database, in one statement, instead of rewriting the whole column from a stale copy.
