@0
Today the coach makes one model call per turn and has no tools. Give it tools and every turn becomes an agent: a model in a loop that reads the task and the history, decides on a tool call or a final answer, lets the harness run the tool, appends the result, and goes round again. The boxes on screen are that loop. One caution: the task on screen is a learner's question about a failing submission, but the tool calls and the answer in this run come from a generic example about open pull requests. Watch the mechanics and the token count, not the content.

@1
Iteration 1. The model reads the transcript and emits a structured tool call, a request to list open pull requests. The prompt so far is about 340 tokens.

@2-3
The harness, not the model, runs the tool. Tool results are the agent's only contact with reality, so this is where you validate arguments and sandbox side effects. The result, 12 items with their creation dates, is appended to the transcript, and everything in the transcript is context for every later decision.

@4-6
Iteration 2. The model needs today's date, so it calls a second tool. The prompt has grown to about 750 tokens, because the whole transcript, including the last tool's output, was sent again. The date comes back and is appended too.

@7
Iteration 3. With everything in context, the model answers instead of calling a tool, and no tool call means the loop ends. The prompt this time was about 1,210 tokens.

@8
Three model calls, two tool calls, roughly 1,210 prompt tokens, and the cost grows roughly with the square of the loop's length, because the transcript is resent every time. That is why a per-request budget like Ascend's undercounts an agent: you budget per iteration, and you cap iterations, here at 6, alongside a token budget, timeouts on tools, and human confirmation for anything irreversible.
