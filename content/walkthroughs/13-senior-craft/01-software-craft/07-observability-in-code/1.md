@0
One request, two processes: a submission goes from the browser through an edge proxy to the Ascend API, which calls the grading service, and both report to Jaeger. Hold onto one idea: a trace is a tree of spans joined by a single trace ID, so the slow part of a request is something you see, not something you infer.

@1
The browser submits code for grading.

@2
The API's tracing layer opens the request span. It never extracts an incoming traceparent header, so the trace starts here: request is the root span, and it carries a new trace ID.

@3
The API asks the grading service to run the tests. The propagator writes the current span's context into the traceparent header: version, trace ID, parent span and the sampled flag. Ascend creates no separate client span, so the header names the request span as the parent.

@4
The grading service extracts the header and runs the job in a grade span whose parent is the API's request span. Same trace ID, second process. The sampled flag came along too, so the grader keeps its span exactly when the API sampled the request.

@5-6
The verdict comes back to the API. A retry to another grading replica would carry the same header, and a test checks that it does. Then the response goes back to the browser.

@7
Both processes export their spans to Jaeger over OTLP, and Jaeger joins them into one tree: request, with grade inside it. How much of the request was spent grading is now a picture, not a guess.

@8
The limit, stated honestly: inside the API there is still only the one span, because no function carries a tracing instrument attribute yet. A slow trace shows the total, not the query that caused it. Each extra span is one attribute away, and every hop that forwards the header keeps the tree in one piece.
