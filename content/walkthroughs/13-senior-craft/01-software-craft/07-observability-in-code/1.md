@0
A trace is a tree of spans, each with a start, a duration, attributes and a parent, and the spans for one request share a single trace id. This picture does not draw the spans themselves. It draws the hops of one typical read path: a browser, a CDN edge, a load balancer, an API service, a Redis cache and a Postgres database. As each arrow appears, imagine a span opening for it.

@1
The first hop never reaches your servers. The browser fetches the app's JavaScript, and the nearest CDN edge serves it from its cache.

@2-3
Now a dynamic request for the lessons. The load balancer terminates encryption and passes it to whichever API instance has the fewest connections; the instances are stateless, so any will do.

@4-5
The API checks the cache first, and misses: the key is not there yet.

@6-7
So it falls through to Postgres, about 5 milliseconds, and gets 42 rows back.

@8
It writes those rows into the cache with a 60 second time to live, so the next minute of reads skips the database.

@9
And it responds. The total is roughly 1 millisecond at the balancer, 1 for the cache miss, 5 at the database, plus serialisation. Without a trace that sum is a guess. With one, each of those numbers is the duration of its own span, and the slow hop is visible instead of inferred.

@10
The next request is a cache hit in about a millisecond. Two questions follow any path like this: what happens when the cache is down, and what happens when the database is slow. A trace answers the second one on sight, but only for the hops that have spans: a single span around the whole request shows you the total, never the query.
