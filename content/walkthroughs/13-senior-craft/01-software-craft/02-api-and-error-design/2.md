@0
Your error contract matters on the other side of the wire too. Here a checkout service calls a payments API through a circuit breaker: a proxy with three states. Closed passes calls through and counts failures. After 3 consecutive failures it opens and fails every call instantly. After 5 seconds it goes half-open and lets a single trial call decide what happens next. Which responses count as failures is decided by the error taxonomy.

@1
Normal operation. The breaker is closed, call 1 returns 200 OK in 40 milliseconds, and the success keeps the failure count at zero.

@2
Call 2 comes back 400: the request itself was invalid. A 400 says the caller is wrong and the dependency is fine, so the breaker does not count it, and the count stays at 0 of 3. If it did count client errors, one buggy client sending invalid requests could open the breaker for every other caller.

@3
Then the payments API starts timing out. Call 3 holds a checkout request for the full 2 second timeout before failing: a timeout counts, failure 1 of 3.

@4
Call 4 gets a 503. A server error says the dependency is failing, so it counts too: failure 2 of 3. The contract, 400s mean fix your request and 500s mean try later, is exactly what tells the breaker which is which.

@5
Call 5 times out as well. That is the third failure, the threshold is reached, and the breaker trips open.

@6
Now call 6 is rejected with a 503 in under a millisecond, without touching the dependency. A slow failure has become a fast one, and checkout is free to serve its fallback: try again later, a cached quote, or payment pending.

@7
Over the next 5 seconds the breaker sheds calls 7 to 21, 15 more, the same way. The payments API gets quiet time to recover instead of a queue of retries.

@8-9
The 5 seconds elapse, and the breaker goes half-open, allowing exactly one trial. The trial, call 22, times out: the dependency is still sick. Back to open for another 5 seconds. Many implementations back that timeout off exponentially.

@10-11
Meanwhile the dependency recovers. Five seconds later the breaker is half-open again, and this time the trial, call 23, returns 200 OK in 45 milliseconds. The breaker closes and resets its count. The outage cost two probe calls, one failed and one successful, instead of 15 more waits for a timeout.

@12
Three ways breakers go wrong. A raw count lets one flaky call trip it too often, so use a failure rate over a sliding window with a minimum volume. One breaker shared across unrelated endpoints lets a broken refund endpoint take down charges. And a breaker with no fallback still fails the user, just faster.

@13
So the taxonomy is part of the contract's caller side: timeouts and 500s are failures that should open the breaker, 400s are not. The breaker gives up the few calls that might have succeeded while it is open, and in exchange makes failure explicit and fast, which is what keeps the rest of the system up.
