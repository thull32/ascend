@0
A client, a payments API, an idempotency store and a ledger. The problem is one every network has: a reply can be lost after the server has already done the work, and the client cannot tell "never arrived" from "succeeded, reply lost". So it retries. The rule that makes the retry safe: the same key produces the same effect exactly once, however many times it arrives.

@1
The client generates a key, k1, for this attempt, and sends it with a request to charge 20 dollars.

@2
The API checks the store. There is no entry, so it claims k1 atomically, with a set-if-not-exists, and marks it in progress. A concurrent duplicate cannot also start processing.

@3
The real work happens once: the ledger records one 20 dollar charge.

@4
Before replying, the API saves the response under k1: 201 Created, with the charge's id. That saved response is what will answer any retry.

@5
Now the reply is sent, and lost. A timeout, a dropped connection, a crashed pod. From the client's side, it has no idea whether the card was charged.

@6
So it retries, with the same key. Without a key, this would be a second 20 dollar charge.

@7-8
The API finds k1 in the store with a saved response, and replays it without touching the ledger. Charges: still 1. At-least-once delivery plus an idempotent server gives you an exactly-once effect.

@9
A different race: a second copy of the request arrives while the first is still in progress. The set-if-not-exists fails, so the API answers 409 Conflict, or waits for the first to finish, rather than charging twice.

@10
Different keys mean different intents. Keys k2 and k3 each charge once, so the ledger now holds 3 charges and the store 3 keys. The key identifies the attempt, not the endpoint.

@11
Three details bite in practice. Scope keys per account, so one caller cannot collide with or replay another's. Store a hash of the request body, so a reused key with a different body is refused with a 422. And expire keys, here after 24 hours, but never before the client's retry window ends: a retry that arrives after its key has expired is treated as new, and charges again.

@12
The cost is one extra store round trip per request and a keyspace to expire. In exchange, retries are safe at every layer. Stripe, Adyen and most payment APIs require a key, and anything with side effects should offer one.
