@0
A client, a payments API and its Postgres database, with the idempotency key table empty. The problem is one every network has: a reply can be lost after the server has already done the work, and the client cannot tell "never arrived" from "succeeded, reply lost". So it retries. The rule that makes the retry safe: the client mints one key for the operation, k1, and sends that same key on every retry, and one key produces the effect at most once.

@1
The first request arrives: POST payments for 20 dollars, with k1 in its Idempotency-Key header.

@2
The API claims the key by inserting a row for k1 with a hash of the body, marked in progress. The key is the table's primary key, scoped to the caller, so only one insert can succeed, and only that request goes on to do the work.

@3-4
A second copy arrives while the first is still in progress: a double click, or a client that gave up early. Its insert fails because k1 already exists, so the API answers 409, retry shortly, and does nothing a second time.

@5
The first request finishes. The charge and the key's saved response commit in one transaction, which is the detail the lesson insists on. Had the process died before the commit, neither would exist, and a retry would simply run again.

@6
Now the reply is sent, and lost. A timeout, a dropped connection, a crashed load balancer. The client has no idea whether the card was charged.

@7-9
So it retries, with the same key. Without the key, the server could not tell this from a new payment and would charge again. Instead it finds k1 done, with a matching body hash, and replays the saved response byte for byte. Charges: still 1. At-least-once delivery plus an idempotent server gives you an exactly-once effect.

@10
A client bug looks different: the same key with a different body, 30 dollars instead of 20. The stored hash does not match, so the server answers 422 and does nothing. The key names another request.

@11
Details that bite. Scope keys per caller, so one client cannot replay another's response. Keep keys longer than any client retries, Stripe says at least 24 hours, because a retry after its key expires is treated as new and charges again. And decide what a failed attempt leaves behind: release the key, or store the failure and replay it.

@12
The cost is one extra write per request and a table of keys to expire. In exchange, retries are safe at every layer. And the key belongs to the operation, not the attempt: a fresh key per retry would deduplicate nothing.
