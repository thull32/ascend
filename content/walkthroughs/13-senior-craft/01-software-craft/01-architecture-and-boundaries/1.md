@0
This is a typical read path, drawn as six boxes: a browser on the left, a CDN edge above it, a load balancer, an API service, and two stores on the right, a Redis cache and a Postgres database. Every arrow you are about to see crosses a boundary, and each side of each boundary speaks its own vocabulary.

@1
First, a static asset. The browser asks for the app's JavaScript bundle, and the nearest CDN edge serves it from its own cache. The origin is never touched.

@2-3
Now a dynamic request for the list of lessons. It reaches the load balancer, which is where encryption terminates, and the balancer hands it to a healthy API instance, the one with the fewest open connections. The instances keep no state of their own, so any one of them will do.

@4-5
The API checks the cache first. That is cache-aside: the application, not the cache, decides what to load. The key is not there yet, so Redis answers with nothing, and the cache box turns red with a miss.

@6-7
So the request falls through to Postgres, which takes about 5 milliseconds and answers with 42 rows.

@8
Before replying, the API writes those rows into the cache with a time to live of 60 seconds, so for the next minute this read never touches the database.

@9
Then it responds: 200 OK, with an entity tag the browser can use to revalidate later. The total is roughly 1 millisecond at the balancer, 1 for the cache miss, 5 at the database, plus the time to serialise the answer.

@10
The next identical request is a cache hit in about a millisecond. To scale, you add API instances behind the balancer; the cache and the database are the shared state. Two questions belong in any design review of a path like this: what happens when the cache is down, where you degrade to the database behind a circuit breaker, and what happens when the database is slow, where you need timeouts and load shedding. Each box is a place to draw a boundary, and each boundary is a place to decide what fails, and how.
