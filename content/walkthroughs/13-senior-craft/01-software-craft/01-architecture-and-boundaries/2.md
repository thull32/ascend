@0
An order service has to do two things for every order: write the order to its database, and publish an event so billing and shipping hear about it. Both must happen, or neither. On screen are the service, Postgres, a relay, Kafka and a consumer, with an empty outbox table underneath. Hold onto one fact: two separate writes can never promise "both or neither".

@1
Here is the naive version, the dual write. First the order commits in Postgres.

@2
Then the service publishes the event, and that arrow is dashed red, because this is the gap. If the service crashes here, or the broker is unreachable, the order exists and the event never goes out, so downstream never learns. Publishing first has the mirror problem: an event for an order that never committed.

@3
The fix is to stop making two writes. The event goes into an outbox table in the same database transaction as the business row, with an event id minted right there. One local commit covers both, and a separate relay moves rows to the broker afterwards.

@4-7
Watch four requests. Each one begins a transaction, inserts the order and its outbox row, and commits. If a transaction fails, neither row exists, so there is nothing to publish. After the fourth, Postgres holds 4 orders and the outbox holds 4 pending events, while Kafka still has none.

@8
The relay polls the outbox for pending rows. It could instead tail the write-ahead log with change data capture, Debezium for example, which avoids polling entirely.

@9
For each pending row, in id order, it publishes the event and then marks the row sent: e1 to e3 go out and are marked. Ordering per order is preserved if you key each event by the order's id.

@10
It publishes e4, and the consumer processes it.

@11
Now the failure the outbox does not remove. The relay crashes after publishing e4 but before marking it sent. The row still says pending, although the event is already in Kafka.

@12
On restart the relay finds e4 pending and publishes it a second time. The outbox gives at-least-once delivery, never exactly-once: Kafka now holds e4 twice.

@13
The consumer receives e4 again, finds that event id already processed, and skips it. Deduplicating on the id minted in the outbox transaction is what makes the effect happen once.

@14
So the trade is reliable publication using nothing but the database's own transaction. The price is an extra table, a relay to run, publish latency of one polling interval or the capture lag, and consumers that must be idempotent. The boundary has moved, not vanished: "at least once, eventually" is now part of the contract.
