@0
On screen is one bucket, for one client, in front of an API. The bucket holds at most 5 tokens and gains 1 every second. A request takes a token; if none is left, it is rejected. Two numbers, two jobs: capacity sets the largest burst, and the refill rate sets the sustained rate.

@1-5
At time zero the client fires a burst. Request 1 takes a token and is forwarded, leaving 4. Requests 2, 3, 4 and 5 do the same, and the bucket drains to zero. Five requests were served in a single instant, which is exactly the burst the capacity allows.

@6-7
Requests 6 and 7 arrive in that same instant, and the bucket is empty. Each is rejected with a 429 and a Retry-After hint. The client, not the API, pays for the overload.

@8
Two seconds later, 2 tokens have refilled. Request 8 takes one and is forwarded, leaving 1.

@9-10
At three seconds another token has arrived, so there are 2 again. Requests 9 and 10 both go through, and the bucket is empty once more. Tally: 8 accepted, 2 rejected.

@11
Sizing is the failure mode. Too large a capacity lets a client dump 5 times the sustained rate on the API in one instant, and everything downstream must absorb it. Too small rejects legitimate bursts, like a page that fires several API calls at once.

@12
The token bucket allows bursts up to capacity while enforcing an average rate, needs only two numbers per client, the token count and the last refill time, and is what most API gateways implement. A leaky bucket, by contrast, forbids bursts and smooths the output. The title's point is the key the bucket hangs from, which this run does not show: in practice there is one bucket per key, an address, an account, a device or a session, and choosing that key is the real decision. Password attempts get a small bucket, general browsing a large one.
