@0
A limiter in front of an API, and the idea that matters is in the title: there is not one bucket but one per key, an IP, an account, a device or a session. Here the key is an email address, and the limit is the lesson's password-reset rule, 3 emails per hour: each bucket holds at most 3 tokens and regains one every 20 minutes. A request spends a token from its own key's bucket, and from no one else's.

@1
The first reset request for Ada's address arrives. There is no bucket for that key yet, so one is created full, with 3 tokens. The request takes one and goes through, leaving 2.

@2-3
Two more requests for Ada's address in the same minute take the next two tokens. Her bucket is now empty.

@4
A fourth request for Ada's address is rejected with a 429, and the Retry-After says 20 minutes, when her next token arrives. Whoever is flooding that inbox has been stopped after three emails.

@5
In the same instant, a reset request for Bob's address arrives. It finds no bucket, so Bob gets his own, full, with 3 tokens, and the request goes through. Ada's empty bucket made no difference to him.

@6
Twenty minutes later, Ada's bucket has earned back one token, and her next request takes it and goes through. Keyed or not, the refill rate is still the sustained rate for each key.

@7
That is the whole point: one key exhausting its bucket never touches another key's. Choosing the key is the real decision. Per IP punishes a class or an office behind one NAT address; per account or per email address stops someone hammering one target from many addresses. And because each key needs only two numbers, idle keys can be expired.

@8
The token bucket allows bursts up to capacity while enforcing an average rate, costs two numbers per key, the tokens and the last refill time, and is what most API gateways implement; a leaky bucket, by contrast, forbids bursts and smooths the output. The sizes follow the risk: password attempts get a small bucket, and general browsing a large one.
