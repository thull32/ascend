@0
A canary release sends a small slice of real traffic to the new version, compares its metrics with the stable version serving everyone else at the same time, and only then widens the slice. Like the canary in the coal mine, it fails first, and few are exposed. On screen: a load balancer, nine stable instances on version 1 with a 0.1 percent error rate, one canary slot, and a metrics box that does the comparing. The gate: the canary's error rate and 99th percentile latency must stay within 1 percent of stable's, with automatic rollback on.

@1
Version 2 is deployed to the one canary instance. Health checks pass, but it takes no traffic yet.

@2-3
Stage 1: one request in ten goes to the canary. If version 2 is broken, at most one user in ten sees it, and only briefly. In this window stable's 99th percentile is 118 milliseconds and the canary's 120, with no errors on either. The analysis compares both on the same window, error rate, latency and saturation, finds the canary within tolerance, and the gate passes.

@4
Stage 2 widens to half the traffic. Now the canary sees enough requests to reach a code path the 10 percent slice never exercised, and it starts failing: an error, and a 99th percentile of 410 milliseconds, while stable stays clean at 118.

@5
The gate fails. Because stable is serving the other half of the same traffic with zero errors, the comparison pins the problem on the release, not on ambient noise.

@6
Automatic rollback: the canary's weight drops to zero, and stable takes everything again. The bad release reached part of the traffic for one analysis window, instead of everyone for as long as it took a human to notice.

@7-8
Version 2.1, with the fix, starts again from 10 percent. Every promotion repeats the same gate; nothing is trusted because it passed last time. At 50 percent it is clean, 121 milliseconds against stable's 118. Because the gate compares like with like, a traffic spike that slowed both versions would not fail it.

@9
Promotion: the remaining instances roll to 2.1, and it becomes the new stable version. The release took a few analysis windows longer than a blue-green flip.

@10
Three ways canaries mislead. With only 5 canary requests in a window there are too few samples to see a 1 percent error rate, so the gate needs a minimum count, not just a rate. A canary that only gets the easy traffic, cache hits or a single region, passes and then fails at 100 percent. And stateful sessions need sticky routing, or one user bounces between versions.

@11
Canaries limit a bad release's blast radius to the canary share and catch what only real traffic reveals. The price is slower rollouts, two versions live for hours, with the same schema and API compatibility rules as blue-green, per-version metrics, and analysis that must be statistically honest.
