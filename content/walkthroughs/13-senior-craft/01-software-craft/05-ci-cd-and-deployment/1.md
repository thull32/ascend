@0
Blue-green runs two identical production environments. One serves all the traffic, the other sits idle. You deploy the new version to the idle one, test it there, then flip the router. Rollback is flipping back. On screen: users, a router, blue running version 1, green idle, and one database that both colours share. Keep that shared database in mind, because it is where blue-green quietly breaks.

@1
Steady state: every request goes to blue, on version 1. Green is idle, scaled down or kept warm.

@2
Version 2 is deployed to green while blue keeps serving. A failed deploy here hurts nobody, because green is not in the path.

@3
The schema change ships first, as an expand step: add a nullable column or a table, and never rename or drop. Both versions will be live against this schema at once, if only for seconds, and the rollback path depends on version 1 still being able to read it.

@4
Green is verified in production with smoke tests and synthetic requests on an internal address. It has the same hardware and configuration as blue, which catches the "works on staging" class of bug.

@5-6
Cut-over. The router, which might be DNS, a load balancer target or a service mesh route, flips, and all traffic moves to green at once. Requests already in flight on blue are drained, not killed. Users are on version 2 with no downtime, and blue is left running exactly as it was.

@7
Now the failure mode. Version 2 has a bug that only real traffic triggers, and green's error rate climbs to 4 percent. Because the switch was all or nothing, every user is affected until someone reacts.

@8
Rollback is the same flip in reverse: seconds, with no rebuild and no redeploy. It works only because the expand-only migration left the schema readable by version 1.

@9
Here is what would have broken it. A migration that renamed or dropped a column for version 2 would have crashed version 1 on rollback. And anything version 2 wrote to its new column is invisible to version 1, so data written during the green window may need reconciling. Sessions and background jobs on the old colour need the same care. The rule: expand now, and contract only after the old version is retired.

@10
Version 2.1, with the fix, goes to green and is flipped in. Blue becomes the idle colour for the next release; the colours alternate.

@11
Only once no version that needs the old shape can ever be live again does the contract step run, dropping the old column. Expand and contract are separate deploys, often days apart.

@12
Blue-green buys zero-downtime deploys and the fastest rollback there is. It costs double the capacity, forces every schema change into expand and contract, and exposes everyone at once, so a bad release hits every user. Canary releases trade that speed for gradual exposure.
