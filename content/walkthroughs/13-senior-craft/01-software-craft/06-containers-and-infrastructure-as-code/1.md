@0
A service mesh gives every service a sidecar proxy, Envoy here, that intercepts all of its traffic in and out. On screen: three services, Orders, Payments and Inventory, each with a sidecar underneath, and a control plane at the top that configures them. Retries, timeouts, mutual TLS, routing and telemetry move out of application code and into the mesh. The policy table says what every sidecar enforces: mutual TLS required, with certificates rotated hourly; Orders may call Payments with a 500 millisecond timeout and 2 retries; and an endpoint is ejected after 5 consecutive server errors.

@1
The control plane pushes routing rules, retry and timeout policy, and short-lived certificates to each sidecar. The application containers never see any of it.

@2
Orders calls Payments as if it were a plain HTTP call. Firewall rules inside the pod redirect the connection into Orders's own sidecar; the app has no idea a mesh exists.

@3
Orders's sidecar finds a healthy Payments endpoint and opens a mutually authenticated TLS connection to Payments's sidecar, with the 500 millisecond timeout. Both sides verify identity from the certificate, not from an IP address.

@4
Payments's sidecar checks the authorization policy, Orders may call Payments, terminates the encryption, and forwards plain HTTP to the application over localhost.

@5
The response, 200 OK in 32 milliseconds, returns through both sidecars, and each records latency, status and a trace span. The two extra hops cost roughly 1 to 2 milliseconds.

@6
Now Payments starts failing, slow and returning server errors. Orders's sidecar applies the retry policy, a second attempt within its budget, with no change to Orders's code.

@7
After 5 consecutive server errors, the sidecar ejects that Payments endpoint from its pool and answers Orders with a fast 503. That is outlier detection, a circuit breaker per endpoint. Once Payments recovers, the endpoint is re-admitted after a cool-down.

@8
Every sidecar reports the same metrics, traces and access logs, so the mesh gives you a service graph, golden signals on every edge, and distributed traces, in the same shape for every language.

@9
Traffic shaping is configuration too. The control plane tells Orders's sidecar to send 10 percent of Payments calls to a version 2 subset. Canary releases, header-based routing and fault injection stop being code.

@10
The failure modes. The control plane is now a critical dependency, and here it is down: sidecars keep running on their last configuration, but new pods cannot join and certificates stop rotating. Every proxy adds latency, memory and processor time to every pod. And debugging now spans the app, the sidecar and the mesh configuration.

@11
So a mesh buys uniform mutual TLS, retries, routing and observability across every language with no app changes, for an extra hop, another control plane to run, and real operational complexity. It is worth it at dozens of services in several languages, and overkill for a handful, where a shared client library would do. One more cost, from the lesson: retries configured in the mesh live far from the code that knows which calls are idempotent.
