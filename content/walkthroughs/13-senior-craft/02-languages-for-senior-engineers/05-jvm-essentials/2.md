@0
Six tasks, each with a duration in ticks, are submitted to a pool of three worker threads. Creating a thread per task would cost about 50 microseconds and a stack each. The pool reuses three threads instead, which also caps how many tasks run at once. The other tasks wait in the queue.

@1
Tick 1. The three workers each take a task: W1 takes t1, which needs 3 ticks; W2 takes t2, 1 tick; W3 takes t3, 2 ticks. Three tasks wait in the queue.

@2
W2 finishes t2 and immediately takes the next task, t4. The same thread, reused.

@3
W3 finishes t3 and takes t5. Only t6 is left in the queue.

@4
W1 finishes t1, and W2 and W3 finish their tasks too. Five tasks are done. W1 takes t6, the last one, and the queue is empty.

@5-6
For the next two ticks only W1 is working, on t6. W2 and W3 sit idle, because there is nothing left to take.

@7
W1 finishes t6, and all three workers are idle.

@8
All six tasks finished in 7 ticks, against 12 if they had run one after another, with the three workers busy 57 percent of the time. Size a pool to its bottleneck: about the core count for processor-bound work, more for work that waits on input and output. And give the queue a bound too. A fixed pool with an unbounded queue never rejects anything: after 100,000 blocking submissions it held 4 threads and 99,996 queued tasks. With a bound, a burst becomes backpressure or a visible rejection instead of memory growth and rising latency.
