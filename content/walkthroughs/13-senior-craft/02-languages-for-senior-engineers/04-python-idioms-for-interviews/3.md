@0
CPython frees most objects the instant their reference count reaches zero. The count lives in every object's header, and every assignment, argument and container slot adjusts it. One object, X, is created and bound to a, which holds the only reference, so its count is 1.

@1-2
b equals a binds a second name to the same object. Nothing is copied but the reference, and the count is 2. Calling f with a binds the parameter p to it, raising the count to 3 for as long as the function runs.

@3
Inside f, a new object Y is created, and its parent attribute is set to p. Y starts at 1, and X rises to 4, because an attribute holding X is a reference too.

@4-5
f returns and its frame releases its locals. p's reference goes, so X drops to 3, and y's goes, so Y drops to 0. Zero means nothing can reach Y, so CPython frees it on the spot. Freeing Y releases every reference Y held, including its parent attribute, so X falls to 2. Frees cascade.

@6-8
del b, and X is at 1. Then del a, the count hits zero, and X is freed immediately. That is why a file opened without a with block usually closes as soon as its last reference disappears.

@9-10
Now the weakness. Two new objects, P and Q, one reference each. p's next attribute is set to q, and q's prev attribute to p. Both counts are 2.

@11
del p and q. No variable reaches P or Q any more, but each still has a count of 1, held by the other. Neither count can ever reach zero.

@12
Reference counting alone will never free P and Q. That is what CPython's separate cycle collector is for: it runs periodically, looks for groups of objects that only reference each other, and frees them. The everyday cost of the counting itself is an increment or decrement on every new reference.
