@0
CPython frees most objects the instant their reference count reaches zero. Every assignment, argument and container slot adjusts a count. The picture uses neutral pseudocode, but the bookkeeping is CPython's. One object, X, is created; a holds the only reference, so its count is 1.

@1-2
b is assigned the same object, and the count is 2. Passing X into a function as parameter p raises it to 3 for as long as the function runs.

@3
Inside the function, a new object Y is created with a parent field pointing at X. Y starts at 1, and X rises to 4, because a reference stored inside another object counts too.

@4-5
The function returns. p and y disappear, so X drops to 3 and Y to 0. Zero means nothing can reach Y, so it is freed right now. Freeing Y releases everything it referenced, so X falls to 2. Frees cascade.

@6-8
b is cleared, and X is at 1. Then a is cleared, the count hits zero, and X is freed immediately. That is why a file opened without a with block usually closes as soon as its last reference disappears.

@9-10
Now the weakness. Two new objects, P and Q, one reference each. P's next field points at Q, and Q's previous field points at P. Both counts are 2.

@11
Clear both variables. Nothing on the stack reaches P or Q any more, but each still has a count of 1, held by the other. Neither will ever reach zero.

@12
With reference counting alone, P and Q leak. That is what CPython's separate cycle collector is for: it runs periodically, and finds and frees unreachable groups like this one. The other fix is a weak reference, which does not count. The everyday cost of the scheme is an increment or decrement on every copy of a reference.
