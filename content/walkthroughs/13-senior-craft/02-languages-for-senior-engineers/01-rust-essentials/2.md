@0
Rc and Arc are reference counts: a strong count stored in the heap block next to the value, raised on every clone and lowered on every drop. One object, X, has just been created with Rc new, and a holds the only Rc, so its strong count is 1.

@1-2
b is an Rc clone of a. Cloning copies the pointer, not the object, and the count is 2. Then a fresh clone is passed into a function as its parameter, p, and the count is 3 for as long as that function runs. Every clone is counted the moment it is made.

@3
Inside the function, a new value Y is created whose parent field holds another clone of p. Y starts at 1, and X rises to 4, because an Rc stored in a field counts like any other.

@4
The function returns, and its variables are dropped in reverse order, y first. y's drop takes Y to 0, so Y is freed right now, and freeing Y drops its parent field: X goes from 4 to 3. Drops cascade through the object graph.

@5
Then the parameter p is dropped, and X falls to 2. Every one of these drops happens at a point you can read off the code.

@6-8
b is dropped, and X is at 1; a still holds it. Then a is dropped, the count hits 0, and X is freed immediately, with no collector. That is the strength of reference counting: destruction happens at a predictable point, the last drop.

@9-10
Now the weakness. Two fresh nodes, P and Q, one strong reference each. Through RefCell, P's next field takes a clone of Q, and Q's previous field takes a clone of P. Each now holds a strong reference to the other, so both counts are 2.

@11
Drop p and q. The stack can no longer reach P or Q, yet each still has a strong count of 1, held by the other. Neither count can ever reach zero.

@12
When main returns, P and Q are leaked. Rc cannot free a cycle, and Rust has no collector to find one. The fix is to make one direction a Weak, which does not keep the value alive. The ongoing cost is an increment or decrement on every clone and drop, and it differs sharply between the two: an Rc clone and drop measured half a nanosecond, an Arc clone 7 nanoseconds on one thread, and 88 nanoseconds each with eight threads cloning the same Arc, because the count's cache line bounces between cores.
