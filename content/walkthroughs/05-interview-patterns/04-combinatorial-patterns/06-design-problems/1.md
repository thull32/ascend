viz: Recency order under a stream of accesses

@0
An app reads keys through a cache that holds 3 of them, with a database behind it. The policy is least recently used. Every access moves its key to the front, and when the cache is full, the key at the back, the one untouched for longest, is evicted. The stream of reads is A, B, A, C, D, B, A.

@1-2
A misses, is loaded from the database and goes to the front. B misses and goes in front of it. There is still room, so nothing is evicted.

@3
A is read again, and this time it hits. It moves from second place to the front. Recency is updated on reads as well as writes, and forgetting that is the most common failing test for this problem.

@4
C misses and takes the last free slot. From front to back the cache holds C, A, B.

@5
D misses, and the cache is full. B was last used at step 2, longer ago than anything else, so B is evicted and D goes to the front.

@6
Now B is wanted again, and it misses. The back of the list is A, last touched at step 3, so A is evicted to make room.

@7
And then A is wanted, and misses too. C, last used at step 4, is evicted. Out of seven reads, only one hit.

@8
That pattern is the failure mode. A one-off scan, such as a report or a crawler reading keys once each, pushes every genuinely hot key out, and the next real requests all miss. Variants such as LRU-K, ARC, or a small probationary segment admit a key to the main cache only on its second touch.

@9
The trade-off: with a hash map and a doubly linked list, every operation is constant time, and the cache adapts instantly when the working set shifts. That is why it is the default almost everywhere. But it tracks recency only, so it cannot tell a key read a thousand times from one read once a moment ago. Redis approximates it by sampling five keys, because the exact list costs memory per entry.
