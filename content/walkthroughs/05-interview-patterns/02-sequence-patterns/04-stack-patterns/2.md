@0
The lesson's min-stack trace, in its two-stack form: a main stack, and a second stack called mins whose top is always the minimum of everything in the main stack. This version saves space by pushing onto mins only when the new value is less than or equal to its top. Watch the or equal, because the whole trace turns on it.

@1
Push 4. Mins is empty, so 4 is the minimum and goes onto both stacks.

@2
Push 2. Two is at most 4, so it goes onto mins too. The minimum is 2.

@3
Push another 2. Two is at most 2, a tie, and with less than or equal the tie is recorded. Mins now reads 4, 2, 2. With strictly less than, this second 2 would have been skipped, and mins would read only 4, 2.

@4
Push 5. Five is more than 2, so mins is unchanged. This is where the space is saved: a value that is not a new minimum costs nothing extra.

@5
Get min reads the top of mins: 2.

@6
Pop 5. It is not the current minimum, so mins is left alone.

@7
Pop a 2. It equals the top of mins, so that is popped too. But mins still holds the other 2, the one the tie recorded, so the minimum stays 2.

@8
Get min: 2, which is correct, because a 2 is still on the main stack. This is the row where strictly less than goes wrong: its mins would have lost its only 2 on the last pop, and get min would answer 4.

@9-10
Pop the last 2. It equals the top of mins, both pop, and the minimum reverts to 4. Get min confirms it: 4.

@11
Every operation was constant time, and in the worst case, a strictly decreasing run of pushes, mins grows as tall as the main stack. Under time pressure, write the pairs version instead, where every entry carries the minimum of itself and everything below it: it cannot get the duplicate case wrong. Mention this space-saving version afterwards, and say why the comparison must be less than or equal.
