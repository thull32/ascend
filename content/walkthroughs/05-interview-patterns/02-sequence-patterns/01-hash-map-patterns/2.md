@0
This is the seen set behind Valid Sudoku. Every filled cell produces three tagged keys: one for its row, one for its column, and one for its three by three box. The key r0 colon 5 means row 0 holds a 5, and c and b do the same for columns and boxes. A conflict is simply a key that is already present. The table here uses open addressing with 16 slots: each key goes to the slot its hash picks, and if that slot is taken, linear probing tries the next slot, then the next.

@1-3
The first cell is the 5 in the top left corner. Its row key hashes to slot 9, which is empty, so it is stored right there, in its home slot.

@4-6
Its column key hashes to slot 8, also empty. Stored at home again.

@7
Its box key hashes to slot 9, the same slot as the row key. Different keys, same home: a collision.

@8-10
Slot 9 holds the row key, which is not a match, so the probe moves on to slot 10. Slot 10 is empty, and the box key is stored there, one past its home. Slots 8, 9 and 10 now form one contiguous run, and that run is the start of primary clustering: every later key that hashes anywhere into it has to walk to its end.

@11-13
The second cell is the 3 next to it, in row 0, column 1, box 0. Its row key hashes to slot 7, which is empty. Stored at home. But the run now covers slots 7 through 10.

@14-18
Its column key also hashes to slot 7. Slot 7 is taken, so the probe walks: slot 8, slot 9, slot 10, each holding some other key.

@19-20
Slot 11 is finally empty. The column key lands 4 slots past home, after 4 occupied slots were checked.

@21-28
Its box key, b0 colon 3, hashes to slot 7 as well. It walks the whole run, slots 7 to 11, five collisions, and lands in slot 12, five past home. Six keys are in, two cells' worth, and five of them sit in one unbroken run.

@29
Now the lookup that decides the board. Later in the scan, the cell at row 2, column 2 holds another 3, and that cell is in box 0 too. Its box key is the very same string, b0 colon 3. It hashes to slot 7.

@30-34
The lookup walks exactly the path the insert took: slots 7, 8, 9, 10 and 11, each a different key.

@35-36
Slot 12 holds b0 colon 3: a match, after 6 probes. The key is already present, so box 0 already has a 3, and the board is invalid. Notice which rule broke: the box, not the row or the column, which is the case candidates forget when they plan to add boxes later.

@37
Six keys in 16 slots is a load factor of about 0.38, yet one lookup took 6 probes, because the keys bunched into a single run. Linear probing is cache friendly, but probe counts explode as the table fills, so tables like this resize long before they are full, around 0.7. And for the problem itself, the tag prefix in each key is the whole solution: it is what keeps row 3 has a 7 from colliding with column 3 has a 7.
