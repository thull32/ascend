@0
A frequency count, run inside a real table: five buckets with chaining, a key's bucket being its hash modulo 5. The input is a, b, a, c, a, and the map goes from each element to how many times it has appeared so far. The invariant to hold onto: after each step, the table is an exact summary of the elements seen so far, one entry per distinct element.

@1-4
A arrives. Its hash is 97, which modulo 5 is bucket 2. The bucket is empty, so a goes in with count 1. Then b: hash 98, bucket 3, count 1.

@5-7
A arrives again. Same key, same hash, same bucket, 2. The chain's first entry is compared and it is equal, so the existing entry is found and its count is overwritten in place, from 1 to 2. No second entry for a: that is what makes this a count rather than a list of everything seen.

@8-9
C: hash 99, bucket 4, empty, count 1. Three distinct elements, three entries.

@10-12
A for the third time. Bucket 2, one comparison, found, and its count becomes 3. Each element costs one hash and a short walk, so the whole count is linear in the input.

@13-18
Now query. Get a: bucket 2, one comparison, 3. Get b: bucket 3, one comparison, 1.

@19-21
Get z, which never appeared. Its hash is 122, which modulo 5 is also bucket 2, so the lookup compares z with a, finds a different key, and reaches the end of the chain. Z is absent. A miss is not free: it walks whatever chain its bucket holds.

@22
Five elements, three entries, five buckets: a load factor of 0.6. The table did nothing clever here. The decision that mattered was the key: the element itself, because the question is how often has this appeared. In an interview, say the key and the value before you say hash map, and if the keys are small dense integers, such as 26 letters, say that a plain array of counts does the same job with no hashing at all.
