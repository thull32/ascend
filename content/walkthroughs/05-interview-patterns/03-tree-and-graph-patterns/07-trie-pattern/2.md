@0
Autocomplete in two moves. Walk down to the node for the prefix, which costs the prefix's length. Then enumerate the subtree below it, and emit a suggestion at every terminal node.

@1-5
First the dictionary goes in. Car creates 3 new nodes. Card and care each share those 3 and add 1. Cat shares 2, c and a, and adds 1. Dog shares nothing and adds 3 of its own, on a separate branch from the root.

@6-8
The user has typed car. Follow c, then a, then r.

@9
We are at the node for car. Every key in the subtree below it starts with car, and no key outside it does, so this subtree is exactly the answer. Cat and dog are never touched. The subtree is enumerated depth-first, with children in sorted order.

@10
Car itself is terminal, so it is suggestion number 1. The walk keeps going, because longer keys may sit below it.

@11-12
Card is terminal: suggestion 2. Care is terminal: suggestion 3.

@13
The suggestions are car, card and care, already in alphabetical order because the children were visited sorted. The cost is the length of the prefix plus the size of the subtree.

@14
That second term is the catch. A short prefix like c can own most of the dictionary, which is why production autocomplete caches the top k completions at each node, so a query only walks to the prefix and reads a list.
