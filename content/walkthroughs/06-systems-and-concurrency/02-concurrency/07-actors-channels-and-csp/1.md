@0
A sender, S, and a receiver, R, connected by a Go channel. Two phases. First an unbuffered channel, where a send completes only when a receiver takes the value. Then a buffered channel with room for 2.

@1
S sends 1. No receiver is waiting, so S blocks. An unbuffered send is a rendezvous, not a drop-off.

@2
R receives, and the value 1 is handed straight from S to R. Both continue. The handoff is also a synchronisation point: everything S did before the send happens before everything R does after the receive.

@3
R is busy processing 1, so when S sends 2, it blocks again. A slow receiver throttles the sender automatically. That is backpressure, for free.

@4
R receives 2. Two sends, two waits: the sender ran exactly at the receiver's pace, in lock-step.

@5
Phase two: a channel made with a buffer of 2. A send now succeeds without a receiver, as long as the buffer has room.

@6-7
S sends 3, which goes into the buffer, and S returns immediately even though R is still busy. S sends 4, and the buffer holds 2 of 2. It is full.

@8
S tries to send 5, and blocks. The buffer let the sender run ahead by its capacity, and then the backpressure came back. A buffer delays backpressure; it does not remove it.

@9
R receives 3, which frees a slot, and S's waiting send of 5 completes into the buffer, which now holds 4 and 5.

@10
S closes the channel. Only the sender closes. R can still drain 4 and 5; after that, a receive returns the zero value with ok set to false, so a range loop over the channel ends cleanly.

@11
The rule of thumb: unbuffered channels for handing work over with a happens-before guarantee, small buffers for smoothing bursts, and never an unbounded queue, because the bound is what makes overload visible.
