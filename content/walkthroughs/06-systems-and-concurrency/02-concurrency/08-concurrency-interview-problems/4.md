@0
A token bucket rate limiter between a client and an API. The bucket holds at most 5 tokens and gains 1 every second. Each request takes one token; with none left, the request is rejected. Two numbers, two jobs: the capacity sets the largest burst, and the refill rate sets the sustained rate.

@1-5
At time zero, the bucket is full, and the client fires a burst. Requests 1 to 5 each take a token and are forwarded. The bucket goes from 5 down to 0, and the API has served 5.

@6-7
Requests 6 and 7 arrive in the same instant and find the bucket empty. Both are rejected with a 429 and a retry-after hint. The client, not the API, pays for the overload.

@8
Request 8 comes at 2 seconds. Two tokens have refilled since time zero, so it is forwarded, leaving 1.

@9-10
At 3 seconds, one more token has refilled, so there are 2. Requests 9 and 10 take them both, and the bucket is empty again. Under sustained load, requests get through at exactly the refill rate.

@11
The failure modes are about capacity. Too large, and a client can dump 5 times the sustained rate on the API in one instant, so everything downstream must absorb that burst. Too small, and it rejects legitimate bursty traffic, like a page that fires several API calls at once.

@12
The trade-off: the token bucket allows bursts up to its capacity while enforcing an average rate, and it needs only two numbers per client, the token count and the last refill time. Tokens are refilled lazily, computed from the time elapsed when a request arrives, and capped at the capacity. Most API gateways implement this. The leaky bucket is the contrast: it forbids bursts and smooths the output instead.
