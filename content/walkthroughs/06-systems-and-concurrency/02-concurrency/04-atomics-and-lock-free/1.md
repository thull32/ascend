@0
Three threads increment one counter, with no lock. Each thread loads the counter into old, then tries a compare-and-swap: if the counter still equals old, set it to old plus one and report success; otherwise change nothing and report failure. That check and set is a single atomic instruction. If it fails, the thread loads again and retries.

@1
All three threads load the counter, which is 0, and each computes 0 plus 1. So far this is identical to the race that lost an update.

@2
T1 tries its swap, expecting 0 and writing 1. The counter is still 0, so the swap happens. The counter is 1.

@3-4
T2 tries the same swap, expecting 0. It fails, because the counter is now 1. And this is the whole difference from the race: the stale update was rejected instead of overwriting T1's work. T2 reloads, sees 1, and will try again with 2.

@5-6
T3 fails for the same reason, reloads 1, and prepares to write 2.

@7
T2's retry expects 1 and writes 2. The counter is still 1, so it succeeds. The counter is 2.

@8-9
T3's retry expects 1 and fails, because the counter is now 2. It reloads 2 and prepares to write 3. No thread ever held a lock, so no thread could block the others.

@10
T3 expects 2 and writes 3, and this time it succeeds.

@11
The counter is 3, correct without a lock. It took 6 attempts for 3 increments, with 3 failures. That is the guarantee called lock-free: every round, at least one swap succeeds, so the system always makes progress, but a particular thread can retry many times, so it is not wait-free. Each failure is wasted work that bounces the cache line again. In the lesson's measurement at 16 threads, each successful swap was preceded by about two failures, and the loop ran 8 times slower than fetch-and-add. So if a single instruction does your update, use it, and keep compare-and-swap loops for conditional updates and pointer swaps.
