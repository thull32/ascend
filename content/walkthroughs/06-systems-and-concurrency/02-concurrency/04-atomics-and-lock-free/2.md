@0
Two cores each increment their own counter: core 0 writes a, core 1 writes b. They never touch each other's data. But a and b sit 8 bytes apart, inside the same 64 byte cache line, and the coherence protocol tracks ownership per line, not per variable.

@1
Core 0 writes a. It requests the line for ownership and holds it in the Modified state. Core 1's copy is invalid.

@2
Core 1 wants to write b. To do that it must invalidate core 0's copy and fetch the line for itself, and core 0 stalls. That is one invalidation.

@3-6
Then core 0 wants a again, and pulls the line back, and core 1 stalls. Then core 1 takes it back. The line ping-pongs between the cores on every write. Each transfer between cores costs tens of nanoseconds, about 35 in the lesson's measurement, against under 4 for a write to a line the core already owns.

@7
In 6 ticks the two cores completed 6 writes and forced 5 invalidations. Each core spends most of its time waiting for the line. This is false sharing: sharing by address, not by intent.

@8
The fix is padding. Put a on its own 64 byte line, and b on another. Now each core holds its own line in the Modified state.

@9-11
Both cores keep writing locally, two writes per tick, and nothing is invalidated.

@12
Shared line: 6 writes in 6 ticks. Padded: 8 writes in 4 ticks. In the lesson's measurement on 16 threads, the difference was 92 million increments a second packed, against more than 3,600 million padded. Watch for this in code written to avoid contention, like an array of per-thread counters. Find it with perf c2c, and fix it with padding or truly thread-local data.
