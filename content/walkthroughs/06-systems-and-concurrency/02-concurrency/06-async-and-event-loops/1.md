@0
Five lines of JavaScript: log A, set a timer of zero milliseconds with a callback called cb, fetch a URL and attach onResponse, attach m to an already resolved promise, and log B. One JavaScript thread runs all of it. The host runs timers and network I/O outside that thread and posts callbacks back through two queues, the microtask queue for promise callbacks and the macrotask queue for timers and I/O. Before it plays: in what order do the letters print?

@1
The script goes on the call stack, and log A runs synchronously. A is printed.

@2
Set timeout hands a timer to the host and returns immediately. Nothing is queued yet: the timer has to expire first, and even zero milliseconds means after the current script.

@3
Fetch starts the request on the host's network thread and returns a pending promise. The JavaScript thread does not wait for the socket.

@4
The promise is already resolved, so its then callback, m, goes straight into the microtask queue.

@5
Log B runs and prints B. By now the timer has expired, and cb is sitting in the macrotask queue. Neither m nor cb has run, because the script is still on the stack, and nothing interrupts running code.

@6
The script finishes and the stack is empty. Now the loop checks its queues, and microtasks always come first.

@7
The microtask queue drains completely. m runs and logs C. Any microtasks m queued would run now too, before any macrotask.

@8
Then one macrotask: cb runs and logs D. After each macrotask, the loop drains microtasks again before taking another.

@9
The response arrives on the network thread, and onResponse is queued. The JavaScript thread was idle while it waited, not blocked.

@10
onResponse runs and logs E.

@11
A, B, C, D, E. The rule is on screen: synchronous code, then all microtasks, then one macrotask, and repeat. Two consequences. A 200 millisecond synchronous loop delays every timer, click and response by 200 milliseconds, so move CPU work to a worker. And because microtasks drain completely, a promise chain that keeps scheduling more of them starves I/O just as badly as a busy loop. A microtask hop costs about 33 nanoseconds; a hop around the loop with set immediate, about 770.
