@0
Two threads, T1 and T2, share one counter, which starts at 0. Each runs counter plus plus. That looks like one operation, but the compiler turns it into three instructions: load the counter into a private register, add 1 to the register, store the register back. The scheduler may switch threads between any two of them, and that gap is the whole bug.

@1-3
First, T1 increments with nobody else running. It loads 0 into its register, adds 1 so the register holds 1 while the shared counter still says 0, and stores 1. Run without interruption, the increment is correct.

@4
Now both threads increment at the same time, and the scheduler interleaves their loads before either one stores.

@5
Both threads load the counter, which is 1. Each register now holds 1.

@6
Each thread adds 1 to its own private copy. Both registers hold 2, and neither thread knows the other exists.

@7
T1 stores 2. The counter is 2.

@8
T2 stores 2 as well, so the counter stays at 2. T1's increment has been overwritten. That is a lost update.

@9
Three increments ran, so the answer should be 3, and it is 2. The result depends on timing, so this code can pass every test you write and fail under production load. And the damage has no floor: a thread that loads 0 and stalls while another completes 999 increments erases all 999 when it stores 1. The fixes are a mutex, which the next animation shows, or an atomic fetch-and-add.
