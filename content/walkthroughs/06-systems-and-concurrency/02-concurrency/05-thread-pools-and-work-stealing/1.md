@0
Eight tasks sit in a queue, each labelled with how many ticks it takes, and three worker threads wait to run them. Creating a thread per task would cost tens of microseconds and a stack each, and under overload it would mean unbounded concurrency. The pool reuses three long-lived threads, and that bounds how much runs at once. The rule each worker follows is simple: take the task at the head of the queue, and come back for the next one when you finish.

@1
W1 takes t1, which needs 3 ticks. W2 takes t2, 1 tick. W3 takes t3, 2 ticks. Five tasks are still queued.

@2
W2 finishes t2 first, so it comes straight back and takes t4, 2 ticks.

@3
W3 finishes t3 and takes t5, 1 tick. Notice that no one assigns tasks to workers. Whoever is free takes the next one.

@4
Three things finish at once: W1's t1, W2's t4 and W3's t5. The three workers take the last three tasks, t6 for 3 ticks, t7 for 2, and t8 for 1. The queue is empty.

@5-7
Now the workers drain. W3 finishes t8 and goes idle, then W2 finishes t7, and finally W1 finishes t6.

@8
All 8 tasks are done in 7 ticks, against 15 if one thread ran them in a row. The workers were busy 71 percent of the time; the idle stretches at the end are where the last long task held things up. Total time is set by the work divided among the workers, not by the number of tasks. Size the pool to the bottleneck: about the number of cores for CPU-bound work, more for I/O-bound work. And give the queue a bound, so a burst turns into backpressure instead of running out of memory.
