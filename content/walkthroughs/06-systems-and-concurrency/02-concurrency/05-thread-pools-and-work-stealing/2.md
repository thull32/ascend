@0
An API gateway with one shared pool of 12 threads calls three dependencies: Payments, Search and Recommendations. The idea on trial is the bulkhead, named after the watertight compartments in a ship's hull: give each dependency its own share of the threads, so a failure in one cannot flood the others. First, the version without it.

@1
Search becomes slow. Calls that took 50 milliseconds now hang for 8 seconds before timing out. Nothing else has changed.

@2
Every request to Search now holds a gateway thread for 8 seconds instead of 50 milliseconds. Six are in flight, and half the shared pool is gone.

@3
Search traffic keeps arriving at the normal rate, but calls leave 160 times slower than they enter. Search alone now holds all 12 threads. The pool is exhausted.

@4
A checkout request arrives. It needs Payments, which is perfectly healthy.

@5
And it is rejected with a 503, because there is no thread to run it. A slow search box has taken down payments. One dependency's latency has become every feature's outage.

@6
The fix: split the 12 threads into 3 pools of 4, one per dependency. A call to Search may only use a Search thread, and when that pool is full, the call is rejected immediately instead of waiting.

@7
Search degrades exactly as before and fills its pool of 4. But it cannot borrow from anyone else.

@8
The next Search call finds its pool full and fails in microseconds, with a clear search unavailable. The page renders without the search box instead of hanging.

@9
Checkout arrives, takes a Payments thread from a pool with 3 to spare, and succeeds. The compartment held.

@10
The fix has its own failure mode: sizing. Too small, and a normal traffic spike to one dependency rejects legitimate calls, a self-inflicted outage. Too large, and the isolation is only nominal. Size each pool from measured concurrency, the request rate times the latency, with headroom, and alert on rejections.

@11
The trade-off: bulkheads cap the blast radius of any dependency at its compartment's size, at the cost of lower peak utilisation, because idle threads in one pool cannot help another, and one more number per dependency to tune. That lost utilisation is the point. The same idea applies to connection pools, worker processes and whole availability zones.
