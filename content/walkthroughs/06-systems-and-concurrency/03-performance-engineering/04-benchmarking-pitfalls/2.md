@0
The same 4 line cache, but now the data is 40 elements, five lines, one more than the cache holds. The loop reads one element per line, 0, 8, 16, 24 and 32, three passes. In the last animation the second pass was all hits. Will one extra line cost a fifth of the hits, or something worse?

@1-4
The first four accesses miss, exactly as before, and fill all four slots with lines 0 to 3.

@5-6
Element 32 is in line 4. It is not cached, and the cache is full, so the least recently used line is evicted. That is line 0. Line 4 takes its slot.

@7-8
The second pass starts with element 0, which lives in line 0, the line just thrown out. A miss. To make room, least recently used evicts line 1.

@9-14
Which is the next one the loop needs. Element 8 misses and evicts line 2. Element 16 misses and evicts line 3. Element 24 misses and evicts line 4. Every eviction removes exactly the line that is about to be read.

@15-26
The third pass is identical. Every access misses, and every miss evicts the next line the loop will want.

@27
Fifteen accesses, zero hits. A hundred and twenty elements fetched to use fifteen of them. One line more than the cache holds, and the hit rate does not drop by a fifth, it drops to nothing: five lines cycling through a four line least recently used cache is the worst case. That is why a benchmark whose data fits in cache flatters code whose production data does not, often by an order of magnitude. Benchmark with production-sized data.
