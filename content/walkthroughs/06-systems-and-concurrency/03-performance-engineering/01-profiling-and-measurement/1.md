@0
A sampling profiler works by freezing the thread many times a second and writing down every frame on its stack, from main to the innermost call. This animation builds the stack behind the widest line of the lesson's folded file, the one that ends in the JSON encoder. It starts with main running alone: one frame.

@1-3
main calls serve, and a new frame goes on top, holding serve's locals and the address in main to return to. serve calls handle order, and handle order calls render JSON. Each call pushes one frame, and each frame remembers who to return to.

@4-6
render JSON calls dumps, dumps calls encode, and encode calls iterencode, the C encoder where the time is actually spent. Seven frames now, main at the bottom and iterencode on top.

@7
Now the profiler interrupts the thread and walks the frames from main up to iterencode. It writes one sample: main, serve, handle order, render JSON, dumps, encode, iterencode, joined by semicolons. That is one line of the folded file. It records only what is on the stack at this instant, nothing about how the program got here or what it does next.

@8-13
The calls finish and the frames come off in reverse order. iterencode returns and encode resumes right after its call. Then encode returns to dumps, dumps to render JSON, render JSON to handle order, handle order to serve, and serve to main.

@14
Back to main alone. The sample saw exactly the frames that were live at one moment. A flame graph stacks thousands of these snapshots and merges identical prefixes, so the width of a box is its share of samples. In the lesson's profile, this exact stack was the most common one, which is why render JSON spans 45.9 percent of the width. The x-axis is not time, and the exposed top edge of a box is its self time.
