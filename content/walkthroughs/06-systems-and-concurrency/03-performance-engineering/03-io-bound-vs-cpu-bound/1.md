@0
Six tasks wait in a queue, each labelled with how many ticks it takes, and a pool of three worker threads runs them. The pool exists to bound concurrency: never more than three tasks at once, however many arrive. The question it raises is how many workers there should be, and the answer depends on what the tasks spend their time doing.

@1
W1 takes t1, 3 ticks. W2 takes t2, 1 tick. W3 takes t3, 2 ticks.

@2-3
W2 finishes t2 first and takes t4, 2 ticks. Then W3 finishes t3 and takes t5, 1 tick. Each worker comes back for the next task as soon as it is free.

@4
At tick 4, three tasks finish together: t1, t4 and t5. Only t6 is left, and W1 takes it, 3 ticks. W2 and W3 find the queue empty and go idle.

@5-6
For two ticks only W1 is working. W2 and W3 sit idle with nothing to take: one long task at the end holds up the finish.

@7
W1 finishes t6, and all six tasks are done.

@8
Seven ticks, against 12 if one thread ran them in a row, with the workers busy 57 percent of the time. That idle tail is a reminder that more workers do not always help. Size the pool to the bottleneck. For CPU-bound tasks, about the number of cores, because more only adds context switches. For tasks that mostly wait, more: the number of cores times one plus the ratio of wait time to compute time. And never more than the downstream can serve. If the database handles 400 queries a second, 80 threads or 8,000 coroutines all wait on it. Concurrency only moves the queue.
