@0
This is the opening puzzle of the lesson in miniature. Two cores each increment their own counter: core 0 writes a, core 1 writes b. In the program's sense nothing is shared. But a and b sit 8 bytes apart in the same 64 byte line, and the coherence protocol tracks ownership per line, not per variable.

@1
Core 0 writes a. It takes the line for ownership and holds it in the Modified state. Core 1's copy is invalid.

@2
Core 1 writes b. To do that it must invalidate core 0's copy and fetch the line, and core 0 stalls.

@3-6
Core 0 wants a again and pulls the line back, and now core 1 stalls. Then the other way. The line ping-pongs between the cores on every single write, although the two variables have nothing to do with each other.

@7
Six ticks, six writes, five invalidations. Each core spends most of its time waiting for the line. This is false sharing: sharing by address, not by intent.

@8
Now pad a out to its own 64 byte line. Each core holds its own line in the Modified state and writes at full speed.

@9-11
Two writes per tick, and no coherence traffic at all.

@12
Shared line: 6 writes in 6 ticks. Padded: 8 writes in 4 ticks. The lesson measured the real version: eight threads incrementing their own counters packed into one line ran about 12 times slower than the same threads with each counter on its own line, from a change that adds no instructions. Watch for it wherever per-thread counters, locks or flags sit side by side in one array or struct. Find it with perf c2c, and fix it with padding or truly thread-local data.
