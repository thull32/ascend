@0
This is the loop from the epoll trace, seen from the programmer's side. One JavaScript thread runs every piece of your code. The host, meaning the kernel through epoll plus the timers, does the waiting on other threads and posts callbacks back through two queues: microtasks and macrotasks. The program logs A, sets a zero millisecond timer, starts a fetch, queues a promise callback called m, and logs B. The question is what order things print in.

@1
The script starts on the call stack and log A runs immediately. A is printed.

@2
Set timeout hands a timer to the host and returns at once. The callback, cb, is not queued yet. Even zero milliseconds means after the current script, never in the middle of it.

@3
Fetch starts a request on the host's network thread and returns a pending promise. The JavaScript thread never blocks waiting for the socket.

@4
Promise dot resolve dot then, with m. That promise is already settled, so m goes straight into the microtask queue.

@5
Log B runs, and B is printed. By now the timer has expired, and cb is waiting in the macrotask queue. Neither m nor cb has run, because the script is still on the stack, and nothing interrupts a running piece of code.

@6
The script finishes and the stack is empty. Now the event loop looks at its queues, and the rule is: microtasks first, always.

@7
The microtask queue is drained: m runs and logs C. If m had queued more microtasks, they would run now too, before any macrotask.

@8
Then exactly one macrotask: cb runs and logs D. After each macrotask, the loop drains microtasks again.

@9
The response arrives on the network thread, and onResponse is queued. Notice the JavaScript thread was idle while it waited, not blocked: it would have run anything else that was ready.

@10
onResponse runs and logs E.

@11
The output is A, B, C, D, E. The rule on screen is the whole model: run the synchronous code, then all microtasks, then one macrotask, and repeat. The cost of having one thread is that every callback runs to completion. A 200 millisecond synchronous loop delays every timer, every click and every socket by 200 milliseconds. So move CPU work off the loop, and never block it on I/O. This same engine sits inside Node, nginx, Redis and Tokio.
