@0
Same reference string, same first in, first out eviction, but now with 4 physical frames instead of 3. More memory should mean fewer faults. Before it plays, the previous run had 9 faults. Hold that number.

@1-8
Pages 1, 2, 3 and 4 each fault once and fill frames 0 to 3. Four faults so far, and no evictions, because every page still fits.

@9-10
Pages 1 and 2 hit. Both are resident. This is the extra frame paying off, so far.

@11-13
Page 5 faults, and there is no free frame. First in, first out evicts page 1, the earliest loaded, even though it was used two accesses ago. Page 5 moves into frame 0.

@14-19
Now the cascade. Page 1 is needed again and faults, evicting page 2. Page 2 is needed and faults, evicting page 3.

@20-25
Page 3 faults and evicts page 4. Page 4 faults, evicts page 5 from frame 0, and takes its place.

@26-28
And page 5, the last access, faults once more and evicts page 1.

@29
Twelve accesses: 2 hits, 10 faults, 6 evictions. Ten faults with four frames, against nine with three. More memory, more faults. That is Belady's anomaly, and first in, first out suffers from it because it ignores use. Least recently used cannot: the pages it holds with k frames are always a subset of those it holds with k plus one, so more memory never hurts it. Real kernels approximate least recently used by sampling the accessed bit the hardware sets, which is the clock algorithm.
