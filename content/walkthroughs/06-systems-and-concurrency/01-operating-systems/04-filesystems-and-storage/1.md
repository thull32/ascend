@0
A filesystem journal is a write-ahead log, and this picture shows the idea in its database form. A client, a database engine with its buffer pool in memory, an append-only log, and the data files. The rule: before a page is changed, a record describing the change is appended to the log and forced to disk. Durability comes from the log, so the data files are allowed to lag behind.

@1
A transaction arrives: update account 1 from 100 to 50.

@2
The engine appends log record number 1 first, describing that change. The page itself has not been touched yet. That ordering is what write-ahead means.

@3
Fsync. The log record is now durable. It was one sequential write at the end of a file, which is far cheaper than writing pages scattered all over the disk.

@4
Only now is the page modified, in the buffer pool. Page 7 is dirty in memory, and the data file on disk still says 100. That is fine, because the log can rebuild the page.

@5
The commit is acknowledged as soon as the log record is on disk, not when the page is. So commit latency is roughly one flush.

@6-7
A second transaction moves account 2 from 0 to 50. It is logged as record 2 and synced, and pages 7 and 9 are now dirty. When many transactions commit at once, one fsync can flush all their records together. That is group commit: throughput scales with the batch while latency stays at one flush.

@8
Now the failure. Power is lost and the buffer pool is gone. The data files still say account 1 is 100 and account 2 is 0, but both commits were acknowledged to the client. The log still holds records 1 and 2.

@9
Recovery reads the log forward from the last checkpoint, which is still log position 0.

@10
Redo: every record newer than a page's own log position is reapplied, and pages 7 and 9 are rebuilt. Each page stores the position of its last change, so replaying twice does no harm. Records from transactions that never committed would be undone.

@11
A checkpoint writes the dirty pages to the data files, and the checkpoint advances to position 2. The log before it can be recycled, and recovery time is bounded by the log written since the last checkpoint.

@12
The trade-off: every change is written twice, but the first write is sequential and batched, and the second is deferred and coalesced. Turn fsync off, or run on a disk that lies about it, and acknowledged commits can vanish. ext4's journal does exactly this for metadata, and Postgres, InnoDB and RocksDB do it for data.
