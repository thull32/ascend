@0
There are about 4.3 billion IPv4 addresses and far more devices, so most hosts share one public address through network address translation. On screen: a laptop at 192.168.1.11, a NAT router whose public address is 203.0.113.5, and a web server at 104.20.23.154, the rows of the table above. One mapping already exists: the other laptop, 192.168.1.10, is connected from port 51000, and the router kept that port for it. The router's job is to rewrite source addresses and ports on the way out, remember each rewrite, and reverse it on the way back.

@1
This laptop sends from 192.168.1.11, port 51000, to the server on port 443. It happened to pick the same source port as its neighbour. And it is a private address: no router on the internet will carry a reply to it.

@2
So the NAT router rewrites the source to its own public address. Public port 51000 is already taken by the other laptop's mapping, so it allocates 51001, and records the new row: 192.168.1.11 port 51000 on one side, public port 51001 on the other. Because the TCP checksum covers both addresses, it recomputes that too, which is why a box that is supposed to work at the IP layer has to parse TCP.

@3
The server sees only the public address. It replies to 203.0.113.5, port 51001.

@4
The router looks up port 51001 in its table, finds this laptop's row, and rewrites the destination back to 192.168.1.11, port 51000. The laptop never knows any of this happened, and the other laptop's flow on port 51000 is untouched.

@5
Every consequence of NAT follows from that table. Nothing outside can start a connection inward, because only an outbound packet creates a row, so inbound connections need port forwarding or hole punching, the way WebRTC does it. Idle rows expire, so long-lived idle connections need keepalives. And IPv6, with enough addresses for every device, removes the need for translation entirely.
