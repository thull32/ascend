@0
What almost every home router and cloud NAT gateway actually does is port address translation: many private hosts share one public address, and the NAT tells their flows apart by rewriting the source port as well as the address. On screen, a laptop at 192.168.1.11, a NAT router whose public address is 203.0.113.5, and a web server at 104.20.23.154, as in the lesson's trace. The router's table already holds one row: laptop A, 192.168.1.10, connected from port 51000 and kept it. Watch the table, because the whole mechanism lives there.

@1
Laptop B sends from its private address, port 51000, the same port A picked, to the server's port 443. That is a private address, which the internet does not route, so this packet cannot leave as it is.

@2
The router rewrites the source to its public address. Port 51000 is taken by A's mapping, so it allocates 51001 and records the new row: B's port 51000 on the inside, public port 51001 on the outside. Every rewrite also patches the IP checksum and the TCP checksum, because TCP's checksum covers both addresses.

@3
The server replies to what it saw: 203.0.113.5, port 51001.

@4
The router looks up port 51001, finds B's row, and rewrites the destination back to 192.168.1.11, port 51000. The reply arrives as if nothing had happened, and A's flow is untouched.

@5
The table explains every NAT behaviour you will debug. An inbound packet finds a mapping only if an inside host created it by sending first, which is why nobody can connect to your laptop without port forwarding or hole punching, the way WebRTC does it with STUN. Idle mappings expire, so quiet long-lived connections need keepalives. And a mapping is unique per destination, so one public address holds only about 64,000 simultaneous flows to a single endpoint, the limit that bites a busy NAT gateway first. With IPv6, there are enough addresses that translation is unnecessary.
