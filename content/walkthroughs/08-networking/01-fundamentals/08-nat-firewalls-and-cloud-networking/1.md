@0
What almost every home router and cloud NAT gateway actually does is port address translation: many private hosts share one public address, and the NAT tells their flows apart by rewriting the source port as well as the address. On screen, a laptop at 192.168.1.20, a NAT router whose public address is 203.0.113.1, and a web server at 93.184.216.34. Watch the table the router keeps, because the whole mechanism lives there.

@1
The laptop sends from its private address, port 51000, to the server's port 443. That is a private address, which the internet does not route, so this packet cannot leave as it is.

@2
The router rewrites the source to its public address and a port it chooses, 40001, and records the mapping: laptop port 51000 on the inside, public port 40001 on the outside. Every rewrite also patches the IP checksum and the TCP checksum, because TCP's checksum covers both addresses.

@3
The server replies to what it saw: 203.0.113.1, port 40001.

@4
The router looks up port 40001, finds the laptop's entry, and rewrites the destination back to 192.168.1.20, port 51000. The reply arrives as if nothing had happened.

@5
The table explains every NAT behaviour you will debug. An inbound packet finds a mapping only if an inside host created it by sending first, which is why nobody can connect to your laptop without port forwarding or hole punching, the way WebRTC does it with STUN. Idle mappings expire, so quiet long-lived connections need keepalives. And a mapping is unique per destination, so one public address holds only about 64,000 simultaneous flows to a single endpoint, the limit that bites a busy NAT gateway first. With IPv6, there are enough addresses that translation is unnecessary.
