@0
TCP's first promise is that both sides agree a connection exists, and that agreement costs a round trip before any request byte moves. On screen, a client that is closed and a server in the listen state. The handshake exists so that both sides learn each other's initial sequence number.

@1
The client sends a SYN carrying its own random initial sequence number, 100, and moves to SYN sent.

@2
The server answers with a SYN-ACK. The acknowledgement number is 101, which means: the next byte I expect from you is 101. In the same packet it sends its own initial sequence number, 300. The server is now in SYN received, and this half-open connection waits in its SYN backlog.

@3
The client acknowledges the server's number with ack 301 and becomes established. This third packet can already carry the request. So one full round trip passes before the first useful byte leaves the client, and the earliest reply arrives two round trips after the client started.

@4
When that ACK lands, the server is established too. Why random initial numbers? They stop old duplicate packets from a previous connection being mistaken for new data, and they stop an attacker blindly spoofing a connection. And TLS 1.3 adds another round trip on top of this one, which is why reusing connections matters more than most engineers assume.
