@0
Closing a TCP connection takes four packets, because each direction shuts down on its own. A FIN means only: no more data from this side. The other side may keep sending. Both ends start established.

@1
The client has nothing more to send. It sends a FIN and enters FIN wait 1.

@2
The server's kernel acknowledges the FIN at once, and the server moves to CLOSE WAIT. It can still send data. CLOSE WAIT has no timer: it lasts exactly as long as the server's application takes to call close. Thousands of sockets stuck there always mean an application bug, a code path that never closes the socket.

@3
The client, its FIN acknowledged, waits in FIN wait 2. Now the server's application finishes and closes, its FIN goes out, and the server waits in last ACK.

@4
The client acknowledges and enters TIME WAIT, for twice the maximum segment lifetime, a fixed 60 seconds on Linux. Two reasons. If that final ACK is lost, the server will resend its FIN, and someone must still be there to answer it. And it stops a new connection on the same addresses and ports from accepting a delayed segment from this old one.

@5
The server receives the ACK and is closed. The client is still in TIME WAIT. Remember who pays: the side that closes first. That is the proxy from the lesson's opening, opening and closing one connection per request to a single backend, and running out of ports at about 470 new connections a second. The fixes, in order: reuse connections, let the server close first where the protocol allows, and consider TCP time wait reuse for outgoing connections. Never shorten the state with routine resets.
