@0
Six actors, left to right: the browser, the stub resolver in the operating system, a recursive resolver, a root server, the dot com servers, and the authoritative server for example dot com. A name is resolved right to left, one level of delegation at a time, and each level only knows who to ask next. Every cache miss walks one level further down.

@1
The browser asks the operating system's stub resolver for the A record of www dot example dot com. The browser's cache and the operating system's cache both miss.

@2
The stub does no detective work of its own. It forwards the question to the recursive resolver it was configured with: your ISP's, 1.1.1.1, 8.8.8.8, or the one in your VPC. That resolver's cache misses too, so it has to walk the hierarchy.

@3
It starts at the top and asks a root server.

@4
The root does not know the answer and does not try to. It returns a referral: here are the servers for dot com, ask them.

@5-6
The resolver asks a dot com server, and gets another referral, this time to example dot com's own authoritative name servers, with glue records giving their addresses so the resolver can reach them.

@7-8
The resolver asks the authoritative server, the source of truth for the zone. This time the answer comes back: an A record, with a time to live of 300 seconds.

@9-10
The recursive resolver caches the record for those 300 seconds and passes the answer back through the stub to the browser, which can finally open a connection. Any lookup in the next 300 seconds is a single cache hit instead of four round trips.

@11
In practice a cold lookup is rarely this long: every busy resolver already holds the root and dot com referrals, which have long time to live values, so a miss usually costs one round trip to the authoritative server. The time to live is the only lever you have over how fast a change spreads. Set it low and failover is fast, but resolvers query you more often and the cold path is slower; set it high and you are stuck with old answers for longer.
