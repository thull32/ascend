@0
A client, a rate limiter, and an API. The limiter keeps a token bucket for this client's API key: it holds at most 5 tokens and gains 1 per second. Each request takes a token, and a request that finds the bucket empty is rejected. Two numbers, two jobs: capacity sets the largest burst, and the refill rate sets the sustained rate.

@1-5
Five requests arrive in the same instant, at time zero. Each takes a token and is forwarded: 4 left, 3, 2, 1, and after the fifth, none. The burst went straight through, because the bucket started full.

@6-7
Requests 6 and 7 arrive in that same instant and find the bucket empty. Each is rejected with a 429, Too Many Requests, and a Retry-After hint. The client pays for the overload, not the API.

@8
Request 8 arrives at 2 seconds. Two tokens have refilled since time zero, so it is accepted, leaving 1.

@9-10
At 3 seconds, one more token has refilled, so there are 2. Requests 9 and 10 take them both, and the bucket is empty again. The log reads 8 accepted, 2 rejected.

@11
Sizing is the failure mode. Make the capacity too large, and a client can dump many times its sustained rate on the API in one instant, a burst downstream must absorb. Make it too small, and you reject legitimate bursts, like a page that fires several calls at once.

@12
Most API gateways implement exactly this: it allows bursts up to capacity while enforcing an average rate, with only two numbers stored per client, the tokens and the last refill time. One more thing for that 429: compute Retry-After from when the next token arrives rather than hard-coding it. A constant tells every client to come back at the same second, and they return in a synchronised wave.
