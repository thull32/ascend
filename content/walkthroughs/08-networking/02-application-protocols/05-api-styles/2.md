@0
Three boxes: a client, an orders API, and the Postgres database that holds both the orders and a table of idempotency keys. The table on screen is that key table: key, a hash of the body, a status, and the saved response. The promise to hold onto: the client mints one key for this operation, K, sends the same K on every retry, and one key creates at most one order, however many times it arrives.

@1
Delivery 1: the client posts an order for amount 10, with K in the Idempotency-Key header.

@2
The API claims the key by inserting a row for K, with the body's hash h1 and the status in progress. K is the table's primary key, so only one insert can ever succeed, and only the request that wins it goes on to do the work.

@3-4
Delivery 2 arrives while the first is still in progress: a double click, or a client that gave up early and retried. Its claim fails, because K already exists and is in progress. The server answers 409 Conflict and creates nothing.

@5
The first request creates order 1, and in the same transaction marks K done and saves the response, 201 order-1. If the process died before the commit, neither the order nor the saved response would exist, and a retry would simply run again.

@6
The response is sent, and lost: a timeout, a dropped connection, a crashed load balancer. The client cannot tell whether the order was created.

@7
Delivery 3: the client retries with the same key. Without the key, this would be a second order.

@8-9
The API finds K done, with a matching body hash: the same request again. It replays the saved response, 201 order-1, byte for byte, and does no work. Orders: still 1. At-least-once delivery plus an idempotent server gives an effect that happens exactly once.

@10
A client bug: the same key K with a different body, amount 20. The stored hash does not match, so the server answers 422 and creates nothing. The key names a different request.

@11
The details that bite. Scope keys to the caller, so one client cannot replay another's response. Keep keys longer than any client retries, because a retry after its key expires is treated as new and creates a second order. And decide what a failed attempt leaves behind: release the key so a retry runs again, or store the failure and replay it.

@12
The cost is one extra write per request and a table of keys to expire. The benefit is that every layer can retry safely. And the key belongs to the operation, not the attempt: a fresh key on every retry would deduplicate nothing.
