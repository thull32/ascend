@0
Four boxes: a client, a payments API, an idempotency store, and a ledger that records charges. The table will show the store's contents: key, status, saved response, kept for 24 hours. The promise to hold onto: the same key produces the same effect exactly once, however many times it arrives.

@1
The client generates a key, k1, a fresh UUID for this attempt, and sends a POST to charge 20 dollars with that key attached.

@2
The API checks the store. There is no entry for k1, so it claims the key atomically, with a set-if-not-exists, marking it in progress. That atomic claim is what stops a concurrent duplicate from also starting work.

@3
Now the real work happens, once: the ledger records a 20 dollar charge.

@4
Before replying, the API saves the response under k1: done, 201 Created, with the new charge's ID. In the lesson's code the charge and the key are committed in the same transaction, so neither can exist without the other.

@5
The reply is sent, and lost: a timeout, a dropped connection, a crashed pod. The client cannot tell whether the charge happened.

@6
So it retries, with the same key. Without the key, this would be a second 20 dollar charge.

@7
The API looks up k1 and finds a saved response.

@8
It replays that response without touching the ledger. Charges: still 1. At-least-once delivery plus an idempotent server gives you an effect that happens exactly once.

@9
A different race: a duplicate arrives while the first request is still in progress. The set-if-not-exists fails, so the API answers 409 Conflict, or waits for the first to finish, rather than charging twice.

@10
Different keys mean different intentions. Keys k2 and k3 each charge once, and the ledger shows 3 charges. The key identifies the attempt, not the endpoint.

@11
The details that bite. Scope keys per account, so two clients cannot collide. Store a hash of the request body, and reject a reused key with a different body with a 422, because that is a client bug. And expire keys, but not before the client's retry window has closed.

@12
The cost is one extra store round trip per request and a keyspace to expire. The benefit is that every layer can retry safely. Payment APIs require it, and anything with side effects should offer it.
