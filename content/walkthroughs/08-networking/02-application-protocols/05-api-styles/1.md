@0
REST's real strength is not the URL design. It is that every piece of infrastructure between a client and your server already speaks HTTP's semantics. Watch one ordinary request on an open connection, and notice how much caching you get without writing any code.

@1
The browser sends a GET for slash api slash lessons, with the usual headers: Host, Accept, Cookie, and If-None-Match, which will matter in a moment.

@2
The server answers 200 OK with the body, and two headers that do the caching work: an ETag, a fingerprint of this version of the resource, and Cache-Control, which tells browsers and CDNs how long they may reuse the response. Because it is a GET, every cache on the path understands it.

@3
Later, the browser needs the resource again. It sends the ETag it holds, in If-None-Match.

@4
Nothing changed, so the answer is 304 Not Modified, with no body: a revalidation in a few hundred bytes.

@5
That machinery is what the other styles give up. GraphQL and gRPC calls are POSTs, so caches, CDNs and proxies treat them as opaque, and none of this comes for free. Retries come with HTTP's semantics too: proxies retry GET, PUT and DELETE because those methods promise idempotency. REST's weakness is the opposite side: resources are normalised and screens are not, so a single screen can over-fetch, or need several waves of requests.
