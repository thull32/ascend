@0
A browser and a server with a single TCP connection between them. The idea that makes HTTP/2 work is the stream identifier. A stream is one request and its response, every frame on the wire names its stream, so frames from different streams can interleave on one connection and be reassembled at the other end.

@1
The browser sends three requests at once, as HEADERS frames: the page on stream 1, app dot js on stream 3, and logo dot png on stream 5. Streams the client opens get odd numbers. HPACK compresses the headers, so fields repeated from earlier requests shrink to a byte or two each.

@2
The responses come back as DATA frames, interleaved: some of stream 3, then stream 1, then stream 5, then more of stream 3. A slow HTML render no longer blocks the JavaScript bytes, because the server can send whatever is ready, and the browser sorts the frames by stream number.

@3
One connection now does what HTTP/1.1 needed about six for. But notice what was fixed. Head-of-line blocking is gone at the HTTP layer and still present at the TCP layer underneath: all these streams share one ordered byte stream, so a single lost packet stalls every one of them. HTTP/3, over QUIC, fixes that by giving each stream its own loss recovery.
