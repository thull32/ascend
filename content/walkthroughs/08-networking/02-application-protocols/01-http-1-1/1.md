@0
A browser and a server, with a TCP connection already open between them and kept alive from an earlier request. HTTP/1.1 is plain text on that connection: a request goes up, a response comes back, and nothing else can use the connection until that response has finished.

@1
The request line says get slash api slash lessons, HTTP 1.1. Headers follow. Host is mandatory, and Accept, Cookie and If-None-Match ride along. None of these headers is compressed in HTTP/1.1, so a large cookie is paid for again on every single request.

@2
The response starts with a status line, 200 OK, then headers, then the body. Content-Length, or chunked encoding, tells the parser where the body ends, because TCP itself has no message boundaries. Two headers matter for what happens next: an ETag, a fingerprint of this version of the resource, and Cache-Control, which says how long the browser may reuse it.

@3
Later, the browser wants the same resource again. Instead of downloading it blindly, it revalidates: it sends the ETag it holds, in an If-None-Match header.

@4
The resource has not changed, so the server answers 304 Not Modified, with no body at all. The cached copy is still good, and the exchange is cheap for both sides.

@5
Now the limitation. One connection carries one response at a time, so a slow response blocks everything queued behind it. That is head-of-line blocking at the HTTP layer. Browsers work around it by opening about six connections per origin, and HTTP/2 fixes it properly by multiplexing many requests on one connection.
