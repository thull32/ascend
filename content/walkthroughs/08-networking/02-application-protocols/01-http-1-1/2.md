@0
HTTP/1.1 keeps connections open by default, and this picture shows what that saves. The first request to a server over HTTPS needs a connection before it can ask for anything: a TCP handshake, then a TLS 1.3 handshake, then the request itself. Keep count of the round trips before the first response byte arrives.

@1
TCP first. The client sends a SYN.

@2
The server answers with SYN-ACK. That is round trip 1, and nothing useful has been asked yet. The client's final ACK can travel with its next message.

@3
TLS 1.3 next. The client sends its ClientHello with its key share, riding along with the TCP acknowledgement.

@4
The server replies with its own key share, its certificate and its Finished message. Round trip 2, and now both sides hold the session keys.

@5
Only now does the request go out: the client sends its Finished and the encrypted request together.

@6
The first byte of the response arrives after round trip 3.

@7
The next request reuses the open connection. That is keep-alive: no SYN, no ClientHello, just the request.

@8
Its first byte arrives after a single round trip.

@9
A reused connection skips two of the three round trips, because the TCP and TLS handshakes are paid once per connection instead of once per request. On a 100 millisecond path that is 300 milliseconds against 100. The lesson measured it with curl against example dot com: the first request took 212 milliseconds, including 66 for TCP and 54 for TLS, and the second, on the reused connection, took 67. The catch is idle timeouts: if the server closes an idle connection just as the client reuses it, you get a 502, so the client's idle timeout must be shorter than the server's.
