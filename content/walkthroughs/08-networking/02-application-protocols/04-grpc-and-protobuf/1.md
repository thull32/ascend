@0
A gRPC call is one HTTP/2 stream. A unary call sends one message each way; a server-streaming call, like this one, keeps the stream open while the server sends many. Three parts to watch for: headers carry the method and the deadline, DATA frames carry protobuf messages, and the status comes last, in trailers.

@1
The client opens the stream with a HEADERS frame. The path names the service and method, here the Watch method of a Search service, and the content type is application slash grpc. The deadline travels here too, as a grpc timeout header, along with any credentials.

@2
Then the request itself, in a DATA frame: a protobuf message behind a short length prefix, 42 bytes here, far smaller than the same thing in JSON.

@3
The server streams its responses as it produces them: message 1, message 2, message 3, each a DATA frame on the same stream. HTTP/2 flow control works per stream, so a slow reader applies backpressure to this call without stalling others on the connection.

@4
The call ends with trailers: a final HEADERS frame carrying grpc status 0, which means OK. That ordering is why gRPC needs trailers at all: the status is only known after the last message has been sent. A non-zero status carries error details. One consequence bites in production: the HTTP status is 200 even when the call failed, so a dashboard that only reads HTTP codes reports perfect success during an outage.

@5
The deadline is the feature to remember: it propagates down a call chain, so a service that has already run out of time does not start work nobody will wait for. Typed stubs are generated from the dot proto file. And browsers cannot speak this directly; they need gRPC-Web or a gateway. So the usual split is gRPC between services, and REST with JSON at the edge, where browsers, caches and humans live.
