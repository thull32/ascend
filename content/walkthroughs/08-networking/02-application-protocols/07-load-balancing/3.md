@0
The same three servers, but now the balancer keeps a count of in-flight requests for each one, and sends every new request to the server with the fewest. All three start at zero. The idea: a server that is slow to finish accumulates in-flight work, and so automatically receives less new work.

@1-2
Request 1 arrives with the counts at 0, 0, 0. It is a tie, and the first server wins ties, so it goes to server 1.

@3-6
Request 2 finds counts of 1, 0, 0 and goes to server 2. Request 3 finds 1, 1, 0 and goes to server 3. So far it looks just like round robin.

@7-8
Request 4 finds 1, 1, 1. Another tie, so server 1 gets it, and now holds 2.

@9
Then server 2 finishes its request, and its count drops to zero. Server 1 has finished nothing yet.

@10-11
Request 5 arrives with counts of 2, 0, 1. Server 2 has the fewest, so it goes there. Round robin would have sent it to the next in turn regardless.

@12-13
Request 6 finds 2, 1, 1. Servers 2 and 3 tie, and server 2, first in order, takes it. Server 1, still holding two unfinished requests, has been passed over twice. That is routing around a slow backend.

@14
The lesson works the earlier example with Little's law: if in-flight counts stay roughly equal, each backend's rate is inversely proportional to its latency, so the backend that is five times slower gets about a fifth of a fast one's traffic, and roughly 1 percent of requests are slow instead of 5. The cost is per-backend state on the balancer, which is fine for an L7 proxy. Two caveats remain. For an L7 proxy, count outstanding requests, because connections are reused and multiplexed. And many independent balancers all see a freshly started backend at zero and send it everything at once.
