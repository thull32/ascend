@0
Two ways for a server to push news to a browser over plain HTTP. With long polling, the browser asks and the server holds the request until it has something to say. With Server-Sent Events, the browser makes one request and the response simply never ends. Same browser, same server, same events; watch how many requests each one needs.

@1
Long polling first. The browser asks for updates, and the server parks the request instead of answering.

@2
Nothing happens yet. The server is waiting for an event, holding the request open for up to 25 seconds, safely under the timeouts of the proxies in between, while the browser waits on the other end.

@3
An event arrives. The server answers with it, and that request is done.

@4
The browser immediately asks again. So every event costs a full request and response, with all its headers. And there is a gap: between the response arriving and the next request landing, about one round trip, new events can only queue on the server. Long polling still has its place, as the fallback that works through every proxy ever built, because it looks like a slow request.

@5
Now Server-Sent Events, for the same traffic.

@6
One request, asking for an event stream.

@7
The response stays open, and events flow down it as newline-delimited chunks of text: a delta, another delta, then done. The browser parses them as they arrive. If the connection drops, it reconnects on its own and sends the ID of the last event it saw, so the server can resume where it left off.

@8
The rule: pick the simplest transport that fits the direction of your data. Long polling works everywhere and costs the most. Server-Sent Events are simple, one way, and plain HTTP; this app streams its AI replies that way. WebSockets are for data that flows both ways, with their own framing.
