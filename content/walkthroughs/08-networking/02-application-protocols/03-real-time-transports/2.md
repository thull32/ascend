@0
A WebSocket begins life as an ordinary HTTP request, and then the same TCP connection stops speaking HTTP at all. One round trip negotiates the switch; after that, both sides send small frames, in either direction, whenever they like.

@1
The client sends a normal GET to slash w s, with a few extra headers: Upgrade naming websocket, Connection set to Upgrade, and a random key.

@2
The server answers 101, Switching Protocols, with an accept value computed by hashing the client's key together with a fixed constant. That is not security. It proves the server genuinely understands WebSockets, rather than being an HTTP cache that echoed the headers back. From here on, HTTP is over on this connection.

@3
Now the client sends a frame: subscribe to chat. No request line and no headers, just a couple of bytes of framing around the message. Client frames are masked with a random four-byte key. That is not encryption either: it stops a malicious page crafting bytes that a badly written proxy would mistake for an HTTP request and cache.

@4
The server pushes a message, hello, without being asked. Ping and pong frames keep the connection from looking idle to the NATs and load balancers on the path, which would otherwise drop it.

@5
So the choice: WebSockets for low-latency traffic in both directions, like games or collaborative editing. For one-way server push, Server-Sent Events are simpler: they stay plain HTTP, reconnect on their own and pass through more proxies.
