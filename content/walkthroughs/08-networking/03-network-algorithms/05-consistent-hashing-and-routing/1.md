@0
A router and three shards, S1, S2 and S3. The rule is the obvious one: hash the key, take it modulo the number of shards, here 3, and that is the shard. Watch the rule work, and then watch what the 3 inside it does to you.

@1
Alice hashes to a large number whose remainder mod 3 is 2, so alice goes to S3. Any router computes the same answer with no shared table, which is the appeal.

@2-3
Bob also lands on remainder 2, S3. So does hank.

@4
Judy's remainder is 0, so she goes to S1.

@5
After four keys the shards hold 1, 0 and 3. With so few keys that is lumpy, but over many keys hashing spreads them evenly, and sequential keys like order numbers scatter just the same, so there is no hot tail.

@6
The first failure mode: a range query, say names from a to c, cannot be routed. Hashing scattered those names, so the router must ask every shard and merge the answers, and the query is only as fast as the slowest shard.

@7
The second, and the one this lesson is about: add a fourth shard. The modulus changes from 3 to 4, and every key's remainder changes with it. All four keys move: bob to S1, hank to S2, alice and judy to S4. For a cache, a moved key is a miss. The lesson's opening is this at scale: ten cache servers grow to eleven, about 91 percent of keys move, the hit rate collapses from 95 percent to about 9, and the database behind it takes nearly twenty times its normal read load. Adding capacity caused an outage.

@8
The third: hashing spreads keys, not load. One celebrity key still lands on one shard, and the fix lives above the hash, such as splitting a hot key into several suffixed copies.

@9
So hash-mod-N gives even spread and stateless routing, and charges you for range queries and, painfully, for resharding. The requirement every scheme in the rest of the lesson meets is minimal disruption: going from N to N plus 1 servers should move only about one in N plus 1 of the keys, and only to the new server.
