@0
This is the other side of the trade. Least connections knows nothing about keys: each request goes to whichever of the three servers has the fewest requests in flight. All three start at zero. Watch the load stay even, and ask yourself where a given user's requests end up.

@1-6
The first three requests each find a tie or a zero and go to server 1, server 2 and server 3 in turn. Every server now holds one.

@7-8
Request 4 finds all three at 1. On a tie, the first server wins, so server 1 takes it and now holds 2.

@9
Server 2 finishes its request and drops to zero.

@10-11
Request 5 finds counts of 2, 0 and 1, and goes to server 2, the least loaded.

@12-13
Request 6 finds 2, 1 and 1. Servers 2 and 3 tie, and server 2 takes it.

@14
The load stayed even, and a server that is slow to finish automatically gets less new work. But nothing here looked at who sent the request or what it was for. The same user's requests land on different backends, so an in-process cache on each instance holds everything at once and helps little, and in-memory sessions are useless. When locality is worth something, cache affinity, live WebSocket or game state, or keeping one account's events in order, you route by key with a consistent hash instead. The catch is that hashing is blind to load, which is why the lesson goes on to bounded loads, which cap how much any one node may take.
