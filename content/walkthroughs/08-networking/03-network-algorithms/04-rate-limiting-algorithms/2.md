@0
The token bucket. It holds at most 5 tokens and gains 1 every second. Each request takes a token, and a request that finds none is rejected. Capacity sets the largest burst, and the refill rate sets the sustained rate. The bucket starts full.

@1-5
Five requests arrive at time zero. Each takes a token and is forwarded: 4 left, 3, 2, 1, none. A full bucket lets a burst straight through.

@6-7
Requests 6 and 7, in the same instant, find the bucket empty and are rejected with a 429 and a Retry-After hint.

@8
At 2 seconds, two tokens have refilled. Request 8 takes one, leaving 1.

@9-10
At 3 seconds, one more token has arrived, so there are 2. Requests 9 and 10 take both.

@11
Request 11, also at 3 seconds, finds the bucket empty and is rejected.

@12
Then a quiet spell. Request 12 arrives at 9 seconds, six seconds later. Six seconds of refill would be 6 tokens, but the bucket holds at most 5, so it has 5, and after this request, 4. Tokens never accumulate beyond the burst size. That cap is the guarantee: in any interval of length T, the bucket admits at most the capacity plus the rate times T.

@13
Sizing is where it goes wrong. Too large a capacity lets a client dump a full bucket of requests on the API in one instant. Too small, and you reject legitimate bursts, like a page that fires several calls at once.

@14
It needs only two numbers per client, the token count and the time of the last refill, which is why most API gateways implement it. Compare the leaky bucket, next, which forbids bursts and smooths the output instead.
