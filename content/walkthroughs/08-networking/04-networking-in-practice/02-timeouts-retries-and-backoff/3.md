@0
TCP retries constantly, and never has to ask the question every application retry must: is it safe to do this twice? Watch why. The receiver acknowledges cumulatively, naming the next byte it expects, and every byte has a sequence number.

@1
Four segments go out. The one at sequence 1001 is lost.

@2
Sequence 1 arrives, and the receiver asks for 1001.

@3-5
Sequences 2001 and 3001 arrive and are buffered, but the receiver keeps asking for 1001. After three duplicate acknowledgements, the sender knows one segment is missing.

@6
It resends sequence 1001, the same bytes with the same sequence number.

@7
The gap is filled, and the acknowledgement jumps to 4001.

@8
Here is the point. If the original segment had only been delayed, not lost, and both copies arrived, the receiver would see the same sequence numbers twice and keep one copy. Deduplication is built into the protocol, so a retransmission can never apply bytes twice. TCP's timeouts also double on each retransmission, the same backoff idea one layer down. Application retries have no such guarantee. A POST that timed out may have succeeded, and repeating it creates a second order. That is why a retried write needs an idempotency key, and why only a failure where the request never reached the server, like a refused connection, is free of side effects.
