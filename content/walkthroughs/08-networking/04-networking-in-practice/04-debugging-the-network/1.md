@0
You, three routers, and a target. Traceroute discovers the path by sending probes with a deliberately small time to live. Each router decrements it, and the router that takes it to zero drops the probe and sends back an ICMP time exceeded message, revealing its address and the round trip to it. Mtr does the same thing continuously and keeps statistics for every hop, which is what intermittent problems need.

@1-2
A probe with a time to live of 1 dies at hop 1, which reports back after about 1 millisecond.

@3-4
A probe with a time to live of 2 passes hop 1 and dies at hop 2, which reveals itself at about 8 milliseconds.

@5
A probe with a time to live of 3 goes out.

@6
No reply comes back. Hop 3 rate-limits or filters ICMP, so traceroute prints three stars. The path still works: traffic passes straight through this router. It just declines to answer probes addressed to it.

@7-8
A probe with a time to live of 4 reaches the target, which answers differently, port unreachable for UDP probes or an echo reply for ICMP ones. That is how traceroute knows it is done.

@9
Now the reading rules, because the output lies in predictable ways. Routers forward packets in hardware, but answer probes from a slow, rate-limited CPU. So loss only counts if it continues to the destination: in the lesson's mtr run, the home router showed 10 percent loss and every later hop none, which means it skipped two replies and dropped no traffic. Latency only counts if it persists: a hop averaging 108 milliseconds before hops averaging 22 is busy answering probes, not delaying packets. And the path back is not the path out, so send output from both ends when you report a problem to a provider.
