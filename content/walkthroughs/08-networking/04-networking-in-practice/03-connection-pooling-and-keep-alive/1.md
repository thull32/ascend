@0
Users, an API gateway, and three dependencies: payments, search and recommendations. First the version without a bulkhead: the gateway has one shared pool of 12 threads, and any call to any dependency may take any of them. The name comes from a ship's watertight compartments, which stop one leak from sinking the whole hull.

@1
Search becomes slow. Calls that took 50 milliseconds now hang for 8 seconds before timing out. Nothing else has changed.

@2
Each search call now holds a gateway thread for 8 seconds instead of 50 milliseconds. Six are in flight, and half the shared pool is gone.

@3
Search traffic keeps arriving at its normal rate, but calls now leave 160 times slower than they enter. That is Little's law: the connections in use equal the arrival rate times how long each is held. Search alone now holds all 12 threads, and the pool is exhausted.

@4
A checkout request arrives. It needs payments, which is perfectly healthy.

@5
It is rejected anyway, with a 503, because there is no thread to run it. A slow search box has taken down checkout. One dependency's latency has become every feature's outage.

@6
The fix: split the 12 threads into three pools of 4, one per dependency. A search call may only use a search thread, and when that pool is full, the call is rejected at once instead of waiting.

@7
Search degrades exactly as before and fills its 4 threads. But it cannot borrow from anyone else.

@8
The next search call finds its pool full and fails in microseconds with a clear search unavailable. The page renders without the search box instead of hanging.

@9
Checkout arrives, takes a payments thread from a pool with 3 to spare, and succeeds. The compartment held.

@10
The fix has its own failure mode: sizing. Too small, and a normal spike to one dependency rejects legitimate calls, a self-inflicted outage. Too large, and the isolation is only nominal. Size from measured concurrency, the request rate times the latency, with headroom, and alert on rejections.

@11
A capped connection pool with a short acquire timeout is exactly this. It fails the excess fast, keeps your service responsive for everything that does not need the sick dependency, and stops you piling connections onto a dependency that is already struggling. The cost is lower peak utilisation, because idle threads in one pool cannot help another, and one more number to tune per dependency.
