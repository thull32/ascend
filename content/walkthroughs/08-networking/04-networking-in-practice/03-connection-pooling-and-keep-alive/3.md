@0
Three servers behind a balancer that picks whichever has the fewest open connections. In this picture each request is its own connection, so the count tracks the work exactly. Watch it work, and then think about what pooling does to that assumption.

@1-6
The first three requests go to server 1, server 2 and server 3, one each.

@7-8
Request 4 finds a three-way tie at 1, and server 1, first in order, takes it.

@9
Server 2 finishes and closes its connection, dropping to zero.

@10-13
Request 5 goes to server 2, the least loaded. Request 6 finds servers 2 and 3 tied at 1, and server 2 takes it.

@14
The counts end at 2, 2 and 1, and here they mean what they say. Now add pooling, or HTTP/2. One long-lived connection can carry hundreds of requests a second, so two servers each holding one connection can carry wildly different load, and the balancer cannot tell. Worse, existing clients keep their pooled connections to the old servers, so new instances you add sit idle. An L4 balancer balances connections, not requests. The fixes: balance per request at L7, with a proxy or sidecar that spreads HTTP/2 streams; client-side balancing, with a connection to every backend; or a maximum connection age on the server, after which it sends GOAWAY and the client reconnects, possibly somewhere else.
