@0
A DNS lookup, end to end: the browser, the operating system's stub resolver, a recursive resolver, and the root, dot com and authoritative servers. Keep one question in mind as it plays: when does this lookup happen? The answer is the whole lesson here. It happens when a connection is opened, not when a request is sent.

@1-2
The browser asks the stub for example dot com, and the stub forwards to the recursive resolver. Every cache misses.

@3-6
The resolver walks the hierarchy. The root refers it to the dot com servers, and dot com refers it to example dot com's authoritative servers.

@7-8
The authoritative server answers with an A record and a time to live of 300 seconds.

@9-10
The resolver caches it for 300 seconds and passes the answer back, and the browser opens its connection to that address.

@11
And from now on, that connection never looks at DNS again. The time to live governs how long resolvers cache the answer. It says nothing about connections that are already open. A pool keeps reusing them against the old address until they close. That is the database failover trap: the record changes, every resolver has the new address within 30 seconds, and the pool still holds 20 connections to the old primary. If the old primary is now a read-only replica, every write fails, indefinitely. The fix is a maximum connection lifetime, say 5 minutes with some jitter, so every connection is replaced, and re-resolved, within that bound.
