@0
The TCP connection is open. Now the second round trip of setup: TLS 1.3, which needs exactly one round trip before encrypted data flows. TLS 1.2 needed two.

@1
The ClientHello carries the client's cipher suites, the server name, and, crucially, its key share. Sending the key share up front is what saves the round trip.

@2
The server replies in one flight: its own key share, and then, already encrypted, its certificate chain, a signature proving it holds the private key, and its Finished message.

@3
The client checks the chain, the name and the dates, sends its Finished, and sends the HTTP request in the same flight.

@4
The encrypted response comes back. One round trip for TLS, on top of one for TCP.

@5
So a cold HTTPS request pays DNS, TCP and TLS before it even asks for anything. A warm connection, with DNS cached, the TCP connection pooled and the TLS session already established, pays only the request itself: one round trip instead of four, about 90 milliseconds instead of 280 on the lesson's 70 millisecond path. That is the whole argument for keep-alive and connection pooling. QUIC folds the transport and TLS handshakes into a single round trip, and resumption with zero round trips removes even that for repeat visits.
