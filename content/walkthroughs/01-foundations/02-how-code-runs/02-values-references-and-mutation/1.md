@0
A dynamic array, the same shape as a Go slice. The small header on the stack holds the length, the capacity and a pointer. The elements live in a separate block on the heap, with room for 2. Copying the header copies only that pointer, so two headers can share one block. Whether they keep sharing it is decided by a capacity the caller never sees.

@1-2
Appending 1 and 2 fits within capacity, so each value is written in place. The block is now full.

@3
Now take p, a reference to the first element. It is an alias into the current block, and it shares the elements with v only until a growth moves them to a new block.

@4-6
Appending 3 finds no room. A new block of 4 is allocated, and the two elements are copied across, one at a time.

@7
The header switches to the new block. The old block is not freed: p still refers to it, so the garbage collector keeps it alive, and nothing crashes. But p is now stale. It still reads the old elements, and a write through it no longer reaches v. This is step 6 of the lesson's trace: the same write that was visible before the append is now invisible.

@8-9
3 and 4 go into the new block, in place. p never sees them, because they were written to a block it does not point at.

@10-14
Appending 5 triggers the next growth: a block of 8, and four elements copied across.

@15
v moves to the block of 8. This time nothing else refers to the block of 4, so it becomes garbage, and the collector will reclaim it. The old block of 2 is still there, held alive by p.

@16-18
5, 6 and 7 are written in place in the new block.

@19
Seven appends, six element copies. The doubling keeps appends cheap on average, but each growth is a moment when the elements move, and every old alias stops seeing new writes. Two identical statements can share or not share, depending on whether a hidden capacity was exceeded. The safe habits: only append to a slice you own, cap the capacity when you hand out a sub-slice, or copy explicitly.
