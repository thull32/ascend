@0
Reference counting. Every heap object carries a count of the references to it, and the rule is simple: the moment the count reaches zero, the object is freed. Here a new object, X, is created and assigned to a, so it starts at 1.

@1
b equals a copies the reference, and X's count goes to 2. Every copy is counted at the moment it is made.

@2
Calling f with a passes the reference in as the parameter p, and the count rises to 3 for as long as f runs.

@3
Inside f, a new object Y is created, held by the local y, and its parent field is set to p. Y starts at 1, and X rises to 4, because a field on the heap is a reference too.

@4
f returns, and its locals p and y go out of scope. X drops to 3, and Y drops to 0. Nobody can reach Y any more, so it is freed right now, not later.

@5
Freeing Y releases everything Y held, including its parent reference, so X falls to 2. Frees cascade through the object graph.

@6
b is set to null. X drops to 1, and nothing else happens, because a still holds it.

@7-8
a is set to null, the last reference. The count hits zero and X is freed on the spot, with no separate collection phase. This is the strength of counting: destruction happens at a predictable point.

@9-10
Now the weakness. Two fresh objects, P and Q, held by the locals p and q. Then p's next field points at Q, and q's prev field points at P. Each object now has a count of 2: one from the stack, and one from the other object.

@11
Set p and q to null. The stack no longer reaches either object, yet each still has a count of 1, from the other. Neither will ever reach zero.

@12
main returns and P and Q are leaked. Reference counting alone cannot free a cycle, and cycles are common: doubly linked lists, trees with parent pointers. The fixes are a weak reference on one edge, or a backup tracing collector, which is what Python's cycle collector is. And the ongoing cost is an increment or decrement on every copy of a reference.
