@0
Clients on the left, a load balancer in the middle, and three servers, each showing how many requests it is currently handling. All three start at zero. The rule is least-connections: every new request goes to the server with the fewest requests in flight. This is the opposite of throwing balls into bins at random, where a third of the bins sit empty and the fullest one sets your tail latency.

@1-2
Request 1 arrives. The counts are 0, 0 and 0, so it goes to Server 1, the first of the tied servers.

@3-6
Request 2 sees counts of 1, 0 and 0, and goes to Server 2. Request 3 sees 1, 1 and 0, and goes to Server 3. Each server now has exactly one request.

@7-8
Request 4 arrives to a three-way tie at 1. It goes to Server 1, which now has 2.

@9
Now something purely random routing would ignore: Server 2 finishes its request early and drops back to 0. Requests do not all take the same time.

@10-11
Request 5 arrives with counts of 2, 0 and 1. The balancer sends it to Server 2, the one that just freed up, rather than piling onto Server 1.

@12-13
Request 6 sees 2, 1 and 1, a tie between Servers 2 and 3, and goes to Server 2. The counts end at 2, 2 and 1. No server is ever more than one request ahead of another.

@14
This adapts to slow requests and uneven backends, but it needs per-backend state on the balancer, which is fine for a layer 7 proxy like Envoy or HAProxy. The lesson's punchline is that you rarely need the whole picture. Sample just two servers at random and pick the emptier one, and the busiest of a million servers handling a million requests drops from 9 requests to 4, almost all of this benefit with no global view of the load.
