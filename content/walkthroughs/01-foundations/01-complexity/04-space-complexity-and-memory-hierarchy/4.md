@0
The process sees 8 virtual pages, but the machine has only 3 physical frames to hold them. The page table maps each virtual page to a physical frame, or marks it not present. Memory is handed out and moved in pages, not bytes, and what has to fit in physical memory is the set of pages you are using right now.

@1-2
The first access is to page 0. Its entry is not present, so the hardware raises a page fault and the operating system takes over. It loads page 0 from disk into frame 0, marks the entry present, and retries the instruction, which now succeeds.

@3-6
Pages 1 and 2 go the same way: a fault, then a load, into frames 1 and 2. All three frames are now full.

@7
Page 0 again. This time the entry is present, so the address is translated in hardware with no help from the operating system. That is a hit, the only one in this run.

@8-10
Page 3 faults, and now there is no free frame. Something has to go. The policy here is first in, first out, so page 0, the earliest loaded, is evicted, written to disk if it was modified, and page 3 takes its frame.

@11-19
The pattern repeats. Page 4 evicts page 1. Then page 1 is wanted again, but it was just thrown out, so it faults and evicts page 2. Page 5 evicts page 3.

@20-22
Finally page 0 comes back. It was evicted earlier, so it faults one more time and pushes out page 4.

@23
Nine accesses: 1 hit, 8 faults, and 5 evictions. A hit is a translation, usually cached; a fault is a trip to disk. Touching a fresh page costs about a microsecond, and once the working set is bigger than physical memory, every memory access risks becoming a disk access. Your working set, not your address space, is what must fit in memory.
