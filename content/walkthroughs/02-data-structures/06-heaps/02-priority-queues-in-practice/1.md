@0
This is the inner loop of a shortest-job-first scheduler. Each task is pushed into a min-heap keyed by its duration, and whenever the processor is free, a pop hands back the shortest task waiting. The heap is an array whose smallest value always sits at position 0.

@1
A task of duration 5 arrives and is pushed. It is alone, so it is the root.

@2-3
A task of duration 2 arrives. It is appended at the end, then sifts up past the 5, because it is shorter.

@4-5
A task of duration 1 arrives. It also climbs to the root. The heap is 1, 5, 2.

@6-7
The processor is free, so pop. Out comes the 1, the shortest job. The last element, 2, moves into the root, and it is already smaller than its child, 5, so it stays.

@8-9
A task of duration 3 arrives while the others wait. It is appended under the 2, and it is larger, so nothing moves.

@10-11
Pop: the 2 runs next. The 3 moves to the root and stays above the 5.

@12-14
Pop the 3, and finally the 5. The heap is empty.

@15
The tasks ran in order of duration: 1, 2, 3, 5. Each push and each pop cost one walk along a single path, logarithmic in the queue's size. Two things this loop does not handle. Ties: a heap is not stable, so equal durations come out in whatever order the sifts leave them; add a sequence counter as a tiebreaker to keep them first in, first out. And starvation: if short tasks keep arriving, the long one never runs. The usual fix is aging, folding the time a job has waited into its key when it is pushed.
