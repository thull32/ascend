@0
We want the three largest values from the stream 4, 9, 1, 7, 3, 8, 2, 6, holding only three at a time. The counter-intuitive part: to keep the largest, use a min-heap. Its root is the weakest of the current top three, and that is the only value a newcomer ever needs to beat.

@1-3
The heap has room for three, so the first values go straight in. Four, then 9, which stays below the 4.

@4-5
Then 1, which sifts up to the root. The heap is full: 1, 9, 4. The root, 1, is the current threshold.

@6-8
Seven arrives and beats the root, 1. So 1 is out of the top three, and 7 overwrites the root in a single step. Then 7 sifts down: its children are 9 and 4, it swaps with the smaller, 4, and stops. The new threshold is 4.

@9
Three arrives. It is not larger than 4, the weakest of the top three, so it is rejected with one comparison. The heap is never touched.

@10-12
Eight beats the root, 4. It replaces it and sifts down, swapping with 7. The threshold is now 7.

@13-14
Two and 6 both lose to 7. Rejected, one comparison each.

@15
The heap holds 7, 9 and 8: the three largest. Each value costs at most one sift of logarithmic size in k, so the whole stream is n log k, with memory for only k values, which is why this works on a stream you cannot store. Once the heap was full, only 7 and 8 got in; the other three values cost one comparison each. On random input that gets far rarer as the stream goes on, because a late value has to beat an ever-higher threshold. The worst case is a stream that arrives in ascending order, where every value beats the root.
