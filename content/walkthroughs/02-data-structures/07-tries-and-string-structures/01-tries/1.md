@0
On screen is an empty trie: just the root, which stands for the empty prefix. A trie stores each string one character at a time along a path from the root, so keys that start the same way share the nodes of that start. A double ring marks a terminal node, which means a key ends here. Hold onto that marker, because it is the whole difference between search and prefix check.

@1-3
First we insert car. There is no edge for c under the root, so a new node is created. Then no edge for a under c, so another, and no edge for r under ca, so a third.

@4
At the end of car, the r node is marked terminal. Without that marker, car would only be the prefix of some longer key, not a key itself.

@5-9
Now cart. The edges for c, a and r already exist, so the insert simply follows them: a shared prefix costs no new nodes. Only the t under car is missing, so one node is created and marked terminal.

@10-13
Cat follows c and a, then needs a new t under ca, which becomes terminal. Two different t nodes now hang in the tree, one under car and one under ca.

@14-20
Do starts a fresh branch: new nodes for d and o, and o is marked terminal. Then dog follows d and o and adds one g, also terminal. So do is an internal node that is also a key.

@21-24
Now the queries. Search for car walks c, a, r. Every character matched and the r node is terminal, so search returns true.

@25-27
Search for ca walks c and a, and every character matches too. But the a node is not terminal: ca is only the prefix of stored keys, so search returns false. Forgetting this check is the most common trie bug.

@28-30
A prefix check for ca walks the same two edges, and this time the answer is true. A prefix check needs no terminal flag; it only needs the path to exist.

@31-34
Last, search for dot. It follows d and o, then looks for a t under do and finds none. The walk falls off the trie after 3 steps, so no stored key starts with dot, and search returns false.

@35
Five keys now live in 9 nodes, counting the root. Every operation walked one character per step, so insert, search and prefix check all cost time proportional to the key's length, no matter how many keys are stored. A hash set ties on exact membership; the trie wins the moment the question is about a prefix.
