@0
A dynamic array is three things: a pointer to a block, the number of elements in use, and the block's capacity. On the stack, the variable v holds just that small header. The elements live in a heap block with room for 2, and right now it is empty: length 0, capacity 2.

@1-2
Append 1, then append 2. Each time the length is below the capacity, so the value is written straight into the next spare slot. That is constant time. After the second append the block holds 1 and 2, and there are no spare slots left.

@3
Now we take p, a pointer to element 0. It points into the current block. Keep an eye on it, because it is only valid until the array next has to grow.

@4
Append 3. The length equals the capacity, so there is no room. The array allocates a new block twice the size, with room for 4, somewhere else on the heap. The old block is untouched for now.

@5-6
Every element is copied across: 1, then 2. Two copies to make room for one append. This is the expensive step, and it costs as many copies as the array holds.

@7
v is pointed at the new block and the old block is freed. But p still holds the old address. It is now dangling, and reading through it is undefined behaviour. This is why Rust refuses to let you hold a reference into a vector across a push, and why the safe habit is to store indices, not pointers, into a growable array.

@8-9
Appends 3 and 4 are cheap again: each writes into a spare slot in the new block. After the fourth, length and capacity are both 4.

@10
Append 5 finds the block full a second time. A new block of 8 is allocated.

@11-14
And the copy runs again, this time four elements: 1, 2, 3 and 4. Notice that each resize copies everything, but the resizes come twice as far apart each time.

@15
v moves to the block of 8 and the block of 4 is freed. Any pointer into it would now be dangling too.

@16-18
Appends 5, 6 and 7 fill slots 4, 5 and 6 without any copying. One spare slot remains.

@19
Count the copies: 2 at the first resize and 4 at the second, so 7 appends cost 6 element copies in total. Because capacity doubles, the copies always add up to less than the number of appends, so append is constant time amortised, even though a single append can copy the whole array. Grow by a fixed 10 slots instead, and the copies add up to roughly n squared over 20: a million appends would copy 50 billion elements.
