@0
The string is ten characters: three a's, a b, two c's and four d's. Run-length encoding replaces each run of the same character with the character and how many times it repeats, and a run of just one is written as the bare character. One pass does it: a run pointer marks where the current run started, a scan moves forward, and the output goes into a builder, never into a string you keep slicing.

@1-3
The scan starts on the a's: a new run, count 1. The next character is also an a, so keep counting: 2. The third a makes it 3, and the character after it is a b. It differs, so the run of a's is over: emit a3 into the output.

@4
The b starts a new run, count 1, and the very next character is a c. So the run of b's ends at length 1, and by the rule it is written bare: just b.

@5-6
The c's: the first starts a run, the second continues it to 2, and the d after it ends it. Emit c2.

@7-10
The d's: one, two, three, four. There is no differing character to end this run, so the end of the text has to do it. Emit d4.

@11
The output reads a3, b, c2, d4: a3bc2d4, 7 characters for 10, exactly what the exercise below expects. It is one linear pass, and every character is read once. And notice that compression only pays off when runs are long: a string with no repeats would come out the same length, and with the count always written it would double.
