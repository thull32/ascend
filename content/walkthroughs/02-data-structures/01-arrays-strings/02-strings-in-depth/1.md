@0
The string is ten characters: three a's, a b, two c's and four d's. Run-length encoding replaces each run of the same character with the character and how many times it repeats. One pass does it: a run pointer marks where the current run started, a scan moves forward, and the output goes into a builder, never into a string you keep slicing.

@1-3
The scan starts on the a's. The second a matches, then the third, so the run keeps growing to a count of 3. Then the scan reaches the b. It differs, so the run of a's is over: emit a3 into the output, and start a new run at the b.

@4
The very next character is a c, so the run of b's ends at length 1. This visualisation emits it as b1. The exercise below uses the more compact rule, where a run of length 1 is written as the bare character, just b.

@5-6
The c's: the second c continues the run, and the first d ends it. Emit c2, and a new run starts at the d.

@7-10
The d's run to the end of the string: two, three, four. There is no differing character to end this run, so the end of the text has to do it. Emit d4.

@11
The output reads a3, b1, c2, d4: 8 characters for 10. Under the exercise's rule the b loses its 1 and you get a3bc2d4. Either way it is one linear pass, and every character is read once. And notice that compression only pays off when runs are long.
