@0
A small hash table: 4 buckets with chaining, and a rule that when the number of entries divided by the number of buckets goes above three quarters, the table doubles and every entry is rehashed. A key's bucket is its hash modulo the bucket count, so the bucket depends on two things: the hash, which never changes, and the modulus, which is about to.

@1-8
Four keys go in. K1 hashes to 3,366, which modulo 4 is bucket 2. K2 is 3,367, bucket 3. K3 is 3,368, bucket 0. K4 is 3,369, bucket 1. One key per bucket, but four entries in four buckets is a load factor of 1, over the limit.

@9
So the table grows. Eight new buckets are allocated beside the old four, and every entry has to be placed again. The hash values are unchanged; only the modulus has gone from 4 to 8.

@10-11
K3: 3,368 modulo 8 is 0, the same bucket number as before. K4: 3,369 modulo 8 is 1, also unchanged.

@12-13
K1: 3,366 modulo 8 is 6, where it used to be 2. K2: 3,367 modulo 8 is 7, where it used to be 3. These two land in different buckets. With doubling, a key either keeps its bucket number or moves up by the old size, so here half of them changed place, but all four had to be recomputed and copied.

@14
The rehash is done: four entries copied, a linear amount of work, and the load factor is back to one half. Spread over the inserts that filled the table, that pause costs a constant amount per insert.

@15-18
K5 and k6 now go straight into buckets 2 and 3 of the larger table, and the load factor climbs back to three quarters.

@19
Inside one process this is harmless: a brief pause, which is why latency-sensitive systems rehash a little at a time. Now make the buckets servers. A key's server is its hash modulo the server count, and the data does not move for free. Going from 4 servers to 5 sends 80 percent of keys to a server that has never seen them, and every one of those is a cache miss that lands on the database. That is the problem consistent hashing solves.
