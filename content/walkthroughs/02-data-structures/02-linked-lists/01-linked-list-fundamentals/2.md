@0
Memory is never fetched one element at a time. It arrives in whole cache lines, here 8 elements each, and this cache has room for 4 lines. Touching one element pulls its 7 neighbours in with it. We will make 16 sequential accesses, like an array scan, and then 12 scattered ones, like a list walk whose nodes are spread around the heap.

@1
The scan starts at element 0. Its line is not cached: a miss. All of line 0, elements 0 to 7, comes in from main memory, about 100 times slower than a hit.

@2-8
But elements 1 through 7 were in that same line, so each of them is a hit, served in a few cycles. One expensive fetch paid for eight reads.

@9-16
Element 8 starts line 1: one more miss, and then seven more hits. Sixteen sequential accesses, two misses. Every element of every fetched line was used.

@17-18
Now the scattered walk begins. Its first two stops, element 0 and element 9, happen to sit in lines that are still cached, so both are hits.

@19-20
Element 18 is in line 2, and element 27 in line 3. Two misses, and the two empty slots fill up. The cache is now full.

@21-28
Element 36 is in line 4. Before it can come in, the least recently used line, line 0, is evicted. Then element 45 evicts line 1, element 54 evicts line 2, and element 63 evicts line 3. Each of these accesses pays for a full line of 8 elements and reads exactly one of them.

@29-34
Element 2 is back in line 0, but line 0 was thrown out, so it misses again. Element 20 misses in line 2, which was also evicted. Element 41 needs line 5, which was evicted only a moment ago to make room for line 2. Misses, one after another.

@35
Element 58 lands in line 7, which is still cached: a rare hit.

@36
The total: 28 accesses, 17 hits and 11 misses. But look at where they fell. The sequential sixteen cost 2 misses. The scattered twelve cost 9. Same number of elements touched; the locality, not the element count, sets the cost. That is why a list walk over scattered nodes is so much slower than an array scan with the same big O.
