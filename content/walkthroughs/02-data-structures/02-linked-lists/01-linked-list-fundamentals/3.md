@0
An app, a cache that holds 3 keys, and a database behind it. The policy is least recently used: keep the 3 keys touched most recently. Inside, it is a hash map plus a doubly linked list. Every access moves the key to the front of the list. When the cache is full, the key at the back, the one untouched for longest, is evicted. The access sequence is A, B, C, A, D, B, E, A.

@1-3
A, B and C all miss. There is room, so each is loaded from the database and inserted at the front. The list reads C, B, A, most recent first.

@4
A again. This time it is a hit, so it moves from rank 3 to the front: A, C, B. Recency is updated on reads as well as writes. In the list that is an unlink and a push to the front, six pointer writes, no search, because the map hands you the node directly.

@5
D misses and the cache is full. The tail is B, last used at step 2, so B is unlinked and dropped from the map, and D goes in at the front: D, A, C.

@6-8
Then B comes back and misses, evicting C. E misses, evicting A. And A comes back and misses, evicting D. Twice, a key was evicted one step before it was needed again.

@9
The score is 1 hit and 7 misses. Here is the failure mode to remember: a one-off scan. Reading 4 keys once each, say a report or a crawler, pushes every genuinely hot key out, and the next real requests all miss. Variants such as LRU-K, ARC, or a small probationary segment admit a key to the main cache only on its second touch.

@10
The trade-off: least recently used is constant time with a hash map and a doubly linked list, adapts instantly to a shifting working set, and is the default almost everywhere. But it tracks recency only. It cannot tell a key read a thousand times from a key read once a moment ago. And the exact list costs memory per entry, which is why Redis approximates it by sampling five keys instead.
