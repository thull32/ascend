@0
This is a log-structured merge tree, the storage engine under RocksDB, LevelDB and Cassandra, and the sorted merge from this lesson sits at its heart. On screen: a client, a write-ahead log, an in-memory memtable that holds four keys, and two levels of files on disk, L0 and L1. Writes go into a sorted table in memory, get flushed as immutable sorted files, and those files are merged later. Every disk write is sequential; the price is that a read may have to look in several places.

@1
The client puts a equals 1 and b equals 2. Each put is appended to the log for crash safety and inserted into the memtable, a sorted in-memory structure such as a skip list. Sub-millisecond, and no disk seeks.

@2
Then c equals 3, and a equals 4. Overwriting a just replaces the value in memory; the log still holds both records.

@3
A put of d equals 5, and the memtable reaches its limit of four keys.

@4
Flush. The memtable is written out as one sorted, immutable file, SST-1, with a sparse index and a Bloom filter, in a single sequential write. That part of the log can now be dropped, and a fresh memtable takes new writes.

@5
Next, b becomes 9, and c is deleted. Neither touches SST-1, because it is immutable. The delete writes a tombstone for c into the memtable. The real removal waits for compaction.

@6
Read c. The memtable is checked first and holds the tombstone, so the answer is "not found", even though SST-1 still contains c equals 3. The newest level wins.

@7
Read a. It is not in the memtable. SST-1's Bloom filter says "maybe", its index points to the right block, and one disk read returns a equals 4. Bloom filters let a read skip any file that cannot hold the key.

@8
Two more puts fill the memtable, and it flushes as SST-2. Now the two L0 files overlap: both hold b and c. A read for b has to check SST-2 before SST-1. That is read amplification, and it grows with every flush.

@9
Compaction fixes it. A background merge, the same take-the-smaller-head merge as the lesson's, combines the two files into one L1 file with no overlap. When both files hold the same key, the newer value wins, so b is 9. And the tombstone for c removes both the old c equals 3 and itself, since nothing older remains.

@10
Read b again. The memtable is empty, L0 is empty, and there is one L1 file to check. Compaction pays a write cost now to make every later read cheaper.

@11
Three ways this goes wrong. Compaction competes with foreground disk work and can fall behind, and then write stalls kick in as L0 piles up. Tombstones must survive until they reach the bottom level, or deleted keys come back to life. And a burst of writes to one key wastes space until compaction catches up.

@12
The trade-off: excellent write throughput and compression, because nothing is updated in place, at the cost of slower point reads and range scans, and background compaction that needs tuning. A B-tree makes the opposite bet. In an interview, the question to expect is how compaction decides which version of a key to keep. The answer is the stable merge's tie rule with a defined priority: within a key, the newest sequence number surfaces first.
