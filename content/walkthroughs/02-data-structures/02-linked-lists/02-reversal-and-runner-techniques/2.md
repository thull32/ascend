@0
On the right, the list 1, 2, 3, 4 on the heap. On the left, the call stack, where the cost of recursive reversal lives. main holds the head, node 1, and calls reverse rec on it. Every call will get its own frame, with its own head.

@1-3
Reverse rec of 1: node 1 has a successor, so it calls reverse rec on node 2 and waits, with its head parked in its frame. Reverse rec of 2 does the same for node 3, and reverse rec of 3 for node 4. Nothing is relinked on the way down; every arrow on the heap is still the original.

@4
Reverse rec of 4: its next is None, so this is the base case, and it returns node 4. Four reverse rec frames are alive, one per node, on top of main. That is the whole cost in one picture: the recursion is as deep as the list is long.

@5
Reverse rec of 4 is popped, and reverse rec of 3 resumes with new head equal to node 4. It points the old successor back at itself, 4 dot next equals 3, then cuts its own forward link, 3 dot next equals None, so 3 is the tail. It returns node 4.

@6-7
The same two assignments, one frame further up each time. Reverse rec of 2 sets 3 dot next to 2 and 2 dot next to None. Reverse rec of 1 sets 2 dot next to 1 and 1 dot next to None. Every frame returns the same node, 4, unchanged.

@8
Reverse rec of 1 returns node 4 to main, which now holds the head of 4, 3, 2, 1. From node 1, only node 1 is reachable.

@9
Four nodes needed four reverse rec frames at the peak. Depth equals the list's length, and the work happens after each call returns, so not even tail-call elimination could discard a frame. On 50 thousand nodes, CPython's limit of a thousand frames raises a recursion error at once. The iterative loop does exactly the same relinking with constant stack.
