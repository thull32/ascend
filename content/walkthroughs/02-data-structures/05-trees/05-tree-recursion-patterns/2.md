@0
The example tree again, and we want the lowest common ancestor of 7 and 10, both highlighted: the deepest node that has both of them below it. This is not a search tree, so the values give no direction, and the search runs bottom-up. Each call returns one thing: the node itself if it is a target; otherwise, if both children report a hit, the node is the answer; otherwise it passes up whichever side hit, or nothing.

@1-3
We enter 4, then minus 3, then 8, asking each node's subtrees whether they hold a target.

@4
Node 7 is a target, so it returns itself immediately. Its own subtree, the leaf minus 1, is never visited: whether the other target is below 7 or elsewhere, 7 is the right thing to report.

@5
Back at 8: the left side reports 7, the right side nothing. One hit, so 8 passes 7 up.

@6-8
Minus 3 now searches its right side. Enter minus 5, then 9, then reach 10, the second target, which returns itself.

@9-10
Node 9 hears 10 from its right and passes it up, and minus 5 does the same.

@11
At minus 3, the left side reports 7 and the right side reports 10. Hits from both sides: minus 3 is the split point, the lowest common ancestor.

@12-13
The search is not over, because the root still asks its right side. Node 6 is a leaf with no targets, so it reports nothing.

@14
At the root, the left side reports minus 3 and the right side nothing. An answer found lower down passes up unchanged.

@15
The lowest common ancestor of 7 and 10 is minus 3, after one post-order pass, linear in the size of the tree. Watch one trap: if one target is missing, say 99 instead of 10, the same function still returns 7 from this walk, and the caller cannot tell "7 is an ancestor of 99" from "99 is absent" unless the function also returns flags saying which targets it found. In a search tree you would not need any of this: the values point the way, and a single walk down from the root finds the split.
