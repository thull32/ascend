@0
The diameter is the longest path between any two nodes, counted in edges. The visualiser inserted 1 to 5 in search tree order, so this tree is a chain leaning right, not the lesson's example tree. Any path either passes through some node as its highest point, or lies lower down, inside a subtree. So each call does two jobs at once: it returns its subtree's height to its parent, and on the way it offers the path through itself as a candidate for a running best.

@1-5
A node cannot measure the path through itself until both children have reported their heights, so the calls run post-order. We enter 1, then 2, 3, 4 and 5, and the call stack holds all five.

@6
Node 5 is a leaf. In this visualiser heights count nodes, so an empty side reports zero, and the path through a node is simply its left height plus its right height. For 5 that is zero plus zero: no path, and the best stays zero. It returns height 1.

@7
Back at 4: zero on the left, one on the right, so the path through 4 is 1 edge. That beats the best, which becomes 1. Node 4 returns height 2.

@8-10
The same thing happens all the way up. Node 3 sees a path of 2 edges, node 2 a path of 3, and the root, 1, a path of 4. Each one beats the running best and passes a height one larger to its parent. The heights are now labelled on every node.

@11
The diameter is 4 edges, the whole chain, highlighted. On a chain the best happens to be at the root, but in the lesson's tree it was found lower down, at node minus 3, and the root's candidate was smaller. That is why the best is updated at every node rather than read off the root. One pass, linear time. The version people write first calls a separate height function at every node, which on this chain of five visits 15 nodes instead of 5, and on a chain of a hundred thousand, about five billion. The fix is always the same: return the helper's value from the same pass.
