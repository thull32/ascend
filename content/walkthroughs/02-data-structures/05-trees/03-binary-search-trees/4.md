@0
Same insert, different order. This time the keys arrive already sorted: 1, 2, 3, 4, 5, 6, 7. Watch what the ordering rule does with them.

@1
One becomes the root.

@2
Two is larger than 1, so it goes right.

@3-4
Three is larger than 1 and larger than 2, so it goes right twice and lands at depth 2.

@5-7
Four compares against 1, 2 and 3, larger every time, and becomes a leaf at depth 3. Every new key is the largest so far, so it always goes right, and it has to walk past every key already there.

@8-16
Five takes four comparisons, and six takes five. The tree is not branching at all. It is growing one node longer to the right with every insert.

@17-22
Seven walks the whole chain, six comparisons, and attaches at depth 6.

@23
Seven nodes, height 6, where a balanced tree would have height 2. That is a linked list wearing a tree costume. Building it took 21 comparisons, and in general sorted input costs about n squared over two; for a million keys, 5 times 10 to the 11. Search, insert and delete are now all linear, and recursive code overflows the stack long before the million. This is not contrived: auto-incrementing IDs, timestamps and sorted exports all arrive in order. The fix is a tree that rebalances itself on every insert, which is the next lesson.
