@0
This is the build side of a hash join. The planner takes the smaller input, here users keyed by id, and loads every row into a hash table of 8 buckets. The keys are written u colon 42 and so on; I will just say user 42. The rule is one line: hash the key, take it modulo 8, and that is the bucket. Keys that land in the same bucket simply share a chain.

@1-2
User 42, Ana, hashes to 3,542,947, and that modulo 8 is 3. Bucket 3 is empty, so the entry goes straight in. One entry in eight buckets: a load factor of about 0.13.

@3-8
The next three rows go the same way. User 77, Raj, lands in bucket 5. User 13, Lee, in bucket 7. User 5, Kim, in bucket 0. Every bucket they hit was empty, so each insert costs one hash and no comparisons. Four entries now, and the load factor is 0.5.

@9
User 91, Ivy, hashes to bucket 5. That bucket already holds user 77.

@10
So the build walks the chain. It compares user 91 with user 77: different keys that happen to share a bucket. Keep walking.

@11
The chain ends with no match, so Ivy is appended. Bucket 5 now has a chain of length 2: a collision. Five entries, load factor 0.63, and the build phase is complete. Notice that the whole build side had to be consumed before a single joined row could come out.

@12-14
Now the probe phase. Each order streams past and looks up its customer id. An order for user 42 hashes to bucket 3, compares once, and finds Ana. One comparison in a chain of 1.

@15-17
An order for user 77 goes to bucket 5. The first entry in the chain is user 77, so it is found after 1 comparison, even though the chain holds 2.

@18-23
User 42 again: bucket 3, one comparison, Ana. Then user 13: bucket 7, one comparison, Lee. Every probe here costs a hash and a comparison or two, no matter how many users were loaded.

@24
Five keys in eight buckets gives a load factor of 0.63, which is the expected chain length. A lookup costs a constant plus that load factor, so it stays constant time as long as the table resizes to keep the load factor bounded. That is why a hash join is linear in the size of both inputs and needs no index and no sort. Two traps. It works only for equality. And a skewed join key, many rows sharing one value, makes some chains long and the probe side slow. If the build side outgrows its memory, 4 megabytes times 2 by default since Postgres 15, it splits both inputs and spills to disk in batches.
