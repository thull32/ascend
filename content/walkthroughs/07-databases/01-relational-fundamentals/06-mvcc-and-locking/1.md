@0
Three transactions and one row, a balance. The idea is multi-version concurrency control: instead of locking rows against readers, the database keeps several versions of each row and shows each transaction the versions that were committed when its snapshot was taken.

@1
T1 begins and takes a snapshot. It will see every transaction committed before transaction id 12, and nothing later, however long it runs.

@2
T1 reads the balance: 100, from the version created by transaction 5. Not deleted, committed, so visible. No lock is taken.

@3
T2, transaction 12, updates the balance to 80. Nothing is overwritten. A new version is appended with an xmin of 12, and the old one is marked as deleted by 12. T2 holds a row lock, but it only matters to other writers.

@4-5
T1 reads again while T2 is still open, and still sees 100. Version 12 is invisible to its snapshot: 12 is not below 12, and it is not committed anyway. That is repeatable read, without waiting on T2's lock.

@6
T2 commits. Its version becomes visible to snapshots taken from now on.

@7
T3 starts afterwards and reads 80. So two open transactions see two different values of the same row, and both are correct for their snapshot.

@8
T1 reads once more: still 100. Its snapshot pins the old version alive.

@9
The first failure mode. T1 now tries to write the row it read, setting the balance to 90. But the current version was changed by transaction 12, which committed after T1's snapshot.

@10
First committer wins, and T1 is aborted with could not serialize access. Retrying T1 from the start is the application's job. Under read committed it would instead re-read and silently overwrite T2's update.

@11
The second failure mode is write skew: two transactions each read a row the other one writes, like two doctors who both go off call after reading that two are on call, and both commit under snapshot isolation. Only serializable isolation catches it, by tracking read and write dependencies.

@12
Once no live snapshot can see the old version, it is garbage, and vacuum reclaims it. The third failure mode: a long-running transaction pins every old version behind it, so tables and indexes bloat and vacuum falls behind.

@13
The trade: readers never wait, and long analytical reads can run alongside short transactional writes. The price is version storage, garbage collection, and anomalies like write skew that snapshot isolation does not prevent. Postgres, Oracle, InnoDB and CockroachDB all work this way.
