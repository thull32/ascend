@0
Two transactions and two row locks, A and B. T1 takes A and then B. T2 takes B and then A. Each takes its locks in a different order, and that is the whole trap.

@1
T1 takes A. T2 takes B. So far, nothing is wrong.

@2
Now neither can move. T1 wants B, but T2 holds it, so T1 blocks while still holding A. T2 wants A, but T1 holds it, so T2 blocks while still holding B. The wait-for graph has a cycle, T1 to T2 and back to T1. Each waits for a lock that only a waiting transaction can release, so no amount of waiting helps. Postgres finds this cycle once a waiter has waited for the deadlock timeout, one second by default, and aborts one of them.

@3
Four conditions all hold here. Mutual exclusion: a lock has one owner. Hold and wait: each keeps what it has while it waits. No preemption: a lock cannot be taken away. And circular wait: the cycle. Break any one and deadlock is impossible.

@4
The fix breaks circular wait with one global order: everyone takes the alphabetically smaller lock first. Replay with that rule.

@5-7
T1 takes A. T2 also wants A first, so it blocks, but it is holding nothing. T1 takes B, holds both and does its work, while T2 keeps waiting with empty hands.

@8-11
T1 releases A and B. T2 takes A, then B, does its work and releases both.

@12
Both finished. With a total order on locks no cycle can form, because a transaction waiting for a lock only ever holds locks that come before it. In the database, that means updating rows in ascending id order, locking them first rather than trusting an update with a list of ids to pick the order. It matters: in the lesson's measurement, transfers in random order managed under 7 a second, and in ascending order over 8,000.
