@0
A Bloom filter answers one question, have I seen this key, with a bit array and a few hash functions. Here the array has 16 bits and there are 3 hash functions. It can answer definitely not, or probably yes, but never definitely yes. And it never forgets a key it was given. The bloom index in Postgres applies this idea per row: each row's column values become a small bit signature.

@1-3
Three values are added. Colour equals red hashes to bits 13, 0 and 15, and those are set. Size equals L sets bits 7, 10 and 5. Brand equals acme hashes to 5, 8 and 3; bit 5 was already set, and it simply stays set. The array never shrinks. Three keys, 8 of the 16 bits now on.

@4-5
Query colour equals red: check bits 13, 0 and 15. All three are 1, so the answer is probably present. The filter can never miss a key it holds: there are no false negatives.

@6
Only now does the app pay for the disk read, and it finds the key. One disk read so far.

@7-8
Query a key that was never added, evt-100. Its bits are 14, 5 and 12. Bit 14 is 0, so it was definitely never added, and the disk read is skipped entirely. This is the win: most lookups for missing keys cost no input or output at all.

@9-10
Now evt-125, also never added. Its bits are 3, 8 and 13, and every one of them was set by other keys: 3 and 8 by brand equals acme, 13 by colour equals red. So the filter says probably yes, the app reads the disk, and finds nothing. That is a false positive. Harmless for correctness, which is why Postgres rechecks the real row, but it is the cost you tune away.

@11
The catch is deletes. Clearing a bit might erase another key's evidence and create a false negative, so you cannot remove a key. Counting filters, with a small counter per bit, or periodic rebuilds handle churn. And the false-positive rate climbs as the filter fills, so size it for the final key count.

@12
The trade: a few bits per key in memory buy a definite no for most misses, at the cost of a tunable false-positive rate and no deletes. In Postgres it answers the case where users filter on any combination of many columns, with one signature per row instead of a dozen B-trees. Log-structured stores check one before every SSTable read, and browsers and databases use them the same way.
