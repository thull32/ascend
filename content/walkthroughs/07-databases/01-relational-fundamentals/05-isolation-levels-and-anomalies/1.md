@0
Two threads each add one to a shared counter. The catch is that one increment is really three steps: load the value into a private register, add one, and store it back. The scheduler can switch threads between any two of them. Two database sessions that select a value, compute the new one in application code, and update it, are exactly these three steps.

@1-3
First, the safe case. T1 loads the counter, 0, into its register. It adds one, so its register says 1 while the shared counter still says 0. Then it stores: the counter is 1. Run without interruption, the increment is correct.

@4
Now both threads increment at the same time, and the scheduler lets both loads happen before either store.

@5
Both load 1. Every register holds 1.

@6
Each adds one to its own copy. Both registers now hold 2.

@7
T1 stores 2. The counter is 2.

@8
T2 stores 2 as well, and the counter stays 2. T1's increment has been overwritten: a lost update.

@9
Three increments were expected and the counter says 2. The result depends on timing, so it can pass every test and fail in production. In the database, this is two items sold and stock decremented once, with nothing complaining at read committed. The fix there is to stop computing the value in the application: one atomic statement that sets stock to stock minus one, where Postgres re-checks the newly committed row before writing. Or run at repeatable read, where the second writer gets a serialisation error to retry instead of a silent loss.
