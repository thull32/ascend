@0
On screen: a client, the database engine with its buffer pool, an append-only write-ahead log, and the data files. The rule to hold onto: before a page is modified, a record describing the change is appended to the log and forced to disk. Durability comes from the log, so the data files are allowed to lag behind.

@1-2
A transaction sets account 1 from 100 to 50. The engine appends a log record first, log sequence number 1, still buffered. The page itself has not been touched yet. That is what write-ahead means.

@3
Fsync: the log record is durable. It is one sequential write at the end of a file, which even a spinning disk does at hundreds of megabytes a second. Random page writes would be about a hundred times slower.

@4
Only now is the page changed, in memory. Page 7 is dirty in the buffer pool, while on disk the data file still says 100. That is fine, because the log can rebuild the page.

@5
The commit is acknowledged when the log record is on disk, not when the page is. So commit latency is roughly one fsync: about 1.4 milliseconds on the lab machine this lesson measured, tens of microseconds on a fast NVMe drive.

@6-7
A second transaction sets account 2 from 0 to 50. It is logged as number 2 and synced, and pages 7 and 9 are now dirty. When many transactions commit at once, one fsync can flush all their records: group commit. Throughput scales while latency stays at one fsync.

@8
Then the power fails. The buffer pool is gone. The data files still say account 1 is 100 and account 2 is 0, yet both commits were acknowledged. The log still holds records 1 and 2.

@9
Recovery reads the log forward from the last checkpoint, which here is at number 0.

@10
Redo: reapply every record newer than the page's own log number. Each page stores the number of its last change, so replaying twice does no harm. Pages 7 and 9 are rebuilt. An engine that updates in place, like InnoDB, then rolls back transactions that never committed from its undo log: redo everything, then undo the losers. Postgres needs no undo phase, because MVCC already treats those uncommitted versions as invisible.

@11
A checkpoint writes the dirty pages to the data files, and the checkpoint advances to number 2. The log before it can be recycled, and recovery time is bounded by the log written since the last checkpoint.

@12
So every change is written twice, but the first write is sequential and batched, and the second is deferred and coalesced. Commit latency is dominated by fsync. Turn fsync off, or run on a disk that lies about it, and you can lose commits you already acknowledged. Postgres, InnoDB, SQLite in WAL mode and RocksDB all work this way.
