@0
DynamoDB hashes each partition key to one partition. The picture shows the same idea with three shards: hash the key, take it modulo 3, and that is the shard. Any router computes the same answer with no shared table.

@1-2
Alice and Bob both hash to numbers with remainder 2, so both land on shard 3.

@3-4
Dave and Erin have remainder 1 and land on shard 2.

@5-6
Ivan and Judy have remainder 0 and land on shard 1.

@7
So after six keys the shards hold two each, as even as six keys over three shards can be. Sequential keys would scatter just as well as random ones, so there is no hot tail.

@8
A range query cannot be routed: it must go to every shard and be merged. That is why single-table design puts everything one access pattern needs under one partition key. The user's profile and all their progress share the key user 42, so one query returns the whole dashboard: the join, done at write time by choosing keys.

@9
Add a fourth shard and the modulus changes from 3 to 4, so five of the six keys now hash somewhere else and would have to move. Only Erin stays put. That is the price of plain modulo hashing.

@10
And hashing spreads keys, not load. An item collection lives on one partition, so a hot key's traffic cannot spread beyond it, and one DynamoDB partition serves at most 3,000 read units and 1,000 write units a second. At 4 read units per page of comments, one lesson tops out at 750 page loads a second. A viral lesson needs a cache in front, or smaller pages. A hot counter gets split across several keys, which is why the leaderboard index is sharded.

@11
Different keys spread evenly; one popular key does not. Hash the partition key to spread load, and keep items sorted by the sort key within the partition, which is exactly the shape of a DynamoDB table.
