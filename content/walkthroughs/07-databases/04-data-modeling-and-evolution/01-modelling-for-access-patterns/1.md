@0
Q6 is the comments on one lesson, in order, and it is served by one B-tree index on target kind, target slug and created at. The table lists the index entries in that order: first by kind, then by slug, then by time. So all the comments on one lesson sit next to each other, already sorted by when they were written. Three leaves hold eight entries: comments on the arrays lesson, the b-trees lesson, the heaps lesson, and on the two-sum problem.

@1
The query asks for comments on the lesson b-trees. It seeks the first entry whose kind is lesson and whose slug is b-trees. The root's first separator is the b-trees comment from September 2 at 11:40, and the start of the b-trees range sorts before it, so the root sends the search to leaf 1.

@2
In leaf 1 the arrays comments come first. The first b-trees entry is the comment from August 30 at 9:15. That is row 1, and no sort is needed: the order the rows come back in is the index's own order.

@3
Leaf 1 ends, so the walk follows the sibling pointer to leaf 2 and reads the comments from September 2 and September 5. That is three rows, and a limit of 3 stops the scan right there.

@4
Even without the limit, the walk would stop at the next entry, a comment on heaps: it is past the b-trees range, so nothing after it can match. Leaf 3, the problem comments, is never read.

@5
Column order is the whole design: the equality columns first, then the sort column. An index on created at, then kind, then slug holds exactly the same data, but one lesson's comments are scattered across the whole time range, so the query would have to scan and then sort.

@6
Newest first is the same index read backwards from the end of the lesson's range: one backward index scan. Q6 costs a descent of a few pages plus the rows it returns, however many comments other lessons have. That is the lesson's rule in one picture. Every hot query names its index, and every index names the query that pays for its writes. The query worth denormalising is the one no index can bound, like Q4, which aggregates over every user.
