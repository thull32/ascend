@0
Moving data to a new store has the same trap as writing two column shapes from separate statements: dual writes can interleave, and across two stores there is no lock to stop them. So write one store and derive the other from its change stream. The old store, Postgres, stays the source of truth. A connector tails its write-ahead log. The sink on the right is labelled search index; here, read it as the new store.

@1
The connector creates a replication slot, so Postgres keeps the log from this point, and copies a consistent snapshot of the existing rows into the new store: the initial copy. From here on, it only needs the log.

@2-3
The app inserts user 1, Ada, and commits at log position 1, unaware of the new store. The connector decodes it and the new store applies it as an upsert.

@4-7
An update to Ada L. at position 2, then a new order at position 3. Each is replayed in commit order, so the new store catches up and then stays in sync, with no dual-write race.

@8-9
A delete of user 1, at position 4, is replayed as a delete by primary key.

@10
If the connector crashes after sending position 4 but before confirming it, it sends 4 again on restart. Replay must be idempotent, so a duplicate is harmless.

@11
And a slot nobody is reading pins the log: down for 3 days, and the primary's disk is 95 percent full. Watch slot lag for as long as the migration runs.

@12
Why not have the application write both stores? A crash between the writes loses one, and two racing requests can land in opposite orders in the two stores, with no request at fault. One log is the single arbiter of order.

@13
Before switching reads to the new store, verify it: count what is missing, compare the shapes, and run shadow reads that serve the old answer and count disagreements, until the counter sits at zero. Then switch reads behind a flag that can go back in seconds.
