@0
A router, two identical environments, blue and green, and one shared database. The deploy style here is blue-green: one environment serves all traffic while the other is idle, the new version goes to the idle one, and the router flips. Whatever the deploy style, the point for schema changes is the same: during a rollout, old and new code run against one schema at once.

@1
Steady state. Every request goes to blue, running version 1. Green is idle.

@2
Version 2 is deployed to green while blue keeps serving. A failure here affects nobody, because green is not in the path.

@3
The schema change ships first, as an expand step: add a nullable column or a new table, never rename, never drop. The database is now at schema version 1 plus, which both versions can run against. Both will be live at once, if only for seconds, and the rollback path depends on it.

@4
Green is verified in production with smoke tests and synthetic requests, on the same hardware and configuration as blue.

@5-6
The router flips, and all traffic moves to green at once. Blue's in-flight requests drain rather than being killed. Users are on version 2 without downtime, and blue stays running exactly as it was.

@7
Then version 2 shows a bug that only real traffic triggers: green's error rate climbs to 4 percent. Because the switch was all or nothing, every user is affected until someone reacts.

@8
Rollback is the same flip in reverse: seconds, no rebuild. It only works because the expand-only migration left the schema readable by version 1.

@9
What would have broken it: a migration that renamed or dropped a column would have crashed version 1 on the way back. And anything version 2 wrote only to its new column is invisible to version 1, so data written in that window may need reconciling.

@10
Version 2.1, with the fix, goes to green and is flipped in. Blue becomes the idle side for the next release.

@11
Only now, once no version that needs the old shape can ever be live again, does the contract step run, and the database moves to schema version 2. Expand and contract are separate deploys, often days apart, because contract is the one step that makes rollback impossible.

@12
In the lesson's example, splitting a name column into first and last names: expand, write both, backfill in batches, read new, and only days later, contract. The deploy style only changes how many users see a bad release. Blue-green gives the fastest rollback but switches everyone at once and needs double the capacity.
