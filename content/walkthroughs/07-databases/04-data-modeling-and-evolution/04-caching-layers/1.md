@0
An app, Redis, and Postgres, which holds user 42 at version 1. In cache-aside the application owns all the cache logic: it reads the cache first, falls back to the database on a miss, and writes the result back itself. The cache never talks to the database.

@1-2
The app asks Redis for user 42 and gets nothing back: a miss. Nothing has been loaded for this key yet.

@3-4
So the app falls through to the database, the source of truth, at about 5 milliseconds, and gets version 1 back.

@5
The app fills the cache with a time to live of 300 seconds. Only keys that are actually read get cached, so memory goes to hot data.

@6
The second read is a hit, about half a millisecond, without touching the database. This is where the real win is: database load is proportional to the miss ratio.

@7
Now a write. The app updates the database first, to version 2.

@8
Then it deletes the cache entry rather than writing version 2 into it. A delete is idempotent and cannot race with another writer's set. The next read reloads the fresh row.

@9
And it does: a miss, a database read, and version 2 goes into the cache. Every write costs one extra miss on the next read.

@10
Now the classic race. Reader A misses and reads version 1 from the database, then pauses. Writer B updates to version 2 and deletes the key. Then A wakes and sets version 1. Postgres says version 2; Redis serves version 1, marked stale, until its time to live runs out. The reader's value was correct when it read it and wrong when it wrote it. The window is usually a millisecond, and occasionally a 200 millisecond garbage collection pause.

@11
Cache-aside is simple and resilient: if the cache goes down, reads just fall through to the database. But cache and database can diverge, so the time to live is your staleness bound; choose it at what the product tolerates. Deleting after commit does not close this race. Leases close it, and so do versioned markers that only fill if newer; invalidation from the database's log narrows it.
