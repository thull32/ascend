@0
A cache stampede, also called a dog-pile. A hot key expires, and every concurrent reader misses at the same moment and recomputes it against the database. The size of the pile is simple arithmetic: requests per second on the key, times the recompute time.

@1
The time to live runs out, and the key vanishes while 40 requests a second are still asking for it.

@2-4
Forty requests arrive in the same instant. All of them check the cache, and all of them miss, because nobody has put the value back yet.

@5
So every request runs the expensive query. A database sized for about one such query a second on this key gets 40 at once. Latency spikes, the connection pool drains, and unrelated queries stall. Scale it up to the lesson's numbers, 2,000 requests a second and a 200 millisecond query, and it is 400 copies at once.

@6
Eventually all 40 return the same result and all 40 set the same value. Cascading failures often start exactly here.

@7-8
Fix one: single-flight. The first request to miss takes a short lock on the key with a set-if-not-exists. The other 39 see the lock and wait briefly, or serve a stale copy if one exists.

@9-10
Only the lock holder queries the database. It fills the cache and releases the lock, and the waiters read the fresh value. One query instead of 40.

@11
Fix two: keep serving the stale value while one background job refreshes it, stale-while-revalidate, or let readers refresh probabilistically just before expiry. In the lesson's simulation, early refresh cut 400 recomputes per expiry to 2.8 on average. Fix three: add jitter to time-to-live values, so many keys filled together never expire together.

@12
Single-flight adds a lock round trip and a short wait on every miss; stale-while-revalidate serves briefly out-of-date data. Both are far cheaper than a database falling over under 40 times its load.
