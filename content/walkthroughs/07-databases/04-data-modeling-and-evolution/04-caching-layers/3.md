@0
An app, a cache and a database holding a view counter, views 9 equals 100. In write-behind, the cache acknowledges a write at once and persists it to the database later, asynchronously and in batches.

@1-2
The app sets views 9 to 101. It lands in the cache, marked dirty, and is acknowledged in about a millisecond, before the database has seen anything. That is where write-behind gets its speed.

@3
A second write, 102, overwrites the dirty entry. Two application writes will become one database write: coalescing.

@4
Then 103, and views 4 equals 7. The buffer keeps only the latest value per key, so there are 2 dirty entries.

@5-6
The flush trigger fires, every 500 milliseconds or when the buffer fills. The cache writes both rows to the database in one batch, one round trip instead of four. The database now has 103 and 7, and the entries are clean.

@7
A new write, 104, is dirty again and acknowledged instantly.

@8
Then the cache node dies before the next flush. The client was told 104 succeeded, but it never reached the database. It is lost.

@9
After recovery the database serves 103. Write-behind turns a durability guarantee into a durability probability.

@10
The trade: the lowest write latency and the fewest database writes, against a window of possible data loss and a database that lags the cache. It turns the cache into a database with a cache's durability. Use it for counters, last-seen times and telemetry, where losing the last fraction of a second is acceptable, and never for anything a user was told was saved.
