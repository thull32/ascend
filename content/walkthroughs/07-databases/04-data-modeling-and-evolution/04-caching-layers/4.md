@0
Writes that bypass the application's write path, from another service, a migration, or a manual update in a terminal, never delete a cache key. Change data capture catches them all. On screen: the app, Postgres, a connector, and the cache. The connector tails the database's write-ahead log and turns every committed change into an event, in commit order, and each event becomes a key to delete.

@1
Setup: the connector creates a replication slot, so Postgres keeps the log from here, and takes a consistent snapshot. After that, it needs only the log.

@2-3
The app inserts user 1, Ada, at log position 1. The connector decodes the change, a consumer turns it into a delete of the cached key, so the next read refills from the database, and the connector confirms position 1. The gap between commit and delete is how long a stale entry can survive.

@4-7
An update to Ada L. at position 2, and an order at position 3, each arrive in commit order and each deletes its key. Every writer is covered, because every committed change goes through the log.

@8-9
The delete of user 1 at position 4 comes through the same way. But the connector has emitted it without confirming it yet: the slot still says 3.

@10
The connector crashes right there. On restart it resumes after the last confirmed position, 3, sends position 4 again, and confirms it. For cache invalidation that is the easy case: deleting a key twice is harmless.

@11
But an abandoned slot pins the log. Down for 3 days, and the primary's disk is 95 percent full. Monitor slot lag.

@12
Compare the alternative, deleting from application code: any path that forgets the delete leaves the cache stale until its time to live. One log makes the database the single arbiter.

@13
The limits. The delete arrives tens of milliseconds after commit, so a slow reader's fill that lands in between is removed, which narrows the slow-fill race without closing it. Facebook described the same design: daemons that tail the MySQL commit log and broadcast deletes. And a delayed second delete, a fixed interval later, is the same narrowing by hand; call it a heuristic in the design doc.
