@0
An app, a cache and a database, both holding price 7 equals 10. In write-through, every write goes to the cache, and the cache writes it to the database synchronously before acknowledging. Cache and database never disagree.

@1
The app sets price 7 to 12. The cache is the front door of the write path.

@2
The cache holds 12 as pending, forwards the update to the database, and waits. That synchronous hop is what makes it through.

@3
The database commits 12.

@4
Only now is the app told OK, so any later read sees 12. The cost is latency: cache write plus database write, about 6 milliseconds instead of about 1.

@5
A read hits the cache and gets 12, guaranteed fresh. There is no invalidation step to forget and no stale window.

@6-7
Now the failure mode. The database is down, and the app sets price 7 to 13. The cache tries the synchronous write and cannot complete it.

@8
So the write fails with an error, and the cache keeps 12. Writes are exactly as available as the database, never more: consistency is kept at the cost of availability.

@9
The database is back, and both still agree on 12. Write-through gives agreement and simple reads, but slower writes, and it fills the cache with keys nobody may read. Two caveats from the lesson. It does nothing about writes that bypass the cache: another service, a migration, a manual fix. And a crash between the database commit and the cache update leaves the cache stale. So it still needs a time to live.
