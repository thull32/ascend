viz: Write-through keeps cache and database in step

@0
An app, a cache and a database, both holding price 7 equals 10. In write-through, every write goes to the cache, and the cache writes it to the database synchronously before acknowledging. So a read after a write through the cache finds the new value.

@1
The app sets price 7 to 12. The cache is the front door of the write path.

@2
The cache holds 12 as pending, forwards the update to the database, and waits. That synchronous hop is what makes it through.

@3
The database commits 12.

@4
Only now is the app told OK, so any later read sees 12. The cost is latency: cache write plus database write, about 6 milliseconds instead of about 1.

@5
A read hits the cache and gets 12, with no invalidation step to forget. That holds as long as every write goes through the cache, one at a time for each key.

@6-7
Now two writers, with nothing ordering their writes to this key. Writer A sets 13 in the cache, and writer B sets 14 right after it, so the cache holds 14.

@8
B's database write lands first: the database says 14 as well.

@9
Then A's delayed database write lands last, and the database says 13. The cache says 14, the database says 13, and they stay that way until the next write or an eviction. The two stores applied the same writes in different orders: the same race as two writers that set in cache-aside. The fix is to serialise writes for each key, with a version check or a per-key lock, so both stores see one order.

@10-11
The second failure mode. With both stores back at 14, the database goes down, and the app sets price 7 to 15. The cache tries the synchronous write and cannot complete it.

@12
So the write fails with an error, and the cache keeps 14. Writes are exactly as available as the database, never more.

@13
Write-through gives simple reads that are fresh after a write, but slower writes, writes that need ordering for each key, and a cache full of keys nobody may read. Two caveats from the lesson. It does nothing about writes that bypass the cache: another service, a migration, a manual fix. And a crash between the database commit and the cache update leaves the cache stale. So it still needs a time to live.
