@0
A search engine's term dictionary has to answer prefix queries: every term that starts with po. The structure here is a trie, a tree of characters. Every term that starts with a prefix sits below one node, so a prefix query walks the prefix once, then enumerates the subtree under it.

@1-2
Insert pool: nothing to share yet, so 4 new nodes, one per letter. Pooling shares all 4 of those and adds 3 more, for i, n and g.

@3
Postgres shares the first two letters, p and o, and adds 6 new nodes.

@4-5
PgBouncer shares only the p and adds 8 nodes. Partition does the same: one shared, 8 new. Common prefixes are stored once.

@6-8
Now the query, po. Follow the edge for p from the root, then the edge for o. We are at the node for po, and every term in the subtree below it starts with po. Enumerate it depth first, visiting children in sorted order.

@9-10
Po itself is not a term, only a prefix, so descend into its 2 children. The first, poo, is not a term either; descend.

@11
Pool is a term, the end of an inserted word, so it is emitted as suggestion 1. Keep going, because longer terms may follow.

@12-14
Down through pooli and poolin, neither a term, to pooling: suggestion 2.

@15-20
Back up to the other child of po. Pos, post, postg, postgr, postgre: each is only a prefix, so the walk keeps descending, until postgres, which is a term: suggestion 3.

@21
The suggestions for po are pool, pooling and postgres, already in alphabetical order because children were visited sorted. PgBouncer and partition were never touched. The cost is the length of the prefix plus the size of the subtree.

@22
Enumerating a subtree costs its size, which is why production autocomplete caches the top completions at each node instead of walking every time. Lucene's term dictionary uses a compressed automaton with the same property: shared prefixes stored once, and a prefix query that walks the prefix and reads what lies beneath. Each term then leads to its postings list, the sorted list of documents that contain it.
