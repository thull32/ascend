@0
An app, Postgres, a change data capture connector, and the search index. The database is the truth, and the index is a derived view that lags it. Instead of the app writing to both, the connector tails the database's write-ahead log and turns every committed change into an event. The database's own commit order becomes the event stream.

@1
Setup. The connector creates a replication slot, so Postgres keeps the log from that point, and takes a consistent snapshot of the existing rows, streaming them as inserts. From here on it needs only the log.

@2-3
The app inserts user 1, Ada, and commits. Postgres writes it to the log at position 1 before acknowledging; the app knows nothing about the index. The connector decodes position 1 into an event with the row's before and after images, and the index applies it as an upsert. The gap between commit and apply is the staleness a search user can see.

@4-7
The same for each commit. The update renaming Ada to Ada L. is position 2, and an insert of order 9 for user 1 is position 3. Each is decoded and applied in commit order.

@8-9
Then user 1 is deleted, at position 4. The connector emits a delete event and the index removes the document by primary key. Deletes are exactly what a polling job would miss.

@10
The first failure mode. Suppose the connector crashes after emitting position 4 but before confirming it to the slot. On restart it resumes from the last confirmed position and sends 4 again: a duplicate. Delivery is at least once, so the sink must be idempotent. In Elasticsearch, index with external versioning, using the change's log position as the version, and a duplicate or an older event is rejected.

@11
The second: the slot pins the log. Here the connector has been down for 3 days, Postgres has kept every segment since the confirmed position, and the disk is 95 percent full. Monitor slot lag, and set a retention cap.

@12
Why not dual writes, where the request handler writes to Postgres and then to the index? A crash between the two loses an update silently. And two racing updates can reach the index in the opposite order and leave the older version there forever. Tailing one log makes the database the single arbiter of order.

@13
The trade: the index follows exactly the database's order, with no application changes, and it sees deletes. In return you are coupled to the schema, delivery is at least once, and you run slots, lag monitoring and connector restarts. And users see the lag: an author who publishes and searches at once may not find the article for a second or more, so a my articles list should read from the database.
