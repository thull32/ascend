@0
This is the write path on each Cassandra replica. Writes go to a sorted table in memory and are flushed as immutable sorted files, SSTables, which are later merged. Every disk write is sequential, and reads may have to look in several places. On screen: the log, which Cassandra calls the commit log, a memtable with room for 4 keys, level 0 files, and a merged level 1.

@1
Put a equals 1 and b equals 2. Each is appended to the commit log and merged into the memtable. Nothing is read first: a write never looks at the old value. That is why writes are so cheap.

@2
Put c equals 3, then a equals 4. The overwrite just replaces a in memory, while the log keeps both records.

@3-4
Put d equals 5 fills the memtable, and it flushes as SST-1, one sorted immutable file with a sparse index and a Bloom filter, written in one sequential pass. The log segment it covered can be recycled.

@5
Put b equals 9, and delete c. SST-1 is immutable, so the delete is written as a tombstone, a marker that hides older data for c.

@6
Read c. The memtable holds the tombstone, so the answer is not found, even though SST-1 still says c equals 3. In Cassandra, every cell carries a write timestamp, and when a read merges the memtable and SSTables, the newest timestamp wins.

@7
Read a. Not in the memtable; SST-1's Bloom filter says maybe, its index points to the block, and one disk read returns a equals 4.

@8
Two more puts fill the memtable and it flushes as SST-2. The level 0 files overlap, both holding b and c, so a read for b must check SST-2 before SST-1. Every flush adds a file that reads may have to consult.

@9-10
Compaction merges the two into one level 1 file. b is 9, and the tombstone removes both itself and c equals 3. Now a read for b touches one file. How many files a read touches is set by the compaction strategy you choose per table.

@11
The failure modes. Compaction can fall behind, and writes stall as level 0 piles up. And tombstones must survive long enough, or deleted keys come back. In Cassandra that means surviving until every replica has seen the delete, so compaction keeps them for the grace period, ten days by default, and every node must complete repair more often than that. A queue-shaped table that inserts and deletes constantly becomes mostly tombstones that every read must scan. Do not build a queue in Cassandra.

@12
The trade: sequential writes, excellent write throughput and compression, at the cost of slower point reads and range scans, and background compaction that must be tuned. Cassandra, HBase, RocksDB and LevelDB all make this bet.
