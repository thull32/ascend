@0
A Cassandra read checks the memtable, then every SSTable that might hold the partition. Each SSTable carries a Bloom filter over its partition keys: a bit array, here 16 bits with 3 hash functions. It can say definitely not, or probably yes, never definitely yes.

@1
One key is added, evt-1. Its three hashes are 14, 13 and 12, and those bits are set.

@2-3
A read for evt-1 checks bits 14, 13 and 12. All three are 1, so the answer is probably present. A filter never misses a key it holds.

@4
So the read pays for the disk access, and finds the key. One disk read.

@5-6
A read for evt-100, which was never written. Its bits are 14, 5 and 12, and bit 5 is 0, so this file definitely does not have it. The disk read is skipped entirely. For a table spread across many SSTables, that is most of the files most reads would otherwise touch.

@7-8
A read for evt-441, also never written. Its bits are 14, 13 and 12, exactly the ones evt-1 set. So the filter says probably yes, the read goes to disk, and finds nothing. A false positive: it costs one index lookup that finds nothing, but never a wrong answer.

@9
You cannot delete from a Bloom filter: clearing a bit might erase another key's evidence. That is fine here, because SSTables are immutable, and each file's filter is rebuilt when compaction writes a new file. The false-positive rate does climb as a filter fills, so it is sized for the file's key count.

@10
A few bits per key in memory buy a definite no for most misses. Cassandra's default false-positive chance is 1 percent, or 10 percent under leveled compaction, where a read touches fewer files to begin with. It is a dial: a lower rate costs more memory per key.
