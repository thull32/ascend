@0
Three replicas of one partition, each holding x as version 1, timestamp 9. In Cassandra every request states a consistency level, how many replicas must respond. Here both the write and the read use quorum: 2 of 3. The arithmetic to remember: a write heard by W replicas and a read that hears from R must share at least W plus R minus N of them. With 2, 2 and 3, that is one replica.

@1-2
A client sends version 2 to a coordinator; any node can coordinate. It sends the mutation to all three replicas, stamped with a timestamp.

@3-4
R1 and R2 acknowledge and now hold version 2 at timestamp 12. R3 is slow, a garbage collection pause or a disk stall. Two acknowledgements are enough, so the write succeeds while R3 still holds version 1. Write latency is the second fastest of three.

@5
A read arrives. For reads the coordinator contacts only as many replicas as the level needs, two: it asks R2 for the full data and R3 for a digest, a hash of the value.

@6
R2 returns version 2 at timestamp 12; R3's digest differs. The coordinator requests full data and gets version 1 at timestamp 9. The two sets had to share a member, and that member has the newest timestamp, so the newest timestamp wins. Newest wins by write timestamp, set from a clock, so two writers whose clocks differ can have the earlier write win.

@7-8
Before answering the client, the coordinator writes version 2 to R3 and waits: blocking read repair, the default since Cassandra 4.0. Only then does the client get version 2. R1 was not contacted; anti-entropy repair, comparing Merkle trees, fixes replicas that no one reads.

@9
Why it blocks. A new write, version 3, is still in flight: R1 has applied it, R2's copy is still on the wire, and the write has not been acknowledged.

@10
Reader B's quorum is R1 and R3, so B sees version 3 at timestamp 15 and returns it.

@11
Reader C starts after B returns and reads R2 and R3. Had B written nothing back, neither has version 3, and C gets version 2: a value appeared, then disappeared.

@12
Because B's read repair blocked, it wrote version 3 to R3 before returning. Version 3 is now on two replicas, a quorum, so C's read must include one of them, and C reads version 3.

@13
The tempting mistake is W and R both 1 for speed. Their sum is not greater than 3, the overlap is zero, and a client can read version 1 after version 2 was acknowledged. Quorum on both sides tolerates one node down; a write at consistency level all tolerates none.

@14
What read repair still cannot fix: concurrent writes decided by timestamps, a write that failed before reaching quorum but sits on one replica and is later repaired into view, and hinted writes accepted by other nodes during a partition, which do not count toward the consistency level. For a compare-and-set, Cassandra has lightweight transactions, a Paxos round costing four round trips.

@15
No leader, no election, and a consistency level per request. With two datacentres, quorum across both means waiting on a remote replica every time, so deployments use local quorum, and accept that a write in one region and a read in the other have no guaranteed overlap.
