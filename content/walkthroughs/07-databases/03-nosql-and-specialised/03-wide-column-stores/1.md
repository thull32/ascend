@0
This is how Cassandra decides where a partition lives. Each partition key hashes to a token on a ring, and nodes own positions on the same ring. The rule: a key belongs to the first node clockwise from its token. Three nodes here: N2 at 161 degrees, N3 at 342, and N1 at 344.

@1-2
User 1 hashes to 187 degrees, and the first node clockwise is N3. User 7, at 181, also lands on N3.

@3
Video 9, at 345 degrees, is just past both N3 and N1, so it wraps around past zero to N2, at 161.

@4-6
Session 3 at 164, cart 5 at 294, and feed 2 at 165 all walk to N3. Notice how lopsided three points make the ring: N3 owns five keys and N1 owns none. In Cassandra, each partition is also stored on the next nodes clockwise, up to the replication factor.

@7
Add N4 at 159 degrees. Only the arc between its predecessor, N1 at 344, and the new node changes hands, and the one key there, video 9, moves from N2 to N4. One key of six. The new node streams only that data, and that is the mechanism behind the phrase linear scalability. With hash modulo the node count, nearly every key would move.

@8
Real deployments give each physical node many positions, virtual nodes, so load evens out and a failed node's work spreads across many neighbours. Cassandra uses 16 per node by default since version 4.0, and 256 before. The catch is that placement only follows the partition key. A query that omits part of it has to ask every node, and Cassandra refuses to run it without allow filtering.
