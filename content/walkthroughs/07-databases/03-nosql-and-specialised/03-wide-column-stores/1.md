@0
This is how Cassandra decides where a partition lives. Each partition key hashes to a token on a ring, and nodes own positions on the same ring: here N1 at 0 degrees, N2 at 120 and N3 at 240. The rule: a key belongs to the first node clockwise from its token. The replication factor is 3, so the next nodes clockwise hold copies too.

@1-2
User 1 hashes to 159 degrees, past N2, so its owner is N3, and the next two nodes clockwise, N1 and N2, hold its copies. User 7, at 124, also belongs to N3, with the same copies.

@3-4
Video 9, at 35 degrees, belongs to N2, with copies on N3 and N1. Session 3, at 73, belongs to N2 as well. With three replicas and three nodes, every node holds a copy of everything; the owner only decides where the walk starts.

@5-6
Cart 5, at 322, wraps past zero to N1, with copies on N2 and N3. Feed 2, at 175, belongs to N3.

@7
Six keys: one owned by N1, two by N2, three by N3.

@8
Add N4. It joins at 167 degrees, between N2 and N3, and claims only that range. User 1 and user 7 sit in it, so those two partitions move from N3 to N4; nothing moves between the old nodes. With hash modulo the node count, going from 3 nodes to 4 would have remapped 5 of these 6 keys. A new node streams only the ranges it takes over, and that is the mechanism behind the phrase linear scalability.

@9
With one position per node, how much a newcomer takes depends on where it lands. Real deployments give each physical node many positions, virtual nodes, so load evens out and a failed node's work spreads across many neighbours. Cassandra uses 16 per node by default since version 4.0, and 256 before. The catch is that placement only follows the partition key. A query that omits part of it has to ask every node, and Cassandra refuses to run it without allow filtering.
