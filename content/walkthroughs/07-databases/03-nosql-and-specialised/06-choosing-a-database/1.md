@0
The question this answers is what consistency each operation needs, asked per operation, not per system. A leaderless store lets each request choose. Three replicas hold x as version 1. A write must be acknowledged by W of them and a read must hear from R. Here W and R are both 2, and because 2 plus 2 is more than 3, every read overlaps every set of replicas that acknowledged a write.

@1-2
A client sends version 2 to a coordinator, which forwards it to all three replicas in parallel, with a timestamp of 12.

@3-4
R1 and R2 acknowledge. R3 is slow, a garbage collection pause or a stalled disk. Two acknowledgements are enough, so the write succeeds while R3 still holds version 1. The write path tolerates one slow or dead replica.

@5
A read arrives. The coordinator contacts only two replicas, not all three: it asks R2 for the data and R3 for a digest, a hash of the value.

@6
R2 returns version 2 at timestamp 12. R3's digest does not match, so the coordinator fetches its full data: version 1 at timestamp 9. At least one of the two had to be in the write quorum, so the newest version is guaranteed to be among the replies, and the newest timestamp wins.

@7-8
Before answering, the coordinator writes version 2 back to R3 and waits for it. That is blocking read repair: the read pays an extra round trip so that no later read can go backwards. Only then does the client get version 2.

@9-10
Now a write still in flight. R1 has applied version 3, but the copy to R2 is still on the wire, and the write has not been acknowledged. Reader B consults R1 and R3, sees version 3 at timestamp 15, and returns it.

@11
Reader C starts after B has finished and consults R2 and R3. Had B written nothing back, neither holds version 3, and C gets version 2: a value appeared and then disappeared.

@12
Blocking read repair closes that gap. B writes version 3 to R3 before returning, so two replicas hold it, and C's read must include one of them.

@13
Now tune it per operation. W and R of 1 each is fast and stays writable, but there is no overlap, and a client can read an old value after a newer one was acknowledged. Writing to all three and reading from one suits read-heavy data. Writing to one suits write-heavy data you can afford to lose. A likes counter can live with staleness. Moving money or decrementing inventory cannot: that needs atomic, isolated transactions over several rows.

@14
What read repair still cannot fix: two concurrent writes ordered by last-writer-wins timestamps, and writes accepted outside the key's home replicas during a partition. Operations that must be linearizable need consensus.

@15
So the trade is no leader and no election, availability through partial failures, and consistency chosen per request, at the cost of touching several replicas for every operation and guarantees weaker than they look. Two traps when someone says eventually consistent. Ask which stale read a user will see, for how long, and what happens when they act on it. And remember that asynchronous replication can lose the last acknowledged writes on any store, relational included.
