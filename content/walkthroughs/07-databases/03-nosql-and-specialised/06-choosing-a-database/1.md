@0
The question this answers is what consistency each operation needs, asked per operation, not per system. A leaderless store lets each request choose. Three replicas hold x as version 1. A write must be acknowledged by W of them and a read must consult R. Here W and R are both 2, and because 2 plus 2 is more than 3, every read set overlaps every write set.

@1-2
A client sends version 2 to a coordinator, which forwards it to all three replicas in parallel, with a timestamp.

@3-4
R1 and R2 acknowledge. R3 is slow, a garbage collection pause or a stalled disk. Two acknowledgements are enough, so the write succeeds while R3 still holds version 1. The write path tolerates one slow or dead replica.

@5-6
A read arrives, and the coordinator waits for the first two of three replies.

@7-8
R3 answers first, with the stale version 1, then R2 with version 2. At least one of the two repliers had to be in the write quorum, so the newest version is guaranteed to be among the replies.

@9-10
The coordinator returns the highest timestamp, version 2, and writes it back to R3: read repair.

@11
Now tune it per operation. W and R of 1 each is fast and stays writable, but a client can read version 1 after version 2 was acknowledged. Writing to all three and reading from one suits read-heavy data. Writing to one suits write-heavy data you can afford to lose. A likes counter can live with staleness. Moving money or decrementing inventory cannot: that needs atomic, isolated transactions over several rows.

@12
Subtleties. During a partition, writes accepted by nodes outside the key's home break the overlap guarantee. Equal timestamps need a tiebreak. And a quorum is not a compare-and-set.

@13
So the trade is no leader and no election, availability through partial failures, and consistency chosen per request, at the cost of N messages per operation and guarantees weaker than they look. Two traps when someone says eventually consistent. Ask which stale read a user will see, for how long, and what happens when they act on it. And remember that asynchronous replication can lose the last acknowledged writes on any store, relational included.
