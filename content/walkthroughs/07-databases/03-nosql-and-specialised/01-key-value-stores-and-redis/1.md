@0
This is a JavaScript event loop, and Redis's loop has the same shape: wait for readiness, run each ready callback to completion, never block. The program logs A, sets a timer with zero delay, starts a network fetch, queues a promise callback, and logs B. One thread runs everything. The host does timers and network on other threads and posts callbacks back through queues.

@1
The script starts on the call stack, and log A runs straight away.

@2
The timer is handed to the host, and the call returns at once. Its callback is not queued yet: even zero milliseconds means after the current script.

@3
The fetch starts a request on the host's network thread and returns a pending promise. The main thread never blocks waiting for the socket.

@4
The promise is already settled, so its callback, m, goes on the microtask queue. Meanwhile the timer has expired, so its callback, cb, goes on the macrotask queue.

@5
Log B runs. Nothing queued has run yet, because the script is still on the stack.

@6
The script finishes and the stack is empty. Now the loop looks at its queues, microtasks first, always.

@7
m runs and logs C.

@8
Then one macrotask: cb runs and logs D. After each one, the loop drains microtasks again.

@9
The response arrives on the network thread, and its handler is queued. The main thread was idle, not blocked.

@10
The handler runs and logs E.

@11
The output is A, B, C, D, E. Because one thread runs every callback, a 200 millisecond synchronous loop delays every timer and every response by 200 milliseconds. That is the Redis bargain. One thread means the keyspace needs no lock, so increment is atomic and a Lua script is all or nothing. But a command is one callback, so a single slow command delays every client queued behind it.
