@0
An app, a cache that holds 3 keys, and the database behind it. The policy is least recently used: every access moves a key to the front, and when the cache is full, the key at the back, the one untouched for longest, is evicted. The requests will be A, B, C, A, D, B, E, A.

@1-3
A, B and C each miss. There is room, so each is loaded from the database and inserted at the front. Three misses, three loads, and the cache is full, with C most recent and A at the back.

@4
A again, and this time it hits. It moves from the back to the front. Recency is updated on reads as well as writes.

@5
D misses. The cache is full, so the key at the back goes: B, last used at step 2. D is loaded and placed at the front.

@6-7
Now the cost of a working set larger than the cache. B comes back and misses, evicting C. E misses and evicts A, even though A was read twice: LRU only remembers when, not how often.

@8
And A, just evicted, is requested again: another miss, which evicts D. One hit in eight requests. Four keys cycling through a cache of three, and almost every access goes to the database.

@9
The failure mode is a one-off scan. A report or a crawler that reads a few keys once each pushes every genuinely hot key out, and the next real requests all miss. Variants admit a key to the main cache only on its second touch.

@10
Exact LRU is constant time with a hash map and a doubly linked list, and it adapts instantly to a shifting working set. But it tracks recency only, so it cannot tell a key read a thousand times from one read once a moment ago. And the list costs 16 bytes of pointers per key. So Redis does not keep one. It stores a clock in each object's header, samples 5 keys by default into a small pool of the idlest candidates, and evicts the idlest. With 10 samples, the hit rate is hard to tell from exact LRU.
