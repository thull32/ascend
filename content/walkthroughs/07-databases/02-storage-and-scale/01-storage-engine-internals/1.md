@0
Four boxes: a client, the engine with its buffer pool, the write-ahead log, and the data files. Writing every changed page at commit would mean random 8 kibibyte writes, and a power cut halfway through would leave a half-applied transaction. The log replaces that with one rule: before a modified page reaches disk, the log record describing the change must be on disk.

@1-2
A transaction changes account 1 from 100 to 50. The engine appends a record to the log first, log sequence number 1. Every record gets one of these numbers, a byte position in the log. The page has not been touched yet.

@3
Fsync, and the record is durable. It is one sequential append at the end of a file, which even a spinning disk does at hundreds of megabytes a second, roughly a hundred times faster than random page writes.

@4
Now page 7 is modified, in the buffer pool only. It is dirty: the data file on disk still says 100. That is safe, because the log can rebuild it.

@5
The client hears commit OK as soon as the log record is on disk, not the page. So a commit costs about one fsync: a tenth of a millisecond to a millisecond on an SSD.

@6-7
A second transaction sets account 2 from 0 to 50, logged as number 2 and synced. Pages 7 and 9 are dirty now. Under load, many commits share one flush; that is group commit, and in the lesson's lab 16 clients averaged about 8 commits per flush.

@8
Power loss. The buffer pool and both dirty pages are gone, and the data files still say 100 and 0. But both commits were acknowledged, and the log holds records 1 and 2.

@9
Recovery starts from the last checkpoint, here at number 0, and reads the log forward.

@10
For each record it compares log numbers. Every page header stores the number of the last record that changed it. If the page is already at or past the record, skip it; if not, apply the change. That is why replaying twice is harmless. Pages 7 and 9 are rebuilt. Engines that update in place, like InnoDB, then roll back uncommitted transactions from an undo log. Postgres has no undo phase: tuples from a transaction with no commit record are simply invisible, and vacuum removes them later.

@11
A checkpoint writes the dirty pages to the data files, and the checkpoint position moves to number 2. Log before that point can be recycled. So the checkpoint interval controls recovery time, not durability, which the commit flush already provided.

@12
Every change is written twice: once sequentially and in batches to the log, and once later, coalesced, to the data files. Commit latency is one fsync. Turn fsync off, or trust a disk that lies about it, and acknowledged commits can vanish. Postgres, InnoDB, SQLite in WAL mode and RocksDB all work this way.
