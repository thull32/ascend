@0
Three replicas, each holding x as version 1, with timestamp 9. A write must be acknowledged by W of the N replicas, and a read must consult R of them. Here N is 3, and W and R are both 2. The rule to hold onto: when W plus R is greater than N, every read set overlaps every write set, so a read sees at least one copy of the latest write.

@1-2
A client sends a write of version 2 to a coordinator; any node can coordinate. The coordinator sends it to all 3 replicas in parallel, with a version timestamp.

@3
R1 and R2 acknowledge and now hold version 2 with timestamp 12. R3 is slow, perhaps a garbage collection pause or a disk stall. Two acknowledgements meet W, so the coordinator does not wait.

@4
The write succeeds even though R3 still holds version 1. A quorum tolerates one slow or dead replica on the write path.

@5-6
A read arrives. The coordinator asks all three replicas and waits for the first two replies.

@7
R3 answers first, with the stale version 1.

@8
Then R2 answers with version 2. Because R plus W is greater than N, at least one of the two repliers must have been in the write quorum, so the newest version is guaranteed to be among the replies.

@9
The coordinator returns the value with the highest timestamp: version 2.

@10
Read repair: the coordinator noticed R3 was stale and writes version 2 back to it. Background anti-entropy sweeps fix replicas that nobody reads.

@11
The failure mode is tuning for speed. With W and R both 1, their sum is not greater than N, so a read may consult only a replica that missed the write, and the client sees version 1 after version 2 was acknowledged. Tune per workload: W equals N and R equals 1 for read-heavy data, W equals 1 for write-heavy data you can afford to lose.

@12
Subtleties. Sloppy quorums, where nodes outside the key's home accept writes during a partition, break the overlap guarantee. Two concurrent writes with the same timestamp need a tiebreak. And even a strict quorum is not linearizable without extra care.

@13
The trade: no leader and no election, availability during partial failures, and consistency tunable per request. But every operation costs N messages, and the guarantees are weaker than they look. Postgres uses only the write half, a synchronous standby list that waits for any one of several replicas, for durability, and keeps reads on one node. Leaderless stores like Cassandra use both halves.
