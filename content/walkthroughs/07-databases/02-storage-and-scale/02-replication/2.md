@0
Three replicas, each holding x as version 1, with timestamp 9. A write must be acknowledged by W of the N replicas, and a read must hear from R of them. Here N is 3, and W and R are both 2. The rule to hold onto: when W plus R is greater than N, every read set overlaps every set of replicas that acknowledged a write, so a read includes at least one copy of the latest acknowledged write.

@1-2
A client sends a write of version 2 to a coordinator; any node can coordinate. The coordinator sends it to all 3 replicas in parallel, with a timestamp.

@3
R1 and R2 acknowledge and now hold version 2 with timestamp 12. R3 is slow, perhaps a garbage collection pause or a disk stall. Two acknowledgements meet W, so the coordinator does not wait.

@4
The write succeeds even though R3 still holds version 1. The write path tolerates one slow or dead replica.

@5
A read arrives. The coordinator contacts only R replicas, two, not all three: it asks R2 for the data and R3 for a digest, a hash of the value.

@6
R2 returns version 2 with timestamp 12, and R3's digest does not match. The coordinator fetches R3's full data: version 1, timestamp 9. Because R plus W is greater than N, at least one of the replicas it heard from was in the write's quorum, so version 2 is among the replies, and the newest timestamp wins.

@7-8
Before answering, the coordinator writes version 2 back to R3 and waits for it. That is blocking read repair: the read pays an extra round trip so that no later quorum read can go backwards. Only then does the client get version 2.

@9
Why the repair has to block. A new write, version 3, is still in flight: R1 has applied it, the copy to R2 is still on the wire, and nobody has been told it succeeded. Overlap is a promise about acknowledged writes only.

@10
Reader B's quorum is R1 and R3. It sees version 3, timestamp 15, on R1, the newest value, so B returns version 3.

@11
Reader C starts after B has returned, and reads R2 and R3. If B's read had written nothing back, neither of them has version 3 yet, and C gets version 2. A value appeared and then disappeared. No single order of events explains that, so quorum reads alone are not linearizable.

@12
Blocking read repair closes this case. B writes version 3 to R3 before returning, so version 3 sits on two replicas, a write quorum, and C's read must include one of them. C reads version 3.

@13
The failure mode is tuning for speed. With W and R both 1 there is no overlap at all, and a read can miss an acknowledged write. Tune per workload: W equals N and R equals 1 for read-heavy data, W equals 1 for writes you can afford to lose.

@14
What blocking read repair still does not fix: two concurrent writes ordered by last-writer-wins timestamps, a write that failed before reaching W yet sits on one replica and is later repaired into view, and sloppy quorums, where writes land outside the key's home replicas. Operations that must be linearizable need consensus.

@15
The trade: no leader and no election, availability during partial failures, and consistency tunable per request, but every operation touches several replicas, and the guarantees are weaker than they look. Postgres uses only the write half, a synchronous standby list that waits for any one of several replicas, for durability, and keeps reads on one node. Leaderless stores like Cassandra use both halves.
