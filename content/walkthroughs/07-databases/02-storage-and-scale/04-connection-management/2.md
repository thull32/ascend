@0
A gateway with one shared pool of 12 threads, calling three dependencies: Payments, Search and recommendations. A bulkhead partitions resources per dependency, so a failure in one compartment cannot flood the others, like the watertight compartments in a ship's hull. First, the version without one.

@1
Search becomes slow. Calls that took 50 milliseconds now hang for 8 seconds before timing out. Nothing else has changed.

@2
Every Search request now holds a gateway thread for 8 seconds instead of 50 milliseconds. Six are in flight, and half the shared pool is gone.

@3
Search traffic keeps arriving at the normal rate, but calls now leave 160 times slower than they enter. Search alone holds all 12 threads.

@4
A checkout request arrives. It needs Payments, which is perfectly healthy.

@5
It is rejected anyway, because there is no thread to run it. A slow search box has taken down payments: one dependency's latency became every feature's outage. A database pool behaves the same way. If a missing index makes one query take 400 milliseconds instead of 1, that query alone wants 120 connections, and every endpoint starts queueing behind it.

@6
The fix: split the 12 threads into 3 pools of 4, one per dependency. A Search call may only use a Search thread, and when that pool is full the call is rejected at once instead of waiting.

@7
Search degrades exactly as before and fills its 4 threads, but it cannot borrow from anyone else.

@8
The next Search call finds its pool full and fails in microseconds with a clear search unavailable. The page renders without the search box instead of hanging.

@9
Checkout arrives, takes a Payments thread from a pool with 3 to spare, and succeeds. The compartment held: the leak in Search never reached Payments.

@10
Then Search recovers, and its pool drains back to empty. The fix has its own failure mode: sizing. Too small, and a normal spike to one dependency rejects legitimate calls, a self-inflicted outage. Too large, and the isolation is nominal. Size from measured concurrency, rate times latency, with headroom, and alert on rejections.

@11
The trade: a bulkhead caps the blast radius of any one dependency at its compartment's size, at the cost of lower peak utilisation, since idle threads in one pool cannot help another, and one more number to tune. For databases, that means one pool per workload, API, batch and admin, each with its own timeout, so a slow report cannot starve the checkout path. And a statement timeout, so one slow query cannot hold its compartment forever.
